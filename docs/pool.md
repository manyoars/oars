# The pool

The pool is an optional server that accounts sign in to, deposit session skeletons (a closed list of fields, each value redacted on your machine first) to, and fetch cells and reads from. Local capture, recall, and reads need none of it: no session data leaves your machine until you sign in to a pool server, accept its covenant, and either send a batch yourself (`oars pool deposit --send <hash>`) or let the sender send. oars installs no scheduler: after a session ends, the session-end hook starts a detached sender, and any `oars` command starts one too (except `oars gate hook`, `oars sessions hook uninstall`, and `oars sessions try`), at most about once an hour, and that sender also reads harnesses that have no session-end hook. After you have accepted the pool's covenant, the sender sends the outbox with no command, and only sessions that have been idle for 6 hours (`SESSION_IDLE_HOURS`) and never sooner than an hour after they end (`HOLD_WINDOW_MS`), which leaves time for `--deny` or a delete: new skeleton batches always, and the redacted raw copies only if you answered yes to the raw prompt (`oars pool raw --consent yes`) and the folder is not set to skeleton only or off. Acceptance is the consent: a machine that has not accepted, has no sign-in, or cannot reach the server sends nothing, and the sender never accepts for you. `oars pool outbox` prints what is queued when you run it, but the sender builds new batches and sends them in the same run without printing them first. `oars pool deposit` itself only writes to the local outbox, and `oars pool fetch` only reads. Telemetry (`docs/telemetry.md`) is separate: it is on by default, records one event per command (its path, flag names, duration, exit code, and error class) and one per hook fire, recall, deposit, and fetch (counts and closed words only), each with a random install id, the oars version, the OS, and the time, and sends those events to the pool server in `OARS_POOL_URL`, else to the Many Oars pool, which is live. The code is in `packages/pool`, a Cloudflare Worker over one D1 database, with R2 buckets for the raw tier and for telemetry, and an Analytics Engine dataset for telemetry.

## Commands

Every command takes the server from `--server <url>`, else `OARS_POOL_URL`, else the Many Oars pool, `https://pool.manyoars.com` (live, with deposits closed until its covenant is published). Plain http goes only to localhost. The server is an origin with no credentials, path, or query, and a redirect is refused, so a token or a skeleton cannot be moved elsewhere.

| Command | What it does |
|---------|--------------|
| `oars pool logout [--server <url>]` | Revokes this machine's credential at the pool (`DELETE /v1/login`), then removes the entry from `<store>/pool-accounts.json`. The request prints before it is sent, with the credential masked. A pool that cannot be reached (or answers 502, 503, or 504) does not keep the entry: it is removed here and the output says the credential was not revoked there, where it lapses on its own or is revoked by the pool's cap on live credentials. Any other refusal keeps the entry so the command can be run again. |
| `oars pool login --provider github\|google` | Asks the pool to start the provider's device flow (RFC 8628; `POST /v1/login/start`), prints the user code and the verification URL, opens the link, and polls the pool (`POST /v1/login/poll`) at the interval it names, adding 5 seconds on `slow_down`, until the person approves, the code expires, or the person denies. The pool calls the provider with its own client ID, holds Google's client secret, reads the person with the token it received, and answers its own credential; the provider's tokens and device code never reach this machine. The command saves the pool's token at `<store>/pool-accounts.json` (mode 0600), pinning the pool's signing key, under its `kid`, on first login (a later login cannot add or replace a key: a new `kid` ships in an `oars` release, see "Rotating the bundle signing key"). No harness token is read, and the client holds no client ID or secret for any provider. With `--verbose`, every request, which goes to the pool alone, prints to stderr before it is sent: the request line, every header, and the body. The login handle and the pool's credential print as `<credential: n bytes>` wherever they appear. It never signs in on its own: when the credential expires, deposits and fetches stop until you run `login` again. |
| `oars pool deposit [--send <hash>] [--accept-covenant <version>] [--in-eu-eea-uk <yes\|no>]` | Writes a batch to the outbox for every session that passes both session gates and has ended, and stops: no session data is sent, and only counts print. With a saved raw yes it reads `GET /v1/covenant` once to learn the version in force; a pool that cannot be asked leaves the build as it was. A session has ended when no transcript of it, main or subagent, has gained a line for `session_idle_hours` (6 hours), judged by the later of its last capture and its raw file's last write; one inside that window builds nothing, is counted as `notEnded`, and has any batch of it from an earlier `deposit` withdrawn. The gates run before any projection does: the folder allowlist (`oars sessions deposit --allow`) and the exclusion check (a listed term in a main or subagent transcript fails it, and so does a session with no raw to scan). A session that fails either is counted by reason and never built; the count never names the term or the folder. A batch is canonical JSON (sorted keys, no optional whitespace, UTF-8) under `<store>/pool-outbox/<hash of server>/`, in a folder named for the vocabulary version, the batch's field list, and the skeleton format, one file per session; a batch built under an older version, field list, or skeleton format is discarded, not sent. A session that no longer passes a gate, has not ended, or is no longer in the store has its batch removed on the next `deposit`, and the removals are counted. It refuses with `vocabulary_expired`, and sends nothing, when this client is more than 30 days past its vocabulary snapshot. `--send <hash>` takes the SHA-256 that `outbox` printed and accepts only a batch that was shown and has not changed on disk since, and it reads and hashes the batch again just before the request. Then it reads `GET /v1/covenant`: a pool with no covenant published stops it with `deposits_closed`, and an account that has not accepted the version in force stops it with `covenant_not_accepted` (exit 3), both before the batch is read for the last time and with no batch sent. Acceptance is typed by a person: on a terminal the client prints the covenant screen the pool serves, then reads the phrase the screen states, and accepts only that phrase. It then asks "Are you in the EU, the EEA, or the UK? (yes/no)" and sends the answer with the acceptance (`POST /v1/covenant/accept` with the version, the screen's hash, `input: typed`, the client version, and `euEeaUk`: `yes` or `no`). Any other phrase, an answer that is not yes or no, no terminal, or a pool with no screen for the version accepts nothing and says why. `--in-eu-eea-uk <yes\|no>` gives the answer without being asked; it needs `--send`. `--accept-covenant <version>` only names the version expected (a different version in force is refused); it never supplies the phrase, it is refused off a terminal, and it does not answer the region question, which is still asked unless `--in-eu-eea-uk` gives the answer. Without `--send` it is a usage error. While the pool is closed to those regions a yes is refused with 403 `region_closed`: the client prints the pool's message and exits 3, and nothing is accepted. A 409 `deposit_conflict` (another deposit of the same session landed first) is sent again, up to three attempts in all, with the same bytes. The sender takes the same lock as `--send`, so a manual send and the sender never send one batch twice; it skips the shown check, because covenant acceptance (and, for raw, the raw yes) is the consent, and it records the hash it sent in `sent.log` in the outbox folder, which `oars pool outbox` and `oars sessions verify` read. It sends each batch and each raw copy once, picks up what a failed run did not send, and records only counts, an outcome word, and `rawHeld: true` when a raw yes given under another covenant was held back, in `pool-nightly.json`. |
| `oars pool enroll --host-class <vps\|cloud\|ci> --launcher <interactive\|orchestrated\|scheduled> --name <label> --allow-repos <owner/name,...> [--days <n>] [--server <url>]` | Enrolls a machine with the pool (`POST /v1/machines/enroll`, the account credential, so `oars pool login` first). Every repository must be private (see "Hold-only enrollment") or nothing is sent and nothing recorded. It prints the one-time enrollment token, which must be activated within 24 hours, then the same env block `--hold-only` prints, `OARS_SESSION_SALT` included, and records the machine in `<store>/machines.jsonl`. `--days` is 1 to 365 (default 90) and is refused locally otherwise. Where to keep the token is under "Machine keys". |
| `oars pool machines [--server <url>]` | Lists the account's machines, one line each: label, id, host class, launcher, state (`pending`, `active`, or `expired`), the day of the last deposit (`never` before a first one), and when the credential held ends. Needs the login. |
| `oars pool machines revoke <id> [--server <url>]` | Revokes one machine (`DELETE /v1/machines/<id>`): its key is refused from its next request. An id that is not this account's, or is already revoked, exits nonzero and names the id. |
| `oars pool raw [--consent yes\|no] [--folder <entry> --mode all\|skeleton\|off]` | The raw prompt: shows it, in plain words, until it is answered. `--consent yes` is a typed answer: at a terminal it prints the prompt and reads the phrase `I consent to sending raw copies`; any other text, or no terminal, records nothing and says why. It lets a locally redacted copy of each full transcript be queued in the outbox beside its skeleton on `deposit` (best-effort redaction; see `docs/sessions-store.md`, "The raw copy"); `no`, or no answer, queues skeletons only. `--folder` with `--mode skeleton` queues no raw copy for that folder, and `off` queues nothing from it; a switch stops future queuing and sending only, and what was sent before stays where it went. No transcript is sent by this command; `--consent yes` reads the covenant version from the pool, and records nothing if the pool has published none. After the phrase it calls `PUT /v1/consent/raw` with the sign-in (the one way back in after a withdrawal) and records nothing here if the pool refuses or cannot be reached; with no sign-in on this machine it saves the yes and tells the pool nothing. A yes is stored with that version, needs the pool reachable (it uses `OARS_POOL_URL` or the default pool, not `--server`), and refuses with `deposits_closed` when no covenant is published. `--consent no` saves the local no first, then calls `DELETE /v1/consent/raw`, which clears the server's yes and records the time and version withdrawn (GDPR Articles 7(3) and 9(2)(a)); if the pool cannot be reached the local no stands, the command says the pool was not told, and exits nonzero, and a rerun retries; a machine with no sign-in that held a yes counts as not told (exit nonzero), since the pool may still hold it. A withdrawal stops new raw copies and the pool's nightly sweep starts erasing the ones already held that night (a large account can take more than one night; "A withdrawal erases the raw copies held"). The sender sends a raw copy only while the answer is yes for the covenant version now in force; a yes given under another version is held back, and `deposit` prints one line naming `oars pool raw --consent yes`. |
| `oars pool outbox [--explain]` | Prints each batch exactly as it would be sent: the request line, every header, and the body, with the bearer credential as `<credential: n bytes>` and nothing else masked, then the batch's SHA-256, and records that this hash was shown. It sends nothing, and it is a separate command from `deposit`. Each batch and raw copy the sender already sent is marked `sent: <time>`. Raw copies print as `raw part i/n sha256: <hash> bytes: <n>`, and `--explain` prints their bodies. The sender sends what is queued without printing it, so print first if you want to read it before it goes. `--explain` adds each field's rule, and a field with no rule fails the command rather than print blank. `oars sessions verify` reports how many batches, on any server, were built under an older vocabulary, field list, or skeleton format. |
| `oars pool prove [--json]` | Proves you control your account with your sign-in alone (`POST /v1/account/proof`, never a machine key) and prints the account and the time the pool stored, to send in reply to the operator's request for proof (GDPR Article 12(6)). A lapsed sign-in says to run `oars pool login` first. On a closed account `oars pool login` is refused 403 `account_closed` and prints the same two values. |
| `oars pool export --out <folder> [--raw]` | Saves your copy of what the pool holds about your account (GDPR Articles 15(3) and 20): JSON, one file a page (`account-export-0001.json`, and on), written owner-only into the folder, which a rerun overwrites (a page of an older, longer export that this run does not reach is removed). It needs `oars pool login`, follows the cursor of `GET /v1/account/export` until it ends, and writes nothing to the pool. With `--raw` it also fetches each raw transcript you deposited that has not been erased, into `<folder>/raw/<sha256>`, and checks each against its hash. It prints what it saved. If any page or object failed it exits nonzero naming each one with the pool's answer and how much was saved: a failed page stops the walk (there is no cursor past it), and a failed object does not stop the others. See "Your copy". |
| `oars pool fetch [--harness <name>] --harness-version <version>` | Fetches that harness's signed bundle at that version, verifies it against the pinned key, and keeps it at `<store>/pool-replica/<hash of server>/<harness>/<version>.json`, still signed, so a fetch for one harness never overwrites another's. `pool-replica.ts` is the one reader of that file (`keptReplica`, `sessionBundle`): `pool fetch`, `oars sessions recall`, the MCP tool, and the hooks all read the kept bundle through it, for the session's own harness and version, and a missing, other-harness, or corrupt bundle means local reads only. A bundle that fails verification, or is for another harness or version, is refused and not written. The version must be a public one; nothing is keyed by stack. `--harness` takes one of `claude-code`, `cursor`, `codex`, `copilot`, `gemini`, `grok`, `opencode`, `pi`, or `vscode-copilot`; any other name is refused before anything is sent. With no `--harness`, it fetches the harness your local store holds the most sessions of (`claude-code` for an empty store or a tie), and says so on stderr before it sends: `No --harness given: fetching cursor, the harness your local store holds the most sessions of (3 of 4). Pass --harness <name> to fetch another (claude-code, cursor, codex, copilot, gemini, grok, opencode, pi, vscode-copilot).` It reads counts only, and none leaves the machine: the request names the harness and the versions, nothing else. Before it sends, it prints the request line and every header to stderr, with the credential as `<credential: n bytes>` and nothing else masked. It keeps the bundle's `ETag` beside it and sends `If-None-Match` next time: a 304 keeps the bundle and says it is unchanged (exit 0). A 429 (the weekly fetch cap) keeps the bundle, says in words when to try again from `Retry-After` (or that the pool did not say), and exits **10**, the code `fetch` alone uses, so a schedule can tell a cap from a failure. |
| `oars pool coverage [--org-size <band>] [--repo-visibility public\|private\|unknown]` | Sets the two coverage bands only you can state, in `<store>/pool-coverage.json`, and prints the current values. `--org-size` takes `solo`, `2-10`, `11-100`, `101-1000`, `over-1000`, or `unknown`. Nothing is read from the network, and a band you leave unset goes on the wire as `unknown`. |

## Hold-only enrollment

`oars pool enroll` without `--hold-only` is the same enrollment plus the pool's token (see "Commands" and "Machine keys"): the block it prints is the one below, without `OARS_HOLD_ONLY`. The token comes from the pool alone, is shown once, and is never stored by the client; keep it as described under "Machine keys" (Enroll). The GitHub check is the same either way: `GH_TOKEN`, then `GITHUB_TOKEN`, and with neither a private repository cannot be confirmed, so enrollment is refused naming both.

A cloud VM can hold its deposit in its own private repository, with no pool credential and nothing sent to a pool. Run `oars pool enroll --hold-only --host-class <vps|cloud|ci|hosted> --launcher <interactive|orchestrated|scheduled> --allow-repos <owner/name,...>` on your own machine (the flag repeats, or takes a comma list). It reads your exclusion term file, refuses an empty one, and checks that every repository is private against GitHub's repository record: a `GH_TOKEN` or `GITHUB_TOKEN` that can read the repository is how a private one is seen (a repository the token cannot see, or any answer that does not say, is refused like a public one). Only then does it record the new machine in `<store>/machines.jsonl` and print the env block to set in the cloud environment: `OARS_HOST_CLASS`, `OARS_LAUNCHER`, `OARS_MACHINE` (the id it minted), `OARS_ALLOW_REPOS`, `OARS_REPO_SALT` and `OARS_SESSION_SALT` (each derived from your store salt, so the store salt never leaves), `OARS_EXCLUSION_TERMS_INLINE`, and `OARS_HOLD_ONLY=1` (the marker that tells the machine's child it has no pool key). The block holds two salts and your terms: treat it as a secret.

At each Stop the machine builds the session's batch as usual, then commits it, with no change to the checkout, to the branch `oars-hold/<machine>/<id>` of the session's own repository and pushes it (`[skip ci]` in the message, the project's own `pre-push` hook skipped, up to three attempts). The branch's tree holds three files: `batch.json` (the batch), `stamp` (its vocabulary and format stamp), and `terms` (a keyed digest of the term list the batch passed). A repository that left `OARS_ALLOW_REPOS` after the batch was built is not committed. A machine missing `OARS_MACHINE` or `OARS_SESSION_SALT` holds nothing and says so at its next Stop. A change to your term list needs this command run again and the new block set in every environment.

## Pulling held batches

`oars pool hold pull [--server <url>]` runs on the machine that enrolled the cloud environments. It rechecks every repository named in `<store>/machines.jsonl` against GitHub's repository record on every run (the same `GH_TOKEN` or `GITHUB_TOKEN` rule as enrollment), and a repository that is public now, or whose record cannot be read, is refused and reported with none of its branches fetched. For the rest it fetches the tips of the `oars-hold/*` branches only (depth 1, no history, no tags) over `https://github.com/<owner>/<name>.git` with this machine's own git credential, into a scratch repository removed when the run ends. With no term file the whole run is refused before anything is fetched.

A branch is admitted to the outbox only if every one of these holds. Any other branch is reported with its name and a reason, nothing is written for it, and it stays where it is:

- Its name is `oars-hold/<machine>/<id>`, the `id` being 16 hex digits (the one shape the outbox keys by), for a machine in `machines.jsonl` that was enrolled for that repository and whose record holds a host class and launcher from the two closed lists of `claimed`, and no newer branch names the same `id`: the newest tip of an `id` alone is considered, so when it is refused an older one is `duplicate_id` and not admitted in its place (`branch_name`, `unknown_machine`, `machine_repo`, `machine_record`, `duplicate_id`).
- Its `stamp` file is a stamp folder name whose version segment is the batch's `vocabVersion` (`stamp_invalid`).
- Its `terms` file equals the keyed digest of this machine's own exclusion terms, so a branch from an environment still holding an older list is kept and reported, whatever its stamp says (`terms_stale`).
- Its `batch.json` carries no `claimed` field (`claimed_present`) and no field outside the batch field list (`field_unknown`), the pool's own reader accepts it with nothing set aside (`batch_invalid`, `off_list`), its `id` is the branch's (`id_mismatch`), and no string or key in it holds a term from this machine's list (`a38_term`). A report names where a refusal was, never a value from the file.

A batch refused under a stamp other than this client's current one is reported as `differing_stamp`, with the refusing reason after it.

What reaches the outbox is the reader's output with `claimed` (the host class and launcher of the machine's enrollment record; field-list version 11, register rows `claimed`, `hostClass`, and `launcher`) added, never the branch's bytes. Nothing else writes `claimed`: the client's own build never carries one. It is filed under the branch's own stamp, so a batch built under an older vocabulary or field list keeps a folder of its own, and `pulled.json` in the outbox folder records its `id` and that stamp. A pull of an `id` already held under another stamp removes the older copy once the new file and `pulled.json` are durable.

Once the batch and its `pulled.json` entry are durable, `hold pull` deletes the branch (the VM's git proxy refuses deletions, so only this machine can), with the lease `--force-with-lease=<ref>:<sha>` so a push that landed after the tip was read is kept and the next pull admits it. A crash between the two leaves the branch, and the next pull replaces the same `id`. A branch that was refused stays, and so does one the remote would not delete; the report says `branch kept`. A night holds the send lock across its whole send, and `hold pull` writes under that lock, so a pull that overlaps a long night stops with `send_locked` after two minutes: the batches it already admitted stay, the tips not yet read are left for the next pull, and the message says to pull again in a minute. A repository with no `oars-hold/*` branch is asked first (`git ls-remote`) and fetched only if one is there, since a depth-1 fetch of nothing fails.

**What a pulled batch lives through.** It waits as long as the covenant stays closed, so everything that would remove a local batch is told about it:

- `pool deposit` (and the nightly, which runs it) keeps the keys `pulled.json` lists at the current stamp when it prunes batches it did not build, and the stale pass (`discardStale`, the stale count in `oars pool outbox` and `verify`) skips each listed key at the stamp it is listed under, and no other, so a local batch left in the same folder is still discarded. A batch filed under an older vocabulary or field list therefore outlives the change.
- The nightly loop, `oars pool deposit --send <hash>`, and `oars pool outbox` read the current stamp and every stamp `pulled.json` lists. An entry leaves `pulled.json` once its hash is in `sent.log`.
- If the pool refuses a pulled batch with `closed_vocabulary` (a value it no longer reads, or a skeleton format older than it reads, which is the same code on the field `format`), the batch stays, unsent and unmarked, the loop goes on to the next batch, and the night's note (`pool-nightly.json`) carries `refused` with the count. It is asked again the next night. A batch this machine built that the pool refuses still ends the night, as before. A pulled batch cannot be rebuilt, since its raw never left the VM, so a format the pool stops reading strands it until the pool reads that format again.
- Every send pass (the nightly and `--send`) reads each pulled batch against the term file as it is now, because the file may have grown since the batch was admitted. A batch that holds a term is removed with its entry and counted as `removed` in the night's note; `--send` of it says so and sends nothing. With the term file missing or empty no pulled batch is sent and none is removed.

## Repo key, coverage bands, and hour

Four frame fields make "the same work" and "who the pool covers" observable. Each is optional on the wire and carries a value only when the client could state one.

- **`repoKey`.** 16 lowercase hex characters: the salted hash of the repository's identity that the store already keeps as `repo` (`docs/sessions-store.md`, "Hashing"), so two clones of one repository, or two harnesses in one, share it. It is hashed under a salt derived from the store salt (an HMAC of the label `repoKey/1`), not under the store salt itself, which never leaves the machine; an enrollment (`oars pool enroll --hold-only`, below) hands that derived salt to its machines as `OARS_REPO_SALT`, so a cloud VM keys a repository as the enrolling machine does. It is on the transcript frame and every frame of its list (not a prompt's frame), and a session whose repository is unknown sends none. The emitter drops any value that is not key-shaped, so a path, a remote URL, or a name never reaches a batch. Cells do not read it.
- **`orgSize`, `team`, `repoVisibility`.** Coverage bands from closed lists: `orgSize` is `solo`, `2-10`, `11-100`, `101-1000`, `over-1000`, or `unknown`; `team` is `solo`, `team`, or `unknown`; `repoVisibility` is `public`, `private`, or `unknown`. `orgSize` and `repoVisibility` are what the operator sets with `oars pool coverage`; `team` is the count of distinct commit authors in the repository's local git log (`git log --format=%aE`, at most 5,000 commits, counted and never sent), one author being `solo`. No network call is made, and anything unread goes as `unknown`. The bands state what the pool can say about its coverage; no read filters on them.
- **`hour`.** The UTC hour of day, 0 to 23, beside the UTC day, on the transcript frame, each prompt frame, and each call frame. It joins no cell.

**The join's limit.** The salt derives from the store's own, this machine's (`localSalt` in `store.ts`); `accountSalt`, the account-wide salt, is still the open M4 seam. So the key joins one operator's harnesses on one repository on one machine, and on the machines an enrollment gave its derived salt to, and nothing else: the same account on a second machine no enrollment reached gets a second key until the account salt lands, two accounts on the same repository get two keys, and the pool cannot join either. A salt rotation, like a new machine, starts new keys, so batches deposited before and after no longer join. The earlier truth stands, that two accounts' sessions cannot be joined.

| Field | Class | Re-derives from `raw/` | Note |
|-------|-------|------------------------|------|
| `repoKey` | clear (a client hash under a salt derived from the store salt, which an enrollment hands to its machines) | yes, with the salt | 16 hex characters |
| `orgSize` | clear | no, operator-set | closed list of six |
| `team` | clear | no, read from the repository's local git log at each deposit | closed list of three |
| `repoVisibility` | clear | no, operator-set | closed list of three |
| `hour` | clear | yes, from the timestamp | 0 to 23 |

The large-deposit fixture's session has `repo`, `tsFirst`, and every prompt's `ts` null, so it carries no `repoKey` and no `hour`: the 128<!-- figure:bands --> bytes it gained are the three `unknown` bands on its two frames, 64<!-- figure:bands-per-frame --> bytes a frame. `repoKey` and `hour` were measured on a fixture that holds them (`pool-wire-coverage.test.ts`, three prompts at three distinct UTC hours and two calls each, 3,517<!-- figure:coverage-bare --> bytes of skeleton without either): the key costs 58<!-- figure:key-cost --> bytes (29<!-- figure:key-per-frame --> on each of the two frames, the transcript's own and the list's one call frame, when no prompt carries a timestamp, 116<!-- figure:key-timed --> across the four frames when three prompts carry three distinct hours), and the hour costs 755<!-- figure:hour-cost --> bytes, because each distinct hour among a session's prompts splits its calls onto one more frame of the list, so a session with many prompts across many hours pays one frame per hour it touched (24 at most). Both figures are pinned in that test.

## Sign-in

The pool brokers both providers' device flows, so the client holds no OAuth value. The pool's client IDs are public and sit in `wrangler.jsonc` `vars`; Google's token call needs its client secret, which is a Worker secret and never in the repo.

| Setting | Holds |
|---------|-------|
| `GITHUB_CLIENT_ID` (var) | The client ID of the Many Oars GitHub OAuth app ("Many Oars CLI", org `manyoars`), with device flow enabled. GitHub's device flow needs no secret. |
| `GOOGLE_CLIENT_ID` (var) | The client ID of the Many Oars Google OAuth client ("oars CLI device flow", project `many-oars`), of type "TVs and Limited Input devices". |
| `GOOGLE_CLIENT_SECRET` (secret) | That client's secret, set with `wrangler secret put`. It is sent only to Google's token route, from the Worker. |

A provider whose client ID is unset (and Google, when its secret is unset) refuses `/v1/login/start` and `/v1/login/poll` with 503 `not_configured` naming the binding, and calls nobody.

**The login routes (the contract).** Both are unauthenticated, JSON in and out.

- `POST /v1/login/start` with `{provider}` (`github` or `google`). The pool posts the provider's device-code route with its own client ID (scope `openid` for Google, none for GitHub) and answers `{handle, userCode, verificationUrl, interval, expiresIn}`: the code to type, the link to open, the poll interval in seconds, and the code's lifetime in seconds. `handle` is opaque. 400 `unknown_provider`, 503 `not_configured`, 502 `provider_error` when the provider cannot be reached, answers no code, or refuses to start (its own error word is in the message, as for `device_flow_disabled`). A client address (Cloudflare's `cf-connecting-ip`, kept only as an HMAC under `PSEUDONYM_KEY`; an IPv6 address counts as its /64, the first four hextets, because one host holds a whole /64 and would otherwise get a fresh count per address; an IPv4 address counts whole) may start `LOGIN_STARTS_PER_HOUR` sign-ins an hour (10 when unset): past it, 429 `rate_limited` with `Retry-After`, and the provider is not called. 503 `login_unavailable` when the count fails (a bound that opens when its store fails is no bound).
- `POST /v1/login/poll` with `{handle}`. The pool unseals the handle, posts the provider's token route once (Google with `GOOGLE_CLIENT_SECRET`), and answers `200` with a `status`: `pending` (the person has not approved yet), `slow_down` (poll less often: the client adds 5 seconds to its interval; the pool answers it itself, without calling the provider, to a poll that comes before the interval it holds for that handle), `expired`, `denied`, or `authorized` with `{token, account, expiresAt, signingKey, kid}`, the pool's credential, the public half of its signing key, and that key's id. On approval the pool reads the person with the provider's token (GitHub's `/user`, Google's userinfo), hashes the subject as before, and drops the token. 400 `missing_field` for `handle`, 401 `invalid_handle` for one this Worker did not seal (tampered, truncated, with its provider or expiry changed, or sealed by another Worker) or whose poll record is gone, 503 `login_unavailable` when the interval store fails, 401 `login_refused` when the provider's profile route does not accept the token it issued, 503 `not_configured`, 502 `provider_error` for a provider that cannot be reached, answers HTML, answers a word the pool does not know, or does not name the user (a GitHub 403 for a rate limit is here, not a refused sign-in; only a 2xx profile answer can sign anyone in, whatever a 403 or 5xx body names). A sign-in for an account the operator closed is answered 403 `account_closed` (the operator closed the account; the message names privacy@manyoars.com), and no credential is issued.

**The handle.** It carries the device code sealed with AES-256-GCM, as `base64url(nonce || header || ciphertext || tag)`. The header is the provider's name and the expiry (one length byte, the name, and the expiry as a 64-bit big-endian integer), readable but bound as the GCM associated data, so a handle with another provider or a later expiry fails the tag and is refused (401 `invalid_handle`) before any provider call. The key is derived from `PSEUDONYM_KEY` by HKDF-SHA-256 under a label of its own (`oars-pool login handle seal v2`), so the secret itself is never the cipher key and no other use of it yields this one; a handle from another Worker (another `PSEUDONYM_KEY`) is refused. The client never sees the provider's device code. A handle past its expiry answers `expired` without calling the provider. **The interval.** The pool holds the provider's `interval` and every `slow_down` it has asked for per handle, in D1 `login_polls` keyed by the handle's SHA-256 (the handle itself is never stored). A poll claims its slot with one atomic update (`next_at <= now`), so two polls at once cannot both reach the provider; one that comes early gets `slow_down` from the pool. A provider `slow_down` adds 5 seconds to the stored interval. Rows are swept after the device code's expiry.

Because the pool only ever reads a person with a token the provider issued to the pool's own client, a token another app holds for that person cannot sign in (register A54): no route takes a provider token from the client. `POST /v1/login` answers 410 `gone`, naming the two routes.

## Machine keys

A person is an account, and each runtime the account runs (a cloud environment, a VPS, a CI runner) is a machine of that account with a key of its own. The account credential (see "Sign-in") enrolls, lists, and revokes machines and never goes to one. A machine key deposits and does nothing else. Neither a token nor a key is stored or logged in the clear: the `machines` table (migration 0024) holds each one's SHA-256, and a token or key is shown once.

- **Enroll.** `POST /v1/machines/enroll`, the account credential only, takes `{hostClass, launcher, label, allowRepos, days}`. `hostClass` is `vps`, `cloud`, or `ci` (a person at the machine uses the account credential, and a hosted run uses a per-run token, so neither enrolls). `launcher` is `interactive`, `orchestrated`, or `scheduled`. `label` is letters, digits, spaces, dots, underscores, and hyphens, 64 at most, starting with a letter or digit. `allowRepos` is at most 100 `owner/name`, each kept once, and may be left out. `days` is how long the key lives from its activation: a whole number from 1 to 365, left out for 90 (`KEY_LIFE_MS`, the one default); over 365, zero or negative, fractional, or not a number is 422 `invalid_field` naming `days`. A value off its list is 422 `closed_vocabulary` or `invalid_field` and a missing one 400 `missing_field`, each naming the field. The answer is 201 `{machine, token}`, and the token dies 24 hours after it is minted if it has not been activated (`TOKEN_LIFE_MS`), whatever `days` asked for. **Keeping the token.** It comes from the pool alone (`oars pool enroll` prints it), is shown once, and is never stored by the client; keep it as a network secret on the cloud environment (Bearer, to the pool's host, `pool.manyoars.com` by default) or in an owner-only file on a server, never in a repository.
- **Activate.** `POST /v1/machines/activate`, with the token as the bearer, binds it as the machine's deposit-only key (state `pending` to `active`) for the `days` its enrollment asked for, 90 by default (`KEY_LIFE_MS`), counted from then, and answers `{machine, rotate}`. Every fresh VM of a runtime whose secret lives only in a proxy presents the same key as a first use, so a `cloud` key activated again answers `{machine, rotate: false}` and moves nothing. On any other class, an `active` key that has not been rotated answers `{machine, rotate: true}` again, so a machine that stopped before it rotated is not stuck.
- **Rotate.** `POST /v1/machines/rotate`, with an active key of a `vps` or `ci` machine, answers `{machine, key}`: a fresh key that never sat in a secret store. The old hash is kept as retired, so the spent token is refused by name (401 `token_retired`, at activate and at rotate); only the latest replaced key is kept, so after a second rotation the first token is 401 `unauthorized`, and the expiry does not move. A `pending` token is 409 `not_activated`, and a `cloud` key, which has nowhere to keep a rotated key, is 409 `not_rotatable`.
- **Refusals at these two routes, and at the deposit and covenant routes.** All 401: `unauthorized` (no bearer, an unknown one, or, at activate and rotate, an account credential), `token_retired`, `token_expired` (unused for 24 hours), `machine_expired` (past its life), and `machine_revoked`. The deposit and covenant routes refuse a key the same way, and a token not yet activated is 409 `not_activated` there, as at rotate; an unknown bearer at those two is not a machine's, so it is answered as it always was (sign in at the deposit route, `accepted: false` at the covenant route). Enrollment and activation of a closed account are the exception to "all 401": they answer 403 `account_closed` (the operator closed the account; the message names privacy@manyoars.com); a revoked key keeps `machine_revoked`.
- **List and revoke.** `GET /v1/machines` lists the account's machines, newest first, as `{id, label, hostClass, launcher, allowRepos, state, expiresAt, createdAt, lastDepositDay}` (`lastDepositDay` is the `YYYY-MM-DD` day of the machine's last stored deposit, or null before a first one; a deposit the brake refuses does not move it); `state` is `pending`, `active`, or `expired`, and no hash, token, or key is in it. `DELETE /v1/machines/:id` revokes one: 204, effective on the machine's next request, which gets 401 `machine_revoked`. Both take the account credential only and see only that account's machines: another account's id is 404 `not_found`, the same as an unknown one or one already revoked.
- **Deposit-only.** Every route answers a machine key 403 `deposit_only` unless it is marked `machine: true` in the route table (`ROUTES` in `worker.ts`): `POST /v1/deposits`, `GET /v1/covenant`, `POST /v1/telemetry` (which reads no credential, so a cloud machine's telemetry is not refused), and these two routes, activate and rotate. The check runs first, in one place (`machineScope`), so it covers the raw tier and an unknown path, and a route added without the mark is closed to a key. A pending token and a revoked key are refused the same way. `machine-scope.test.ts` walks `ROUTES` and the raw routes and fails for a route that lets a key through. A machine key never takes raw consent or accepts the covenant.
- **Deposit.** `POST /v1/deposits` takes a machine key as well as the account credential. A key deposits for its machine's account, under that account's covenant acceptance, and the ledger row is stamped from the key: `machine` (the opaque id the account lists), `hostClass`, and `launcher` are the machine's own, and nothing in the batch can change them. The account credential's row is `machine` null, `hostClass` `local`, and `launcher` `unknown`, because the pool cannot tell a person from a job there. A session sent again is stamped again, so a row carries the provenance of the write that last set it, and a batch sent in parts is stamped by the key that sends the last part. Migration `0025_deposit_provenance.sql` adds these columns, and no wire field comes with them. Each deposit a machine's key stores also records the UTC day on the machine, its last deposit day; a deposit the operator's brake refuses records none.
- **`claimed`.** A batch held on a branch or pulled from a cloud session is sent later under the account credential, so its stamp says `local`. Such a batch may carry `claimed`, a closed `{hostClass, launcher}` that states the run it came from: `hostClass` is `local`, `vps`, `cloud`, `ci`, or `hosted`, and `launcher` is `interactive`, `orchestrated`, `scheduled`, `ci`, `hosted-run`, or `unknown`, and both are required. The pool keeps it in `claimed_host_class` and `claimed_launcher` beside the stamp and never in place of it. It reaches no tier and no count; it exists so a held week of cloud work is not read as a laptop's. The pool reads it before the skeleton, so it is neither an unknown field nor kept in the bag. A value off its list is 422 `closed_vocabulary` naming its field: `claimed.hostClass`, `claimed.launcher`, `claimed.<key>` for a key beside those two, and `claimed` for anything that is not an object. A null `claimed` is none, and a resend without it clears an earlier claim. A machine key claims nothing, because its batch is stamped from the key: any `claimed` under one is 422 on `claimed`. `oars pool hold pull` is the one client path that writes it (field list 11; register rows `claimed`, `hostClass`, and `launcher`).
- **On the machine.** The child asks one module (`machine-credential.ts`) for its pool credential. On host class `cloud` the key is proxy-held: the child sends no `Authorization` header and the network secret is added outside the VM. On any other class it uses the key file, `<store>/machine-key`, written owner-only, else the token from `OARS_MACHINE_TOKEN_FILE` or `<store>/machine-token` (enrollment names no path; this is the one the child reads). Before its first deposit the child calls `activate`. On `rotate: true` it calls `rotate`, writes the fresh key to the key file, and only then deletes the token, so a crash between the two leaves the token, and the next run finds the key file, sends with it, deletes the leftover token, and makes no activate call (the pool has retired that token, so activating again would be refused). A crash after the pool rotated but before the key was written leaves a retired token and no key: the pool answers 401 `token_retired`, and the child tells the person to enroll the machine again. A machine enrolled with `--hold-only` has no pool key: its printed block carries `OARS_HOLD_ONLY=1` (a machine enrolled before that must set it by hand), and it makes no `activate` call. Any other 401 `unauthorized` (a proxy holding a wrong or old secret, or a key file the pool does not know) is reported as a notice. On `rotate: false` (a `cloud` key) it keeps the proxy-held token. A key or token value is never written to a log line, a notice, or any file but the key file.
- **Sending from the machine.** Once the key is active and `GET /v1/covenant` says accepted, the child, under the send lock, sends every unsent batch in its outbox, so a batch a VPS held before the covenant was accepted goes out with a later run, once. Raw is never sent under a machine key. A refusal leaves the batch unsent and reported, and a 401 `machine_revoked` sends nothing and deletes nothing. Batches `hold pull` admitted are sent by the account, not the child.
- **The expiry notice.** The child records `machineExpiresAt` (from a deposit or covenant answer) or a `machine_expired` or `machine_revoked` refusal in `<store>/machine-notice.json`, and the next Stop prints one `systemMessage` naming `oars pool machines` when the key expires within 14 days, has expired, or was revoked, at most once a day (an expired or revoked key replaces an "expires on" notice). A key with more than 14 days left prints nothing.
- **Expiry.** The 201 of a deposit made with a machine key and the 200 of `GET /v1/covenant` made with one carry `machineExpiresAt`, the key's expiry in milliseconds since the epoch, so a machine can say a key is ending before it has. An account credential's answers carry no such field. A part retried after its batch was stored answers `{ok, id}` alone.

## What the server enforces

- **Deposits are closed by default.** With no `COVENANT_VERSION` binding, every deposit gets 403 `deposits_closed`. Once one is set, an account must have accepted exactly that version, or it gets 403 `covenant_not_accepted`, and a new version asks again. Reads and `fetch` are not affected.
- **Closed fields, open names.** A shape error (a wrong type, a malformed value) gets 422 `closed_vocabulary` with the field named, and nothing is stored. An unknown field goes to the extensions bag, and an unknown enumerated value is read as `other`. A name off the public lists (an MCP server, skill, pull name, program, subcommand, flag name, native tool name, model, or harness version) is not refused: it is stored and served only at the floor (next bullet). What is stored is the parsed skeleton, not the text that came in.
- **One class table, hashed hosts, and the floor.** `packages/pool/src/field-classes.ts` gives each wire field a class, and the register below carries the same column (`field-classes.test.ts` keeps them equal). The value of the `host` field is replaced by an HMAC-SHA-256 under the pool-wide `INGEST_HASH_KEY` before anything is written (rows, the extensions bag, literals, cells, and motifs), and a pool with no key refuses every deposit with 503 `not_configured`. A long-tail name is held in clear at rest and served only once `PUBLIC_FLOOR` (5 by default, see "Serve floors") distinct accounts report it; below that no cell, motif, read, count, or denominator shows it, and the smallest served name beside a sub-floor one is withheld too. Every signed bundle states the floor it applied (`floor`). No host is written in clear at any point: hosts are hashed before any readable write, and a part of a batch sent in parts is sealed (AES-GCM) while it is staged, so a part held for a later join, or kept after a 409 `deposit_conflict` or 403 `deposit_limit`, is unreadable without the deploy's `INGEST_HASH_KEY`.
- **Intervention outcome (field-list version 6).** A prompt may carry `intervention`: what the next human prompt did to its work, one of `none`, `after-error`, `redo`, `revert`, `user-stop` (the human rejected a call or interrupted the turn; t912, no new field, so the field-list version does not move for it), or `unknown` (the rule and each limit are in `docs/sessions-store.md`, "Prompt intervention"). It is an outcome row, not a quality claim: no grade or score is named, and `none` is silence in the records, not approval. It is computed on the client from the stored records, so no prompt text, path, or command crosses; the bucket alone does. **Absent means not computed** (the stored prompt predates the signal); `unknown` means computed and not sayable, as for the last prompt of a transcript. A value off the list reads as `other` and is kept as sent in the bag. The pool holds it per prompt in the stored skeleton and no read, cell, or bundle serves it (`served-families.test.ts` pins that); its one stated consumer is the later test of whether the per-prompt graph predicts intervention above chance on held-out repo keys, after the first 1,000 pooled prompts. The field is a closed list of constants, not a name, so it passes no long-tail name gate.
- **Step attribution (formats 3, 4, and 5).** A step names the frame it ran in and the skill whose run it sits in, and a frame names the reach of its session, so harness, version, model, skill, and the servers, skills, and plugins in reach resolve from a step without a join the parser cannot check. A transcript sends `frames`, its distinct frames (its own first), and each step a `frame`, a position in that list; the parser refuses a position outside it. A call's frame is its prompt's frame (the transcript's before the first prompt) with the call's own `model` and `harnessVersion` where its line named them, so a model that changes in the middle of a prompt reaches the steps that ran on it; a call that recorded neither takes its prompt's. A step made inside a skill's run carries `skill`: the name after redaction, or `private` when it counts as redacted. Only Claude Code writes `attributionSkill`; an absent step `skill` on any other harness means not recorded. The harness marks no end to a run: it stops naming the skill on the next line, and that is where the run ends here (limit: a skill the harness does not name on the line shows nothing, and a nested skill shows only the outer name the line carries). A frame in `frames` and the transcript's `frame` carry `reach`: `{ filled, mcp, skills, plugins }`, each `mcp` and `skills` member the name after redaction, or `private` when it counts as redacted (a plugin is always `private`, since no plugin list is pinned), from the session's `setup`, its `funnel`, the MCP tools it called, and the skills it called. `filled` is false when the record holds neither `setup` nor `funnel` (Cursor, Copilot, Grok Build, OpenCode, Pi, and a capture before version 12), and then the lists are empty and must not be read as no tools. The large-deposit fixture in `packages/pool/src/ingest.test.ts` pins the skeleton at 887,141<!-- figure:skeleton --> bytes (about 819,000 before a null `errorCode` went on each call and a null `spawnedIn` on the transcript, about 877,000 before a null usage and remainingTokens, about 887,000 before the coverage bands), up from about 785,000 bytes before step attribution. The cell computation does not read the new fields: a cell is still keyed on the prompt's frame, so a mid-prompt model change moves no cell. **Model version:** a model literal holds the model's name as the harness wrote it (`claude-opus-5-5`) and no version beyond it, so a cell and a frame cannot tell two builds of one name apart; a model-boundary read is not built.
- **The skeleton form (formats 3, 4, and 5; formats 1 and 2 are refused with 422 naming `format`).** A step carries a shell call's projected `program`, `sub`, and `flags` in place of the joined shell command a step used to carry: a program is sent as its basename after redaction, whether or not a public list holds it, and a `private` program holds no subcommand, flag, or pull. The subcommand and flag names of every program that is not `private` go through the same gate as any name (a flag value never leaves: `--token=abc` sends the flag as `private`, and a short flag with its value attached, `-psecret`, is dropped, since a single-dash flag goes only as one letter, or as a public flag such as `-NoProfile`), and the parser accepts an off-list subcommand and flag name. A model and a harness version go the same way, as the string after the gate. A call's own model and version, which capture keeps as its line names them, reach the pool as that string; the frame of a transcript or a prompt carries the value capture closed it to (the public name, else `<literal>`), sent as it is. Capture still drops a subcommand or flag off the pinned vocabulary of its program, so a real session sends no off-list subcommand (`sub` is null) and no off-list flag until a capture bump (owed); a multi-letter single-dash flag no public list holds is dropped, as an earlier client dropped it. A name goes as `private` only when the client's redaction changes it, it matches your exclusion terms, it is not a name (a mis-parsed command), or it is over 128 characters; an older client's `private` is still accepted. An MCP server, skill, pull name, and native tool name are sent as they are after the same check, and a host is sent as it is and hashed on arrival (see "One class table" above). The parser refuses `<literal>` at those places. Capture stores a skill-run name, a host, and a pull name as they are after your redaction (CAPTURE 24), so a real session sends them through the same gate with no second projection; a store captured before it holds `<literal>` for the off-list ones until the next deposit captures it again (see `docs/sessions-store.md`). Usage, `errors`, `wallSec`, and a step's `tokens` and `ms` are Section 7 buckets, never exact counts; the one exact time is `durationMs` per tool step. A transcript and a prompt still carry their `frame` (each member has a Section 1.2 row, and the bucket key and the strata read it); only the shell step's joined command went. `deltas` is on the form and holds the batch's local delta entries, if any (see Local deltas); an entry outside its field's row is refused. A failed call carries its `errorCode` (a member of the closed `ERROR_CODES` list, `other` for a value off it, which also goes to the extensions bag, or `null` when the harness captured none) and, on a call that did not succeed, `recoveryCalls`: `next`, the canonical actions of up to the next five calls in the same prompt (what followed, never a fix; an action off the list reads as `other`), and `editFollowed`, true when a `file.edit` or `file.write` whose own result was not an error was among them (not a success flag). The list must equal the one the batch's own calls give, or the batch is refused. No signature hash, text, or argument goes with either. The exact-count form (format 1) and format 2 are refused with 422 naming `format`; nothing is migrated. Cells count a bucketed value as the bucket's lowest value, so a cell's `tokens` and `durationMs` are lower bounds. The cell computation is one module (`cell-increments.ts`) that the pool's ingest and the client's local read both call; the local read projects its store with the open gate (name shape and length, but not your redaction or exclusion terms), because it sends nothing. A step's calls and a prompt's place are positions in the batch, not the log's numbers: tool `n`, prompt `index`, and a step's `seg` (its place in its call, which the server rebuilds from position) are not sent. **Edges and the spawn link.** A step carries `edges` when any arrive, each `{ kind, target }`: `kind` is one of the closed list `next` (order within a prompt's line of work), `spawned`, `retried`, and `after-error`, and `target` is the position of the step it names, counted over the steps of one transcript in call order (a position in the batch, never a call number). The client decides `retried` and sends the result, since the pool holds none of the raw keys it compares. A `spawned` edge sits on a subagent's first step and names a step of the spawning transcript. The parser reads an unknown kind as `other` (kept in the extensions bag, its target held to a count only), and refuses a target that is not an earlier step of the same transcript (a `spawned` target must be a step of the spawning transcript), and a `next` whose target ran in another prompt. A transcript carries `spawnedIn`, the position in the batch's `transcripts` of the transcript that spawned it, and a step's `parent` is the position of the spawning call in that transcript's `tools`, so a subagent two deep rebuilds its tree from the batch alone. `spawnedIn` is null for the main run and for a subagent whose spawner the batch does not hold; the parser refuses a position outside the batch, the transcript itself, a cycle, and a spawner on the main run. **Which harnesses fill it:** Claude Code alone, from the subagent's `.meta.json` tool-use id; Codex and Gemini read a subagent but record no spawning call, so they send null, and the other harnesses record no subagent run. The cell computation does not read an edge: a motif is still a linear window inside one prompt, and the cells are byte-identical with and without edges. A skeleton-derived store (`cell-increments.ts`) carries both back, so it holds the same graph as the local store on the fields both keep. `usage.thinking` is a token count and goes as the `tokens` bucket like the other usage fields. A usage category the source never recorded goes as `null` (its key stays required), never as the bucket of zero, so a prompt with no counts at all sends five nulls and a partial total sends a number only for the categories it observed; every prompt also sends `usageResponses`, a `count` bucket of the responses that reported usage, so the numbers say what they cover (field list version 7, after the intervention field at 6; the field is left out only on a record that predates the coverage, capture version 20). A step's `remainingTokens` goes as `null` or is left out when steps follow it and none of them reported tokens, and otherwise as the bucket of the sum over the ones that did (a lower bound). A client that predates this sends the five numbers, and the parser still accepts them. A cell never holds a list longer than one: a motif keys on a shell step's program and subcommand, and each flag and each pull is its own one-step cell (spec rules 1 and 2), so a step with two flags makes two flag cells and one program cell.
- **Two planes.** A deposit writes its parsed skeleton and its deltas (the ledger column still holds `[]`: see the local deltas bullet below) to the ledger (`deposits`), and, in the same transaction, its cell increments to the index: `cells`, `motifs`, and rule 3's `strata`, each cell's `clusters` a held count. A `contributors` record per (cell or stratum, account, UTC day) tells a returning cluster from a new one, so only a new one raises a count. The ledger has no expiry: no code deletes a `deposits` row or a `contributors` record, and a database trigger aborts any `DELETE` on either (migration `0009_ledger_no_delete.sql`). An erasure ("Erasure" below) replaces a row's content in place and leaves the row. A bundle is read from the index alone (`packages/pool/src/stored.ts`: four statements whose rows grow with the cells, not with deposits). A session sent again adds only the difference to its earlier batch. A large batch of varied steps runs its cell JSON to about four times its skeleton's size, and D1 takes 2 MB in one value, so ingest binds each payload in chunks of at most 1 MB, one statement per chunk, all in the one transaction under the one guard. Two limits of the stored form stand until a later change rebuilds what they need, and tests pin them: a session sent again over a held row that no longer parses adds its whole batch a second time, since the cells keep that row's increments and there is no parsed batch to take back; and a session sent again that leaves a cell lowers its `sessions` but not its `clusters` or the account's `contributors` record, so four accounts plus one that left still read as five (one record cannot show whether another of the account's batches still holds the cell).
- **Local deltas (`deltas`).** The client compares its own windows and sends what changed, once. `pool deposit` takes the sessions that pass both session gates and have ended, and counts `DELTA_DAYS` (7) windows on a fixed grid from the epoch, so adding, losing, or finishing a session moves no window; a pair of windows next to each other, each with at least `DELTA_MIN_SESSIONS` (5) of them, makes a delta, and the batch of the session that fills the after window (its fifth, in time order, ties by id) carries it. An entry holds a `deltaKind`, a `field`, a `name` or null, a `registry` or null, a `metric`, and a `change`, and nothing else: no session id, root, window date, or exact value. Four fields enter, per the spec's first exception to rule 3: `plugin` as `added` or `removed`, `permissionMode` and `effort` as `changed` (named by the field alone, the most common value of each window differing, so one odd session is not a change and two values off the effort list are no change), and `package` as `removed` (called in the before window and gone by a clean manifest edit, or by a Write that lists the same file without it in the after window; a Read never says a package is gone, since it may show part of a file; a public name with its registry, else `private` with none, and all `private` ones are one entry). A plugin goes as `private` always, since no plugin registry is pinned, and plugins are compared only over the sessions of a harness that records them (Claude Code), with none built when either window holds no such session. The after window is read as its first five sessions, so the entry is fixed when the window fills. `change` is the signed bucket of the move: calls per session in `count` buckets (-7 to 7), thinking per prompt in `tokens` buckets (-11 to 11) for an effort. The parser holds each field to its own row and refuses an entry outside it, and `oars pool outbox --explain` shows a row for each field of an entry.
  **Once only.** A delta is marked in `deltas-sent.log` in the outbox folder (a hash of the account, the entry without its `change`, and the index of its after window on the grid; the filler session is not in it, since which session fills a window can change from one deposit to the next, while the index cannot) after the batch that carries it is written, never before: a deposit that stops first builds it again. A later deposit builds no delta it has marked, so a session rebuilt under the same key replaces its batch with one that carries none. **Limit:** a batch that carried a delta and was never sent is replaced by that rebuild without it, so the delta is lost; the mark is written with the batch, not at send time, because sending less beats sending wrong and nothing is sent to a real pool yet. **Limit:** the public package list is held by bare name, so `pypi:typescript` goes as the public name `typescript` with its registry until the list is held per ecosystem. Also not built: an `upgraded` delta for the harness version, rule 4's "pool neither when both changed", and the batch's summary `exposure` (no deposit reads an exposure tag yet). The Worker parses an entry and keeps it inside the stored skeleton, but derives no delta cell and its `deposits.deltas` column still holds `[]`; the weekly limit on one delta for each cell is the pool's, not built here.
- **Cell grain and effort (rules 3 and 6).** A cell is keyed on the UTC week (`grain: week`, `day` the Monday), except a `live` cell, which stays at UTC day (`grain: day`) and holds none of rule 3's bound fields. Each read answers from one grain and filters the other out, so adoption and change state weeks (`firstWeek`, `lastWeek`, `weeks`, `weeksSinceLast`), never days. `effort` is in no cell key: it is recorded only as the (`effort`, `thinking` bucket) cell, which joins no `model` or `harnessVersion`, so `fit` and the interaction read no longer slice by it. Migration `0008_cell_grain.sql` adds the grain column; nothing is deployed, so it moves no data. A local `cells.jsonl` written before the grain has no `grain` field, fails the stored-cell check, and is derived again from the store the next time a pool is built or served. On the 3,400<!-- figure:large-steps -->-step test deposit a batch counts 887,141<!-- figure:skeleton --> bytes of skeleton and 11,548<!-- figure:cells --> cells (3,988,993<!-- figure:cell-json --> bytes of cell JSON, 4.50<!-- figure:cell-ratio~0.01 --> times the skeleton) and stores 887,145<!-- figure:stored --> bytes (skeleton, deltas, and the 2<!-- figure:extensions -->-byte extensions bag); no default limit counts them (see No cap on contributing). A cell states its **exposure** in three readings: `shown` (inside a shown recommendation's window), `held` (inside the window of one the holdback withheld), and `unknown`. A deposit derives it from the `recommendations` its skeleton carries (format 6), placed on the main run's calls that are not sidechain; a call inside both a shown and a held window counts as shown. A session that carries no row reads `unknown` throughout, never `unexposed`, because the pool cannot tell it from a client that never looked. The last field of a stored cell key is the reading's code (0 `unknown`, 1 `shown`, 2 `held`), so a key written before this keeps its meaning, and `exposed` stays as 1 for a shown cell and 0 for any other. Migration `0021_cell_exposure.sql` adds the `exposure` column (check: `shown`, `held`, or `unknown`) and every row stored before it reads `unknown`, since none of them had the input. A served cell carries `exposure`. The local read still derives a recall's own step and its exposed window from the local recall rows, which the skeleton does not carry.
- **Stack shares, explore, and the two pairs (rule 3).** Every frame's `stack` on the wire carries `languageShares`, one `{language, languageShare}` per language, the share one of `0`, `under-10`, `10-50`, and `over-50`; a share outside that list is dropped and its language still goes in `languages`, and a language off the pinned list goes as `other` (in a share only; the frame's `languages` list holds the pinned names alone). A prompt carries `explore`, a `calls` bucket of its steps that only look (`file.read`, `file.search`, `web.search`, `web.fetch`), or `null` for a record captured before the strata; the exact count never leaves, and the deposit's local store counts a prompt as its bucket's lowest value, which no read serves yet (the store holds the bucket's lowest value). The `calls` edges are the `count` edges and then double: 1, 2, 3, 5, 9, 17, 33, 65, 129, 257, 513, 1025, 2049, and 4097, so the last bucket is over 4,096, as the `count` bucket's is over 32. Two strata are counted beside the single ones, each a stratum of its own and never a cell: `languageShare` (value `<language>/<share>`, per frame) and `repoFilesExplore` (value `<stack size, xs to xl>/<explore bucket>`, per prompt, none when either is missing). They are held to the public floor (`PUBLIC_FLOOR`, 5 by default) accounts pool-wide like the others, appear only in the bundle's `strata`, and a cell still holds at most `q_dims` dimensions. This closes the limits that the wire sent no language share and the deposit derived `explore` as zero. **Limit:** the `live` family's provider errors by `model` and by `harnessVersion` are not built here: a skeleton step carries `status` (`ok`, `error`, or `none`) and no `errorCode`, so no day cell can name a `429` or a `5xx`.
- **Pseudonymous accounts.** The pool brokers the provider's device flow ("Sign-in", above): it starts the flow with its own client ID, polls the provider's token route itself, and reads the subject from the provider's profile route with the token it received, so every token it reads was issued to its own client. It hashes the subject under `PSEUDONYM_KEY` (which the database never holds) and discards the token. No email, login, provider id, provider token, or device code is stored. A login also deletes the token rows past their expiry.
- **The public floor.** A read is served only at `PUBLIC_FLOOR` or more clusters, and a cluster is a set of accounts the pool treats as one operator ("Clusters" below), so one account's many sessions count once and so do accounts the "Clusters" signals join (shared repo keys, or one creation window with deposits in lockstep). Only accounts that have stood count (the "Access" row below: a counting batch 90 days old): a free account that has not holds a cell and counts toward no floor until it has, so k-1 fresh accounts depositing a guessed private name beside one real account leave the cell below the floor and cannot tell whether that account holds it (S13). `PUBLIC_FLOOR` keeps its number and changes what it counts; the holdings of an account that has not stood are kept, and count at the next recount after it has. The first thresholded reads are served 90 days after deposits open, at the earliest; a clear cell at a clear floor of 1 serves from the first deposit (next bullet). The floor is a binding on the Worker, not a constant in the code: it is 5 unless the deploy sets another (`wrangler.jsonc` states the 5; a clear cell has its own floor, the next bullet), and a deploy can give single read families a floor of their own (`PUBLIC_FLOOR_FAMILIES`, see "Serve floors" below). Changing a floor is a deploy and never a client release: cells are stored with their held counts and the floor is applied when a bundle is served, so lowering it serves what was held, and raising it withdraws what was served, at the next generation of the bundle, with no redeposit. The bundle states the floors it was served at (`floors`, and the public one again as the bundle's `floor`), every served read states the floor it cleared (`floor`), and the `ETag` changes with them. A cell's `clusters` is its held count of verified-distinct clusters, and a read's is the largest held count among the cells it cites, with no union over accounts: the fetch path reads no per-account record, so as many accounts as the floor, each in a different week, serve no read, since each week's cell holds one (a later change brings held counts for a key's `n` and `c`). That many accounts on that many days of one week share each week cell and serve the week reads, and no `live` read, since a `live` cell is one day. A cell served on its own needs the floor in that cell, and a strata cell needs it pool-wide (strata take the public floor, whatever a family's). A `live` read cites only the sliced day's cells, so its floor counts the clusters held on that day and never those in its seven-day baseline; the baseline sums only baseline cells at the floor, and with none `value.baseline` and `value.ratio` are `null`. A read the CLI computes on one operator's own store states `clusters: 1` and applies no public floor.
- **Two floors, by cell class.** A cell is `clear` when every part of its key is closed public vocabulary (a listed model, harness version, program, subcommand, flag, tool, or skill) or a client hash, and `thresholded` when any one part is long-tail: a single long-tail part makes the whole cell thresholded, and a cell whose motif the pool does not hold is thresholded too. A failed call's `error:` or `error-version:` class that carries a name with an identity (`error:429/shell.exec[program=git sub=push]`) is thresholded even when every name in it is listed, since the pool does not parse the name, so it waits for the public floor, which serves less and never more; a class form the pool does not know is thresholded as well. A thresholded cell is served at `PUBLIC_FLOOR` (5 by default); a clear cell is served at `CLEAR_FLOOR` (1 by default, never above `PUBLIC_FLOOR`; a value that is set and outside that range or not a whole number is refused at load, with one line logged, and the public floor is used, so a typo is strict and never loose). **What a floor of 1 shows:** a clear cell served on one cluster says that one operator used a public tool on that day or week, with that model and version, and states that operator's session, success, and failure counts, tokens, and duration; it names nothing off the public lists. A long-tail name is never served below `PUBLIC_FLOOR` (5 by default), or its family's own floor. A clear cell at a clear floor of 1 counts every account that holds it, standing or not, because a floor of 1 has no k to protect and waiting 90 days to serve what one account used a public tool would protect no one; at a floor above 1 (a family's, or a raised `CLEAR_FLOOR`), and for every thresholded cell, only accounts that have stood count (the paragraph above). Both floors are stated in the signed bundle (`floors.public`, `floors.clear`) and feed its `ETag`. A total beside its parts is held back when it would show a part that is not served (**Limit:** a thresholded count that served clear cells at the clear floor determine is not yet held back; the rank-check brief closes it), and each part is judged against its own class's floor: a version-free clear total beside a long-tail part under 5 is withheld, and a clear total beside clear parts at the clear floor is served (the version-free cells under "Fit by platform and shell"). A shape total carries no identity, so it is a clear cell, and when one of its named cells is a long-tail name under 5 it is served only if a named cell of 5 or more standing accounts is withheld in its place, and is withheld itself when none is (complementary withholding below). The rule also covers a total that no cell holds: an action's calls, which its `target` cells and its one-step shape cells (one per model) both sum to. Where a long-tail model's one-step shape cell is under 5 beside a listed model's, the `target` cells are withheld unless a model cell of 5 or more standing accounts is withheld in its place, since a fresh account that knows its own listed-model count would otherwise read the long-tail model's count as the `target` total less its own. The bundle's top-level `floor` stays the thresholded floor.
- **A fetch cap.** An account without access may fetch `FETCH_CAP` bundles (default 1) per ISO week, counted per account and not per harness or harness version. Past it the pool answers 429 `fetch_cap` with `Retry-After` in seconds to the next Monday 00:00 UTC, before it reads the pool. The count is one atomic statement, and a count from an earlier week is dropped. A fetch that fails after it spent gives the spend back, since the account received no bundle. An account with access is not capped.
- **Access.** The `access` record is null, `pending`, or `standing`, and only a counting batch sets it: ingested at tier committed or higher, or at `skeleton` when every transcript's harness writes no raw file (Cursor), with one prompt and one tool step over the batch, subagents folded in, and at least one cell increment written over the row held now (a batch sent again unchanged writes none); an ingest that writes none leaves the flag and the batch's date alone. It is `pending` while it rests on batches counted inside the last 90 days (`STANDING_AFTER_DAYS`), clears when every one falls to `none`, and is `standing` once one has stood the 90 days. The 90 days gate the flag only; the batch stays on the ledger. A resend that still counts keeps a batch's first `counted_at`; one that no longer counts clears it, and the flag falls if no counting batch is left. A claude-code batch with a prompt and a tool step now lifts the cap, because the batch carries its roots and is written at `committed` (the next row).
- **The tier of a batch.** Ingest writes the batch's own tier, on a first deposit and again on a resend (`tier = excluded.tier`): the lowest of its transcripts', subagents folded in. A transcript is `skeleton` when its harness writes no raw file (Cursor), `none` when its root cannot be real (no leaves under any hash but the SHA-256 of no bytes, or that hash over leaves), else `committed`. A batch with one failed transcript is `none`, takes no part in access, and a resend that fixes it counts again. A batch ingested at `none` still writes its cell increments. Stated limit: a fabricated but well-formed root, and a forged skeleton, still earn `committed` until the raw-file check of a later layer.
- **A 304 spends nothing.** A 200 carries an `ETag` that names the code, the floors (both, and any a family has of its own), the harness and version asked for, and a generation of the stored cells (triggers on `cells` and `strata` move it in the same write as a change; a write to `deposits` changes no served cell and moves nothing). An `If-None-Match` that holds it gets 304 with no body, before the spend and without reading the pool, so a conditional request can neither use up a fetch nor force a read. A weakened `W/` tag matches.
- **Two deposits of one session at once.** A deposit replaces the batch the account held under its id, and nets its cells against that earlier row, so two at once would each net against the same row and add the batch twice. The upsert therefore takes the row only if it is still the one that was read (its `ingest` mark), and the other gets 409 `deposit_conflict`: nothing of it is stored, and the client sends it again, which then nets against the winner.
- **A deposit holds something.** A skeleton with no prompt and no tool gets 422 `closed_vocabulary` naming `transcripts`, since only a counting batch lifts the fetch cap (see Access). A forged skeleton that holds invented prompts passes this check, and with a well-formed root it lifts the cap under any harness until the raw-file check of a later layer (see the tier row under Access).
- **No cap on contributing.** The pool does not ration what an account deposits: sessions, bytes, harnesses, and machines per account are unlimited by default, and a redeposit of a held session replaces its row (an `UPDATE`, so the never-delete triggers of the ledger hold) and counts against nothing. `MAX_DEPOSITS_PER_ACCOUNT` (rows) and `MAX_DEPOSIT_BYTES_PER_ACCOUNT` (stored bytes: the skeleton, the deltas, and the extensions bag) remain as an operator's brake, off unless a binding sets one; a value that is not a positive whole number leaves the account unlimited. With a brake set, a new session past it, or a deposit that would take the account past the byte brake, gets 403 `deposit_limit`; a redeposit that fits still replaces. A brake bounds one account's ledger, not a fetch: a fetch reads the stored cells, never the ledger. The only cap on reading is the fetch cap for accounts with no access (see Access).
- **A batch past one request goes in parts.** One request carries 1 MiB at most. The client cuts a larger batch into parts of 512 KiB (never inside a character), in order, each sent with `oars-part: n/m` and `oars-batch: <SHA-256 of the whole batch>`. The server holds the parts in `deposit_parts` (outside the ledger), answers 202 `pending` until all `m` are held, then checks that their join hashes to `oars-batch` (400 `part_mismatch` otherwise, and the parts are dropped) and stores one deposit by the path a whole one takes, so its refusals (422 `closed_vocabulary`) and its netting are the same. Parts may arrive in any order. A part sent again lands on its own row and changes nothing; once the deposit has finished, any part of that batch is answered 201 from the stored marker, with no second write and no second count. The join is refused past 1,800,000<!-- figure:join-limit --> bytes (413 `too_large`), because one D1 row holds 2,000,000 bytes at most and the skeleton and its extensions bag share it: a session larger than that needs its skeleton stored across rows, which is not built. At most 8 parts make a batch (the client's 512 KiB parts make 4<!-- figure:join-parts --> at most for a join the cap allows). Staging is bounded by the same cap: a part that takes the held bytes past 1,800,000<!-- figure:join-limit --> is refused at once with 413 `too_large` and the batch is dropped, so an unfinished batch never holds more than that. An account also holds at most 16 unfinished batches at once (`MAX_STAGED_BATCHES`: the CLI sends one batch at a time under a send lock and a batch is 4 parts at most, so 16 leaves room for several machines with an interrupted batch each): a part that begins a seventeenth is refused with 429 `staging_full` and a `Retry-After` of one day, and a part of a batch already held always passes. The count and the insert are one SQL statement, so parts that arrive together cannot each read room that another has taken. A staged batch whose oldest part is over 24 hours old is dropped by the account's next staging write, with no cron trigger (`deposit_parts.staged_at`, migration 0017; a part staged before it counts as old), so an account stages about 29 MB of sealed text at most and a client that comes back later sends every part again. A finished batch's marker is not swept. A part that names another count than the ones held writes nothing: the batch is dropped and the part gets 400 `bad_part`, so the client's next full send starts clean. A staged part's `body` is sealed: AES-GCM under a key HKDF derives from `INGEST_HASH_KEY`, the account, and the batch id, with a fresh IV stored in front of each part. The join opens every part and then hashes hosts by the path a whole deposit takes; a part that does not open (a changed byte, another key) is refused as `part_mismatch` and the batch is dropped. A joined batch refused with 409 `deposit_conflict` or 403 `deposit_limit` keeps its parts, still sealed, until the batch is sent again. No new secret, client change, or wire change. The detached sender sends in these parts after covenant acceptance.
- **A frame's day is real and not ahead of the server.** A day that is not a calendar date, or is later than tomorrow UTC, gets 422 `closed_vocabulary` naming the field, since the latest day of a bundle's own bucket sets its `asOf` (its version-free cells can be later).

## What a bundle serves

A bundle's reads are derived from the stored cells with the code a local store runs (`packages/pool/src/derive.ts`), except the (name, `platform`, `shell`) read of `fit`, which runs only in the bundle: a local store writes those cells but no local read answers from them. A read is served when at least one of its cells clears the floor and is not withheld (below), and it cites and counts only those.

**What a served number counts.** The reads run over the bundle's cells at or above the floor of their class in their family (`PUBLIC_FLOOR` for a thresholded cell unless `PUBLIC_FLOOR_FAMILIES` names the family, and the clear floor below it for a clear cell) and no others (`readsOf`, `derive.ts`), and a read states the lowest of the floors of the cells it cites, so every count, sum, and denominator a read holds is a sum of served cells: its `n` and `failed`, a share's denominator (`tool-day`'s `value.steps`, a `live` read's `of` and its baseline, and a `fit` sum across weeks), and a sum across models. A sub-floor cell is in no `n`, no denominator, and no `inputs`, so no two numbers of one family's reads at one grain, set against each other, show the size of a sub-floor cell. A week cell and the day cells of its days count the same steps, as do a shape cell and the named cells of its actions, so across grains the bundle withholds one more part (`complement.ts`): where a served week has a sub-floor day it also withholds its smallest served day (fewest accounts, ties to the earliest day) from `cells` and the reads, and where a served shape has a sub-floor name it also withholds its smallest served name; the week and the other parts stay, and the rule repeats over both pairs until it adds nothing. The shape cells of one facet are parts of a count with no cell for the whole. `target` splits an action's calls (a call with no path reads `none`). `keys` splits the calls that sent a key and is treated as the action's calls, which it equals for a tool with a required key and which elsewhere can only withhold more. `dropped` splits only the calls with an unsent key, a count no other cell holds. Per key, `size`, `depth`, `extension`, and `dir` split the calls that send the key with a value of their kind and are treated as all of them, and `enum` splits them for a boolean or an exhaustive list; the `enum` of an open list (`subagent_type`, `model`) splits only its on-list values, again a count of its own. So a fully served facet, or the `fit` sum of the action, less another facet's served parts that sum to the same count would show a sub-floor cell's exact count. Where such a partition (an action, a facet, and for a keyed facet the key, in one frame, week, and exposure) has a sub-floor part, the bundle also withholds its smallest served part, and the same repeat covers it; the facets that hold a call in several cells or none (`arg`, `pattern`, `change`) are not partitions. The `keys` cells that hold a key are parts of that key's facets (a key's `size` cells and the `keys` cells whose list holds it count the same calls), so the bundle withholds along that nesting too: where those `keys` cells have a sub-floor part, their smallest served one goes, and a lone one with no served partner takes the smallest served cell of each of that key's facets with it. A part withheld for one family counts as unserved in every other, so a family left with exactly one unserved part withholds its smallest served part as well (or, with none, its whole). Families also combine: the served totals of several can add and subtract to a cell that no one of them leaves alone (a sub-floor `keys` cell is the `size` total of one of its keys plus another's less the action's calls), so each family states one equation (its whole, or the calls its parts split, equals the sum of its parts; an action's calls are also the sum over models and exposure of its one-step shape cells, which the `fit` read serves, and count as known where the bundle holds none of those cells; that sum equals the calls only where each call has one step, since those cells count every step and a facet cell one per call, and elsewhere the tie can only withhold more; a `dropped` or open-list `enum` count is an unknown of its own, so those cells tie to no other family), and the bundle withholds until no unserved cell follows from those equations: while one does, it withholds the smallest served cell of that combination that shares a family with it. The week less its served days is then a sum over at least two days, one of them at or above the floor, which no reader can split; a week with no sub-floor day keeps every day. A tool-day or `live` read's `steps` or `of` is the day's steps over the served tools only, so a tool served at the floor reads against the served tools' day and not the whole day's. `asOf.pool`, `asOf.day`, and `weeksSinceLast` come from the served cells alone, so a sub-floor cell's size moves none of them, while the first sub-floor part of a family withholds one more part, which a reader sees. The (name, `platform`, `shell`) cells keep the rule of `environmentOf` (every part served or the total is not) and are also dropped when their (motif, grain, day, exposure) matches a withheld bucket cell. Flag and pull cells overlap their program cells, so they are neither parts nor triggers of the shape/name rule. **What the withholding checks cover, and what they do not.** Relations between cells are checked as linear equalities against the code that emits the cells, for every store the test fixtures' held cells allow: the test derives the relations from that code and fails when the cells a bundle serves determine a below-floor cell. Two seeded fixtures are kept as known open cases, in which served cells still give back a below-floor count, one of them at the default floors. Two things are outside that check, and they are stated here rather than settled. (1) Bounds from non-negativity and integer reasoning are neither checked nor enforced, because no linear-programming check or value rule has been built: a count is never below 0 and is a whole number, and a reader who uses that can infer a below-floor zero, and from that zero, in some cells, an exact below-floor count. (2) Bundles are checked one at a time, so a relation that holds only across bundles (the cells of two harness versions read together) is not covered. The `arg` cells are held and never served, because the server does not hold the kind of each key and no equation closes them; they stay in the held cells so `arg` `none` still protects the `keys` family. **What a capped system costs.** The work is limited by counting it, not by a clock, so the same cells give the same bundle. A set of cells linked by these equations that holds more than 5,000 terms (a long-tail action of thousands of `keys` cells) is not worked out. One meter of 10 million touched terms covers a whole bundle, across every week and every floor, and each elimination is charged `|row| + |pivot|` before it runs; systems run smallest first, so small ones finish before a large one can spend the meter. A system that is over 5,000 terms, or cannot pay for its next elimination, has every served cell withheld, which shows nothing of any cell and never under-withholds. That costs the action's facet, one-step shape, and named cells, at day and week grain, for that week and version bucket. The meter is a count of work, not a bound on seconds: a longer coefficient makes a unit slower. The local read has no floor and sums every cell it holds.

The pool serves all nine order 1 families, `recovery` included. `fit` serves a call's shape from the shape cells (below); the local call-shape method (`read-call-shape.ts`, a tool and its key names read from the store, citing the `shape:<action>/keys/<names>` week cells of the weeks the shape failed) stays out, because a bundle holds no store; `recovery` serves only the edge a skeleton can carry (below), not the signature record, because a skeleton has no error row, `sigHash`, or `outcome`.

| Family | Served | Left out, and why |
|---|---|---|
| `fit` | per (shape or named motif, harness version bucket, model), per (name, `platform`, `shell`), and per (action, shape facet, harness version bucket) from the shape cells (`fit-shape`, below) | The local call-shape method (a tool and its key names, read from the store, citing the `shape:<action>/keys/<names>` week cells of the weeks the shape failed): a bundle holds no store, so the pool serves the same facts, for every facet and not this one tool's, from the shape cells instead. The (name, `errorCode`, `harnessVersion`) cell exists (`error-version:<code>/<name>`, see `live`), but no `fit` read derives from it yet. The (`package`, `packageVersion`, `errorCode`) form: no cell is keyed that way. A flag or a pull has no (name, `platform`, `shell`) cell, since it would be four dimensions. |
| `cost` | tokens and wall time per prompt class, model, and week, from class cells | The spec's per-metric bucket cells and `tokensPerCommit`: they are not stored cells, and the read states its values from a class cell's `tokens` and `durationMs`, and divides `tokens` by the cell's `tokenPrompts`, the prompts that recorded input (migration 0013 stores it beside `tokenSessions`; a row from before it is coverage unknown, and its read says `tokenCoverage: unknown` with no `tokensPerPrompt`). |

| `live` | an action's share of one day beside its trailing week, from day cells | Nothing is withheld. Besides the share, the family holds day cells per (name, `model`, `errorCode`) (`error:<code>/<name>`) and per (name, `harnessVersion`, `errorCode`) (`error-version:<code>/<name>`), so a `429` or a `5xx` is named by model and by version. A failed call whose harness captured no code sends `errorCode` null and makes no cell. The model and version error cells count the same failed calls, so a served total beside served parts can reveal a sub-floor part by subtraction (no guard, unlike the env cells, whose total is withheld when a part is under the floor). |
| `adoption` | first and last week seen, weeks, and share of steps, from week cells | The `funnelStage` forms (offered, loaded, removed): no capture writes them. |
| `method` | a shape's share of the windows of its length, per model | The by-class axis: a cell holds no class, because a step has none. |
| `next-step` | the step after a prefix of one to three actions, by count | The remaining-work forms (`remainingCalls`, `remainingTokens`): the read does not take them. |
| `tool-day` | a tool's failure rate and share of the day's steps, from one-step shape day cells; its floor counts within its day, so a day with fewer accounts than the floor on the tool serves none | No form is left out; a day can be withheld with its week (above). |
| `recovery` | what others did next after a failed call: per (failed action, `errorCode`, next action), a week cell `recovery:<code>/<failed action>><next action or none>`; the read's value is `{followed, of, share}`, the count and share of failures of that action and code that the next action followed | The signature record: a read of error rows (a signature hash, the next calls, `outcome`) needs `sigHash` and `outcome`, which a skeleton does not hold, and signature text stays local. The read is worded as what others did next, never as a fix: there is no fix field, and `editFollowed` is not success. The cell counts the immediate next call (`none` when nothing followed), so each failure counts once and shares sum to 1. A served edge's `of` sums the served sibling edges only (cells at or above the floor), so no read counts a cell under the floor. |

The (name, `platform`, `shell`) cell is its own cell, `env:<platform>:<shell>`, a week cell that names no version and no model, so a bundle for any harness version holds it (a session of a harness that records no version has none to key on). It counts the same calls as the version cells, so a total beside only some of its parts would show the rest by subtraction. The pool therefore serves it for a motif, week, and exposure only when the total clears the floor of its class and no cell of that motif, week, and exposure, in any bucket or environment, is under the floor of its own class (the `fit` family's floor, less the clear gap for a `clear` cell); one sub-floor part withholds the total (`stored.ts`, `environmentOf`). A total of a clear name is served at the clear floor, so a long-tail version, model, or shell beside it that is under 5 still withholds it, and a clear part under the clear floor does the same. **Known limit of that rule:** a motif with a long tail of versions, models, or shells has a sub-floor part in any week one of them is under the floor, so on a live pool this read is likely to serve rarely (no real pool exists to measure it), and one new version's first account withholds every motif it calls that week. Sending less is the side the rule is on; a later decision about this cell should weigh how often it serves.

**A harness with no version on record.** Cursor, Gemini, Grok Build, and Pi keep no harness version in their local files, and a VS Code Copilot Chat session keeps one only when a request's serialized Copilot Chat `agent` (`extensionId` `GitHub.copilot-chat`, not a third-party participant) carries `extensionVersion` (`sessions-store.md`, each source's section; the VS Code reader is fixture-derived, never run live), so a session with none fills `<harness>/unknown/<model>` cells (`harnessBucket(null)` is `unknown`). A numbered request never reaches them. The route therefore takes the word `unknown` as the version (`/bundle/cursor/unknown/<vocabVersion>`, `oars pool fetch --harness cursor --harness-version unknown`): `bucketPrefix` is `cursor/unknown/`, the same derivation, the same public floor (`PUBLIC_FLOOR`), the same withholding rules, and the same environment cells as any bundle, and the payload's `harnessVersion` is `unknown`, which `verifyBundle` checks like a number. It serves nothing a numbered bundle would not: a request for a harness that does record a version finds no cell of its own under `unknown` (only sessions that recorded none land there). `served-families.test.ts` pins the families of that bundle. **Known limit (t849's, unchanged):** the fallback does not widen a cell. A harness whose few accounts split across models fills each `unknown/<model>` cell separately, so the fallback serves less than the number of its accounts suggests, and the version-free total beside it is withheld by the same rule as above.

`served-families.test.ts` pins the limit at the wire: a skeleton whose tool carries `sigHash` or `outcome`, or that carries error rows, keeps that field in the extensions bag and nowhere a read can reach, and a five-account bundle holds a tool-day read and a recovery read but no read of the local call-shape method; the recovery family is withheld at four accounts and served at five.

**What a call touched, in shape and not in value (t870).** A tool carries `keys` (its input key names, sorted), `keysDropped` (a `count` bucket of the names not sent), `targetClass`, and `argClass`; each is optional and absent on a call captured before them. The rule and its limit:

- *Key names only, never a value.* A tool with a pinned input list (`TOOL_INPUT_KEYS` in `public-vocabulary.ts`: the built-in tools of Claude Code) sends the names on its list and counts the rest in `keysDropped`; any other tool sends a name only when it passes the client's one gate (local redaction, the exclusion terms, the name shape, `NAME_MAX`), and counts the rest. A tool that went as `private` sends no names, since a private tool's keys name private work. The server holds a long-tail name and serves it at threshold (`t881`); a name off a pinned list, or a key that is no name shape, reads as `other` and lands in the extensions bag, not a 422. The limit: a public tool with no pinned list (every harness but Claude Code's built-ins, and every MCP tool) takes the gate path, so a name the gate passes goes to the server as it is.
- *`targetClass`* is derived at capture from the target's base and the path's suffix (`source`, `test`, `config`, `doc`, `lockfile`, `generated`, `data`, `none`, `other`; the order a path is asked is `call-shape.ts`, pinned in `call-shape.test.ts`). A call with no path target is `none`. The path never leaves the extractor (a file's own name and the folder names below the repository do, as name tokens: see `names` below). The class reads the key the target is hashed on (relative to the repository, or to the cwd), so the folders above a repository never decide it. The limit: a path outside both keeps its absolute key and its leading folders are read, a directory (a search's `path`, or the root as `.`) is `other`, a file the table does not know is `other`, and the order is intended: the folder names the role before the extension does, so `src/doc/render.ts` reads `doc` (a `doc`, `docs`, or `documentation` folder), and a `.json` file outside a test, generated, or doc folder reads `config`, so `data/rows.json` is not `data`.
- *`argClass`* is derived at capture from the call's input: the sorted set of `path`, `url`, `pattern`, `command`, `number`, `flag`, `text`, and `none` its arguments hold. A key name classes a string (`file_path` is a path, `pattern` a pattern), a number or a boolean classes itself, and any other value is text. The value never leaves the extractor. The limit: a string under a key the table does not know is `text`, even when it is a path.

`pool-wire-keys.test.ts` plants a value in every argument of a captured call and searches the whole batch for it. Nothing of a planted value (a path, a pattern, a command, text) is on the wire; the key names and the two classes are, and so are the file and folder names a path held, as name tokens (below).

**What a call's values are like, and never what they are (format 4).** Capture computes three more fields from the input (`call-shape.ts`, CAPTURE 27); each is a closed-list member, and the wire carries an entry only for a key the call sent in `keys`, so a dropped key's features and values go nowhere. Anonymizing the sender does not make a value safe, so no value text is sent at all; the examples below are invented.

- *`argFeatures`*, per sent key: `valueSize`, the value's length as written (`0`, `1-8`, `9-32`, `33-128`, `129-512`, `513-2k`, `2k-8k`, `over-8k`); for a path, `pathDepth` (folders below the repository root, else the working folder: `0`, `1`, `2`, `3-4`, `5-8`, `over-8`, or `outside` for an absolute path under neither, whose folders are never read; a relative path is taken from the working folder first, so it reads as the absolute path to the same file does), `extension` (`source`, `doc`, `config`, `data`, `image`, `none`, `other`), and `dirKind` (`root`, `source`, `test`, `doc`, `generated`, `hidden`, `other`); for a pattern, `patternFeatures`, the sorted set of `alternation`, `anchor`, `class`, `escape`, `group`, `literal`, `quantifier`, `recursive`, and `wildcard` it uses (a Glob call's pattern and a `glob`, `include`, or `exclude` key read as globs, any other pattern as a regular expression). A boolean and a null have none. Example: Read of `src/app/main.ts` sends `{"key": "file_path", "valueSize": "9-32", "pathDepth": "2", "extension": "source", "dirKind": "source"}`; Grep of `^(foo|bar)$` sends `{"key": "pattern", "valueSize": "9-32", "patternFeatures": ["alternation", "anchor", "group"]}`.
- *`argValues`*, per sent key: a boolean as `true` or `false`, and a string only when its tool's closed list for the key holds it (`CLOSED_ARG_VALUES` in `public-vocabulary.ts`: Grep `output_mode`, Agent and Task `subagent_type` (the built-in types) and `model`, NotebookEdit `cell_type` and `edit_mode`). Example: `{"key": "replace_all", "enumValue": "true"}`, `{"key": "subagent_type", "enumValue": "Explore"}`. A custom agent's name is off the list, so it is not sent here; it is sent as an `agent` name (`names`, below).
- *`changeKind`*: what changed from the previous call of the same tool in the same prompt, the sorted set of `same`, `key-added`, `key-removed`, `feature-changed` (a kept key's features or closed value moved), `value-changed` (a kept key's value moved while its features did not), and `target-changed`. The first call of a tool in a prompt has none. Example: a Bash call that failed, then the same command again with a `timeout`, sends `["key-added"]` on the retry, which is the recovery signal.

The limit: a size, a depth, and a pattern's features are facts about a value, and a rare combination of them (a 2k-8k pattern with every feature) narrows what the value could have been, though it never states it. `pool-wire-values.test.ts` captures a call whose path, pattern, and content hold a secret-looking token and checks that no five characters of it are anywhere in the batch.

**The names a call's values held (format 5).** Capture also reads the name-like tokens of the same values (`argNamesOf` in `call-shape.ts`, CAPTURE 33). These are sent as they are written, with no count floor and no threshold, so file, directory, and variable names are sent: a folder called `ledger-core` goes to the pool as `ledger-core`, and it can identify a project. A name is a word and never a value: no argument text, path, or command is sent.

- *`names`*: a sorted list of `{"kind", "name"}` entries, one per distinct token, `kind` one of `file`, `dir`, `env`, `flag`, and `agent`. `file` is the basename of each path value and `dir` the names of the folders of that path below the repository root (else the working folder); a path outside both sends its file's own name only, and no folder above the root is read, since that segment is the machine's own and is usually an account name; a path that is exactly a home folder, on any mount (`/home/jsmith`, `C:\Users\jsmith`, `/mnt/c/Users/jsmith`, `/c/Users/jsmith`, `/var/home/jsmith`, `/export/home/jsmith`, `\\wsl.localhost\Ubuntu\home\jsmith`), sends no name at all, as does a path outside the root whose parent folder is named `home` or `users`, and a path that starts with a variable (`$HOME/notes/plan.md`, `%USERPROFILE%\notes\plan.md`) counts as outside the root. `env` is a variable a shell command assigns (`API_REGION=eu ./deploy.sh`), references (`$HOME`, `${BUILD_ID}`), or an `env` argument holds, never its value. `flag` is a long flag's value when it is one word (`--region eu`, `--region=eu`, and `--region="eu"` send `eu`; an assignment such as `API_REGION="eu"` sends `API_REGION` the same way, while a single quote or a substitution after the `=` sends nothing), or the next word of `-k` on pytest (`pytest -k test_login`, `python -m pytest -k test_login`), the one short flag read that way; the next word of any other one-letter flag, and of `-k` on any other program, is not read (`-p hunter2`, `-i needle`, `openssl enc -k hunter2`, `curl -k host`), since it may be a credential or a plain argument. Neither is the value of a flag that takes text (`-m`, `--message`, `--body`, `--query`, and the like) or a credential (`--token`, `--password`, `--secret`, `--api-key`, their common spellings, and any flag whose last word, set off by a hyphen, an underscore, or a capital letter, is one of those or `pass`, `pwd`, `passphrase`, `credential`, or `cookie`, or that ends in `password`, `passwd`, `passphrase`, `secret`, or `token` with no separator at all, or in `key` after `api`, `private`, `secret`, `access`, `encryption`, `signing`, `master`, `license`, `shared`, or `session`, such as `--db-password`, `--db-pass`, `--github-token`, unseparated `--dbpassword` and `--clientsecret`, camelCase `--clientSecret` and `--dbPassword`, acronym-led `--AWSSecret`, or `--encryption-key`: the value after one is never read, joined with `=` or not; `--bypass`, `--tokenizer`, `--sort-key`, and a bare `--key` are read). The list of credential flag names is finite, so a credential passed under a flag name it does not hold can cross as a name. A long switch followed by an argument can still be read as if the argument were its value. The value of a text or credential flag is not read as a flag name, but when it is exactly a variable reference (`curl --token $API_TOKEN x`) that variable's name is sent (`API_TOKEN`). A variable is read only from a word that is exactly one reference as written, quotes included: any of `$NAME`, `${NAME}`, PowerShell's `$env:NAME` in any case, or a scope form (`$script:NAME`, `$global:NAME`, read as `NAME`, and the braced `${env:NAME}`), bare or in double quotes. On a POSIX shell the `$env:`, `$script:`, and `$global:` forms read the text after the colon (`mysql --password $env:hunter2` still sends `hunter2`), while a word before any other colon (`$local:x`, `$private:x`) is read for no variable. No name is read from a word after the command's first single quote or heredoc marker (`'` or `<<`) or, in any command whatever its shell (a harness does not always say which it ran), after the first typographic single or double quote (U+2018 to U+201E), block comment (`<#`), or stop-parsing token (`--%`), and, in a POSIX shell, after the first unquoted backtick or escaped double quote (`\"`), since a bare `$name` there may be literal text. A command substitution (`$(...)` or a backtick pair) opened inside double quotes does the same for every word after it, since its end is found by a scan that can close early. Every other word is read for no variable, so text in single quotes, a `$'...'` or `$"..."` string, an escaped `$` (`abc\$tail`, ``abc`$tail``), a command substitution (`"$(cmd 'x$tail')"`), a percent-wrapped word (`%NAME%`, which neither a POSIX shell nor PowerShell expands), and a name inside a longer word (`prefix-$NAME`, `${NAME:-default}`) are never read; that sends less, never more. `agent` is a custom agent's name (`subagent_type` off the built-in list). Example: `[{"kind": "file", "name": "plan.md"}, {"kind": "dir", "name": "ledger-core"}, {"kind": "env", "name": "BUILD_ID"}]`. A name that has no name shape (a space, a character outside ASCII letters, digits, and `_.+-` apart from a leading `@` and a `:` between parts, a first character that is not a letter, digit, or `_` so `.github` is dropped, or over 128 characters) or that the secret-shape check changes is not sent, and neither is a name that holds one of your exclusion terms. The pool stores the entries in the deposit and no cell is keyed on one, and nothing of them is in a bundle.
- *`namesDropped`*: a `count` bucket of the tokens of a call that were not sent for one of those three reasons, so how much of a call's names went unsaid is itself readable. It is a number and never the names, and it is absent when nothing was dropped. Example: `"namesDropped": 1` beside a `names` that lacks the one folder whose name held an exclusion term.

**A call's commands and edits as shapes (format 5).** Capture also reads each shell command as a template (`templatesOf` in `call-shape.ts`) and each file edit as a list of shape words (`diffShapeOf`), both CAPTURE 34. A template is a program, a subcommand, and flag names with every other word replaced by a slot, and a shape is a word from a closed list: no argument text, path, or edited line is sent.

- *`templates`*: a list of strings, one per command of a shell call, in the order the commands run: its program's base name in lower case, without a Windows launcher suffix (a program given as a path is `<path>`), its subcommand when the program's own public list has one, and its flags that are on the public flag list or one letter, and every other word as a slot from a closed list, `<text>`, `<path>`, `<ident>`, `<num>`, `<url>`, `<var>`, or `<flag>` (a flag that is not spelled: a private script's flag, a cluster, a value attached to a short flag). A word is typed by its shape alone, never sent: a URL, then a number, then a path (a separator, a glob character, a home or dot folder, or a file extension), then one identifier-like word, else text; a quoted word and a word after `--` are slots, a word at or after the command's opaque point (the points `names` lists) is `<text>`, except that a flag-shaped word there keeps its name when it is on the public flag list or one letter, and never its value, and the word after a credential flag, a text flag (`--token`, `-m`), or any one-letter flag but `-k` on pytest (`sshpass -p hunter2` is `sshpass -p <text> ...`, since the type of a value the names reader will not read is not sent), apart or joined, is `<text>` whatever its shape, or goes inside `<flag>` when it is joined to a flag whose name is not sent (`--db-password=abc` is `<flag>`). A program, subcommand, or flag goes through the same gate as a name: a template with one the secret-shape check changes, an exclusion term matches, or that is not a name is dropped whole and counted. Example: `git commit -m "charge acme_corp twice"` is `git commit -m <text>` and `pytest tests/test_billing.py` is `pytest <path>`; no argument crosses. A private program's name is sent the same way, as a step's program is.
- *`templatesDropped`*: a `count` bucket of the templates of a call that were not sent, so how many commands went unsaid is itself readable. It is a number and never the templates, and it is absent when nothing was dropped. Example: `"templatesDropped": 1` beside a `templates` that lacks the one command whose program held an exclusion term.
- *`diffShape`*: a sorted list of words from a closed list, on a call that edits a file: `import-added`, `import-removed`, `identifier-renamed`, `lines-added`, `lines-removed`, `lines-changed`, `whitespace-only`, and `file-written`. A write is `file-written`, whatever it wrote. An edit, or each entry of a multi-edit, is compared line by line on your machine, blank lines and indentation aside: an added or removed `import`, `from ... import`, `require(`, `#include`, `using`, or `use` line is an import; a removed line and an added line that read alike but for their names, each old name replaced by one new name, are a rename; other paired lines are changed; any lines left over are added or removed; and an edit that differs in whitespace alone is `whitespace-only`. A call has the union of its edits' shapes. Only the shape's name is sent, never the text, a line, or a name that was compared. An edit that changes nothing or only moves lines sends none, and neither does an edit whose harness records no old and new text (an adapter's `Edit` with only `file_path`). Example: replacing `const total = sum(items);` with `const subtotal = sum(items);` sends `["identifier-renamed"]`, and adding one line inside a function sends `["lines-added"]`. No threshold or floor applies, and the pool stores the list in the deposit and keys no cell on it.
**The text an edit wrote (format 7).** Capture also keeps a digest of the old and new text of every Edit, MultiEdit, and Write call (`editDigestsOf` in `extract.ts`, CAPTURE 35), so an edit that restores earlier content can be told from one that does not.

- *`digests`*: a list of `{"old", "new"}` pairs, each value the first 32 hex digits of the SHA-256 of the exact UTF-8 text, so a line ending or a trailing space is a difference. An Edit sends one pair, a MultiEdit one pair per edit in order, and a Write a `new` digest alone: its call does not hold the file's earlier text, so `old` is absent, never the digest of an empty string. A tool that is no edit sends none. The digest is plain, not keyed, so the same text gives the same digest in every session and account; it is a one-way hash of text the call held, and the pool joins it to nothing today. A short or common text can be checked against its digest by anyone who guesses it, so the digest is a match key and not a secret; the text itself never goes. A batch with a digest that is not 32 lowercase hex digits is refused at its path.
- A `git restore <path>` or `git checkout -- <path>` names its path the way an edit's `file_path` does, so the path is in the call's `names` (`file` and `dir` tokens) and needs no field of its own.

**Shape cells.** Each call counts in one week cell per facet of its shape, `shape:<action>/<facet>/<value>` on the harness version bucket with no model (three dimensions: action, facet value, version), counted by the call's own status: `target` (its `targetClass`), `arg` (one cell per `argClass` member; held, never served), `dropped` (its `keysDropped` bucket), `keys` (the sorted key names, comma joined), `size`, `depth`, `extension`, `dir`, and `pattern` (one per feature, valued `<key>=<member>`), `enum` (`<key>=<value>`), and `change` (one per change kind). `fit-shape` reads each but `arg` as a failure rate per (action, facet, value, version bucket); an `arg` cell is held and serves no read. The pool classes a `keys` cell `thresholded`, a keyed facet `clear` when its key is on a public tool's pinned list (`PUBLIC_INPUT_KEYS`) and `thresholded` otherwise, and every other facet `clear`, served at the clear floor (`CLEAR_FLOOR`, 1 by default). The cells of one partition facet (`target`, `keys`, `dropped`, and per key `size`, `depth`, `extension`, `dir`, and `enum`) do not overlap, though only `target` reaches every call of its action ("What a served number counts" above says which calls each splits), so where one has a sub-floor cell the bundle withholds the smallest served cell of that partition, and the `keys` cells that hold a key are parts of that key's facets (above). A facet a record did not capture adds no cell, so a call captured before CAPTURE 27, or sent in format 3, counts in the `target`, `arg`, `dropped`, and `keys` cells only.

### The set of four (`oars sessions books`)

`oars sessions books` ends with four lines read from the last bundle `oars pool fetch` kept (checked again against the pinned key; with none, it prints `no pool bundle yet`). The bundle carries the same numbers as `books`: totals only, no list that names a value under the floor. Each states its floor (the public floor, `PUBLIC_FLOOR`, 5 by default), the bundle format, the vocabulary version, and the as-of day of the served cells.

- **Served cells** counts week cells at or above the floor of their class that the bundle serves, with a count by week and by constructor tuple (harness, version bucket, and model, which the frame bucket encodes). Environment and version-free cells count in the total and by week and name no tuple, so a version-free cell's calls are not counted a second time beside the versioned cell. **Below floor** is one number: every other week cell the pool holds for the bundle, the sub-floor ones and the served ones that complementary withholding drops, so the served count never overstates what a reader can see. Environment cells enter the served count when served, and the backlog only when withheld, since a sub-floor environment cell is not read. The backlog is per bundle (one harness version), not the whole pool.
- **Panel** counts accounts with a counting deposit in the last 28 days, once each. An account's `source` (migration 0012, default `user`) marks an input that is not a depositor; an operator-fleet or seed account is set to another value and is not counted. It names no account and is not held to the floor. The count is taken on the first fetch of a UTC day and kept in one row, so a fetch reads one row whatever the ledger holds and a deposit after that read counts from the next day; `panelDay` says which day. The bundle's ETag follows the stored cells, so a 304 keeps the panel of the bundle already held.
- **Demand** (accounts that fetched a comparison read, then follow-on reads) and the **goal metric** (read yield, cost per served cell, yield per served cell) have no source yet: no comparison read, follow-on read, or yield exists. Each prints `no source yet` with its reason and is `null` in `--json`, never 0. A later brief fills each place (`DEMAND_SOURCE` and `GOAL_SOURCE` in `packages/pool/src/books.ts`).

Inputs are not stock: a seed or fleet account adds nothing to the panel, and the numbers are counts of cells and accounts, never of rows deposited. `booksTotals` in `packages/cli/src/sessions/pool-books.ts` returns the totals as flat numbers (null for a field with no source) for the health batch to read.

## Clusters

A cell's held count is its number of verified-distinct clusters of accounts, not its number of accounts, so sign-ins made together, on the same repositories, or less than 30 days old count as one cluster or a half, and someone acting alone clears `PUBLIC_FLOOR` only with that many separate accounts that each wait out the 90-day standing rule. It is a weighting, never a cap: no account, deposit, or cell is refused, dropped, or hidden by it. Only the count a floor compares changes, and every served read states that count in its `clusters` field (an integer, rounded down). Account ids and signal values never appear on a read.

Two accounts holding a cell join one cluster when any of these holds, and a cluster is the transitive closure (A joins B and B joins C: one cluster):

| Signal | Rule | What the pool keeps |
|---|---|---|
| Machine | They deposited from the same machine id. | Nothing yet. The wire carries no per-machine id, so this signal is absent and joins no one; `repoKey` is hashed under a salt derived from one store's salt (an enrollment hands it to its machines, so they key a repository alike), so accounts that share repo keys (next row) are the nearest the pool can see. |
| Repo keys | Each account's set holds at least 3 repo keys and the sets' Jaccard overlap is 0.8 or more. | Each account's distinct `repoKey` values from its deposits (`account_repo_keys`). |
| Age and cadence | They were created within the same 24 hours, and each has deposited on at least 3 distinct days (`CADENCE_MIN_DAYS`; fewer is a team installing together, not a sybil cluster), and their deposits fall in the same hour (UTC) on at least 90 percent of the days either deposited. | Creation: GitHub's `created_at`, read from the profile call the sign-in already makes, else the pool's first sight of the account (Google gives none). Cadence: the UTC day and hour the pool received each deposit (`deposit_hours`), on the pool's own clock. |

Only an account that has stood is a holder here: its `access` is `standing`, or its first counting batch is 90 days old (`STANDING_AFTER_DAYS`, "Access" under the pool's rules). A cell none of whose holders has stood is written 0. The standing of an account is read at each recount, so it counts from the first recount after the day it stands, which a deposit of its own makes within a day for an account that deposits daily.

A cluster counts 1, or 0.5 when every account in it was under 30 days old at its first deposit to the cell (an account whose age is not known is not young). The weighted sum is rounded down. The thresholds (`YOUNG_DAYS`, `YOUNG_WEIGHT`, `CLUSTER_WINDOW_MS`, `REPO_KEYS_MIN`, `REPO_KEYS_JACCARD`, `CADENCE_SHARE`, `CADENCE_MIN_DAYS`) are constants in `packages/pool/src/clusters.ts`, not deploy settings. The count is written to a cell's and a stratum's `clusters` column after each deposit lands, from the committed records, so the SQL that compares the column to a floor and the bundle's own decision (`clustersOf` in `floors.ts`) read one number. A deposit recounts every cell and stratum its account holds, not only the batch's, since the repo keys and hours it adds belong to the account. The recount reads what is committed and then writes, so two deposits at once can leave a count that misses the later one until the next deposit that touches that key.

## Wire field register

One row per field a format 3, 4, 5, 6, or 7 batch carries (section 17 of the direction conclusion, rules 2 to 4): no row, no field. `consumer` is the read family that reads the field today, or the future read that is stated for it. The class is the field's projection class at formats 3, 4, 5, 6, and 7: `clear` (a closed or public list, or a hash the client made that the pool uses only as an opaque key), `thresholded` (held always, served once a public floor of clusters report the same value; `PUBLIC_FLOOR`, 5 by default, see "Serve floors" below), `hashed at ingest` (the pool hashes the value on arrival under `INGEST_HASH_KEY`, a Worker secret), or `raw tier` (stored, served only to the account that deposited it); no skeleton field is `raw tier`. The client sends a long-tail name after redaction and the server holds it in clear; only a host is hashed at ingest. `Re-derives` says whether a deposit of the field can be built again from the local store (`raw/`) while the store exists, with new consent. A field marked `no` is a constant of the client build.

`Bytes` is measured, not estimated: the canonical bytes of one invented session (`REGISTER_FIXTURE` in `packages/cli/src/sessions/pool-fixture.ts`: one transcript with its frames, one prompt, two calls, five steps, one delta, one recommendation), summed over every place the field occurs. A container's bytes are its braces, brackets, and commas, and its members' bytes are theirs, so the column adds up to the batch less 11<!-- figure:envelope --> bytes of top-level braces, commas, and newline (4,154<!-- figure:register --> bytes in all; the test pins both figures). A real session holds more steps, so read the column as the shape of the cost, not its size. `pool-wire-register.test.ts` parses this table and fails on a field the client emits with no row, a row for a field it does not emit, and a bytes figure that no longer matches the fixture.

An unknown field name a client sends lands in the `extensions` bag of the deposit, not in a row. The bag is ledger class, kept, served to no one but the account that deposited it (`GET /v1/account/export`), joined to no read, and left out of every bundle (`wire-contract.test.ts`). A field, a literal, or a value over 8 KiB (`MAX_EXTENSION_BYTES`, as JSON) gets a 422 `too large` at its path, whatever its kind; a newer client's larger structure belongs in a new format version, not an extension.

### Serve floors

These settings sit beside the field register. They are not fields: no batch carries them, the client does not send them and applies none, and the pool states them back in every bundle. Each is a Worker binding read on each request (`packages/pool/src/floors.ts`), with the defaults set as plain variables in `wrangler.jsonc`; an unset binding is the default, and so is a value that is not a whole number of at least 1 (a fraction, a negative, `0`, hex, or text), with one line in the Worker's log, so a bad binding can never serve below the floor (`CLEAR_FLOOR` excepted: a bad value is the public floor). A floor is a deploy: no client release, no redeposit, no re-derive by hand.

A read family on its own floor is derived from the cells served at that floor, with complementary withholding computed at that floor, so it holds the same differencing guarantee as one on the public floor, and it applies to that family and no other. The bundle's `cells` are those served at the public floor, and beside them any cell a read of a family on its own floor cites; a lower family floor therefore makes its own cells visible in the bundle, which is the cost of that setting. A read counts a cell's clusters through one function (`clustersOf`, `packages/pool/src/floors.ts`), the cell's held count of clusters of accounts ("Clusters" above). The `fit` family's floor also decides the version-free (name, `platform`, `shell`) cells. A deploy that lowers a floor widens what the pool discloses; any notice the covenant requires for that is the operator's to give, and the pool does not enforce it.

## The raw tier

A locally redacted raw transcript can be sent to the pool, stored, and served to no one but the account that deposited it. It is the one place the pool holds content, so the rules are narrow.

**What it takes.** An account that is signed in, has accepted the covenant in force, and has given **raw consent**, which is its own answer, apart from the covenant (the client asks it separately; nothing in the covenant records it). Every request states, as headers, the redaction version the transcript went through (`oars-redaction-version`) and the capture version (`oars-capture-version`), each 1 to 64 letters, digits, dots, dashes, or underscores, and the first request of an account also states `oars-raw-consent: granted` with the covenant version it answered (`oars-raw-consent-version`; migration `0026` stores it beside `accounts.raw_consent`). With `COVENANT_VERSION` set, a yes is accepted only for the version in force: 403 `raw_consent_stale` for another version, and 403 `raw_consent_required` for a row with no version. After `DELETE /v1/consent/raw`, raw routes refuse with 403 `raw_consent_withdrawn` whatever a request states, `granted` included, so a machine that still holds a local yes cannot undo a withdrawal; the one way to record a yes after it is `PUT /v1/consent/raw` (below), and the withdrawal time and version stay on record. Before any withdrawal the pool records a `granted` for the version in force (`accounts.raw_consent`) and a later request for that version need not repeat it; a request that states anything else is refused even when consent is held. The covenant check is the deposit's: with `COVENANT_VERSION` unset every raw route is 403 `deposits_closed`.

**What it refuses**, each by name: before any byte is read, 401 `unauthorized`; 403 `deposits_closed`; 403 `covenant_not_accepted`; 422 `redaction_required` (no redaction version, or one that is not a version); 422 `capture_required`; 403 `raw_consent_required` (no yes, or a yes with no version); 403 `raw_consent_stale` (a yes for another covenant version); 403 `raw_consent_withdrawn` (the account withdrew and has not said yes again through `PUT /v1/consent/raw`); 503 `not_configured` when the `RAW` bucket is unbound; and once the part is read, 413 `too_large` for a part over 1 MB (unread when it declares its length) and 422 `empty_part`. A completion is also refused 422 `hash_mismatch` when the parts do not hash to the SHA-256 in the path (see The upload).

**The upload.** A transcript goes in parts of at most 1 MB, the cap a deposit has, keyed by its SHA-256 (64 lowercase hex):

- `PUT /v1/raw/:sha256/parts/:n` stores part `n` (1 to 999,999) under `staging/` in R2. A part sent again replaces itself, so a client retries a lost answer freely. An account holds at most 1000 staged part objects at once (`MAX_STAGED_RAW_PARTS`, one R2 list page): a part that would add one past that gets 429 `staging_full`, and a part that replaces a staged one always passes. The list is read again after the put: a part that finds the page full then, because others arrived with it, deletes its own object and gets the same 429. For an object that already stands it writes nothing and answers 200 `{ok, stored}`, after reading the part (under local workerd on Windows, an answer over an unread body resets the connection).
- `POST /v1/raw/:sha256/complete` takes `{parts, bytes}`, joins parts 1 to `parts` into one object `raw/<account>/<sha256>`, checks that they hold exactly `bytes` and hash to `:sha256`, and writes the ledger row. 409 `part_missing` names the first part that never arrived; 422 `bytes_mismatch` names the count it found; 422 `hash_mismatch` (field `sha256`) means the parts hash to something else; each leaves no object and no row, and the parts stay for the client to send the rest and complete again. A completion sent again answers 200 `{ok, stored}`.

R2 will not complete a multipart upload from parts under 5 MiB (the last excepted) and wants the others equal, so a 1 MB request cannot be an R2 part. The pool stages each request as its own object, then assembles through an R2 multipart upload, cutting the stream into equal 5 MiB parts; memory holds one 5 MiB buffer and one staged part. The staged parts are deleted once the row is written; parts numbered past the `parts` a completion names are not, and are left to the lifecycle rule. A transcript that is never completed leaves its staged parts behind: the deploy steps give the bucket a lifecycle rule that expires `staging/` after 7 days.

**The effective ceiling.** There is no cap on a transcript, but one `complete` does all its work in one Worker request: one R2 `get` per staged part (1 MB each), one `uploadPart` per 5 MiB, the multipart create and complete, and one batched delete (R2 takes at most 1,000 keys in one). The Worker's per-request subrequest limit (1,000 on the paid plan) and CPU time (the hash and the copy) therefore set a practical maximum, roughly several hundred MB by subrequest count, and CPU may bite sooner. Neither is measured against production R2; Miniflare enforces neither. The deploy steps say to verify it before the raw tier opens.

**A ledger row, never the bytes.** D1 holds one `raw_objects` row per object: account, SHA-256, bytes, capture version, redaction version, and the time. The bytes are only in R2. The row is ledger class: migration `0011_raw_tier.sql` gives it the never-delete trigger of `deposits` and `contributors`, and `ledger.test.ts` guards it. `raw.test.ts` dumps every D1 table after an upload and fails if the transcript is in any of them.

**It serves nothing, except to the account that deposited it.** No route returns a raw byte, a hash, or a count of what an account holds to anyone else, and the answers to the two uploads carry `ok`, `stored`, or `part` and nothing else. No bundle, read, or `derive` touches the bucket or the table. The one read is an account's own copy ("Your copy", Article 15(3)): `GET /v1/account/export/raw/:hash` streams one object, only when the `raw_objects` row is the signed-in account's and neither the row nor an erasure tombstone marks it erased. `raw-serves-nothing.test.ts` fails if any file but `raw.ts` and `export.ts` names the binding or the table, if `raw.ts` lists or heads the bucket or builds a response of its own, if `export.ts` calls the bucket for anything but one `get` or builds more than one response, and if any other method or path under `/v1/raw` answers anything but 404. The raw tier is not licensed or published either: serving it to anyone else would need a new decision and a change to that test.

**No limit on contribution.** There is no per-account cap on raw objects or bytes, and `MAX_DEPOSITS_PER_ACCOUNT` and `MAX_DEPOSIT_BYTES_PER_ACCOUNT` do not apply to it (`raw.test.ts` sets both to 1 and uploads three transcripts). Storage figures belong to telemetry.

**What the pool cannot check.** It cannot verify redaction: it takes the client's word, in the redaction version it records, that the transcript was redacted and its hosts masked before it was sent, and it runs no scanner over the bytes. It does check the hash: `complete` runs SHA-256 over the staged parts as it assembles them and refuses 422 `hash_mismatch` unless the digest is the one in the path, so the ledger's hash is the object's own. Redaction, host masking, and the raw consent prompt are the client's (t884).

## The sample pack

`npm run sample-pack -w packages/pool -- --terms <file> --owners <file> --index-key <file> --buyer-key <key> --out <folder> [--size 25] [--seed 1] [--min-turns 20]` (`packages/pool/scripts/sample-pack.ts`) builds an evaluation sample for one buyer from a local session store, offline. It reads the store `APPDATA` (or `XDG_CONFIG_HOME`) points at and the transcripts `CLAUDE_CONFIG_DIR` points at, so the operator runs it on a copy, never the live store. It uploads nothing, and it refuses an output folder inside a git repository or one that is not empty, and an owners file inside a git repository (the operator index lands beside it). It builds in `<folder>.partial` and renames that to the output folder when the run finishes, so a run that stops partway leaves no half pack under the output folder; the next run refuses to start until the unfinished `.partial` folder is deleted. The term list, the owners file, and the index key are local files named on the command line and never enter a repository.

**What it leaves out.** Only accepted sessions are taken. Sessions are drawn in a seeded order (SHA-256 of the seed and the session id) from the main sessions with a user turn (a subagent transcript is never drawn, and a session another one superseded holds no turns), until `--size` are written. A session is left out, in this order: when the client's exclusion check (`checkSession`, `packages/cli/src/sessions/exclusion.ts`) finds a listed term in its main or any subagent transcript, when it has no raw transcript to scan (a Codex session has no copy in the harness folder or the raw archive; the gate reads the rollout where Codex keeps it, through the Codex source), or when the term file is missing or empty (no session is written then, though an empty `manifest.jsonl` and `pack.json` still are); when no owners entry matches its project folder; when its harness has no terms row; when it is an orchestration lead session (its first prompt, a slash command read as its name and arguments, matches `LEAD_PROMPTS` in `sample-pack.ts`: `/loop /orchestrate`, `/orchestrate`, or `/handoff resume`, extendable through `PackOptions.leadPrompts`; it holds private company business and is counted `lead`); when it has fewer than `--min-turns` turns (user plus assistant; the default is 20); when the store recorded no repository for it; and when it is a duplicate, a resumed session that replays an earlier one, losing to the longer of the two (a tie to the lower session id), whichever the draw reaches first. Two sessions are one conversation when they share a repository and the first three things the person typed (all of them when a session has fewer), one list being the start of the other. What the harness wrote is skipped: an `isMeta` line, a line that opens with a local command's tag (`<local-command-caveat>`, `<command-name>`, `<command-message>`, `<local-command-stdout>`, `<local-command-stderr>`), and a tool result. Text is compared and nothing else of a line (never `timestamp`, `uuid`, `parentUuid`, or `sessionId`, so a resume that rewrites them still matches); a Codex rollout's `user_message` events count the same. Two unrelated sessions that both open with `continue` and go on differently are both kept. The longer of the two is chosen only among sessions that pass every rule above, so a longer twin another rule drops never costs the shorter its place. Each session is read up to its first typed turn and no further (`typedPromptsOf(path, 1)`, one line each); the rules above run only for a session the draw reaches and for the members of a group that shares a first prompt, so a singleton the draw never reaches is never gated. The duplicate rule runs before the secret scan (the scan costs a full redaction), so a duplicate that also holds a key is counted `duplicate`. A session whose redacted text, after the ids are masked, still holds something shaped like a key is dropped as well (see "The secret scan"). Rights must be stated, so each gate fails closed. `pack.json` holds no transcript text: the counts, one per rule (`excluded`, `noOwner`, `noHarnessTerms`, `lead`, `tooShort`, `noRepo`, `duplicate`, `secret`, and `emitted`), the `--min-turns` in force, the pack's `bytes` (`sessions/` and `manifest.jsonl`), and the run's `elapsedMs`.

**The secret scan.** After a session is redacted and its ids masked, and before anything of it is written, every transcript text is read again for key shapes (`secretIn`: a private key block, an AWS access key id, GitHub, Stripe, Slack, and Google keys, a webhook secret, an `sk-` key, a JSON web token, and a password in a URL). The shapes are most of those `redact.ts` masks (not its `Bearer` and NAME=value rules, whose output is a placeholder), but unanchored, so a key stuck to the word before it, which the redactor's word-boundary rules can miss, is still found (the bare `sk-` shape keeps a left guard and a digit, so a hyphenated word like `task-management-notes` is not read as a key). A base64 image's data is left out of what is scanned (a source's `data`, and a Read's `toolUseResult.file.base64`, whose object has an `image/...` type; a `base64` field on any other object is scanned), so a screenshot never trips a shape by chance. A hit drops the whole session, writes none of its files, manifest row, or index row, and adds to `counts.secret`. The scan stops a pack from carrying a key it knows the shape of; it does not prove the pack is free of secrets, and the operator still reads it before a recipient sees it.

**What is stripped.** Every transcript goes through the client's `redactTranscript`, which recognizes an injected block by where the harness puts it, never by its wording: an `attachment` record of an injected type (`instructions` and `nested_memory` carry CLAUDE.md bodies and the memory index), a `<system-reminder>` that leads a user message, every `<system-reminder>` in a tool result, the text of an `isMeta` user message, and a request's system prompt and tool descriptions. Each becomes `[injected <kind> <hash>]`, the hash keyed per buyer, so one CLAUDE.md gives one marker within a pack and two buyers' markers cannot be compared. A Codex rollout is stripped the same way: a user message that opens with `<user_instructions>`, `<environment_context>`, or `# AGENTS.md instructions`, every developer message, and the `instructions`, `base_instructions`, and `developer_instructions` fields of its head records. What the person typed and what the model said stay. The same call masks secrets, emails, the account name, hosts, and home paths.

**Redaction version 4.** What the first Fable read of a pack (version 3) asked for, each rule with a test in `injected-system.test.ts`, `redact-pack.test.ts`, or `sample-pack-redact.test.ts`. (1) A `role: system` request blob is marked by form under the kind its attachment copy gets, so the same block gives the same marker in both: SessionStart hook output, the skill listing, the agent roster, the `# Environment` block, MCP server instructions, and `Contents of <path>` rules and CLAUDE.md, AGENTS.md, and MEMORY.md blocks; an `edited_text_file` of a memory file and a "changed on disk" system message are marked too. (2) The GitHub account a session's repositories live under (each `url =` of the `.git/config` of every session `cwd`, linked worktrees followed, plus an optional `handles` list on an owners entry) is `<owner>` wherever it stands as a path segment or remote account. `session-owner` `accountUuid` and `organizationUuid` were already keyed under the buyer key when a line carries them as keys; inside a quoted string (a settings file or tool output) they were clear, and are keyed now. (3) A tool use id and its result's `tool_use_id` are keyed under the buyer key to one value (`toolu_<hex>`) instead of `<secret>`, so a call and its result pair; a bare number under a `token` name (`tokens: 12345`, `"inputTokens": 98765`) is kept; `@scope/name@1.2.3` is not an `<email>`; a synthetic GitHub, Stripe, or Slack token is masked like a real one (shorter minimums, and a left guard that lets `FAKE_ghp_...` start a token); `1password:` before a colon is not a secret key; and a public host a session fetched or searched (the URL or `allowed_domains` of a WebFetch or WebSearch input) stays in the clear in that call's result, while loopback, private-range, IP-literal, `.local` and other internal hosts, and organization domains stay masked. (4) Lead sessions are not drawn (above).

**The manifest.** `manifest.jsonl` has one row per session: `matchId`, `harness`, `harnessVersions`, `repoOwner` and `sourceLicense` (from the owners file: a list of `{folder, owner, license}`, the first glob matching the project folder, `license` null when unknown), `harnessTerms` (the terms the session ran under and their version), `permittedUses` (`evaluation`, `benchmarking`, `task-design`), `training` (`not-offered` unless the harness terms allow it as a priced add-on; neither Claude Code's nor Codex's do), `transcripts`, `redactionVersion`, `startedAt`, and `endedAt`. Transcripts sit under `sessions/<matchId>/`.

**Harness terms.** A harness has a row in `HARNESS_TERMS` (`sample-pack.ts`) or its sessions are left out and counted `noHarnessTerms`. Each row names the pages a session ran under and the version each page prints for itself, read on 2026-11-10:

| Harness | Page | Version in the manifest | Source |
|---|---|---|---|
| Claude Code | Anthropic Consumer Terms | `effective 2025-10-08` | `anthropic.com/legal/consumer-terms`: section 3 bars using the service to develop competing models |
| Claude Code | Anthropic Usage Policy | `effective 2026-11-12` | `anthropic.com/legal/aup`: no use of outputs to train a model "without prior authorization from Anthropic" |
| Codex | OpenAI Terms of Use | `effective 2026-01-01` | `openai.com/policies/terms-of-use/`: the user owns Output, and may not use it to develop models that compete with OpenAI |
| Codex | OpenAI Usage Policies | `effective 2026-11-20` | `openai.com/policies/usage-policies/`: no supplying training material or signals for models that substitute for OpenAI's |

`training` is `not-offered` on both rows. The Claude Code row is for the Consumer Terms (the plan is not checked per session). A lot sold before a page's effective date rests on the previous version of that page, and the row is changed when the page is read again.

**Match ids.** A session's server key is the HMAC-SHA-256 of its id under the operator's index key (64 or more hex characters), and its match id is the HMAC-SHA-256 of that server key under the buyer key. No session id reaches a buyer: the manifest carries the match id only, and every emitted line has its `sessionId` (and any other mention of a session the store knows) rewritten to that session's match id, and every line uuid (`uuid`, `parentUuid`, and any other key ending in `uuid`), `requestId`, and, in a Codex rollout, `session_meta.id`, `session_id`, and every `call_id` rewritten to the same keyed HMAC, cut to the shape of the id it replaces (a uuid, or `req_` and `call_` followed by 24 hex characters), so `parentUuid` still names the line before and a call still names its output. A Codex rollout's own id is its session's match id. The map from session id to match id is `index.jsonl` beside the owners file (one row per emitted session: `pack`, `session`, `project`, `matchId`, appended per run), which the operator keeps and never sends. So two buyers' ids for one session cannot be joined without their keys. The transcript text and the harness's message, tool, and agent ids are the same in every pack, so two buyers who compare packs can match sessions by content; the masks stop only an id lookup. One buyer's id is the same in every pack, and nobody without the index key can test a session id against a match id.

## Erasure

The ledger never deletes (migrations `0009` and `0011`), so the pool had no way to remove a secret that slipped past the redactor or to answer a lawful erasure request. Three things can now be erased by the **operator's own command** and not by a route: the Worker has no route that erases and holds no token for one. The one erasure the Worker does itself is the raw copies of an account that withdrew its raw consent ("A withdrawal erases the raw copies held", below), on the nightly cron and not on a request. The command runs with the operator's `wrangler` login on their machine: D1 through `wrangler d1 execute --remote` and R2 through `wrangler r2 object delete --remote` (`--local` points it at local state). It changes nothing without `--confirm`.

```
npm run erase -w packages/pool -- raw <raw/account/sha256>               [--confirm] [--local]
npm run erase -w packages/pool -- row --account <id> --id <session>      [--value-stdin] [--confirm] [--local]
npm run erase -w packages/pool -- account --account <id>                 [--confirm] [--local]
npm run erase -w packages/pool -- close --account <id>                   [--confirm] [--local]
npm run erase -w packages/pool -- restrict --account <id>                [--lift] [--confirm] [--local]
npm run erase -w packages/pool -- export --account <id> --out <folder>   [--raw] [--local]
npm run erase -w packages/pool -- withdraw --account <id>                [--confirm] [--local]
npm run erase -w packages/pool -- raw --contains --value-stdin           (--account <id> | --all-accounts) [--local]
npm run erase -w packages/pool -- row --contains --value-stdin           (--account <id> | --all-accounts) [--local]
```

`close` is not an erasure (covenant 6.1, 7.2(a)). It sets `accounts.closed_at` (milliseconds, null while open; the first time stands, and it is the start of the retention clock in 7.2(a)), deletes the account's token rows, and moves every machine of the account to `revoked`; it writes one `erasure_audit` row (kind `close`, reason `account-close`). Sign-in (`POST /v1/login/poll`, after the provider approves), `POST /v1/machines/enroll`, and `POST /v1/machines/activate` then answer 403 `account_closed` (enrollment and activation: "This account is closed. To reopen it, write to privacy@manyoars.com."; sign-in: the message that records the proof, with `account` and `provedAt` in the body); a revoked machine key keeps its 401 `machine_revoked`. It keeps every Deposit, raw object, tombstone, and shared total, and an account the pool has never seen is an error. It prints `{"rowsChanged":n}`, the rows it changed, since a close erases nothing. A rerun changes nothing and writes no second audit row. Reopening is by hand on a written request (`pool-rights.md`). Erasure of a closed account is the separate `account` step above.

`restrict` is not an erasure either (GDPR Art. 18). It sets `accounts.restricted_at` (milliseconds, null when not restricted; the first time stands) and `--lift` clears it; each writes one `erasure_audit` row (kind `restrict` or `lift`, reason `account-restrict` or `account-lift`), and a rerun changes nothing. It revokes and deletes nothing. While the column is set, `POST /v1/deposits` (a machine key too) and the raw routes answer 403 `account_restricted`; its `account_weeks` rows leave every club board and `GET /v1/board`, and `POST /v1/clubs` and `POST /v1/clubs/join` refuse it the same way (`src/clubs.ts`); a lift lists it again; `POST /v1/machines/enroll` refuses it the same way (new processing, Art. 18(1); listing and revoking its machines still work); the contributor reads in `src/cluster-store.ts` skip the account, and the same run recounts every cell and stratum it contributes to (`recount`, through the store), so the account stops counting toward each holder count at once and a cell only it holds goes to zero clusters; a shared cell still above its floor keeps its totals (sessions, outcomes, tokens, and duration), which include the account's earlier increments, because a cell above the floor relates to no identifiable person (Art. 4(1), Recital 26), so Art. 18(1) does not reach it and no recompute is built; `--lift` recounts the same ones with the account counted again; and the telemetry rollup (`src/telemetry-rollup.ts`) rolls none of its batches. `POST /v1/telemetry` itself reads no credential (census S23), so it cannot refuse an account: its batches carry no account, and the retention sweep drops them. The account's export, an erasure, the withdrawal sweep, and the retention sweeps still run (Art. 18(2)).

| Kind | Reason class | What it does |
|------|--------------|--------------|
| A raw object, by its R2 key | `raw` | Deletes the object, writes a tombstone of the key's SHA-256, and marks the object's `raw_objects` row (`erased_on`). The row holds a hash and a byte count and nothing else, so it stays. |
| A deposit row that holds a leaked secret | `leaked-secret` | Replaces the row's skeleton with the marker `{"erased":"leaked-secret"}` in place (its extensions and deltas with `[]`, its request country with null), and tombstones the session. No row is dropped, and its tier, counted date, and ingest mark stay. With `--value-stdin` the command also reads the leaked value from standard input (never from an argument, so it is in no shell history and on no wrangler command line) and erases every other deposit row that holds it, scrubs it from the stored motifs (replacing it with `[erased]`), and from the cell keys, harness buckets, and frame buckets and the contributor records that name it (a frame's `model` and `harnessVersion` are kept in clear there), replacing it with `[erased:<first 12 hex of its SHA-256>]` in place so two leaked values stay two distinct keys and every count stands, and bumps the pool's generation once so a client holding the old copy fetches the scrubbed one, drops the unfinished staged parts of each account whose row held it (staged parts are sealed with a key the command does not hold, so they cannot be searched; another account's wait for its own next staging write to sweep them), and tombstones its SHA-256, so ingest refuses a deposit that carries the same string again. Only the digest is kept. |
| One account's content, for a lawful request | `lawful-request` | Rewrites every deposit row of the account to its anonymous shape, marked `{"erased":"lawful-request"}` (see "Rights and what answers them", Art. 17), deletes every raw object it holds, drops its staged parts, scrubs the label and allow list of its machines, deletes its repo keys and deposit hours, makes its tokens unusable, clears its id from its telemetry days, deletes its contributor records and moves the generation, and tombstones each deposit and object (GDPR Articles 17(1) and 17(3)(e); the next section says what stays). |

**Finding the raw objects that hold a text.** A person a deposit names (a tenant, a customer, a colleague written in prose, whom no redactor masked) can ask to be erased (GDPR and UK GDPR Article 17), and they do not know whose deposit names them. `raw --contains --value-stdin` finds the raw objects that hold their text. It reads the text from standard input, never from an argument (so it is not in the process table, a shell history, or wrangler's logs), at least 8 characters like the row scrub's value, and takes exactly one of `--account <id>` (one account's objects) or `--all-accounts` (every account's). It goes through the ledger's `raw_objects` rows that are not marked erased and reads each object from R2 one at a time with `wrangler r2 object get --file`, into a scratch file in a folder only the operator can read that is removed as soon as the object has been read. The command streams that file in 64 KiB pieces, keeping only the tail of the last piece so a match across a boundary is found, so memory holds one piece however large the object (raw objects are stored as the bytes the client sent, not compressed or encrypted, so nothing needs decoding). The match is an exact substring, as the value scrub's is, and it looks for the text as given and as a JSON transcript writes it (a quote or backslash escaped). For each object that holds it, the command prints one JSON line of its key, account, and size, and last the number of objects read, matched, and missing (a ledger row whose object R2 no longer holds). **It deletes nothing and writes nothing:** it runs SELECTs and object reads only, no tombstone and no audit row, so it needs no `--confirm`. It never prints the text or any byte around a match. Each key it reports goes to `raw <r2-key>` above, which deletes the object and tombstones it; whether an object names the person, and whether the request is lawful, is the operator's to decide from the object, which this command does not show. The parts of a raw object still being uploaded (`staging/` in R2) are not searched, because they have no ledger row and wrangler cannot list them, and they expire in 7 days; a deposit's staged part is sealed and cannot be searched. A text held in a deposit row, a motif, a cell, or a contributor record is found by `row --contains --value-stdin`, below. `row --value-stdin --confirm` erases it wherever it is held and tombstones it, and it reports counts, not which rows held it. Because wrangler reports every remote 404 as a missing key, a wrong bucket would count every object as missing and read nothing, so the command exits 1 when any object is missing.

**Finding the deposit rows that hold a text.** `row --contains --value-stdin` is the same find for the deposit side, for a person a deposit names (Art. 15(1) and 11(2): the text they send is what lets the operator look). It takes the text from standard input and exactly one of `--account <id>` or `--all-accounts`, at least 8 characters, and uses the same search as the value scrub (`findValue`), so what it lists is what `row --value-stdin --confirm` would erase. It prints one JSON line of account, session, and day for each live deposit row whose skeleton or extensions hold the text, and last the count of deposit rows, motifs, cells, and contributor records that hold it. With `--account`, the deposits and contributor records are that account's, and the cells and motifs are the ones it contributed to. **It changes nothing:** it runs SELECTs only, takes no `--confirm`, and never prints the text or anything around it. Run it beside the raw find, then erase each row you accept with `row --value-stdin` and each key with `raw <key>`. Neither searches the parts of a raw object still being uploaded (`staging/`, no ledger row) or a deposit's staged parts (sealed): wait seven days from the first search and run the raw find again, since a staged raw part by then has become a raw object or expired under the `staging/` rule.

For each right in the GDPR and UK GDPR and what answers it today, see "Rights and what answers them" below.

**What a tombstone does.** `erasure_tombstones` (migration `0018`) holds a kind (`raw-object`, `deposit`, `value`, or `account`, which holds the pool's account id and not a digest and is what migration `0027` reads), a SHA-256, the reason class (`raw`, `leaked-secret`, `lawful-request`, or `consent-withdrawn`), and the date. Ingest reads it and refuses with 403 `erased`: a raw part or completion for a tombstoned key (checked before the "already stored" answer, since the ledger row stands), a deposit for a tombstoned `account/session`, and a deposit in which any string value is a tombstoned value. The refusal names no row and no reason. A value match is on a whole string, as the wire carries it; a secret embedded inside a longer string is found by the row selector, not by this check. The raw tier is opaque bytes: the command that finds a raw object holding a text (above) reports its key, and a raw object that holds a secret is erased by its key.

**The audit.** `erasure_audit` gets one row per run: kind (`raw-object`, `row`, or `account`), reason class, date, how many rows and how many objects were erased, and the pool's own account id. It holds no content. The Worker's nightly withdrawal sweep (`sweepWithdrawnRaw`, `raw.ts`) writes one row of kind `raw-object` and reason `consent-withdrawn` for each night that erased anything, with the number of objects and no account. Both tables are append-only: a database trigger aborts an update or a delete of any row of either.

**What an account erasure removes.** Its repo keys and deposit hours are deleted. Its `tokens` rows keep their account and expiry, which is the record that a sign-in happened, and their hash, the credential, becomes `erased:<rowid>`, which no token hashes to, so a token it held stops working (the person signs in again to the same account). Its `telemetry_install_days` rows keep their install, day, and counts, and the account column holds `erased:<rowid>`, one placeholder per row, because the table is keyed by day, install, and account and two erased accounts of one install must not collide. Its `contributors` records, which say which account added to a shared cell or stratum, are deleted, and the pool's generation moves, so a client fetches the bundle again; a cluster count drops the account once a deposit recounts that cell. Those records are ledger class and the database refuses to delete them (migration `0009`); migration `0027` lets the delete through only for an account whose `account` tombstone (written first, and holding the pool's own account id, the same one `erasure_audit` keeps) is already there. A machine's label and allow list are replaced with `[erased]` and `[]`. `cells` and `strata` carry no account id, so there is nothing in them to remove.

**What stays.** The shared totals: `cells`, `strata`, and the counts and clusters stored in them are exactly as they were, and a bundle read that does not name the account is unchanged. A cluster count was written from the records just deleted, so it drops the account the next time a deposit recounts that cell. The account's `covenant_acceptances` (append-only: the proof that the covenant was accepted, kept as Article 17(3)(e) allows for the defense of a legal claim), its `accounts` row without `provider_created`, the tombstones and the audit rows (which keep the account id and a digest of `account/id`), the hash, byte count, and date of every raw object it held (the `raw_objects` row), the deposit rows, each holding its anonymous Skeleton (closed lists, buckets, listed names, tool shapes, and step order; a Deposit erased before this change holds the marker only), with their tier and counts, and a machine's hashes, host class, launcher, state, and dates (which a revoked or live key needs to be refused or served). A deposit row keeps its `host_class`, `launcher`, `claimed_host_class`, and `claimed_launcher` columns, and the machine keeps its `last_deposit_day`, because they are closed-list values. The next paragraph says which of these rows still name the account.

**Which kept rows name the account (covenant 6.6(d)).** After `erase account` only the records 6.6(d) lists keep the pool's account id; every other kept row is rewritten to one random id and joins to no one, with no key (Recital 26: a hash under a key the operator holds could be recomputed from a GitHub id, so none is used). The rewritten rows carry no erasure date and no insert order that points at their audit row: `deposits.erased_on` is null on them (a reader that needs "erased" reads the `erased:` prefix), and the bare `accounts` row and each rewritten deposit take a random negative rowid, so no live row's place or order (a later account still gets the next rowid) dates or orders them.

The rewrite finds rows by the account id, so a rerun of `erase account` finds none and changes nothing; an erased account that deposits again and is erased again gets a second random id for the new rows. `rows` in the audit counts erased content and not these rewrites. A run that stops between two of the rewriting statements leaves the rest for the rerun, which uses a second id: the kept rows are then split between two random ids, which names no one. An erasure does not stop an account from depositing new sessions; that is the account's own opt-out. `erase account` also rewrites the telemetry batches in R2 that name the account (Article 17(1); `scripts/erase-batches.ts`). It lists `telemetry/<day>/` for every day inside the 90-day window and reads each batch's own record, so a batch is found by what it says and not by an index. For each batch that names the account it writes a copy in which the account id is the placeholder `erased:` and every install id the account's records carry is one fresh random id (one per old install, per erasure, kept in no mapping), and `received` and every event's `at` cut to the Monday 00:00 UTC of their week, so the rewrite cannot be matched to an Analytics Engine row by its exact times; counts, commands, and durations come as they were. Every other batch within the window that carries one of those install ids (the install's batches that name no account, which is every batch since 2026-11-07) is rewritten the same way with the same fresh id, its account field left as it was. A rerun after a full run changes nothing, and a rerun after a stop between the rewrite and the delete finishes the delete. Batches past 90 days are left to the sweep. Limits: batches written since 2026-11-07 carry no `account`, so only older ones are found by the account (the install's newer batches are reached through its install id). A batch the install sends after the run keeps its own id, so the day of the erasure can count that install twice. A rewrite that names another account (an install shared by two accounts) is read and rewritten again by a later erasure of that account. Analytics Engine data points sent before 2026-11-07 hold the account in `blob6` until Cloudflare's three-month retention ends and cannot be deleted; no write since then puts an account in any blob or double (`blob6` is always empty), and the points' `index1` is the old install id, which the run replaces in every D1 row and R2 batch it finds; a batch the install sends afterward, that day's `telemetry_quota` row (dropped the next night), and D1 Time Travel still hold it. A rewrite keeps each event's duration and command, so until the Analytics Engine points expire (three months) the sequence can still match them to the old install. The listing uses R2's S3 API, since wrangler cannot list a bucket, so the operator exports `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, and `R2_SECRET_ACCESS_KEY` (a token with read on `oars-telemetry`) before `erase account`; without them every other step finishes and the command stops before the audit row, naming them, and a rerun completes it. The nightly rollup still maps an account with an `account` tombstone to `erased:` (`telemetry-rollup.ts`). Staged raw parts cannot be listed through wrangler: they expire after 7 days (the bucket's lifecycle rule), and a tombstone refuses the completion of an object it names.

**A withdrawal erases the raw copies held.** `DELETE /v1/consent/raw` (GDPR Article 7(3)) drops the account's staged raw parts at once. The nightly cron then erases the account's held raw objects (`sweepWithdrawnRaw`, `raw.ts`), whole, since raw bytes are opaque and nothing searches them: each gets a tombstone of reason `consent-withdrawn`, its R2 object is deleted, and its `raw_objects` row is marked (`erased_on`) and keeps the hash, byte count, and date. An account with no yes standing has every held object erased; one that said yes again (`PUT /v1/consent/raw`) has the objects stored before that yes erased and keeps the ones stored under it. The sweep takes at most 500 objects a night across every withdrawn account (five pages of 100, within the Worker's subrequest allowance), so a large account, or a night shared with other withdrawals, can take more than one night and the next night takes the rest; a run with nothing left changes nothing. It runs without an operator, so no `erase` mode was added beside `raw`. What it does not reach: a copy a recipient already holds, a bundle already served, and a client's own replica.

**Rerunning.** Each step is written so a run that stopped halfway runs again to the end: the tombstone goes first, then the content, then the audit row. A second run changes no row, moves no generation, and adds an audit row with zero counts.

## Your copy

A signed-in person can read back what the pool holds about their account, in JSON, and write nothing to anyone (GDPR and UK GDPR Articles 15(3) and 20). It needs no covenant: the right does not depend on having deposited under one. `oars pool export --out <folder>` does the walk (see Commands); the routes are `GET /v1/account/export` and `GET /v1/account/export/raw/:hash` (see Routes). Both are account-only (a machine key is refused 403 `deposit_only`, so a runtime that deposits cannot read the account back), and the account always comes from the sign-in, never from the cursor or the path, so no request reaches another account's row (`export.test.ts` plants a second account in every table).

**Format.** Every page states `format: "oars-pool-account-export"` and `version: 1`; a change to a page's shape moves the version, and the client refuses a version it does not read. A page holds rows of one section, in this order: `account` (the account row: id, covenant version, raw consent time and the covenant version it answered, when and at which version a withdrawal was recorded, access, source, first seen, provider created, fetch counters), `tokens` (when each sign-in ends, and nothing else), `covenant` (each acceptance: version, time, text hash, typed input, client), `machines` (every machine ever enrolled, a revoked one too, as its record without its key hashes, with the day of its last deposit and its key days), `repoKeys`, `depositHours`, `telemetry` (a row for each day and install: batches, events, measures), `rawLedger` (key, SHA-256, bytes, capture and redaction versions, stored time, and `tombstone`, the day it was erased or null), `depositParts` (each staged part of a batch not yet assembled or swept: batch, part, count, staged time, deposit, and body), `erasures` (each erasure audit row keyed to the account: kind, reason, day, rows and objects erased), and `deposits` (each stored session as it now reads: tier, versions, bag, deltas, ingest digest, skeleton, the machine that sent it and the host class and launcher the pool stamped, the host class and launcher the batch claimed, and `tombstone`; an erased one holds the marker the erasure left). An empty section is passed over, so only the last page can be empty.

**Paging.** A page holds at most 500 rows, or 10 deposits (one deposit can hold 1 MB, so its pages are short enough for the Worker's response and D1's result limits). The cursor is the section a page came from and the last row's ordering values, as base64url JSON, so a row is never sent twice, and a row added behind the cursor while the walk runs is not seen until the next export. A cursor is a position and nothing else: a forged one, or one taken from another account, moves only within the caller's own rows. A cursor that does not decode, or names no section, is 400 `bad_cursor`.

**What is not in it, and why.** Credential material: a token, a machine's key, and the hashes of them are not selected, since handing out a credential's hash would weaken the account's security (Article 32). Pooled derived cells, strata, bundle reads, and `contributors` (the rows that tie an account to the cells it fed) are shared totals over many accounts, so exporting them would disclose other people's data (Article 15(4)); the account's own deposits, which feed them, are exported (Articles 15(3) and 20). Rectification (Article 16) and restriction (Article 18) are not served here, and there is no request intake: this is a read the person runs themselves.

## Boards

Boards are the pool side of the virality memo's loop 2 (P100 (19) to (21)). They share counts between people who chose to share them, and nothing else: no session, project, prompt, token, or cost is held in a board table, so none can be shown or ranked. `oars club` and `oars board` (packages/cli) are the commands over these routes; the site page is a later brief.

**Tables** (migration `0036_boards.sql`). `account_weeks` is the account's own count per ISO week (sessions, tool steps, failed steps, a UTC weekday mask, and the harness names), written by ingest in the transaction that writes the deposit's cells. A session counts in the week its deposit first counted (`deposits.counted_at`), so a resend that still counts never moves it, and one restored after a tier-only break returns to its first week; a resend that stops counting takes its sessions and steps back, and if it also changed cells, the session counts again in the week it next counts. The day mask and harnesses only grow. `clubs` holds a club's id, name, and the SHA-256 of its code (never the code); the one reserved row `open` has no code. `club_members` is the club, the account, a nickname (unique per club, case-insensitive), and the join time. `club_consents` is append-only, like `covenant_acceptances`: the account, the club, the SHA-256 of the exact text shown, and the time; it holds no nickname, a rejoin adds a row, and it survives account erasure. `board_standing` is the hand grants (account, `granted_at`, `granted_by`, `reason`); no route writes it. `account_weeks`, `club_members`, and `board_standing` are in the account export and removed by `erase account`.

**Routes.** Every club route is account-only (a machine key is 403 `deposit_only`). `GET /v1/clubs/consent` is public and answers `{club, open}`, each `{text, sha256}`: the text a person is shown and the hash a join sends back as `consent`. `POST /v1/clubs` takes `{name, nickname, consent}` and answers 201 `{id, name, code}`: the creator is the first member, and the code (six characters, no look-alikes) is shown once. `POST /v1/clubs/join` takes `{code, nickname, consent}`; a club holds 50 members at most (409 `club_full`), a nickname is unique in the club (409 `nickname_taken`), and a missing or wrong consent hash is 422 `consent_required`. `GET /v1/clubs/:id` is members only (404 for anyone else, and for `open`). `DELETE /v1/clubs/:id/me` leaves: 204, and the row is gone from every view at once. `GET /v1/board` is public (a machine key is 403 `deposit_only` here too; `Cache-Control: no-store`) and answers `{board: "open", members}`.

**What a club code protects.** A club's code is stored as an unsalted SHA-256 (`clubs.code_hash`) and shown once. That keeps a code off the page but not out of reach of a copy of the database: the code space is about 2^30, so the hash can be reversed in seconds. A code only admits to a club, and a member can leave at any time; it is not a secret that guards anything else. There is no pool secret keyed into it (a lead ruling). An account is braked, so a code cannot be guessed at speed: see "Brakes" below.

**Closed accounts.** An account the operator closed (`closeAccount`, covenant 6.1) leaves every board at once, because it can no longer sign in to leave; its `club_members` rows stay, as closing deletes nothing.

**Ranking.** Members are ordered by weeks rowing (the run of consecutive ISO weeks with a counting deposit, ending this week or last), then active days, then nickname. A member whose account has no counting deposit is "ashore": listed last with `ashore: true` and no numbers. Each row shows weeks rowing, active days, sessions, and strokes this week (tool steps); sessions and strokes are shown, never ranked, and no token or cost field exists in any answer.

**The open board and standing.** Joining the open board uses the code word `OPEN` on the same route, with its own consent text (it says the board is public). The public list shows a member only when the account has standing: its first counting deposit is at least 90 days old (`STANDING_AFTER_DAYS`), its `accounts.access` has latched to `standing`, or `board_standing` holds a grant. Everyone else who joined is not listed at all, and appears when they stand. Leaving removes the row at once.

**Granting standing by hand** (the operator's own fleet): `npm run grant-standing -w packages/pool -- --account <id> --by <who> --reason <why> [--local] [--confirm]`. It is a dry run until `--confirm`, refuses an account the pool has not seen, and keeps the first grant of an account. Run it against the live pool only as the operator; tests and `wrangler dev` use `--local`.

**Brakes** (migration `0037_club_brakes.sql`, table `club_attempts`). Per account, a join with a code no club holds counts as a wrong guess; the 11th wrong guess inside a rolling hour, and every join after it until the oldest guess leaves the window, is 429 `rate_limited` with `retry_after` (seconds, also the `retry-after` header). A join or create with an invalid nickname or consent is refused 422 first and is not counted. A right code inside the limit joins. The attempt is reserved with one conditional insert before the code is looked up (a right code gives the reservation back), so a burst of parallel requests cannot pass the limit. Creating a club counts too: the 6th inside a rolling day is 429 `rate_limited`. The limit applies to every join, right code or not, once it is reached. The attempts are in the account export (`clubAttempts`) and removed by `erase account`.

**Nickname rule.** A nickname is normalized to NFKC, then must be 2 to 24 characters of letters (with the combining marks scripts such as Devanagari and Thai need), digits, space, `-`, `_`, and `.`, with no space at either end, no `@`, and no web address (`www.` or a dot before a common top-level domain). Enclosing marks, and runs of three combining marks, are refused. Anything else is 422 `nickname_invalid`, and the message states the rule in one line. A club name keeps its own rule (`bad_name`).

**Hiding a nickname** (the operator): `npm run hide-nickname -w packages/pool -- --club <id|open> --nickname <name> --by <who> --reason <why> [--local] [--confirm]`. It is a dry run until `--confirm`, matches the nickname in any case, removes that member's row, and records who and why in `club_hides`, once per seating, so a run that failed before the delete can be run again (also in the export as `clubHides` and removed by `erase account`). It does not bar the account: the same account can join the same club again, under any nickname, the hidden one included, because no law, page promise, or known exposure asks for a block list. Tests and `wrangler dev` use `--local`; never run it from a test against the live pool.

**Before the open board is linked anywhere,** covenant Part C.2 must name the purpose it serves (a public list of nicknames and counts); nothing here links or announces it, and the lead tracks that.

## Telemetry storage

`POST /v1/telemetry` keeps every accepted batch twice, for two jobs.

**The record is R2.** One object per batch at `telemetry/<YYYY-MM-DD>/<uuid>.json`, the day the batch arrived (UTC). The nightly cron deletes objects older than 90 days (`retention.ts`, `RETENTION_DAYS`, the retention Cloudflare gives Analytics Engine): a sweep and not an R2 lifecycle rule, because `wrangler.jsonc` has no field for a lifecycle rule, so only a deploy step would hold the bound and no repo test could check it. The sweep keeps a cursor in D1 (`telemetry_sweep`, migration 0015): the oldest day it has not yet emptied. Each night it resumes there and empties every day up to the cutoff, oldest first, so a day with more batches than one night's calls, or nights the cron missed (any number), are finished on a later night. It spends the calls the rollup left in the invocation's allowance of about 1,000 subrequests (the rollup reports what it used; a night the rollup used in full sweeps little or nothing and does not throw), and the cursor moves past a day only when a listing of it comes back empty. A pool with no cursor starts at the cutoff day. The same sweep drops the expired rows of `login_polls`, `login_starts`, and `telemetry_quota`. The object is `{received, batch}`: `received` is the arrival time, and `batch` is the request body exactly as it came, so an event type or field this server has never seen is kept. No address, user agent, or other header is read, so none is kept. The route does not join a batch to a deposit, and a batch reaches no bundle.

**The index is Analytics Engine.** Each event becomes one data point, written after the object is kept. A failed write costs the index and never the object (the answer says `indexed: false`). The layout is fixed, because a read names columns by position:

| Column | Holds |
|--------|-------|
| `index1` | the install id (also the sampling key) |
| `blob1` | event `type` |
| `blob2` | `cli`, the oars version |
| `blob3` | `os` |
| `blob4` | the command path, space-joined (`data.path`) |
| `blob5` | `data.errorClass` |
| `blob6` | empty (the route reads no credential since t956; the column is kept so positions do not move) |
| `blob7` | the flag names, comma-joined (`data.flags`) |
| `double1` | `v`, the schema version |
| `double2` | the event time, epoch milliseconds (0 when unreadable) |
| `double3` | `data.durationMs` |
| `double4` | `data.exitCode` |

A field an event does not carry is an empty blob or 0, so a read of `command` events filters on `blob1`. A blob is cut at 128 characters in the index; the record keeps the full text. Only strings and numbers of the known fields are indexed, so an event type this server has never seen reaches the index as its envelope.

## Telemetry rollup

The operator's read lists anomalies over the 30 day window only and counts installs with `COUNT(DISTINCT install)` queries; it never loads the whole table, and finds the first fleet read by reading the rollup from its oldest day a month at a time, stopping at the month that served a cell. A day counts as served when any cell is served in the widest window (30 days), since a 7 day cell implies a 30 day one: five installs reporting a week apart serve a cell on the day the fifth reports. The fleet read and the operator's read come from `telemetry_install_days` (migration 0011), one row per install, account, and day (the account column stays empty since t956, because `POST /v1/telemetry` reads no credential, so the operator's account figures stay empty too): the day's batch and event counts and its cells (a latency histogram, or hits and observations for a rate). A nightly cron (`17 3 * * *` in `wrangler.jsonc`) runs `nightly` (`nightly.ts`): `rollupRecent`, which rolls up yesterday and then the day before, since a batch whose first answer was lost arrives a day late; then the retention sweeps ("Telemetry storage"). A day is rolled up by its R2 prefix (the day the batch arrived), by deleting its rows and writing them in one transaction, so a second run changes nothing. An event counts once per install however many batches carried it (the CLI's delivery is at least once, so a resent batch repeats its events; two events with the same time and data from one install are one).

**Why R2 and not Analytics Engine.** A Worker has a binding to write Analytics Engine and none to read it, so reading it means the SQL API with an account token held as a secret and a second network hop. R2 is already bound and is the record, kept for 90 days, the retention Analytics Engine has. The index stays what it was, for ad hoc queries outside the Worker.

**Bounds.** One run reads at most 800 batches in all, shared by the two days it rolls (a Worker invocation allows about a thousand subrequests, and each batch read is one). Yesterday is read first, since no earlier run has counted it; the day before gets what is left, and when that cannot read it whole it keeps the rows an earlier night wrote. Batches past the cap go uncounted until a Queue exists: a run lists the same keys in the same order, so the next run reads the same first ones again, and `Rolled.truncated` says the day was cut. A row keeps at most 64 cells, so a crafted batch cannot grow a row. The rollup reads only the telemetry record and writes only its own table: no file of it names a deposit or a contributor (a test pins that), and `ledger.test.ts` allows no other scheduled job. A hook cell's group value is `<harness>/<version>`: the harness from the closed list, else `other`, and `unrecorded` when the fire has none (a nightly run, or a fire from before the field); the version is as written, `other` when not version-shaped, or `unrecorded` when the fire saw none (for example `codex/unrecorded`). A command or store cell's is the oars version as written, or `other` when it is not a version-shaped word. Listing a day's keys is one subrequest per page of 1000, on top of the 800 reads.

## Covenant record and the funnel read

Acceptance is the consent to upload, so the pool keeps who accepted which covenant version and when. Migration `0020_covenant_record.sql` adds two append-only tables. `covenant_acceptances` holds one row per account and version with the epoch milliseconds of the first acceptance; `POST /v1/covenant/accept` writes it in one transaction with the `accounts.covenant` update the deposit gate still reads, a repeat of a version keeps its first time, and a later version adds a row beside the earlier one. `covenant_served` holds, once per version, the time the pool first served it. It is written by the first `GET /v1/covenant` or acceptance with that version in force (`INSERT OR IGNORE`, so no deploy step to remember and no write while `COVENANT_VERSION` is unset). Apply the migration before setting `COVENANT_VERSION`: a time not stored when an account accepts cannot be recovered. Apply it to the remote database only as part of the deploy steps below.

Migration `0022_covenant_proof.sql` adds three nullable columns to `covenant_acceptances`: the SHA-256 of the text the account was shown (`text_sha256`), the input method (`input`), and the client version (`client`). The pool holds the screen texts in `packages/pool/src/covenant-texts.ts`, keyed by version and shipped empty until the covenant is published: a text is the screen verbatim, with a `Full text: <url>` line and a `To accept, type: <phrase>` line. With `COVENANT_VERSION` set and no text held for it the pool refuses an acceptance, because a record of a text the pool cannot show proves nothing. The 0020 append-only triggers cover the new columns, and a repeat acceptance keeps the first row, proof included. The client stores the raw-copy yes with the covenant version in force when it was given, a saved yes with no version reads as not asked, and accepting a different covenant version clears a yes tied to another one.

The published covenant is held in two places that a test keeps equal. `docs/covenant/<version>.md` is the full text the site copies word for word, and `packages/pool/src/covenant-texts.ts` holds the same text (`COVENANT_FULL_TEXTS`) and the screen a person accepts (`COVENANT_TEXTS`: Part A, then the acceptance block with the link and the phrase `I AGREE`) under one version. The version is `2.0-` and the first 12 hex digits of the SHA-256 of the full text (UTF-8, LF line endings, one trailing newline) with the Version line still holding its placeholder, so the recorded version proves the text; `covenant-texts.test.ts` recomputes it and fails if the text, the file, or the version drift. The pool serves the version from the opening deploy, when `COVENANT_VERSION` is set to it (Deploy steps, step 8); until then it answers `{"version":null}`.

**Where the person is.** Migration `0035_request_country.sql` adds the answer to the region question (`eu_eea_uk`: `yes` or `no`) and the two-letter country Cloudflare reported for the request (`request_country`) to `covenant_acceptances`, and the request country to `deposits`; the country is null when Cloudflare gave none, and rows from before the migration have neither. An acceptance stores both and a deposit stores the country of the request that sent it (a redeposit replaces it with the newest). Two letters name a country, not a person; the covenant lists the country among the identifiers it keeps, and `GET /v1/account/export` carries all three values (`euEeaUk` and `requestCountry` in `covenant`, `requestCountry` in `deposits`). The refusal is on acceptances only: `PROTECTED_REGIONS` in `covenant.ts` lists the 27 EU member states, the EU territory that has its own code (Åland and the French outermost regions: `AX`, `GF`, `GP`, `MQ`, `RE`, `YT`, `MF`), Iceland, Liechtenstein, Norway, and the United Kingdom (`GB`), and a deposit is never refused by its country, because a cloud machine's country is its data center and not the person's place. An erasure of a deposit sets its `request_country` to null.

`queries/covenant-funnel.sql` reads the V17(2) counts from those tables, `telemetry_install_days`, and the ledger. Run it from `packages/pool`, in a POSIX shell, with `wrangler d1 execute oars-pool --remote --json --command="$(cat queries/covenant-funnel.sql)"` (the `=` is needed because the file opens with a comment, and a bare value that starts with a dash reads as a flag); a remote `--file` is a D1 import that returns only totals, not rows (wrangler 4.158.0), so the query goes in through `--command`, as `scripts/erase-wrangler.ts` does. `--local --file queries/covenant-funnel.sql` reads the local database. Name the covenant version in the one edit at the top of the file, or leave it empty to read the version served most recently. It prints one row and no verdict: `version`, `start_day` (the UTC day the pool first served it), `installs` (distinct install ids whose earliest day in the rollup is on or after `start_day`, the first 300 by that day and then by install id), `installs_before_cap`, `accepted` (accounts with an acceptance row for the version, input-source accounts left out), and `depositing_4w` (those with a counting deposit at least 28 days after their own acceptance time). `covenant-funnel.test.ts` runs the file against fixture rows in a local D1.

What it cannot tell. An install is the first telemetry event an install id sends, so a user who runs with telemetry off is not counted, and CI runs are not separated from other installs. Installs and accounts are not joined: they are two counts from one start time, and the rollup's `account` column stays empty. Day grain: an install first seen on `start_day` counts even if it was seen earlier that day. "Shown the covenant" is not recorded. Retention: nothing deletes or rolls up `telemetry_install_days` rows except the nightly re-roll of one day, which replaces that day's rows (the sweeps drop R2 batches past 90 days and three other tables, never these rows), so an install's earliest day is not lost to retention. The count is still wrong in two cases: a day cut by the 800-batch budget keeps only the installs in the batches read, and a day the cron missed is never rolled up (the cron reaches only the last two days; `rollupDay` by hand fills one while R2 still holds it), so an install seen only on that day shows up on its next active day. A hand `rollupDay` on a day past the 90-day sweep lists no batches and still replaces that day's rows with nothing, so it must not be run for such a day. No retention was changed. An erasure leaves an account's acceptance rows in place, because they hold only the pool's own account id, the version, the time, the hash of the text shown, the input method, the client version, the answer to the region question, and the request's country, and are the record of consent.

## Tests

`packages/pool` runs the bundled handler and its D1 store under the Workers runtime through Miniflare, in-process, with a stub sign-in provider behind the Worker's outbound fetch (its device, token, and profile routes), so it needs no Docker, account, or network. `full-run.test.ts` drives the real CLI commands against it over a local socket.

## Known gaps

**Bundles read at different times or versions.** Withholding is decided within one bundle, from the cells it holds. Two bundles of one harness version fetched at different times can still be set against each other: a deposit between them can change which day is the smallest served, so the first withholds one day and the second another, and a reader who holds both has each day's number and the week's. Another version's bundle can still serve an environment cell this bundle dropped, so bundles of different versions can also undo withholding by subtraction.

A live read's baseline is not traceable through lineage: the floor counts only the sliced day's cells, so the read cites those and states `value.baseline` from cells it does not cite (cells at the floor, like every other number a bundle serves).

`POST /v1/login/start` and `POST /v1/login/poll` are unauthenticated: each start spends one call to the provider's device-code route and each poll one to its token route (and, on approval, its profile route) from the Worker's address. The Worker bounds both itself (a start per client address, a poll per handle, "Sign-in"), and the rate-limit rule in deploy step 6 is the outer bound: the pool must not be deployed without that rule.

`POST /v1/telemetry` is unauthenticated, and each request writes one R2 object of up to 512 KiB that the nightly sweep deletes after 90 days. The Worker caps an install at 24 batches a day, but the install id is the sender's claim, so the rate-limit rule in deploy step 6 is what bounds a sender who rotates ids, and the pool must not be deployed without that rule.

An account may enroll any number of machines: `POST /v1/machines/enroll` has no cap per account, and each call writes one `machines` row. The nightly sweep does not delete a revoked machine or an expired one, so the rows stay until a sweep is added.

## Where D1's own limits bind

With no cap on contributing, the only ceilings left are D1's. Cloudflare's page (`developers.cloudflare.com/d1/platform/limits`) could not be reached when this was written, so the figures below are from memory and **unverified**: a database holds 10 GB on the paid plan (500 MB on the free plan), and a row (a string, a BLOB, or the table row) holds 2,000,000 bytes.

- **A row.** The 1,800,000<!-- figure:join-limit -->-byte join limit above is that row limit less the room for the row's small columns. By the fixture's numbers (about 278<!-- figure:per-call~1 --> bytes of skeleton for each tool call: a 5,000<!-- figure:big-calls -->-call session is 1,391,362<!-- figure:big --> canonical bytes, `parts.test.ts`) a session of about 6,500<!-- figure:row-calls~500 --> tool calls is the largest one row holds. A longer session is refused with 413 until its skeleton is stored across rows or in R2.
- **A database.** The ledger holds about 1,900<!-- figure:sample~100 --> bytes for a one-prompt, two-step session (`ingest.test.ts` pins the fixture at 1,939<!-- figure:sample -->) and about 278<!-- figure:per-call~1 --> bytes for each tool call beyond it, so 10 GB holds roughly 5.2 million<!-- figure:sample-sessions~100000 --> minimal sessions, or about 100,000 sessions of 100 KB. The `cells` and `strata` rows add to this and are shared across accounts. These are the numbers that make a migration off a single D1 database the trigger to plan for, at around half of the database (about 5 GB), well before the write fails.

## Run a pool locally

To try the CLI against a pool on your own machine, with no Cloudflare account. Run these in `packages/pool`.

1. Apply the migrations to the local D1: `npm exec -- wrangler d1 migrations apply oars-pool --local`.
2. Make `packages/pool/.dev.vars` (git-ignored; wrangler reads it as the Worker's secrets). The names a sign-in needs:
   - `PSEUDONYM_KEY`: any long random string. `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`.
   - `BUNDLE_SIGNING_KEY`: an Ed25519 private key as a JWK on one line, in single quotes. `node -e "console.log(JSON.stringify(require('node:crypto').generateKeyPairSync('ed25519').privateKey.export({format:'jwk'})))"`.
   - `INGEST_HASH_KEY`: another long random string, made the same way as `PSEUDONYM_KEY`. It is not needed to sign in; without it every deposit answers 503 `not_configured`.
   - `GOOGLE_CLIENT_SECRET`: only for Google sign-in, and only a real one works.

   Without `PSEUDONYM_KEY` the sign-in answers 503 `This pool has no PSEUDONYM_KEY binding.`; without `BUNDLE_SIGNING_KEY`, the poll after the person approves answers 503 `no BUNDLE_SIGNING_KEY binding`.
3. Start it: `npm run dev` (`wrangler dev --port 8788`, with the local D1 and R2 under `.wrangler/`).
4. Point the CLI at it: `OARS_POOL_URL=http://localhost:8788 oars pool login --provider github`. Add `--verbose` to see each request.

A local pool has no stand-in provider. Finishing a sign-in takes a real provider's device flow: GitHub works with the client ID already in `wrangler.jsonc` (its device flow needs no secret), and Google needs the secret above. Never point a test run at `pool.manyoars.com`.

### Rotating the bundle signing key

A client pins each public key under its `kid` at its first login (`pool-accounts.json`, `signingKeys`) and never changes it: a later login that names a different key behind a held `kid`, or a `kid` the entry does not hold and no release ships, is refused (`signing_key_changed`, `signing_key_unpinned`). A bundle is checked against the key its `kid` names, from the pinned keys and the keys the running release ships (`RELEASE_KEYS` in `pool-wire.ts`, which win under a shared `kid`), and a bundle whose `kid` is in neither set, or whose signature fails, is refused naming the `kid`. A bundle with no `kid` is read as `k1`. A new `kid` therefore reaches a client only through a release, never through the pool's own answer.

1. Make the next key pair and pick its id (`k2`).
2. Ship an `oars` release with the new public key in `RELEASE_KEYS` under `k2`. If the old key leaked, list `k1` in `RETIRED_KEY_IDS` in the same release: that release refuses any bundle under it, pinned or not.
3. Once clients have upgraded, set the Worker secret `BUNDLE_SIGNING_KEY` to the new key and the variable `BUNDLE_KEY_ID` to `k2`, then deploy. No new secret is needed.
4. A client on the new release verifies `k2` bundles from `RELEASE_KEYS` and accepts a login that names `k2`; a client on an older release says the bundle is signed with a key it does not know and to upgrade.

Gap: a client on a release from before step 2 keeps trusting the leaked key until it upgrades, because its pinned set is all it has. `RELEASE_KEYS` is empty until the pool's first rotation; no real key pair exists before the first deploy.
