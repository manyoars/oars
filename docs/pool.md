# The pool

The pool is an optional server that accounts sign in to, deposit closed-vocabulary session skeletons to, and fetch cells and reads from. Local capture, recall, and reads need none of it: no session data leaves your machine unless you sign in and run `oars pool fetch`, and `oars pool deposit` only writes a batch to a local outbox (sending a batch is disabled in this release). Telemetry (`docs/telemetry.md`) is separate: it is on by default, records one event per command (its path, flag names, duration, exit code, and error class) and one per hook fire, recall, deposit, and fetch (counts and closed words only), each with a random install id, the oars version, the OS, and the time, and sends those events only to the pool server in `OARS_POOL_URL`. The code is in `packages/pool`, a Cloudflare Worker over one D1 database.

## Commands

Every command takes the server from `--server <url>` or `OARS_POOL_URL`. There is no default, and plain http goes only to localhost. The server is an origin with no credentials, path, or query, and a redirect is refused, so a token or a skeleton cannot be moved elsewhere.

| Command | What it does |
|---------|--------------|
| `oars pool login --provider github\|google` | Runs the provider's device flow (RFC 8628) itself, with the smallest scope that names the account (Google's `openid`, GitHub's none), then sends the provider's token to the pool once and saves the pool's own token at `<store>/pool-accounts.json` (mode 0600), pinning the pool's signing key on first login. No harness token is read. Every request, to the provider and to the pool, prints to stderr before it is sent: the request line, every header, and the body. The device code, the provider's token, and the pool's credential print as `<credential: n bytes>` wherever they appear; `client_id`, `scope`, `grant_type`, and Google's `client_secret` print as they are. It never signs in on its own: when the credential expires, deposits and fetches stop until you run `login` again. The client ID and secret come from the environment (below); one that is unset stops the command before it sends anything, and names what is missing. |
| `oars pool deposit [--send <hash>] [--accept-covenant <version>]` | Writes a batch to the outbox for every session that passes both session gates and has ended, and stops: nothing is sent, and only counts print. A session has ended when no transcript of it, main or subagent, has gained a line for `session_idle_hours` (6 hours), judged by the later of its last capture and its raw file's last write; one inside that window builds nothing, is counted as `notEnded`, and has any batch of it from an earlier `deposit` withdrawn. The gates run before any projection does: the folder allowlist (`oars sessions deposit --allow`) and the exclusion check (a listed term in a main or subagent transcript fails it, and so does a session with no raw to scan). A session that fails either is counted by reason and never built; the count never names the term or the folder. A batch is canonical JSON (sorted keys, no optional whitespace, UTF-8) under `<store>/pool-outbox/<hash of server>/`, in a folder named for the vocabulary version, the batch's field list, and the skeleton format, one file per session; a batch built under an older version, field list, or skeleton format is discarded, not sent. A session that no longer passes a gate, has not ended, or is no longer in the store has its batch removed on the next `deposit`, and the removals are counted. It refuses with `vocabulary_expired`, and sends nothing, when this client is more than 30 days past its vocabulary snapshot. `--send <hash>` takes the SHA-256 that `outbox` printed and accepts only a batch that was shown and has not changed on disk since, and it reads and hashes the batch again just before the request. In this release sending is disabled: `--send` runs those checks, then stops with `sending_disabled` (exit 5) and no request, because it waits on the pool covenant. There is no flag, variable, or setting that turns it on, and `--accept-covenant` without `--send` is a usage error; with sending disabled it accepts nothing. When it is on, a 409 `deposit_conflict` (another deposit of the same session landed first) is sent again, up to three attempts in all, with the same bytes. |
| `oars pool outbox [--explain]` | Prints each batch exactly as it would be sent: the request line, every header, and the body, with the bearer credential as `<credential: n bytes>` and nothing else masked, then the batch's SHA-256, and records that this hash was shown. It sends nothing, and it is a separate command from `deposit`: there is no automatic mode. `--explain` adds each field's rule, and a field with no rule fails the command rather than print blank. `oars sessions verify` reports how many batches, on any server, were built under an older vocabulary, field list, or skeleton format. |
| `oars pool fetch [--harness <name>] --harness-version <version>` | Fetches that harness's signed bundle at that version, verifies it against the pinned key, and keeps it at `<store>/pool-replica/<hash of server>/<harness>/<version>.json`, still signed, so a fetch for one harness never overwrites another's. A bundle that fails verification, or is for another harness or version, is refused and not written. The version must be a public one; nothing is keyed by stack. `--harness` takes one of `claude-code`, `cursor`, `codex`, `copilot`, `gemini`, `grok`, or `vscode-copilot`; any other name is refused before anything is sent. With no `--harness`, it fetches the harness your local store holds the most sessions of (`claude-code` for an empty store or a tie), and says so on stderr before it sends: `No --harness given: fetching cursor, the harness your local store holds the most sessions of (3 of 4). Pass --harness <name> to fetch another (claude-code, cursor, codex, copilot, gemini, grok, vscode-copilot).` It reads counts only, and none leaves the machine: the request names the harness and the versions, nothing else. Before it sends, it prints the request line and every header to stderr, with the credential as `<credential: n bytes>` and nothing else masked. It keeps the bundle's `ETag` beside it and sends `If-None-Match` next time: a 304 keeps the bundle and says it is unchanged (exit 0). A 429 (the weekly fetch cap) keeps the bundle, says in words when to try again from `Retry-After` (or that the pool did not say), and exits **10**, the code `fetch` alone uses, so a schedule can tell a cap from a failure. |

## Sign-in settings

The OAuth apps are the operator's to create, so the client reads their values from the environment. None is secret: every copy of the CLI would ship them, and Google's device flow requires its `client_secret` at the token route.

| Variable | Holds |
|----------|-------|
| `OARS_GITHUB_CLIENT_ID` | The client ID of the Many Oars GitHub OAuth app, with device flow enabled. |
| `OARS_GOOGLE_CLIENT_ID`, `OARS_GOOGLE_CLIENT_SECRET` | The client ID and secret of the Many Oars Google OAuth client, of type "TVs and Limited Input devices". |

## What the server enforces

- **Deposits are closed by default.** With no `COVENANT_VERSION` binding, every deposit gets 403 `deposits_closed`. Once one is set, an account must have accepted exactly that version, or it gets 403 `covenant_not_accepted`, and a new version asks again. Reads and `fetch` are not affected.
- **Closed vocabulary.** A shape error (a wrong type, a malformed value) gets 422 `closed_vocabulary` with the field named, and nothing is stored. An unknown field goes to the extensions bag, and an unknown enumerated value is read as `other`. What is stored is the parsed skeleton, not the text that came in.
- **Step attribution (format 3).** A step names the frame it ran in and the skill whose run it sits in, and a frame names the reach of its session, so harness, version, model, skill, and the servers, skills, and plugins in reach resolve from a step without a join the parser cannot check. A transcript sends `frames`, its distinct frames (its own first), and each step a `frame`, a position in that list; the parser refuses a position outside it. A call's frame is its prompt's frame (the transcript's before the first prompt) with the call's own `model` and `harnessVersion` where its line named them, so a model that changes in the middle of a prompt reaches the steps that ran on it; a call that recorded neither takes its prompt's. A step made inside a skill's run carries `skill`, a list member or `private`. Only Claude Code writes `attributionSkill`; an absent step `skill` on any other harness means not recorded. The harness marks no end to a run: it stops naming the skill on the next line, and that is where the run ends here (limit: a skill the harness does not name on the line shows nothing, and a nested skill shows only the outer name the line carries). A frame in `frames` and the transcript's `frame` carry `reach`: `{ filled, mcp, skills, plugins }`, each member a list member or `private` (a plugin is always `private`, since no plugin list is pinned), from the session's `setup`, its `funnel`, the MCP tools it called, and the skills it called. `filled` is false when the record holds neither `setup` nor `funnel` (Cursor, Copilot, Grok Build, and a capture before version 12), and then the lists are empty and must not be read as no tools. The large-deposit fixture in `packages/pool/src/ingest.test.ts` pins the skeleton at 876,815 bytes (818,998 before t868 put a null `errorCode` on each call and t869 a null `spawnedIn` on the transcript), up from 784,636 bytes before step attribution. The cell computation does not read the new fields: a cell is still keyed on the prompt's frame, so a mid-prompt model change moves no cell. **Model version:** a model literal holds the model's name as the harness wrote it (`claude-opus-5-5`) and no version beyond it, so a cell and a frame cannot tell two builds of one name apart; a model-boundary read is not built.
- **Intervention outcome (field-list version 5).** A prompt may carry `intervention`: what the next human prompt did to its work, one of `none`, `after-error`, `redo`, `revert`, or `unknown` (the rule and each limit are in `docs/sessions-store.md`, "Prompt intervention"). It is an outcome row, not a quality claim: no grade or score is named, and `none` is silence in the records, not approval. It is computed on the client from the stored records, so no prompt text, path, or command crosses; the bucket alone does. **Absent means not computed** (the stored prompt predates the signal); `unknown` means computed and not sayable, as for the last prompt of a transcript or one the user stopped. A value off the list reads as `other` and is kept as sent in the bag. The pool holds it per prompt in the stored skeleton and no read, cell, or bundle serves it (`served-families.test.ts` pins that); its one stated consumer is the later test of whether the per-prompt graph predicts intervention above chance on held-out repo keys, after the first 1,000 pooled prompts. The field is a closed list of constants, not a name, so it passes no long-tail name gate.
- **The skeleton form (format 3; formats 1 and 2 are refused with 422 naming `format`).** A step carries a shell call's projected `program`, `sub`, and `flags` in place of the joined shell command a step used to carry: a program is a curated-list member or `private`, a `private` program holds no subcommand, flag, or pull, a subcommand outside the curated lists, and a flag that is neither on them nor a single letter, are dropped, and a program only the client's snapshot lists goes as `private`. Every other name the pool has no row for (an MCP server, skill, host, pull name, and a native tool name) goes as `private` too, never as `<literal>`, which the parser refuses at those places. Usage, `errors`, `wallSec`, and a step's `tokens` and `ms` are Section 7 buckets, never exact counts; the one exact time is `durationMs` per tool step. A transcript and a prompt still carry their `frame` (each member has a Section 1.2 row, and the bucket key and the strata read it); only the shell step's joined command went. `deltas` is on the form and holds the batch's local delta entries, if any (see Local deltas); an entry outside its field's row is refused. A failed call carries its `errorCode` (a member of the closed `ERROR_CODES` list, `other` for a value off it, which also goes to the extensions bag, or `null` when the harness captured none) and, on a call that did not succeed, `recoveryCalls`: `next`, the canonical actions of up to the next five calls in the same prompt (what followed, never a fix; an action off the list reads as `other`), and `editFollowed`, true when a `file.edit` or `file.write` was among them (not a success flag). The list must equal the one the batch's own calls give, or the batch is refused. No signature hash, text, or argument goes with either. The exact-count form (format 1) and format 2 are refused with 422 naming `format`; nothing is migrated. Cells count a bucketed value as the bucket's lowest value, so a cell's `tokens` and `durationMs` are lower bounds. The cell computation is one module (`cell-increments.ts`) that the pool's ingest and the client's local read both call. A step's calls and a prompt's place are positions in the batch, not the log's numbers: tool `n`, prompt `index`, and a step's `seg` (its place in its call, which the server rebuilds from position) are not sent. **Edges and the spawn link (t869).** A step carries `edges` when any arrive, each `{ kind, target }`: `kind` is one of the closed list `next` (order within a prompt's line of work), `spawned`, `retried`, and `after-error`, and `target` is the position of the step it names, counted over the steps of one transcript in call order (a position in the batch, never a call number). The client decides `retried` and sends the result, since the pool holds none of the raw keys it compares. A `spawned` edge sits on a subagent's first step and names a step of the spawning transcript. The parser reads an unknown kind as `other` (kept in the extensions bag, its target held to a count only), and refuses a target that is not an earlier step of the same transcript (a `spawned` target must be a step of the spawning transcript), and a `next` whose target ran in another prompt. A transcript carries `spawnedIn`, the position in the batch's `transcripts` of the transcript that spawned it, and a step's `parent` is the position of the spawning call in that transcript's `tools`, so a subagent two deep rebuilds its tree from the batch alone. `spawnedIn` is null for the main run and for a subagent whose spawner the batch does not hold; the parser refuses a position outside the batch, the transcript itself, a cycle, and a spawner on the main run. **Which harnesses fill it:** Claude Code alone, from the subagent's `.meta.json` tool-use id; Codex and Gemini read a subagent but record no spawning call, so they send null, and the other harnesses record no subagent run. The cell computation does not read an edge: a motif is still a linear window inside one prompt, and the cells are byte-identical with and without edges. A skeleton-derived store (`cell-increments.ts`) carries both back, so it holds the same graph as the local store on the fields both keep. `usage.thinking` is a token count and goes as the `tokens` bucket like the other usage fields. A cell never holds a list longer than one: a motif keys on a shell step's program and subcommand, and each flag and each pull is its own one-step cell (spec rules 1 and 2), so a step with two flags makes two flag cells and one program cell.
- **Two planes.** A deposit writes its parsed skeleton and its deltas (the ledger column still holds `[]`: see the local deltas bullet below) to the ledger (`deposits`), and, in the same transaction, its cell increments to the index: `cells`, `motifs`, and rule 3's `strata`, each cell's `clusters` a held count. A `contributors` record per (cell or stratum, account, UTC day) tells a returning cluster from a new one, so only a new one raises a count. The ledger has no expiry: no code deletes a `deposits` row or a `contributors` record, and a database trigger aborts any `DELETE` on either (migration `0009_ledger_no_delete.sql`). A bundle is read from the index alone (`packages/pool/src/stored.ts`: four statements whose rows grow with the cells, not with deposits). A session sent again adds only the difference to its earlier batch. A large batch of varied steps runs its cell JSON to about four times its skeleton's size, and D1 takes 2 MB in one value, so ingest binds each payload in chunks of at most 1 MB, one statement per chunk, all in the one transaction under the one guard. Two limits of the stored form stand until a later change rebuilds what they need, and tests pin them: a session sent again over a held row that no longer parses adds its whole batch a second time, since the cells keep that row's increments and there is no parsed batch to take back; and a session sent again that leaves a cell lowers its `sessions` but not its `clusters` or the account's `contributors` record, so four accounts plus one that left still read as five (one record cannot show whether another of the account's batches still holds the cell).
- **Local deltas (`deltas`).** The client compares its own windows and sends what changed, once. `pool deposit` takes the sessions that pass both session gates and have ended, and counts `DELTA_DAYS` (7) windows on a fixed grid from the epoch, so adding, losing, or finishing a session moves no window; a pair of windows next to each other, each with at least `DELTA_MIN_SESSIONS` (5) of them, makes a delta, and the batch of the session that fills the after window (its fifth, in time order, ties by id) carries it. An entry holds a `deltaKind`, a `field`, a `name` or null, a `registry` or null, a `metric`, and a `change`, and nothing else: no session id, root, window date, or exact value. Four fields enter, per the spec's first exception to rule 3: `plugin` as `added` or `removed`, `permissionMode` and `effort` as `changed` (named by the field alone, the most common value of each window differing, so one odd session is not a change and two values off the effort list are no change), and `package` as `removed` (called in the before window and gone by a clean manifest edit, or by a Write that lists the same file without it in the after window; a Read never says a package is gone, since it may show part of a file; a public name with its registry, else `private` with none, and all `private` ones are one entry). A plugin goes as `private` always, since no plugin registry is pinned, and plugins are compared only over the sessions of a harness that records them (Claude Code), with none built when either window holds no such session. The after window is read as its first five sessions, so the entry is fixed when the window fills. `change` is the signed bucket of the move: calls per session in `count` buckets (-7 to 7), thinking per prompt in `tokens` buckets (-11 to 11) for an effort. The parser holds each field to its own row and refuses an entry outside it, and `oars pool outbox --explain` shows a row for each field of an entry.
  **Once only.** A delta is marked in `deltas-sent.log` in the outbox folder (a hash of the account, the entry without its `change`, and the index of its after window on the grid; the filler session is not in it, since which session fills a window can change from one deposit to the next, while the index cannot) after the batch that carries it is written, never before: a deposit that stops first builds it again. A later deposit builds no delta it has marked, so a session rebuilt under the same key replaces its batch with one that carries none. **Limit:** a batch that carried a delta and was never sent is replaced by that rebuild without it, so the delta is lost; the mark is written with the batch, not at send time, because sending less beats sending wrong and nothing is sent to a real pool yet. **Limit:** the public package list is held by bare name, so `pypi:typescript` goes as the public name `typescript` with its registry until the list is held per ecosystem. Also not built: an `upgraded` delta for the harness version, rule 4's "pool neither when both changed", and the batch's summary `exposure` (no deposit reads an exposure tag yet). The Worker parses an entry and keeps it inside the stored skeleton, but derives no delta cell and its `deposits.deltas` column still holds `[]`; the weekly limit on one delta for each cell is the pool's, not built here.
- **Cell grain and effort (rules 3 and 6).** A cell is keyed on the UTC week (`grain: week`, `day` the Monday), except a `live` cell, which stays at UTC day (`grain: day`) and holds none of rule 3's bound fields. Each read answers from one grain and filters the other out, so adoption and change state weeks (`firstWeek`, `lastWeek`, `weeks`, `weeksSinceLast`), never days. `effort` is in no cell key: it is recorded only as the (`effort`, `thinking` bucket) cell, which joins no `model` or `harnessVersion`, so `fit` and the interaction read no longer slice by it. Migration `0008_cell_grain.sql` adds the grain column; nothing is deployed, so it moves no data. A local `cells.jsonl` written before the grain has no `grain` field, fails the stored-cell check, and is derived again from the store the next time a pool is built or served. On the 3,400-step test deposit a batch counts 876,815 bytes of skeleton and 11,548 cells (3,342,305 bytes of cell JSON, 3.81 times the skeleton) and stores 876,819 bytes (skeleton, deltas, and the 2-byte extensions bag); no default limit counts them (see No cap on contributing). A session with a shown recall derives different local cells from its deposit, because a deposit is built from the skeleton, which has no recall graph, so the recall's step and exposure appear only in the local read.
- **Stack shares, explore, and the two pairs (rule 3).** Every frame's `stack` on the wire carries `languageShares`, one `{language, languageShare}` per language, the share one of `0`, `under-10`, `10-50`, and `over-50`; a share outside that list is dropped and its language still goes in `languages`, and a language off the pinned list goes as `other` (in a share only; the frame's `languages` list holds the pinned names alone). A prompt carries `explore`, a `calls` bucket of its steps that only look (`file.read`, `file.search`, `web.search`, `web.fetch`), or `null` for a record captured before the strata; the exact count never leaves, and the deposit's local store counts a prompt as its bucket's lowest value, which no read serves yet (the store holds the bucket's lowest value). The `calls` edges are the `count` edges and then double: 1, 2, 3, 5, 9, 17, 33, 65, 129, 257, 513, 1025, 2049, and 4097, so the last bucket is over 4,096, as the `count` bucket's is over 32. Two strata are counted beside the single ones, each a stratum of its own and never a cell: `languageShare` (value `<language>/<share>`, per frame) and `repoFilesExplore` (value `<stack size, xs to xl>/<explore bucket>`, per prompt, none when either is missing). They are held to `K_CELL` accounts pool-wide like the others, appear only in the bundle's `strata`, and a cell still holds at most `q_dims` dimensions. This closes the limits that the wire sent no language share and the deposit derived `explore` as zero. **Limit:** the `live` family's provider errors by `model` and by `harnessVersion` are not built here: a skeleton step carries `status` (`ok`, `error`, or `none`) and no `errorCode`, so no day cell can name a `429` or a `5xx`.
- **Pseudonymous accounts.** The pool never calls a provider to start or poll a device flow. It takes the provider's token once, reads the subject from the provider's profile route, hashes it under `PSEUDONYM_KEY` (which the database never holds), and discards the token. No email, login, provider id, or provider token is stored, and the pool holds no OAuth value. A login also deletes the token rows past their expiry.
- **Five accounts to a read.** A read is served only at 5 or more clusters (`K_CELL` in `packages/pool/src/derive.ts`, the spec's proposal, which a later decision may move), and a cluster is an account, so one account's many sessions count once. A cell's `clusters` is its held count of accounts, and a read's is the largest held count among the cells it cites, with no union over accounts: the fetch path reads no per-account record, so five accounts in five different weeks serve no read, since each week's cell holds one (a later change brings held counts for a key's `n` and `c`). Five accounts on five days of one week share each week cell and serve the week reads at 5 clusters, and no `live` read, since a `live` cell is one day. A cell served on its own needs 5 accounts in that cell, and a strata cell needs 5 accounts pool-wide. A `live` read cites only the sliced day's cells, so its floor counts the clusters held on that day and never those in its seven-day baseline; the baseline sums only baseline cells at the floor, and with none `value.baseline` and `value.ratio` are `null`.
- **A fetch cap.** An account without access may fetch `FETCH_CAP` bundles (default 1) per ISO week, counted per account and not per harness or harness version. Past it the pool answers 429 `fetch_cap` with `Retry-After` in seconds to the next Monday 00:00 UTC, before it reads the pool. The count is one atomic statement, and a count from an earlier week is dropped. A fetch that fails after it spent gives the spend back, since the account received no bundle. An account with access is not capped.
- **Access.** The `access` record is null, `pending`, or `standing`, and only a counting batch sets it: ingested at tier committed or higher, or at `skeleton` when every transcript's harness writes no raw file (Cursor), with one prompt and one tool step over the batch, subagents folded in, and at least one cell increment written over the row held now (a batch sent again unchanged writes none); an ingest that writes none leaves the flag and the batch's date alone. It is `pending` while it rests on batches counted inside the last 90 days (`STANDING_AFTER_DAYS`), clears when every one falls to `none`, and is `standing` once one has stood the 90 days. The 90 days gate the flag only; the batch stays on the ledger. A resend that still counts keeps a batch's first `counted_at`; one that no longer counts clears it, and the flag falls if no counting batch is left. A claude-code batch with a prompt and a tool step now lifts the cap, because the batch carries its roots and is written at `committed` (the next row).
- **The tier of a batch.** Ingest writes the batch's own tier, on a first deposit and again on a resend (`tier = excluded.tier`): the lowest of its transcripts', subagents folded in. A transcript is `skeleton` when its harness writes no raw file (Cursor), `none` when its root cannot be real (no leaves under any hash but the SHA-256 of no bytes, or that hash over leaves), else `committed`. A batch with one failed transcript is `none`, takes no part in access, and a resend that fixes it counts again. A batch ingested at `none` still writes its cell increments. Stated limit: a fabricated but well-formed root, and a forged skeleton, still earn `committed` until the raw-file check of a later layer.
- **A 304 spends nothing.** A 200 carries an `ETag` that names the code, the floor, the harness and version asked for, and a generation of the stored cells (triggers on `cells` and `strata` move it in the same write as a change; a write to `deposits` changes no served cell and moves nothing). An `If-None-Match` that holds it gets 304 with no body, before the spend and without reading the pool, so a conditional request can neither use up a fetch nor force a read. A weakened `W/` tag matches.
- **Two deposits of one session at once.** A deposit replaces the batch the account held under its id, and nets its cells against that earlier row, so two at once would each net against the same row and add the batch twice. The upsert therefore takes the row only if it is still the one that was read (its `ingest` mark), and the other gets 409 `deposit_conflict`: nothing of it is stored, and the client sends it again, which then nets against the winner.
- **A deposit holds something.** A skeleton with no prompt and no tool gets 422 `closed_vocabulary` naming `transcripts`, since only a counting batch lifts the fetch cap (see Access). A forged skeleton that holds invented prompts passes this check, and with a well-formed root it lifts the cap under any harness until the raw-file check of a later layer (see the tier row under Access).
- **No cap on contributing.** The pool does not ration what an account deposits: sessions, bytes, harnesses, and machines per account are unlimited by default, and a redeposit of a held session replaces its row (an `UPDATE`, so the never-delete triggers of the ledger hold) and counts against nothing. `MAX_DEPOSITS_PER_ACCOUNT` (rows) and `MAX_DEPOSIT_BYTES_PER_ACCOUNT` (stored bytes: the skeleton, the deltas, and the extensions bag) remain as an operator's brake, off unless a binding sets one; a value that is not a positive whole number leaves the account unlimited. With a brake set, a new session past it, or a deposit that would take the account past the byte brake, gets 403 `deposit_limit`; a redeposit that fits still replaces. A brake bounds one account's ledger, not a fetch: a fetch reads the stored cells, never the ledger. The only cap on reading is the fetch cap for accounts with no access (see Access).
- **A batch past one request goes in parts.** One request carries 1 MiB at most. The client cuts a larger batch into parts of 512 KiB (never inside a character), in order, each sent with `oars-part: n/m` and `oars-batch: <SHA-256 of the whole batch>`. The server holds the parts in `deposit_parts` (outside the ledger), answers 202 `pending` until all `m` are held, then checks that their join hashes to `oars-batch` (400 `part_mismatch` otherwise, and the parts are dropped) and stores one deposit by the path a whole one takes, so its refusals (422 `closed_vocabulary`) and its netting are the same. Parts may arrive in any order. A part sent again lands on its own row and changes nothing; once the deposit has finished, any part of that batch is answered 201 from the stored marker, with no second write and no second count. The join is refused past 1,800,000 bytes (413 `too_large`), because one D1 row holds 2,000,000 bytes at most and the skeleton and its extensions bag share it: a session larger than that needs its skeleton stored across rows, which is not built. At most 8 parts make a batch (the client's 512 KiB parts make 4 at most for a join the cap allows). Staging is bounded by the same cap: a part that takes the held bytes past 1,800,000 is refused at once with 413 `too_large` and the batch is dropped, so an unfinished batch never holds more than that. A part that names another count than the ones held writes nothing: the batch is dropped and the part gets 400 `bad_part`, so the client's next full send starts clean. Sending a batch is still disabled in this release; the parts are proved against the Workers runtime.
- **A frame's day is real and not ahead of the server.** A day that is not a calendar date, or is later than tomorrow UTC, gets 422 `closed_vocabulary` naming the field, since the latest day of a bundle's own bucket sets its `asOf` (its version-free cells can be later).

## What a bundle serves

A bundle's reads are derived from the stored cells with the code a local store runs (`packages/pool/src/derive.ts`), except the (name, `platform`, `shell`) read of `fit`, which runs only in the bundle: a local store writes those cells but no local read answers from them. A read is served when at least one of its cells clears the floor and is not withheld (below), and it cites and counts only those.

**What a served number counts.** The reads run over the bundle's cells at or above `k_cell` accounts and no others (`readsOf`, `derive.ts`), so every count, sum, and denominator a read holds is a sum of served cells: its `n` and `failed`, a share's denominator (`tool-day`'s `value.steps`, a `live` read's `of` and its baseline, and a `fit` sum across weeks), and a sum across models. A sub-floor cell is in no `n`, no denominator, and no `inputs`, so no two numbers of one family's reads at one grain, set against each other, show the size of a sub-floor cell. A week cell and the day cells of its days count the same steps, as do a shape cell and the named cells of its actions, so across grains the bundle withholds one more part (`complement.ts`): where a served week has a sub-floor day it also withholds its smallest served day (fewest accounts, ties to the earliest day) from `cells` and the reads, and where a served shape has a sub-floor name it also withholds its smallest served name; the week and the other parts stay, and the rule repeats over both pairs until it adds nothing. The week less its served days is then a sum over at least two days, one of them at or above the floor, which no reader can split; a week with no sub-floor day keeps every day. A tool-day or `live` read's `steps` or `of` is the day's steps over the served tools only, so a tool served at 5 accounts reads against the served tools' day and not the whole day's. `asOf.pool`, `asOf.day`, and `weeksSinceLast` come from the served cells alone, so a sub-floor cell's size moves none of them, while the first sub-floor part of a family withholds one more part, which a reader sees. The (name, `platform`, `shell`) cells keep the rule of `ENVIRONMENT_CELLS` (every part served or the total is not) and are also dropped when their (motif, grain, day, exposure) matches a withheld bucket cell. Flag and pull cells overlap their program cells, so they are neither parts nor triggers of the shape/name rule. The local read has no floor and sums every cell it holds.

The pool serves all nine order 1 families, `recovery` included. `fit`'s call-shape method stays out, because a skeleton does not carry `keys`; `recovery` serves only the edge a skeleton can carry (below), not the signature record, because a skeleton has no error row, `sigHash`, or `outcome`.

A numbered request never reaches them. The route therefore takes the word `unknown` as the version (`/bundle/cursor/unknown/<vocabVersion>`, `oars pool fetch --harness cursor --harness-version unknown`): `bucketPrefix` is `cursor/unknown/`, the same derivation, the same `k_cell` floor, the same withholding rules, and the same environment cells as any bundle, and the payload's `harnessVersion` is `unknown`, which `verifyBundle` checks like a number. It serves nothing a numbered bundle would not: a request for a harness that does record a version finds no cell of its own under `unknown` (only sessions that recorded none land there). `served-families.test.ts` pins the families of that bundle. **Known limit (t849's, unchanged):** the fallback does not widen a cell. A harness whose few accounts split across models fills each `unknown/<model>` cell separately, so the fallback serves less than the number of its accounts suggests, and the version-free total beside it is withheld by the same rule as above.

`served-families.test.ts` pins the limit at the wire: a skeleton whose tool carries `keys`, `sigHash`, or `outcome`, or that carries error rows, keeps that field in the extensions bag and nowhere a read can reach, and a five-account bundle holds a tool-day read and a recovery read but no call-shape read; the recovery family is withheld at four accounts and served at five.

## Wire field register

One row per field a format 3 batch carries (section 17 of the direction conclusion, rules 2 to 4): no row, no field. `consumer` is the read family that reads the field today, or the future read that is stated for it. The class is the field's projection class at format 3: `clear` (a closed or public list, or a hash the client made that the pool uses only as an opaque key), `thresholded` (served once a public floor of clusters report the same value; `PUBLIC_FLOOR` is planned, `t888`), `hashed at ingest` (the pool hashes the value on arrival under a key it holds; `INGEST_HASH_KEY` is planned, `t881`), or `raw tier` (stored, never served); no skeleton field is `raw tier`. Neither constant exists in code yet. A long-tail name is `private` on the wire until `t881` moves the client's projection to the server, so its thresholded class is the stated one. `Re-derives` says whether a deposit of the field can be built again from the local store (`raw/`) while the store exists, with new consent. A field marked `no` is a constant of the client build.

`Bytes` is measured, not estimated: the canonical bytes of one invented session (`REGISTER_FIXTURE` in `packages/cli/src/sessions/pool-wire-register.test.ts`: one transcript with its frames, one prompt, one call, four steps, one delta), summed over every place the field occurs. A container's bytes are its braces, brackets, and commas, and its members' bytes are theirs, so the column adds up to the batch less 9 bytes of top-level braces, commas, and newline (2,976 bytes in all; the test pins both figures). A real session holds more steps, so read the column as the shape of the cost, not its size. `pool-wire-register.test.ts` parses this table and fails on a field the client emits with no row, a row for a field it does not emit, and a bytes figure that no longer matches the fixture.

An unknown field name a client sends lands in the `extensions` bag of the deposit, not in a row. The bag is ledger class, kept and never served, joined to no read, and left out of every bundle (`wire-contract.test.ts`). A field, a literal, or a value over 8 KiB (`MAX_EXTENSION_BYTES`, as JSON) gets a 422 `too large` at its path, whatever its kind; a newer client's larger structure belongs in a new format version, not an extension.

## The raw tier

A locally redacted raw transcript can be sent to the pool, stored, and not served. It is the one place the pool holds content, so the rules are narrow.

**What it takes.** An account that is signed in, has accepted the covenant in force, and has given **raw consent**, which is its own answer, apart from the covenant (the client asks it separately; nothing in the covenant records it). Every request states, as headers, the redaction version the transcript went through (`oars-redaction-version`) and the capture version (`oars-capture-version`), each 1 to 64 letters, digits, dots, dashes, or underscores, and the first request of an account also states `oars-raw-consent: granted`. The pool records the first `granted` (`accounts.raw_consent`) and a later request need not repeat it; a request that states anything else is refused even when consent is held. The covenant check is the deposit's: with `COVENANT_VERSION` unset every raw route is 403 `deposits_closed`.

**What it refuses**, each by name: before any byte is read, 401 `unauthorized`; 403 `deposits_closed`; 403 `covenant_not_accepted`; 422 `redaction_required` (no redaction version, or one that is not a version); 422 `capture_required`; 403 `raw_consent_required`; 503 `not_configured` when the `RAW` bucket is unbound; and once the part is read, 413 `too_large` for a part over 1 MB (unread when it declares its length) and 422 `empty_part`. A completion is also refused 422 `hash_mismatch` when the parts do not hash to the SHA-256 in the path (see The upload).

**The upload.** A transcript goes in parts of at most 1 MB, the cap a deposit has, keyed by its SHA-256 (64 lowercase hex):

- `PUT /v1/raw/:sha256/parts/:n` stores part `n` (1 to 999,999) under `staging/` in R2. A part sent again replaces itself, so a client retries a lost answer freely. For an object that already stands it writes nothing and answers 200 `{ok, stored}`, after reading the part (an answer over an unread body resets the connection on Windows).
- `POST /v1/raw/:sha256/complete` takes `{parts, bytes}`, joins parts 1 to `parts` into one object `raw/<account>/<sha256>`, checks that they hold exactly `bytes` and hash to `:sha256`, and writes the ledger row. 409 `part_missing` names the first part that never arrived; 422 `bytes_mismatch` names the count it found; 422 `hash_mismatch` (field `sha256`) means the parts hash to something else; each leaves no object and no row, and the parts stay for the client to send the rest and complete again. A completion sent again answers 200 `{ok, stored}`.

R2 will not complete a multipart upload from parts under 5 MiB (the last excepted) and wants the others equal, so a 1 MB request cannot be an R2 part. The pool stages each request as its own object, then assembles through an R2 multipart upload, cutting the stream into equal 5 MiB parts; memory holds one 5 MiB buffer and one staged part. The staged parts are deleted once the row is written; parts numbered past the `parts` a completion names are not, and are left to the lifecycle rule. A transcript that is never completed leaves its staged parts behind: the deploy steps give the bucket a lifecycle rule that expires `staging/` after 7 days.

**The effective ceiling.** There is no cap on a transcript, but one `complete` does all its work in one Worker request: one R2 `get` per staged part (1 MB each), one `uploadPart` per 5 MiB, the multipart create and complete, and one batched delete (R2 takes at most 1,000 keys in one). The Worker's per-request subrequest limit (1,000 on the paid plan) and CPU time (the hash and the copy) therefore set a practical maximum, roughly several hundred MB by subrequest count, and CPU may bite sooner. Neither is measured against production R2; Miniflare enforces neither. The deploy steps say to verify it before the raw tier opens.

**A ledger row, never the bytes.** D1 holds one `raw_objects` row per object: account, SHA-256, bytes, capture version, redaction version, and the time. The bytes are only in R2. The row is ledger class: migration `0011_raw_tier.sql` gives it the never-delete trigger of `deposits` and `contributors`, and `ledger.test.ts` guards it. `raw.test.ts` dumps every D1 table after an upload and fails if the transcript is in any of them.

**It serves nothing in v1.** No route returns a raw byte, a hash, or a count of what an account holds, and the answers to the two uploads carry `ok`, `stored`, or `part` and nothing else. No bundle, read, or `derive` touches the bucket or the table. `raw-serves-nothing.test.ts` fails if any file but `raw.ts` names the binding or the table, if `raw.ts` lists or heads the bucket or builds a response of its own, and if any other method or path under `/v1/raw` answers anything but 404. The raw tier is not licensed or published either: serving it would need a new decision and a change to that test.

**No limit on contribution.** There is no per-account cap on raw objects or bytes, and `MAX_DEPOSITS_PER_ACCOUNT` and `MAX_DEPOSIT_BYTES_PER_ACCOUNT` do not apply to it (`raw.test.ts` sets both to 1 and uploads three transcripts). Storage figures belong to telemetry.

**What the pool cannot check.** It cannot verify redaction: it takes the client's word, in the redaction version it records, that the transcript was redacted and its hosts masked before it was sent, and it runs no scanner over the bytes. It does check the hash: `complete` runs SHA-256 over the staged parts as it assembles them and refuses 422 `hash_mismatch` unless the digest is the one in the path, so the ledger's hash is the object's own. Redaction, host masking, and the raw consent prompt are the client's (t884).

| `POST /v1/telemetry` | Product telemetry from the CLI (docs/telemetry.md), not a deposit: it needs no covenant and no sign-in, and it is answered with deposits closed. Takes `{install, events}`: `install` is the CLI's random UUID, `events` is 1 to 250 objects (Analytics Engine's per-request write limit), each with a `type` of 1 to 64 characters. Answers 201 `{ok, kept, indexed}`. 400 `invalid_telemetry` names the first bad field (`body`, `install`, `events`, `events[2]`, `events[2].type`); 413 `too_large` past 1 MiB; 503 `not_configured` with no `TELEMETRY` bucket and 503 `telemetry_unavailable` when R2 fails (nothing is indexed then, so the resend does not count twice). See "Telemetry storage". |
| `GET /bundle/:harness/:harnessVersion/:vocabVersion` | A signed bundle for one harness at one version, or at `unknown` for a harness that records none (the harness is a required segment, since a number does not name its harness and two harnesses can share a numbered bucket; 400 `unknown_harness` for a name off the list, 400 `harness_required` on the old two-segment path): `{payload, signature}`, Ed25519 over the payload's exact bytes. The request names no family. It holds the cells for that version's bucket (`unknown`: the `<harness>/unknown/<model>` cells of sessions that recorded no version, under the same `k_cell` floor and the same derivation) and the reads the pool derives today (fit without call shape, cost, change, live, adoption, method, next-step, tool-day, and recovery; reads above order 1 are not served), the version-free (name, `platform`, `shell`) cells that clear the check under "What a bundle serves", plus rule 3's strata cells (language, framework, repo size, and the two pairs, language with its share and repo size with its explore bucket) counted pool-wide. 401 with no valid credential (`harness_required` is answered with or without one, since the old path is named before any credential is read), 400 `unknown_harness_version` (anything but a public number or the exact word `unknown`) or `unknown_vocab_version` by name, 404 for any other path. The old `/v1/slices/:stack` route is gone. |

## Bindings

All of these are set at the deploy, never in `wrangler.jsonc`, which holds no account id, resource id, secret, route, or domain. An unset one refuses the route that needs it.

| Binding | Holds |
|---------|-------|
| `DB` | The D1 database. |
| `PSEUDONYM_KEY` | The key accounts are hashed under. Changing it makes every account new. |
| `BUNDLE_SIGNING_KEY` | An Ed25519 private key as a JWK. Clients pin the public half, so changing it fails their next login. |
| `RAW` | The R2 bucket for the raw tier, bound by name in `wrangler.jsonc` (`oars-pool-raw`). Unset refuses the raw routes with 503 `not_configured`. |
| `COVENANT_VERSION` | The covenant in force. Leave it unset until the covenant is published. |
| `FETCH_CAP` | Optional. Bundles one account may fetch per ISO week; a value that is not a positive whole number is 1. |
| `MAX_DEPOSITS_PER_ACCOUNT` | Optional, off by default. An operator's brake on the rows one account may hold; unset, empty, or not a positive whole number is no limit. |
| `MAX_DEPOSIT_BYTES_PER_ACCOUNT` | Optional, off by default. An operator's brake on the stored bytes one account may hold; unset, empty, or not a positive whole number is no limit. |
| `TELEMETRY` | The R2 bucket `oars-telemetry`, the record of every telemetry batch. Named in `wrangler.jsonc`, which binds it by name. Unset, `POST /v1/telemetry` answers 503. |
| `TELEMETRY_EVENTS` | The Analytics Engine dataset `oars_telemetry`, the index reads come from. Named in `wrangler.jsonc`. Unset, batches are kept and not indexed. |

## Telemetry storage

`POST /v1/telemetry` keeps every accepted batch twice, for two jobs.

**The record is R2.** One object per batch at `telemetry/<YYYY-MM-DD>/<uuid>.json`, the day the batch arrived (UTC). No lifecycle rule sets an expiry, matching the raw tier, because Cloudflare's limits page gives Analytics Engine three months of retention and the record must outlast that. The object is `{received, account?, batch}`: `received` is the arrival time, `account` is the pseudonym of the credential the request carried (absent when it carried none, or one the pool does not know), and `batch` is the request body exactly as it came, so an event type or field this server has never seen is kept. No address, user agent, or other header is read, so none is kept. The route does not join a batch to a deposit, and a batch reaches no bundle.

**The index is Analytics Engine.** Each event becomes one data point, written after the object is kept. A failed write costs the index and never the object (the answer says `indexed: false`). The layout is fixed, because a read names columns by position:

| Column | Holds |
|--------|-------|
| `index1` | the install id (also the sampling key) |
| `blob1` | event `type` |
| `blob2` | `cli`, the oars version |
| `blob3` | `os` |
| `blob4` | the command path, space-joined (`data.path`) |
| `blob5` | `data.errorClass` |
| `blob6` | the account pseudonym, or empty |
| `blob7` | the flag names, comma-joined (`data.flags`) |
| `double1` | `v`, the schema version |
| `double2` | the event time, epoch milliseconds (0 when unreadable) |
| `double3` | `data.durationMs` |
| `double4` | `data.exitCode` |

A field an event does not carry is an empty blob or 0, so a read of `command` events filters on `blob1`. A blob is cut at 128 characters in the index; the record keeps the full text. Only strings and numbers of the known fields are indexed, so an event type this server has never seen reaches the index as its envelope.

## Tests

`packages/pool` runs the bundled handler and its D1 store under the Workers runtime through Miniflare, in-process, with a stub sign-in provider (its profile route for the Worker, and its device and token routes for the CLI's own `fetch`), so it needs no Docker, account, or network. `full-run.test.ts` drives the real CLI commands against it over a local socket.

## Known gaps

**Bundles read at different times or versions.** Withholding is decided within one bundle, from the cells it holds. Two bundles of one harness version fetched at different times can still be set against each other: a deposit between them can change which day is the smallest served, so the first withholds one day and the second another, and a reader who holds both has each day's number and the week's. Another version's bundle can still serve an environment cell this bundle dropped, so bundles of different versions can also undo withholding by subtraction.

A live read's baseline is not traceable through lineage: the floor counts only the sliced day's cells, so the read cites those and states `value.baseline` from cells it does not cite (cells at the floor, like every other number a bundle serves).

`POST /v1/login` is unauthenticated and, in the Worker, unlimited: the rate-limit rule in deploy step 6 is what bounds it, so the pool must not be deployed without that rule.

`POST /v1/telemetry` is unauthenticated and, in the Worker, unlimited, and each request writes one R2 object of up to 1 MiB that never expires: the same rate-limit rule in deploy step 6 is what bounds it, so the pool must not be deployed without that rule.

The pool does not check that the provider token it is sent was issued to the Many Oars client ID, so a token any other app holds for a person would sign in as that person; that is not acceptable once the pool opens, and it closes before deposits open.

## Where D1's own limits bind

With no cap on contributing, the only ceilings left are D1's. Cloudflare's page (`developers.cloudflare.com/d1/platform/limits`) could not be reached when this was written, so the figures below are from memory and **unverified**: a database holds 10 GB on the paid plan (500 MB on the free plan), and a row (a string, a BLOB, or the table row) holds 2,000,000 bytes.

- **A row.** The 1,800,000-byte join limit above is that row limit less the room for the row's small columns. By the fixture's numbers (about 275 bytes of skeleton for each tool call: a 5,000-call session is 1,376,219 canonical bytes, `parts.test.ts`) a session of about 6,500 tool calls is the largest one row holds. A longer session is refused with 413 until its skeleton is stored across rows or in R2.
- **A database.** The ledger holds about 1,800 bytes for a one-prompt, two-step session (`ingest.test.ts` pins the fixture at 1,811) and about 275 bytes for each tool call beyond it, so 10 GB holds roughly 5.5 million minimal sessions, or about 100,000 sessions of 100 KB. The `cells` and `strata` rows add to this and are shared across accounts. These are the numbers that make a migration off a single D1 database the trigger to plan for, at around half of the database (about 5 GB), well before the write fails.

## Deploy steps

Nothing has been deployed or provisioned. Each step is owed once, by the account holder, in this order:

1. Create a GitHub OAuth app with device flow enabled, and note its client id. The CLI reads it from `OARS_GITHUB_CLIENT_ID`; the pool holds none of it.
2. Create a Google OAuth client of type "TVs and Limited Input devices", and note its id and secret, which the CLI reads from `OARS_GOOGLE_CLIENT_ID` and `OARS_GOOGLE_CLIENT_SECRET`.
3. Run `wrangler d1 create oars-pool` and `wrangler r2 bucket create oars-telemetry` in `packages/pool`. The config binds both by name, so commit no `database_id`. Set no lifecycle rule on the telemetry bucket: the batches are the record and do not expire. The Analytics Engine dataset `oars_telemetry` is created by the first write; if the account has not used Analytics Engine, turn it on in the dashboard first. Then create the raw tier's bucket the same way: `wrangler r2 bucket create oars-pool-raw` (the name `wrangler.jsonc` binds), and give it a lifecycle rule that expires objects under the `staging/` prefix after 7 days: `wrangler r2 bucket lifecycle add oars-pool-raw staging-expiry staging/ --expire-days 7`. Keep the raw bucket private: it takes no public domain and no `r2.dev` URL. Before the raw tier opens, verify the raw-tier ceiling against production R2: upload and complete a transcript of a few hundred MB and read the subrequest and CPU figures (see The effective ceiling).
4. Run `wrangler d1 migrations apply oars-pool --remote` in `packages/pool`.
5. Run `wrangler secret put` for `PSEUDONYM_KEY` (32 random bytes) and `BUNDLE_SIGNING_KEY`, and leave `COVENANT_VERSION` unset.
6. Before `wrangler deploy`, add a Cloudflare rate-limiting rule on `/v1/login` and `/v1/telemetry` (in the dashboard, or with the rulesets API). Neither route takes a credential. Each `/v1/login` call spends one read of the provider's profile route from the Worker's address, and each `/v1/telemetry` call writes one R2 object of up to 1 MiB that is never deleted, so without a rule anyone can drive that spend and that storage. The Worker holds no limiter of its own.
7. Run `wrangler deploy` in `packages/pool`, confirm it bound the database from step 3 rather than creating another, and attach the custom domain in the dashboard or with `--domain`. Only `--dry-run` has been exercised.
8. Publish the covenant, and only then run `wrangler secret put COVENANT_VERSION`, which opens deposits.
