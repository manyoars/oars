# The pool

The pool is an optional server that accounts sign in to, deposit closed-vocabulary session skeletons to, and fetch cells and reads from. Local capture, recall, and reads need none of it: nothing leaves your machine unless you sign in and run `oars pool fetch`, and `oars pool deposit` only writes a batch to a local outbox (sending a batch is disabled in this release). The code is in `packages/pool`, a Cloudflare Worker over one D1 database.

## Commands

Every command takes the server from `--server <url>` or `OARS_POOL_URL`. There is no default, and plain http goes only to localhost. The server is an origin with no credentials, path, or query, and a redirect is refused, so a token or a skeleton cannot be moved elsewhere.

| Command | What it does |
|---------|--------------|
| `oars pool login --provider github\|google` | Runs the provider's device flow (RFC 8628) itself, with the smallest scope that names the account (Google's `openid`, GitHub's none), then sends the provider's token to the pool once and saves the pool's own token at `<store>/pool-accounts.json` (mode 0600), pinning the pool's signing key on first login. No harness token is read. Every request, to the provider and to the pool, prints to stderr before it is sent: the request line, every header, and the body. The device code, the provider's token, and the pool's credential print as `<credential: n bytes>` wherever they appear; `client_id`, `scope`, `grant_type`, and Google's `client_secret` print as they are. It never signs in on its own: when the credential expires, deposits and fetches stop until you run `login` again. The client ID and secret come from the environment (below); one that is unset stops the command before it sends anything, and names what is missing. |
| `oars pool deposit [--send <hash>] [--accept-covenant <version>]` | Writes a batch to the outbox for every session that passes both session gates and has ended, and stops: nothing is sent, and only counts print. A session has ended when no transcript of it, main or subagent, has gained a line for `session_idle_hours` (6 hours), judged by the later of its last capture and its raw file's last write; one inside that window builds nothing, is counted as `notEnded`, and has any batch of it from an earlier `deposit` withdrawn. The gates run before any projection does: the folder allowlist (`oars sessions deposit --allow`) and the exclusion check (a listed term in a main or subagent transcript fails it, and so does a session with no raw to scan). A session that fails either is counted by reason and never built; the count never names the term or the folder. A batch is canonical JSON (sorted keys, no optional whitespace, UTF-8) under `<store>/pool-outbox/<hash of server>/`, in a folder named for the vocabulary version, the batch's field list, and the skeleton format, one file per session; a batch built under an older version, field list, or skeleton format is discarded, not sent. A session that no longer passes a gate, has not ended, or is no longer in the store has its batch removed on the next `deposit`, and the removals are counted. It refuses with `vocabulary_expired`, and sends nothing, when this client is more than 30 days past its vocabulary snapshot. `--send <hash>` takes the SHA-256 that `outbox` printed and accepts only a batch that was shown and has not changed on disk since, and it reads and hashes the batch again just before the request. In this release sending is disabled: `--send` runs those checks, then stops with `sending_disabled` (exit 5) and no request, because it waits on the pool covenant. There is no flag, variable, or setting that turns it on, and `--accept-covenant` without `--send` is a usage error; with sending disabled it accepts nothing. When it is on, a 409 `deposit_conflict` (another deposit of the same session landed first) is sent again, up to three attempts in all, with the same bytes. |
| `oars pool outbox [--explain]` | Prints each batch exactly as it would be sent: the request line, every header, and the body, with the bearer credential as `<credential: n bytes>` and nothing else masked, then the batch's SHA-256, and records that this hash was shown. It sends nothing, and it is a separate command from `deposit`: there is no automatic mode. `--explain` adds each field's rule, and a field with no rule fails the command rather than print blank. `oars sessions verify` reports how many batches, on any server, were built under an older vocabulary, field list, or skeleton format. |
| `oars pool fetch [--harness <name>] --harness-version <version>` | Fetches that harness's signed bundle at that version, verifies it against the pinned key, and keeps it at `<store>/pool-replica/<hash of server>/<harness>/<version>.json`, still signed, so a fetch for one harness never overwrites another's. A bundle that fails verification, or is for another harness or version, is refused and not written. The version must be a public one; nothing is keyed by stack. `--harness` takes one of `claude-code`, `cursor`, `codex`, `copilot`, `gemini`, `grok`, or `vscode-copilot`; any other name is refused before anything is sent. With no `--harness`, it fetches the harness your local store holds the most sessions of (`claude-code` for an empty store or a tie), and says so on stderr before it sends: `No --harness given: fetching cursor, the harness your local store holds the most sessions of (3 of 4). Pass --harness <name> to fetch another (claude-code, cursor, codex, copilot, gemini, grok, vscode-copilot).` It reads counts only, and none leaves the machine: the request names the harness and the versions, nothing else. Before it sends, it prints the request line and every header to stderr, with the credential as `<credential: n bytes>` and nothing else masked. It keeps the bundle's `ETag` beside it and sends `If-None-Match` next time: a 304 keeps the bundle and says it is unchanged (exit 0). A 429 (the weekly fetch cap) keeps the bundle, says in words when to try again from `Retry-After` (or that the pool did not say), and exits **10**, the code `fetch` alone uses, so a schedule can tell a cap from a failure. |

## Sign-in settings

The OAuth apps are the operator's to create, so the client reads their values from the environment. None is secret: every copy of the CLI would ship them, and Google's device flow requires its `client_secret` at the token route.

| Variable | Holds |
|----------|-------|
| `OARS_GITHUB_CLIENT_ID` | The client ID of the Many Oars GitHub OAuth app, with device flow enabled. |
| `OARS_GOOGLE_CLIENT_ID`, `OARS_GOOGLE_CLIENT_SECRET` | The client ID and secret of the Many Oars Google OAuth client, of type "TVs and Limited Input devices". |

## What the server enforces

- **Deposits are closed by default.** With no `COVENANT_VERSION` binding, every deposit gets 403 `deposits_closed`. Once one is set, an account must have accepted exactly that version, or it gets 403 `covenant_not_accepted`, and a new version asks again. Reads and `fetch` are not affected.
- **Closed vocabulary.** A skeleton holding an unknown field or a value outside the vocabulary gets 422 `closed_vocabulary` with the field named, and nothing is stored. What is stored is the parsed skeleton, not the text that came in.
- **The skeleton form (format 2).** A step carries a shell call's projected `program`, `sub`, and `flags` in place of the joined shell command a step used to carry: a program is a curated-list member or `private`, a `private` program holds no subcommand, flag, or pull, a subcommand outside the curated lists, and a flag that is neither on them nor a single letter, are dropped, and a program only the client's snapshot lists goes as `private`. Every other name the pool has no row for (an MCP server, skill, host, pull name, and a native tool name) goes as `private` too, never as `<literal>`, which the parser refuses at those places. Usage, `errors`, `wallSec`, and a step's `tokens` and `ms` are Section 7 buckets, never exact counts; the one exact time is `durationMs` per tool step. A transcript and a prompt still carry their `frame` (each member has a Section 1.2 row, and the bucket key and the strata read it); only the shell step's joined command went. `deltas` is on the form and holds the batch's local delta entries, if any (see Local deltas); an entry outside its field's row is refused. The exact-count form (format 1) is refused with 422 naming `format`; nothing is migrated. Cells count a bucketed value as the bucket's lowest value, so a cell's `tokens` and `durationMs` are lower bounds. The cell computation is one module (`cell-increments.ts`) that the pool's ingest and the client's local read both call. A step's calls and a prompt's place are positions in the batch, not the log's numbers: tool `n`, prompt `index`, a step's `seg` (its place in its call, which the server rebuilds from position), a step's `edges`, and a transcript's `spawnedIn` are not sent, and a step's `parent` is the spawning call's position in the main run, sent only for a subagent the main run spawned. A nested spawn (a subagent that spawns one) sends no link at all, never a wrong one; this is a limit, not an oversight. `usage.thinking` is a token count and goes as the `tokens` bucket like the other usage fields. A cell never holds a list longer than one: a motif keys on a shell step's program and subcommand, and each flag and each pull is its own one-step cell (spec rules 1 and 2), so a step with two flags makes two flag cells and one program cell.
- **Two planes.** A deposit writes its parsed skeleton and its deltas (the ledger column still holds `[]`: see the local deltas bullet below) to the ledger (`deposits`), and, in the same transaction, its cell increments to the index: `cells`, `motifs`, and rule 3's `strata`, each cell's `clusters` a held count. A `contributors` record per (cell or stratum, account, UTC day) tells a returning cluster from a new one, so only a new one raises a count. The ledger is meant to expire (not built yet); the index does not, and a bundle is read from the index alone (`packages/pool/src/stored.ts`: three statements whose rows grow with the cells, not with deposits). Deleting a batch's ledger rows leaves every served cell, the bundle's bytes, and its ETag as they were. A session sent again adds only the difference to its earlier batch. A large batch of varied steps runs its cell JSON to about four times its skeleton's size, and D1 takes 2 MB in one value, so ingest binds each payload in chunks of at most 1 MB, one statement per chunk, all in the one transaction under the one guard. A cluster that returns after its record expires would be counted again; expiring a record is a later change. Two limits of the stored form stand until a later change rebuilds what they need, and tests pin them: a session sent again over a held row that no longer parses adds its whole batch a second time, since the cells keep that row's increments and there is no parsed batch to take back; and a session sent again that leaves a cell lowers its `sessions` but not its `clusters` or the account's `contributors` record, so four accounts plus one that left still read as five (one record cannot show whether another of the account's batches still holds the cell).
- **Local deltas (`deltas`).** The client compares its own windows and sends what changed, once. `pool deposit` takes the sessions that pass both session gates and have ended, and counts `DELTA_DAYS` (7) windows on a fixed grid from the epoch, so adding, losing, or finishing a session moves no window; a pair of windows next to each other, each with at least `DELTA_MIN_SESSIONS` (5) of them, makes a delta, and the batch of the session that fills the after window (its fifth, in time order, ties by id) carries it. An entry holds a `deltaKind`, a `field`, a `name` or null, a `registry` or null, a `metric`, and a `change`, and nothing else: no session id, root, window date, or exact value. Four fields enter, per the spec's first exception to rule 3: `plugin` as `added` or `removed`, `permissionMode` and `effort` as `changed` (named by the field alone, the most common value of each window differing, so one odd session is not a change and two values off the effort list are no change), and `package` as `removed` (called in the before window and gone by a clean manifest edit, or by a Write that lists the same file without it in the after window; a Read never says a package is gone, since it may show part of a file; a public name with its registry, else `private` with none, and all `private` ones are one entry). A plugin goes as `private` always, since no plugin registry is pinned, and plugins are compared only over the sessions of a harness that records them (Claude Code), with none built when either window holds no such session. The after window is read as its first five sessions, so the entry is fixed when the window fills. `change` is the signed bucket of the move: calls per session in `count` buckets (-7 to 7), thinking per prompt in `tokens` buckets (-11 to 11) for an effort. The parser holds each field to its own row and refuses an entry outside it, and `oars pool outbox --explain` shows a row for each field of an entry.
  **Once only.** A delta is marked in `deltas-sent.log` in the outbox folder (a hash of the account, the entry without its `change`, and the index of its after window on the grid; the filler session is not in it, since which session fills a window can change from one deposit to the next, while the index cannot) after the batch that carries it is written, never before: a deposit that stops first builds it again. A later deposit builds no delta it has marked, so a session rebuilt under the same key replaces its batch with one that carries none. **Limit:** a batch that carried a delta and was never sent is replaced by that rebuild without it, so the delta is lost; the mark is written with the batch, not at send time, because sending less beats sending wrong and nothing is sent to a real pool yet. **Limit:** the public package list is held by bare name, so `pypi:typescript` goes as the public name `typescript` with its registry until the list is held per ecosystem. Also not built: an `upgraded` delta for the harness version, rule 4's "pool neither when both changed", and the batch's summary `exposure` (no deposit reads an exposure tag yet). The Worker parses an entry and keeps it inside the stored skeleton, but derives no delta cell and its `deposits.deltas` column still holds `[]`; the weekly limit on one delta for each cell is the pool's, not built here.
- **Cell grain and effort (rules 3 and 6).** A cell is keyed on the UTC week (`grain: week`, `day` the Monday), except a `live` cell, which stays at UTC day (`grain: day`) and holds none of rule 3's bound fields. Each read answers from one grain and filters the other out, so adoption and change state weeks (`firstWeek`, `lastWeek`, `weeks`, `weeksSinceLast`), never days. `effort` is in no cell key: it is recorded only as the (`effort`, `thinking` bucket) cell, which joins no `model` or `harnessVersion`, so `fit` and the interaction read no longer slice by it. Migration `0008_cell_grain.sql` adds the grain column; nothing is deployed, so it moves no data. A local `cells.jsonl` written before the grain has no `grain` field, fails the stored-cell check, and is derived again from the store the next time a pool is built or served. On the 3,400-step test deposit a batch counts 784,584 bytes of skeleton and 11,139 cells (3,241,663 bytes of cell JSON, 4.13 times the skeleton) and stores 784,586 bytes against the account's 64 MB, so about 85 such batches fit before the byte limit binds. A session with a shown recall derives different local cells from its deposit, because a deposit is built from the skeleton, which has no recall graph, so the recall's step and exposure appear only in the local read.
- **Pseudonymous accounts.** The pool never calls a provider to start or poll a device flow. It takes the provider's token once, reads the subject from the provider's profile route, hashes it under `PSEUDONYM_KEY` (which the database never holds), and discards the token. No email, login, provider id, or provider token is stored, and the pool holds no OAuth value. A login also deletes the token rows past their expiry.
- **Five accounts to a read.** A read is served only at 5 or more clusters (`K_CELL` in `packages/pool/src/derive.ts`, the spec's proposal, which a later decision may move), and a cluster is an account, so one account's many sessions count once. A cell's `clusters` is its held count of accounts, and a read's is the largest held count among the cells it cites, with no union over accounts: the fetch path reads no per-account record, so five accounts in five different weeks serve no read, since each week's cell holds one (a later change brings held counts for a key's `n` and `c`). Five accounts on five days of one week share each week cell and serve the week reads at 5 clusters, and no `live` read, since a `live` cell is one day. A cell served on its own needs 5 accounts in that cell, and a strata cell needs 5 accounts pool-wide. A `live` read cites only the sliced day's cells, so its floor counts the clusters held on that day and never those in its seven-day baseline; the baseline takes the same floor on its own, and under it `value.baseline` and `value.ratio` are `null`.
- **A fetch cap.** An account without access may fetch `FETCH_CAP` bundles (default 1) per ISO week, counted per account and not per harness or harness version. Past it the pool answers 429 `fetch_cap` with `Retry-After` in seconds to the next Monday 00:00 UTC, before it reads the pool. The count is one atomic statement, and a count from an earlier week is dropped. A fetch that fails after it spent gives the spend back, since the account received no bundle. An account with access is not capped.
- **Access.** The `access` record is null, `pending`, or `standing`, and only a counting batch sets it: ingested at tier committed or higher, or at `skeleton` when every transcript's harness writes no raw file (Cursor), with one prompt and one tool step over the batch, subagents folded in, and at least one cell increment written over the row held now (a batch sent again unchanged writes none); an ingest that writes none leaves the flag and the batch's date alone. It is `pending` while it rests on batches inside `ledger_days` (90), clears when every one falls to `none`, and is `standing` once one has stood the 90 days. A resend that still counts keeps a batch's first `counted_at`; one that no longer counts clears it, and the flag falls if no counting batch is left. A claude-code batch with a prompt and a tool step now lifts the cap, because the batch carries its roots and is written at `committed` (the next row).
- **The tier of a batch.** Ingest writes the batch's own tier, on a first deposit and again on a resend (`tier = excluded.tier`): the lowest of its transcripts', subagents folded in. A transcript is `skeleton` when its harness writes no raw file (Cursor), `none` when its root cannot be real (no leaves under any hash but the SHA-256 of no bytes, or that hash over leaves), else `committed`. A batch with one failed transcript is `none`, takes no part in access, and a resend that fixes it counts again. A batch ingested at `none` still writes its cell increments. Stated limit: a fabricated but well-formed root, and a forged skeleton, still earn `committed` until the raw-file check of a later layer.
- **A 304 spends nothing.** A 200 carries an `ETag` that names the code, the floor, the harness and version asked for, and a generation of the stored cells (triggers on `cells` and `strata` move it in the same write as a change; expiry on `deposits` changes no served cell and moves nothing). An `If-None-Match` that holds it gets 304 with no body, before the spend and without reading the pool, so a conditional request can neither use up a fetch nor force a read. A weakened `W/` tag matches.
- **Two deposits of one session at once.** A deposit replaces the batch the account held under its id, and nets its cells against that earlier row, so two at once would each net against the same row and add the batch twice. The upsert therefore takes the row only if it is still the one that was read (its `ingest` mark), and the other gets 409 `deposit_conflict`: nothing of it is stored, and the client sends it again, which then nets against the winner.
- **A deposit holds something.** A skeleton with no prompt and no tool gets 422 `closed_vocabulary` naming `transcripts`, since only a counting batch lifts the fetch cap (see Access). A forged skeleton that holds invented prompts passes this check, and with a well-formed root it lifts the cap under any harness until the raw-file check of a later layer (see the tier row under Access).
- **Deposits per account.** Past `MAX_DEPOSITS_PER_ACCOUNT` rows (default 20,000) a new session gets 403 `deposit_limit`, and so does any deposit that would take the account past `MAX_DEPOSIT_BYTES_PER_ACCOUNT` stored bytes (default 64 MB). A redeposit of a held session replaces it if the account still fits. They bound one account's ledger, not a fetch: a fetch reads the stored cells, never the ledger. On the test fixture (one session, one prompt, two shell steps) a batch stores 1,196 bytes of skeleton plus 2 of deltas, so the 64 MB default admits about 56,000 such batches and the 20,000-row limit binds first, at about 24 MB; its five cells are shared index rows, and its six `contributors` rows per UTC day of ingest (five cells and one stratum) sit on the ledger outside this budget; an account's distinct days and motifs add `cells` rows that every fetch then reads.
- **A frame's day is real and not ahead of the server.** A day that is not a calendar date, or is later than tomorrow UTC, gets 422 `closed_vocabulary` naming the field, since the latest day sets a bundle's `asOf`.

## Routes

| Route | Answer |
|-------|--------|
| `POST /v1/login` | Takes `{provider, token}`, the provider's access token. Answers `{token, account, expiresAt, signingKey}`: the pool's credential and the public half of its signing key. 400 `unknown_provider` or `missing_field` by name, 401 `login_refused` when the provider does not accept the token, 502 `provider_error` when it cannot be reached or does not name the user. |
| `GET /v1/covenant` | `{version, accepted}`. `version` is null when deposits are closed. Sign-in is optional. |
| `POST /v1/covenant/accept` | Takes `{version}`. 409 `covenant_version` for any version but the one in force. |
| `POST /v1/deposits` | Takes one skeleton, 1 MB at most. A larger one gets 413 `too_large`, unread when it declares its length. |
| `GET /bundle/:harness/:harnessVersion/:vocabVersion` | A signed bundle for one harness at one version (the harness is a required segment, since a number does not name its harness and two harnesses can share a numbered bucket; 400 `unknown_harness` for a name off the list, 400 `harness_required` on the old two-segment path): `{payload, signature}`, Ed25519 over the payload's exact bytes. The request names no family. It holds the cells for that version's bucket and the reads the pool derives today (fit without call shape, cost, change, live, adoption, method, and next-step; recovery, tool-day, and reads above order 1 are not served), plus rule 3's strata cells (language, framework, and repo size) counted pool-wide. 401 with no valid credential (`harness_required` is answered with or without one, since the old path is named before any credential is read), 400 `unknown_harness_version` or `unknown_vocab_version` by name, 404 for any other path. The old `/v1/slices/:stack` route is gone. |

## Bindings

All of these are set at the deploy, never in `wrangler.jsonc`, which holds no account id, resource id, secret, route, or domain. An unset one refuses the route that needs it.

| Binding | Holds |
|---------|-------|
| `DB` | The D1 database. |
| `PSEUDONYM_KEY` | The key accounts are hashed under. Changing it makes every account new. |
| `BUNDLE_SIGNING_KEY` | An Ed25519 private key as a JWK. Clients pin the public half, so changing it fails their next login. |
| `COVENANT_VERSION` | The covenant in force. Leave it unset until the covenant is published. |
| `FETCH_CAP` | Optional. Bundles one account may fetch per ISO week; a value that is not a positive whole number is 1. |
| `MAX_DEPOSITS_PER_ACCOUNT` | Optional. Rows one account may hold. |
| `MAX_DEPOSIT_BYTES_PER_ACCOUNT` | Optional. Stored bytes one account may hold. |

## Tests

`packages/pool` runs the bundled handler and its D1 store under the Workers runtime through Miniflare, in-process, with a stub sign-in provider (its profile route for the Worker, and its device and token routes for the CLI's own `fetch`), so it needs no Docker, account, or network. `full-run.test.ts` drives the real CLI commands against it over a local socket.

## Known gaps

A live read's baseline is not traceable through lineage: the floor counts only the sliced day's cells, so the read cites those and states `value.baseline` from cells it does not cite.

`POST /v1/login` is unauthenticated and, in the Worker, unlimited: the rate-limit rule in deploy step 6 is what bounds it, so the pool must not be deployed without that rule.

The pool does not check that the provider token it is sent was issued to the Many Oars client ID, so a token any other app holds for a person would sign in as that person; that is not acceptable once the pool opens, and it closes before deposits open.

## Deploy steps

Nothing has been deployed or provisioned. Each step is owed once, by the account holder, in this order:

1. Create a GitHub OAuth app with device flow enabled, and note its client id. The CLI reads it from `OARS_GITHUB_CLIENT_ID`; the pool holds none of it.
2. Create a Google OAuth client of type "TVs and Limited Input devices", and note its id and secret, which the CLI reads from `OARS_GOOGLE_CLIENT_ID` and `OARS_GOOGLE_CLIENT_SECRET`.
3. Run `wrangler d1 create oars-pool` in `packages/pool`. The config binds it by name, so commit no `database_id`.
4. Run `wrangler d1 migrations apply oars-pool --remote` in `packages/pool`.
5. Run `wrangler secret put` for `PSEUDONYM_KEY` (32 random bytes) and `BUNDLE_SIGNING_KEY`, and leave `COVENANT_VERSION` unset.
6. Before `wrangler deploy`, add a Cloudflare rate-limiting rule on `/v1/login` (in the dashboard, or with the rulesets API). The route takes no credential and each call spends one read of the provider's profile route from the Worker's address, so without a rule anyone can drive that spend. The Worker holds no limiter of its own.
7. Run `wrangler deploy` in `packages/pool`, confirm it bound the database from step 3 rather than creating another, and attach the custom domain in the dashboard or with `--domain`. Only `--dry-run` has been exercised.
8. Publish the covenant, and only then run `wrangler secret put COVENANT_VERSION`, which opens deposits.
