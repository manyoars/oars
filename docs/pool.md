# The pool

The pool is an optional server that accounts sign in to, deposit session skeletons (a closed list of fields, each value redacted on your machine first) to, and fetch cells and reads from. Local capture, recall, and reads need none of it: no session data leaves your machine until you sign in to a pool server, accept its covenant, and either send a batch yourself (`oars pool deposit --send <hash>`) or let the nightly task send. After you have accepted the pool's covenant, the nightly task sends the outbox with no command: new skeleton batches always, and the redacted raw copies only if you answered yes to the raw prompt (`oars pool raw --consent yes`) and the folder is not set to skeleton only or off. Acceptance is the consent: a machine that has not accepted, has no sign-in, or cannot reach the server sends nothing, and the nightly task never accepts for you. `oars pool outbox` prints what is queued when you run it, but the nightly task builds new batches and sends them in the same run without printing them first. `oars pool deposit` itself only writes to the local outbox, and `oars pool fetch` only reads. Telemetry (`docs/telemetry.md`) is separate: it is on by default, records one event per command (its path, flag names, duration, exit code, and error class) and one per hook fire, recall, deposit, and fetch (counts and closed words only), each with a random install id, the oars version, the OS, and the time, and sends those events to the pool server in `OARS_POOL_URL`, else to the Many Oars pool, which is not deployed yet, so until it is a send fails and the events stay in the spool. The code is in `packages/pool`, a Cloudflare Worker over one D1 database, with R2 buckets for the raw tier and for telemetry, and an Analytics Engine dataset for telemetry.

## Commands

Every command takes the server from `--server <url>`, else `OARS_POOL_URL`, else the Many Oars pool, `https://pool.manyoars.com` (not deployed yet: until it is, a command that reaches it exits 8). Plain http goes only to localhost. The server is an origin with no credentials, path, or query, and a redirect is refused, so a token or a skeleton cannot be moved elsewhere.

| Command | What it does |
|---------|--------------|
| `oars pool login --provider github\|google` | Asks the pool to start the provider's device flow (RFC 8628; `POST /v1/login/start`), prints the user code and the verification URL, opens the link, and polls the pool (`POST /v1/login/poll`) at the interval it names, adding 5 seconds on `slow_down`, until the person approves, the code expires, or the person denies. The pool calls the provider with its own client ID, holds Google's client secret, reads the person with the token it received, and answers its own credential; the provider's tokens and device code never reach this machine. The command saves the pool's token at `<store>/pool-accounts.json` (mode 0600), pinning the pool's signing key on first login. No harness token is read, and the client holds no client ID or secret for any provider. Every request, which goes to the pool alone, prints to stderr before it is sent: the request line, every header, and the body. The login handle and the pool's credential print as `<credential: n bytes>` wherever they appear. It never signs in on its own: when the credential expires, deposits and fetches stop until you run `login` again. |
| `oars pool deposit [--send <hash>] [--accept-covenant <version>]` | Writes a batch to the outbox for every session that passes both session gates and has ended, and stops: it sends nothing itself, and only counts print. A session has ended when no transcript of it, main or subagent, has gained a line for `session_idle_hours` (6 hours), judged by the later of its last capture and its raw file's last write; one inside that window builds nothing, is counted as `notEnded`, and has any batch of it from an earlier `deposit` withdrawn. The gates run before any projection does: the folder allowlist (`oars sessions deposit --allow`) and the exclusion check (a listed term in a main or subagent transcript fails it, and so does a session with no raw to scan). A session that fails either is counted by reason and never built; the count never names the term or the folder. A batch is canonical JSON (sorted keys, no optional whitespace, UTF-8) under `<store>/pool-outbox/<hash of server>/`, in a folder named for the vocabulary version, the batch's field list, and the skeleton format, one file per session; a batch built under an older version, field list, or skeleton format is discarded, not sent. A session that no longer passes a gate, has not ended, or is no longer in the store has its batch removed on the next `deposit`, and the removals are counted. It refuses with `vocabulary_expired`, and sends nothing, when this client is more than 30 days past its vocabulary snapshot. `--send <hash>` takes the SHA-256 that `outbox` printed and accepts only a batch that was shown and has not changed on disk since, and it reads and hashes the batch again just before the request. Then it reads `GET /v1/covenant`: a pool with no covenant published stops it with `deposits_closed`, and an account that has not accepted the version in force stops it with `covenant_not_accepted` (exit 3), both before the batch is read for the last time and with no batch sent. `--accept-covenant <version>` accepts that version first (`POST /v1/covenant/accept`); without `--send` it is a usage error and accepts nothing. A 409 `deposit_conflict` (another deposit of the same session landed first) is sent again, up to three attempts in all, with the same bytes. The nightly task takes the same lock as `--send`, so a manual send and the nightly never send one batch twice; it skips the shown check, because covenant acceptance (and, for raw, the raw yes) is the consent, and it records the hash it sent in `sent.log` in the outbox folder, which `oars pool outbox` and `oars sessions verify` read. It sends each batch and each raw copy once, picks up what a failed night did not send, and records only counts and an outcome word in `pool-nightly.json`. |
| `oars pool raw [--consent yes\|no] [--folder <entry> --mode all\|skeleton\|off]` | The raw prompt: shows it, in plain words, until it is answered. `--consent yes` lets a locally redacted copy of each full transcript be queued in the outbox beside its skeleton on `deposit` (best-effort redaction; see `docs/sessions-store.md`, "The raw copy"); `no`, or no answer, queues skeletons only. `--folder` with `--mode skeleton` queues no raw copy for that folder, and `off` queues nothing from it; a switch stops future queuing and sending only, and what was sent before stays where it went. Nothing is sent by this command; the nightly task sends a raw copy only while the answer is yes. |
| `oars pool outbox [--explain]` | Prints each batch exactly as it would be sent: the request line, every header, and the body, with the bearer credential as `<credential: n bytes>` and nothing else masked, then the batch's SHA-256, and records that this hash was shown. It sends nothing, and it is a separate command from `deposit`. Each batch and raw copy the nightly task already sent is marked `sent: <time>`. Raw copies print as `raw part i/n sha256: <hash> bytes: <n>`, and `--explain` prints their bodies. The nightly task sends what is queued without printing it, so print first if you want to read it before it goes. `--explain` adds each field's rule, and a field with no rule fails the command rather than print blank. `oars sessions verify` reports how many batches, on any server, were built under an older vocabulary, field list, or skeleton format. |
| `oars pool fetch [--harness <name>] --harness-version <version>` | Fetches that harness's signed bundle at that version, verifies it against the pinned key, and keeps it at `<store>/pool-replica/<hash of server>/<harness>/<version>.json`, still signed, so a fetch for one harness never overwrites another's. `pool-replica.ts` is the one reader of that file (`keptReplica`, `sessionBundle`): `pool fetch`, `oars sessions recall`, the MCP tool, and the hooks all read the kept bundle through it, for the session's own harness and version, and a missing, other-harness, or corrupt bundle means local reads only. A bundle that fails verification, or is for another harness or version, is refused and not written. The version must be a public one; nothing is keyed by stack. `--harness` takes one of `claude-code`, `cursor`, `codex`, `copilot`, `gemini`, `grok`, `opencode`, `pi`, or `vscode-copilot`; any other name is refused before anything is sent. With no `--harness`, it fetches the harness your local store holds the most sessions of (`claude-code` for an empty store or a tie), and says so on stderr before it sends: `No --harness given: fetching cursor, the harness your local store holds the most sessions of (3 of 4). Pass --harness <name> to fetch another (claude-code, cursor, codex, copilot, gemini, grok, opencode, pi, vscode-copilot).` It reads counts only, and none leaves the machine: the request names the harness and the versions, nothing else. Before it sends, it prints the request line and every header to stderr, with the credential as `<credential: n bytes>` and nothing else masked. It keeps the bundle's `ETag` beside it and sends `If-None-Match` next time: a 304 keeps the bundle and says it is unchanged (exit 0). A 429 (the weekly fetch cap) keeps the bundle, says in words when to try again from `Retry-After` (or that the pool did not say), and exits **10**, the code `fetch` alone uses, so a schedule can tell a cap from a failure. |
| `oars pool coverage [--org-size <band>] [--repo-visibility public\|private\|unknown]` | Sets the two coverage bands only you can state, in `<store>/pool-coverage.json`, and prints the current values. `--org-size` takes `solo`, `2-10`, `11-100`, `101-1000`, `over-1000`, or `unknown`. Nothing is read from the network, and a band you leave unset goes on the wire as `unknown`. |

## Repo key, coverage bands, and hour

Four frame fields make "the same work" and "who the pool covers" observable. Each is optional on the wire and carries a value only when the client could state one.

- **`repoKey`.** 16 lowercase hex characters: the salted hash of the repository's identity that the store already keeps as `repo` (`docs/sessions-store.md`, "Hashing"), so two clones of one repository, or two harnesses in one, share it under one store's salt. It is on the transcript frame and every frame of its list (not a prompt's frame), and a session whose repository is unknown sends none. The emitter drops any value that is not key-shaped, so a path, a remote URL, or a name never reaches a batch. Cells do not read it.
- **`orgSize`, `team`, `repoVisibility`.** Coverage bands from closed lists: `orgSize` is `solo`, `2-10`, `11-100`, `101-1000`, `over-1000`, or `unknown`; `team` is `solo`, `team`, or `unknown`; `repoVisibility` is `public`, `private`, or `unknown`. `orgSize` and `repoVisibility` are what the operator sets with `oars pool coverage`; `team` is the count of distinct commit authors in the repository's local git log (`git log --format=%aE`, at most 5,000 commits, counted and never sent), one author being `solo`. No network call is made, and anything unread goes as `unknown`. The bands state what the pool can say about its coverage; no read filters on them.
- **`hour`.** The UTC hour of day, 0 to 23, beside the UTC day, on the transcript frame, each prompt frame, and each call frame. It joins no cell.

**The join's limit.** The salt is the store's own, this machine's (`localSalt` in `store.ts`); `accountSalt`, the account-wide salt, is still the open M4 seam. So the key joins one operator's harnesses on one repository on one machine and nothing else: the same account on a second machine gets a second key until the account salt lands, two accounts on the same repository get two keys, and the pool cannot join either. A salt rotation, like a new machine, starts new keys, so batches deposited before and after no longer join. The earlier truth stands, that two accounts' sessions cannot be joined.

| Field | Class | Re-derives from `raw/` | Note |
|-------|-------|------------------------|------|
| `repoKey` | clear (a client hash, per store: this machine's salt) | yes, with the salt | 16 hex characters |
| `orgSize` | clear | no, operator-set | closed list of six |
| `team` | clear | no, read from the repository's local git log at each deposit | closed list of three |
| `repoVisibility` | clear | no, operator-set | closed list of three |
| `hour` | clear | yes, from the timestamp | 0 to 23 |

The large-deposit fixture's session has `repo`, `tsFirst`, and every prompt's `ts` null, so it carries no `repoKey` and no `hour`: the 128<!-- figure:bands --> bytes it gained are the three `unknown` bands on its two frames, 64<!-- figure:bands-per-frame --> bytes a frame. `repoKey` and `hour` were measured on a fixture that holds them (`pool-wire-coverage.test.ts`, three prompts at three distinct UTC hours and two calls each, 3,516<!-- figure:coverage-bare --> bytes of skeleton without either): the key costs 58<!-- figure:key-cost --> bytes (29<!-- figure:key-per-frame --> on each of the two frames, the transcript's own and the list's one call frame, when no prompt carries a timestamp, 116<!-- figure:key-timed --> across the four frames when three prompts carry three distinct hours), and the hour costs 755<!-- figure:hour-cost --> bytes, because each distinct hour among a session's prompts splits its calls onto one more frame of the list, so a session with many prompts across many hours pays one frame per hour it touched (24 at most). Both figures are pinned in that test.

## Sign-in

The pool brokers both providers' device flows, so the client holds no OAuth value. The pool's client IDs are public and sit in `wrangler.jsonc` `vars`; Google's token call needs its client secret, which is a Worker secret and never in the repo.

| Setting | Holds |
|---------|-------|
| `GITHUB_CLIENT_ID` (var) | The client ID of the Many Oars GitHub OAuth app ("Many Oars CLI", org `manyoars`), with device flow enabled. GitHub's device flow needs no secret. |
| `GOOGLE_CLIENT_ID` (var) | The client ID of the Many Oars Google OAuth client ("oars CLI device flow", project `many-oars`), of type "TVs and Limited Input devices". |
| `GOOGLE_CLIENT_SECRET` (secret) | That client's secret, set with `wrangler secret put`. It is sent only to Google's token route, from the Worker. |

A provider whose client ID is unset (and Google, when its secret is unset) refuses `/v1/login/start` and `/v1/login/poll` with 503 `not_configured` naming the binding, and calls nobody.

**The login routes (the contract).** Both are unauthenticated, JSON in and out.

- `POST /v1/login/start` with `{provider}` (`github` or `google`). The pool posts the provider's device-code route with its own client ID (scope `openid` for Google, none for GitHub) and answers `{handle, userCode, verificationUrl, interval, expiresIn}`: the code to type, the link to open, the poll interval in seconds, and the code's lifetime in seconds. `handle` is opaque. 400 `unknown_provider`, 503 `not_configured`, 502 `provider_error` when the provider cannot be reached, answers no code, or refuses to start (its own error word is in the message, as for `device_flow_disabled`).
- `POST /v1/login/poll` with `{handle}`. The pool unseals the handle, posts the provider's token route once (Google with `GOOGLE_CLIENT_SECRET`), and answers `200` with a `status`: `pending` (the person has not approved yet), `slow_down` (poll less often: the client adds 5 seconds to its interval), `expired`, `denied`, or `authorized` with `{token, account, expiresAt, signingKey}`, the pool's credential and the public half of its signing key. On approval the pool reads the person with the provider's token (GitHub's `/user`, Google's userinfo), hashes the subject as before, and drops the token. 400 `missing_field` for `handle`, 401 `invalid_handle` for one this Worker did not seal (tampered, truncated, or sealed by another Worker), 401 `login_refused` when the provider's profile route does not accept the token it issued, 503 `not_configured`, 502 `provider_error` for a provider that cannot be reached, answers HTML, answers a word the pool does not know, or does not name the user (a GitHub 403 for a rate limit is here, not a refused sign-in).

**The handle.** It carries `{provider, deviceCode, expiresAt}` sealed with AES-256-GCM under a key derived from `PSEUDONYM_KEY` (HMAC-SHA-256 of a fixed label, so the secret itself is never the cipher key), a fresh random nonce each time, as `base64url(nonce || ciphertext || tag)`. The client never sees the provider's device code, a handle that was altered fails the tag check, and a handle from another Worker (another `PSEUDONYM_KEY`) is refused. A handle past its `expiresAt` answers `expired` without calling the provider. The pool keeps no state between the two routes; a device code the provider has already spent is the provider's to refuse.

Because the pool only ever reads a person with a token the provider issued to the pool's own client, a token another app holds for that person cannot sign in (register A54): no route takes a provider token from the client. `POST /v1/login` answers 410 `gone`, naming the two routes.

## What the server enforces

- **Deposits are closed by default.** With no `COVENANT_VERSION` binding, every deposit gets 403 `deposits_closed`. Once one is set, an account must have accepted exactly that version, or it gets 403 `covenant_not_accepted`, and a new version asks again. Reads and `fetch` are not affected.
- **Closed fields, open names.** A shape error (a wrong type, a malformed value) gets 422 `closed_vocabulary` with the field named, and nothing is stored. An unknown field goes to the extensions bag, and an unknown enumerated value is read as `other`. A name off the public lists (an MCP server, skill, pull name, program, subcommand, flag name, native tool name, model, or harness version) is not refused: it is stored and served only at the floor (next bullet). What is stored is the parsed skeleton, not the text that came in.
- **One class table, hashed hosts, and the floor.** `packages/pool/src/field-classes.ts` gives each wire field a class, and the register below carries the same column (`field-classes.test.ts` keeps them equal). The value of the `host` field is replaced by an HMAC-SHA-256 under the pool-wide `INGEST_HASH_KEY` before anything is written (rows, the extensions bag, literals, cells, and motifs), and a pool with no key refuses every deposit with 503 `not_configured`. A long-tail name is held in clear at rest and served only once `PUBLIC_FLOOR` (5 by default, see "Serve floors") distinct accounts report it; below that no cell, motif, read, count, or denominator shows it, and the smallest served name beside a sub-floor one is withheld too. Every signed bundle states the floor it applied (`floor`). No host is written in clear at any point: hosts are hashed before any readable write, and a part of a batch sent in parts is sealed (AES-GCM) while it is staged, so a part held for a later join, or kept after a 409 `deposit_conflict` or 403 `deposit_limit`, is unreadable without the deploy's `INGEST_HASH_KEY`.
- **Intervention outcome (field-list version 6).** A prompt may carry `intervention`: what the next human prompt did to its work, one of `none`, `after-error`, `redo`, `revert`, `user-stop` (the human rejected a call or interrupted the turn; t912, no new field, so the field-list version does not move for it), or `unknown` (the rule and each limit are in `docs/sessions-store.md`, "Prompt intervention"). It is an outcome row, not a quality claim: no grade or score is named, and `none` is silence in the records, not approval. It is computed on the client from the stored records, so no prompt text, path, or command crosses; the bucket alone does. **Absent means not computed** (the stored prompt predates the signal); `unknown` means computed and not sayable, as for the last prompt of a transcript. A value off the list reads as `other` and is kept as sent in the bag. The pool holds it per prompt in the stored skeleton and no read, cell, or bundle serves it (`served-families.test.ts` pins that); its one stated consumer is the later test of whether the per-prompt graph predicts intervention above chance on held-out repo keys, after the first 1,000 pooled prompts. The field is a closed list of constants, not a name, so it passes no long-tail name gate.
- **Step attribution (format 3).** A step names the frame it ran in and the skill whose run it sits in, and a frame names the reach of its session, so harness, version, model, skill, and the servers, skills, and plugins in reach resolve from a step without a join the parser cannot check. A transcript sends `frames`, its distinct frames (its own first), and each step a `frame`, a position in that list; the parser refuses a position outside it. A call's frame is its prompt's frame (the transcript's before the first prompt) with the call's own `model` and `harnessVersion` where its line named them, so a model that changes in the middle of a prompt reaches the steps that ran on it; a call that recorded neither takes its prompt's. A step made inside a skill's run carries `skill`: the name after redaction, or `private` when it counts as redacted. Only Claude Code writes `attributionSkill`; an absent step `skill` on any other harness means not recorded. The harness marks no end to a run: it stops naming the skill on the next line, and that is where the run ends here (limit: a skill the harness does not name on the line shows nothing, and a nested skill shows only the outer name the line carries). A frame in `frames` and the transcript's `frame` carry `reach`: `{ filled, mcp, skills, plugins }`, each `mcp` and `skills` member the name after redaction, or `private` when it counts as redacted (a plugin is always `private`, since no plugin list is pinned), from the session's `setup`, its `funnel`, the MCP tools it called, and the skills it called. `filled` is false when the record holds neither `setup` nor `funnel` (Cursor, Copilot, Grok Build, OpenCode, Pi, and a capture before version 12), and then the lists are empty and must not be read as no tools. The large-deposit fixture in `packages/pool/src/ingest.test.ts` pins the skeleton at 887,140<!-- figure:skeleton --> bytes (about 819,000 before t868 put a null `errorCode` on each call and t869 a null `spawnedIn` on the transcript, about 877,000 before t891's null usage and remainingTokens, about 887,000 before t871's coverage bands), up from about 785,000 bytes before step attribution. The cell computation does not read the new fields: a cell is still keyed on the prompt's frame, so a mid-prompt model change moves no cell. **Model version:** a model literal holds the model's name as the harness wrote it (`claude-opus-5-5`) and no version beyond it, so a cell and a frame cannot tell two builds of one name apart; a model-boundary read is not built.
- **The skeleton form (format 3; formats 1 and 2 are refused with 422 naming `format`).** A step carries a shell call's projected `program`, `sub`, and `flags` in place of the joined shell command a step used to carry: a program is sent as its basename after redaction, whether or not a public list holds it, and a `private` program holds no subcommand, flag, or pull. The subcommand and flag names of every program that is not `private` go through the same gate as any name (a flag value never leaves: `--token=abc` sends the flag as `private`, and a short flag with its value attached, `-psecret`, is dropped, since a single-dash flag goes only as one letter, or as a public flag such as `-NoProfile`), and the parser accepts an off-list subcommand and flag name. A model and a harness version go the same way, as the string after the gate. A call's own model and version, which capture keeps as its line names them, reach the pool as that string; the frame of a transcript or a prompt carries the value capture closed it to (the public name, else `<literal>`), sent as it is. Capture still drops a subcommand or flag off the pinned vocabulary of its program, so a real session sends no off-list subcommand (`sub` is null) and no off-list flag until a capture bump (owed); a multi-letter single-dash flag no public list holds is dropped, as the client before t900 dropped it. A name goes as `private` only when the client's redaction changes it, it matches your exclusion terms, it is not a name (a mis-parsed command), or it is over 128 characters; an older client's `private` is still accepted. An MCP server, skill, pull name, and native tool name are sent as they are after the same check, and a host is sent as it is and hashed on arrival (see "One class table" above). The parser refuses `<literal>` at those places. Capture stores a skill-run name, a host, and a pull name as they are after your redaction (CAPTURE 24), so a real session sends them through the same gate with no second projection; a store captured before it holds `<literal>` for the off-list ones until the next deposit captures it again (see `docs/sessions-store.md`). Usage, `errors`, `wallSec`, and a step's `tokens` and `ms` are Section 7 buckets, never exact counts; the one exact time is `durationMs` per tool step. A transcript and a prompt still carry their `frame` (each member has a Section 1.2 row, and the bucket key and the strata read it); only the shell step's joined command went. `deltas` is on the form and holds the batch's local delta entries, if any (see Local deltas); an entry outside its field's row is refused. A failed call carries its `errorCode` (a member of the closed `ERROR_CODES` list, `other` for a value off it, which also goes to the extensions bag, or `null` when the harness captured none) and, on a call that did not succeed, `recoveryCalls`: `next`, the canonical actions of up to the next five calls in the same prompt (what followed, never a fix; an action off the list reads as `other`), and `editFollowed`, true when a `file.edit` or `file.write` was among them (not a success flag). The list must equal the one the batch's own calls give, or the batch is refused. No signature hash, text, or argument goes with either. The exact-count form (format 1) and format 2 are refused with 422 naming `format`; nothing is migrated. Cells count a bucketed value as the bucket's lowest value, so a cell's `tokens` and `durationMs` are lower bounds. The cell computation is one module (`cell-increments.ts`) that the pool's ingest and the client's local read both call; the local read projects its store with the open gate (name shape and length, but not your redaction or exclusion terms), because it sends nothing. A step's calls and a prompt's place are positions in the batch, not the log's numbers: tool `n`, prompt `index`, and a step's `seg` (its place in its call, which the server rebuilds from position) are not sent. **Edges and the spawn link (t869).** A step carries `edges` when any arrive, each `{ kind, target }`: `kind` is one of the closed list `next` (order within a prompt's line of work), `spawned`, `retried`, and `after-error`, and `target` is the position of the step it names, counted over the steps of one transcript in call order (a position in the batch, never a call number). The client decides `retried` and sends the result, since the pool holds none of the raw keys it compares. A `spawned` edge sits on a subagent's first step and names a step of the spawning transcript. The parser reads an unknown kind as `other` (kept in the extensions bag, its target held to a count only), and refuses a target that is not an earlier step of the same transcript (a `spawned` target must be a step of the spawning transcript), and a `next` whose target ran in another prompt. A transcript carries `spawnedIn`, the position in the batch's `transcripts` of the transcript that spawned it, and a step's `parent` is the position of the spawning call in that transcript's `tools`, so a subagent two deep rebuilds its tree from the batch alone. `spawnedIn` is null for the main run and for a subagent whose spawner the batch does not hold; the parser refuses a position outside the batch, the transcript itself, a cycle, and a spawner on the main run. **Which harnesses fill it:** Claude Code alone, from the subagent's `.meta.json` tool-use id; Codex and Gemini read a subagent but record no spawning call, so they send null, and the other harnesses record no subagent run. The cell computation does not read an edge: a motif is still a linear window inside one prompt, and the cells are byte-identical with and without edges. A skeleton-derived store (`cell-increments.ts`) carries both back, so it holds the same graph as the local store on the fields both keep. `usage.thinking` is a token count and goes as the `tokens` bucket like the other usage fields. A usage category the source never recorded goes as `null` (its key stays required), never as the bucket of zero, so a prompt with no counts at all sends five nulls and a partial total sends a number only for the categories it observed; every prompt also sends `usageResponses`, a `count` bucket of the responses that reported usage, so the numbers say what they cover (field list version 7, after t882's intervention at 6; the field is left out only on a record that predates the coverage, capture version 20). A step's `remainingTokens` goes as `null` or is left out when steps follow it and none of them reported tokens, and otherwise as the bucket of the sum over the ones that did (a lower bound). A client that predates this sends the five numbers, and the parser still accepts them. A cell never holds a list longer than one: a motif keys on a shell step's program and subcommand, and each flag and each pull is its own one-step cell (spec rules 1 and 2), so a step with two flags makes two flag cells and one program cell.
- **Two planes.** A deposit writes its parsed skeleton and its deltas (the ledger column still holds `[]`: see the local deltas bullet below) to the ledger (`deposits`), and, in the same transaction, its cell increments to the index: `cells`, `motifs`, and rule 3's `strata`, each cell's `clusters` a held count. A `contributors` record per (cell or stratum, account, UTC day) tells a returning cluster from a new one, so only a new one raises a count. The ledger has no expiry: no code deletes a `deposits` row or a `contributors` record, and a database trigger aborts any `DELETE` on either (migration `0009_ledger_no_delete.sql`). A bundle is read from the index alone (`packages/pool/src/stored.ts`: four statements whose rows grow with the cells, not with deposits). A session sent again adds only the difference to its earlier batch. A large batch of varied steps runs its cell JSON to about four times its skeleton's size, and D1 takes 2 MB in one value, so ingest binds each payload in chunks of at most 1 MB, one statement per chunk, all in the one transaction under the one guard. Two limits of the stored form stand until a later change rebuilds what they need, and tests pin them: a session sent again over a held row that no longer parses adds its whole batch a second time, since the cells keep that row's increments and there is no parsed batch to take back; and a session sent again that leaves a cell lowers its `sessions` but not its `clusters` or the account's `contributors` record, so four accounts plus one that left still read as five (one record cannot show whether another of the account's batches still holds the cell).
- **Local deltas (`deltas`).** The client compares its own windows and sends what changed, once. `pool deposit` takes the sessions that pass both session gates and have ended, and counts `DELTA_DAYS` (7) windows on a fixed grid from the epoch, so adding, losing, or finishing a session moves no window; a pair of windows next to each other, each with at least `DELTA_MIN_SESSIONS` (5) of them, makes a delta, and the batch of the session that fills the after window (its fifth, in time order, ties by id) carries it. An entry holds a `deltaKind`, a `field`, a `name` or null, a `registry` or null, a `metric`, and a `change`, and nothing else: no session id, root, window date, or exact value. Four fields enter, per the spec's first exception to rule 3: `plugin` as `added` or `removed`, `permissionMode` and `effort` as `changed` (named by the field alone, the most common value of each window differing, so one odd session is not a change and two values off the effort list are no change), and `package` as `removed` (called in the before window and gone by a clean manifest edit, or by a Write that lists the same file without it in the after window; a Read never says a package is gone, since it may show part of a file; a public name with its registry, else `private` with none, and all `private` ones are one entry). A plugin goes as `private` always, since no plugin registry is pinned, and plugins are compared only over the sessions of a harness that records them (Claude Code), with none built when either window holds no such session. The after window is read as its first five sessions, so the entry is fixed when the window fills. `change` is the signed bucket of the move: calls per session in `count` buckets (-7 to 7), thinking per prompt in `tokens` buckets (-11 to 11) for an effort. The parser holds each field to its own row and refuses an entry outside it, and `oars pool outbox --explain` shows a row for each field of an entry.
  **Once only.** A delta is marked in `deltas-sent.log` in the outbox folder (a hash of the account, the entry without its `change`, and the index of its after window on the grid; the filler session is not in it, since which session fills a window can change from one deposit to the next, while the index cannot) after the batch that carries it is written, never before: a deposit that stops first builds it again. A later deposit builds no delta it has marked, so a session rebuilt under the same key replaces its batch with one that carries none. **Limit:** a batch that carried a delta and was never sent is replaced by that rebuild without it, so the delta is lost; the mark is written with the batch, not at send time, because sending less beats sending wrong and nothing is sent to a real pool yet. **Limit:** the public package list is held by bare name, so `pypi:typescript` goes as the public name `typescript` with its registry until the list is held per ecosystem. Also not built: an `upgraded` delta for the harness version, rule 4's "pool neither when both changed", and the batch's summary `exposure` (no deposit reads an exposure tag yet). The Worker parses an entry and keeps it inside the stored skeleton, but derives no delta cell and its `deposits.deltas` column still holds `[]`; the weekly limit on one delta for each cell is the pool's, not built here.
- **Cell grain and effort (rules 3 and 6).** A cell is keyed on the UTC week (`grain: week`, `day` the Monday), except a `live` cell, which stays at UTC day (`grain: day`) and holds none of rule 3's bound fields. Each read answers from one grain and filters the other out, so adoption and change state weeks (`firstWeek`, `lastWeek`, `weeks`, `weeksSinceLast`), never days. `effort` is in no cell key: it is recorded only as the (`effort`, `thinking` bucket) cell, which joins no `model` or `harnessVersion`, so `fit` and the interaction read no longer slice by it. Migration `0008_cell_grain.sql` adds the grain column; nothing is deployed, so it moves no data. A local `cells.jsonl` written before the grain has no `grain` field, fails the stored-cell check, and is derived again from the store the next time a pool is built or served. On the 3,400<!-- figure:large-steps -->-step test deposit a batch counts 887,140<!-- figure:skeleton --> bytes of skeleton and 11,548<!-- figure:cells --> cells (3,746,485<!-- figure:cell-json --> bytes of cell JSON, 4.22<!-- figure:cell-ratio~0.01 --> times the skeleton) and stores 887,144<!-- figure:stored --> bytes (skeleton, deltas, and the 2<!-- figure:extensions -->-byte extensions bag); no default limit counts them (see No cap on contributing). A session with a shown recall derives different local cells from its deposit, because a deposit is built from the skeleton, which has no recall graph, so the recall's step and exposure appear only in the local read.
- **Stack shares, explore, and the two pairs (rule 3).** Every frame's `stack` on the wire carries `languageShares`, one `{language, languageShare}` per language, the share one of `0`, `under-10`, `10-50`, and `over-50`; a share outside that list is dropped and its language still goes in `languages`, and a language off the pinned list goes as `other` (in a share only; the frame's `languages` list holds the pinned names alone). A prompt carries `explore`, a `calls` bucket of its steps that only look (`file.read`, `file.search`, `web.search`, `web.fetch`), or `null` for a record captured before the strata; the exact count never leaves, and the deposit's local store counts a prompt as its bucket's lowest value, which no read serves yet (the store holds the bucket's lowest value). The `calls` edges are the `count` edges and then double: 1, 2, 3, 5, 9, 17, 33, 65, 129, 257, 513, 1025, 2049, and 4097, so the last bucket is over 4,096, as the `count` bucket's is over 32. Two strata are counted beside the single ones, each a stratum of its own and never a cell: `languageShare` (value `<language>/<share>`, per frame) and `repoFilesExplore` (value `<stack size, xs to xl>/<explore bucket>`, per prompt, none when either is missing). They are held to the public floor (`PUBLIC_FLOOR`, 5 by default) accounts pool-wide like the others, appear only in the bundle's `strata`, and a cell still holds at most `q_dims` dimensions. This closes the limits that the wire sent no language share and the deposit derived `explore` as zero. **Limit:** the `live` family's provider errors by `model` and by `harnessVersion` are not built here: a skeleton step carries `status` (`ok`, `error`, or `none`) and no `errorCode`, so no day cell can name a `429` or a `5xx`.
- **Pseudonymous accounts.** The pool brokers the provider's device flow ("Sign-in", above): it starts the flow with its own client ID, polls the provider's token route itself, and reads the subject from the provider's profile route with the token it received, so every token it reads was issued to its own client. It hashes the subject under `PSEUDONYM_KEY` (which the database never holds) and discards the token. No email, login, provider id, provider token, or device code is stored. A login also deletes the token rows past their expiry.
- **The public floor.** A read is served only at `PUBLIC_FLOOR` or more clusters, and a cluster is a set of accounts the pool treats as one operator ("Clusters" below), so one account's many sessions count once and so do accounts the "Clusters" signals join (shared repo keys, or one creation window with deposits in lockstep). Only accounts that have stood count (the "Access" row below: a counting batch 90 days old): a free account that has not holds a cell and counts toward no floor until it has, so k-1 fresh accounts depositing a guessed private name beside one real account leave the cell below the floor and cannot tell whether that account holds it (S13). `PUBLIC_FLOOR` keeps its number and changes what it counts; the holdings of an account that has not stood are kept, and count at the next recount after it has. The first reads are served 90 days after deposits open, at the earliest. The floor is a binding on the Worker, not a constant in the code: it is 5 unless the deploy sets another (`wrangler.jsonc` states the 5; a clear cell has its own floor, the next bullet), and a deploy can give single read families a floor of their own (`PUBLIC_FLOOR_FAMILIES`, see "Serve floors" below). Changing a floor is a deploy and never a client release: cells are stored with their held counts and the floor is applied when a bundle is served, so lowering it serves what was held, and raising it withdraws what was served, at the next generation of the bundle, with no redeposit. The bundle states the floors it was served at (`floors`, and the public one again as the bundle's `floor`), every served read states the floor it cleared (`floor`), and the `ETag` changes with them. A cell's `clusters` is its held count of verified-distinct clusters, and a read's is the largest held count among the cells it cites, with no union over accounts: the fetch path reads no per-account record, so as many accounts as the floor, each in a different week, serve no read, since each week's cell holds one (a later change brings held counts for a key's `n` and `c`). That many accounts on that many days of one week share each week cell and serve the week reads, and no `live` read, since a `live` cell is one day. A cell served on its own needs the floor in that cell, and a strata cell needs it pool-wide (strata take the public floor, whatever a family's). A `live` read cites only the sliced day's cells, so its floor counts the clusters held on that day and never those in its seven-day baseline; the baseline sums only baseline cells at the floor, and with none `value.baseline` and `value.ratio` are `null`. A read the CLI computes on one operator's own store states `clusters: 1` and applies no public floor.
- **Two floors, by cell class.** A cell is `clear` when every part of its key is closed public vocabulary (a listed model, harness version, program, subcommand, flag, tool, or skill) or a client hash, and `thresholded` when any one part is long-tail: a single long-tail part makes the whole cell thresholded, and a cell whose motif the pool does not hold is thresholded too. A thresholded cell is served at `PUBLIC_FLOOR` (5 by default); a clear cell is served at `CLEAR_FLOOR` (1 by default, never above `PUBLIC_FLOOR`; a value that is set and outside that range or not a whole number is refused at load, with one line logged, and the public floor is used, so a typo is strict and never loose). **What a floor of 1 shows:** a clear cell served on one cluster says that one operator used a public tool (a listed program, or a listed model, on a listed version), and nothing else about them, since every name in it is on a public list. A long-tail name is never served below `PUBLIC_FLOOR` (5 by default), or its family's own floor. A clear cell at a clear floor of 1 counts every account that holds it, standing or not, because a floor of 1 has no k to protect and waiting 90 days to serve what one account used a public tool would protect no one; at a floor above 1 (a family's, or a raised `CLEAR_FLOOR`), and for every thresholded cell, only accounts that have stood count (the paragraph above). Both floors are stated in the signed bundle (`floors.public`, `floors.clear`) and feed its `ETag`. A total beside its parts is held back when it would show a part that is not served, and each part is judged against its own class's floor: a version-free clear total beside a long-tail part under 5 is withheld, and a clear total beside clear parts at the clear floor is served (the version-free cells under "Fit by platform and shell"). A shape total carries no identity, so it is a clear cell, and when one of its named cells is a long-tail name under 5 it is served only if a named cell of 5 or more standing accounts is withheld in its place, and is withheld itself when none is (complementary withholding below). The bundle's top-level `floor` stays the thresholded floor.
- **A fetch cap.** An account without access may fetch `FETCH_CAP` bundles (default 1) per ISO week, counted per account and not per harness or harness version. Past it the pool answers 429 `fetch_cap` with `Retry-After` in seconds to the next Monday 00:00 UTC, before it reads the pool. The count is one atomic statement, and a count from an earlier week is dropped. A fetch that fails after it spent gives the spend back, since the account received no bundle. An account with access is not capped.
- **Access.** The `access` record is null, `pending`, or `standing`, and only a counting batch sets it: ingested at tier committed or higher, or at `skeleton` when every transcript's harness writes no raw file (Cursor), with one prompt and one tool step over the batch, subagents folded in, and at least one cell increment written over the row held now (a batch sent again unchanged writes none); an ingest that writes none leaves the flag and the batch's date alone. It is `pending` while it rests on batches counted inside the last 90 days (`STANDING_AFTER_DAYS`), clears when every one falls to `none`, and is `standing` once one has stood the 90 days. The 90 days gate the flag only; the batch stays on the ledger. A resend that still counts keeps a batch's first `counted_at`; one that no longer counts clears it, and the flag falls if no counting batch is left. A claude-code batch with a prompt and a tool step now lifts the cap, because the batch carries its roots and is written at `committed` (the next row).
- **The tier of a batch.** Ingest writes the batch's own tier, on a first deposit and again on a resend (`tier = excluded.tier`): the lowest of its transcripts', subagents folded in. A transcript is `skeleton` when its harness writes no raw file (Cursor), `none` when its root cannot be real (no leaves under any hash but the SHA-256 of no bytes, or that hash over leaves), else `committed`. A batch with one failed transcript is `none`, takes no part in access, and a resend that fixes it counts again. A batch ingested at `none` still writes its cell increments. Stated limit: a fabricated but well-formed root, and a forged skeleton, still earn `committed` until the raw-file check of a later layer.
- **A 304 spends nothing.** A 200 carries an `ETag` that names the code, the floors (both, and any a family has of its own), the harness and version asked for, and a generation of the stored cells (triggers on `cells` and `strata` move it in the same write as a change; a write to `deposits` changes no served cell and moves nothing). An `If-None-Match` that holds it gets 304 with no body, before the spend and without reading the pool, so a conditional request can neither use up a fetch nor force a read. A weakened `W/` tag matches.
- **Two deposits of one session at once.** A deposit replaces the batch the account held under its id, and nets its cells against that earlier row, so two at once would each net against the same row and add the batch twice. The upsert therefore takes the row only if it is still the one that was read (its `ingest` mark), and the other gets 409 `deposit_conflict`: nothing of it is stored, and the client sends it again, which then nets against the winner.
- **A deposit holds something.** A skeleton with no prompt and no tool gets 422 `closed_vocabulary` naming `transcripts`, since only a counting batch lifts the fetch cap (see Access). A forged skeleton that holds invented prompts passes this check, and with a well-formed root it lifts the cap under any harness until the raw-file check of a later layer (see the tier row under Access).
- **No cap on contributing.** The pool does not ration what an account deposits: sessions, bytes, harnesses, and machines per account are unlimited by default, and a redeposit of a held session replaces its row (an `UPDATE`, so the never-delete triggers of the ledger hold) and counts against nothing. `MAX_DEPOSITS_PER_ACCOUNT` (rows) and `MAX_DEPOSIT_BYTES_PER_ACCOUNT` (stored bytes: the skeleton, the deltas, and the extensions bag) remain as an operator's brake, off unless a binding sets one; a value that is not a positive whole number leaves the account unlimited. With a brake set, a new session past it, or a deposit that would take the account past the byte brake, gets 403 `deposit_limit`; a redeposit that fits still replaces. A brake bounds one account's ledger, not a fetch: a fetch reads the stored cells, never the ledger. The only cap on reading is the fetch cap for accounts with no access (see Access).
- **A batch past one request goes in parts.** One request carries 1 MiB at most. The client cuts a larger batch into parts of 512 KiB (never inside a character), in order, each sent with `oars-part: n/m` and `oars-batch: <SHA-256 of the whole batch>`. The server holds the parts in `deposit_parts` (outside the ledger), answers 202 `pending` until all `m` are held, then checks that their join hashes to `oars-batch` (400 `part_mismatch` otherwise, and the parts are dropped) and stores one deposit by the path a whole one takes, so its refusals (422 `closed_vocabulary`) and its netting are the same. Parts may arrive in any order. A part sent again lands on its own row and changes nothing; once the deposit has finished, any part of that batch is answered 201 from the stored marker, with no second write and no second count. The join is refused past 1,800,000<!-- figure:join-limit --> bytes (413 `too_large`), because one D1 row holds 2,000,000 bytes at most and the skeleton and its extensions bag share it: a session larger than that needs its skeleton stored across rows, which is not built. At most 8 parts make a batch (the client's 512 KiB parts make 4<!-- figure:join-parts --> at most for a join the cap allows). Staging is bounded by the same cap: a part that takes the held bytes past 1,800,000<!-- figure:join-limit --> is refused at once with 413 `too_large` and the batch is dropped, so an unfinished batch never holds more than that. An account also holds at most 16 unfinished batches at once (`MAX_STAGED_BATCHES`: the CLI sends one batch at a time under a send lock and a batch is 4 parts at most, so 16 leaves room for several machines with an interrupted batch each): a part that begins a seventeenth is refused with 429 `staging_full` and a `Retry-After` of one day, and a part of a batch already held always passes. The count and the insert are one SQL statement, so parts that arrive together cannot each read room that another has taken. A staged batch whose oldest part is over 24 hours old is dropped by the account's next staging write, with no cron trigger (`deposit_parts.staged_at`, migration 0017; a part staged before it counts as old), so an account stages about 29 MB of sealed text at most and a client that comes back later sends every part again. A finished batch's marker is not swept. A part that names another count than the ones held writes nothing: the batch is dropped and the part gets 400 `bad_part`, so the client's next full send starts clean. A staged part's `body` is sealed: AES-GCM under a key HKDF derives from `INGEST_HASH_KEY`, the account, and the batch id, with a fresh IV stored in front of each part. The join opens every part and then hashes hosts by the path a whole deposit takes; a part that does not open (a changed byte, another key) is refused as `part_mismatch` and the batch is dropped. A joined batch refused with 409 `deposit_conflict` or 403 `deposit_limit` keeps its parts, still sealed, until the batch is sent again. No new secret, client change, or wire change. The nightly task sends in these parts after covenant acceptance.
- **A frame's day is real and not ahead of the server.** A day that is not a calendar date, or is later than tomorrow UTC, gets 422 `closed_vocabulary` naming the field, since the latest day of a bundle's own bucket sets its `asOf` (its version-free cells can be later).

## What a bundle serves

A bundle's reads are derived from the stored cells with the code a local store runs (`packages/pool/src/derive.ts`), except the (name, `platform`, `shell`) read of `fit`, which runs only in the bundle: a local store writes those cells but no local read answers from them. A read is served when at least one of its cells clears the floor and is not withheld (below), and it cites and counts only those.

**What a served number counts.** The reads run over the bundle's cells at or above the floor of their family (`PUBLIC_FLOOR` unless `PUBLIC_FLOOR_FAMILIES` names it) and no others (`readsOf`, `derive.ts`), so every count, sum, and denominator a read holds is a sum of served cells: its `n` and `failed`, a share's denominator (`tool-day`'s `value.steps`, a `live` read's `of` and its baseline, and a `fit` sum across weeks), and a sum across models. A sub-floor cell is in no `n`, no denominator, and no `inputs`, so no two numbers of one family's reads at one grain, set against each other, show the size of a sub-floor cell. A week cell and the day cells of its days count the same steps, as do a shape cell and the named cells of its actions, so across grains the bundle withholds one more part (`complement.ts`): where a served week has a sub-floor day it also withholds its smallest served day (fewest accounts, ties to the earliest day) from `cells` and the reads, and where a served shape has a sub-floor name it also withholds its smallest served name; the week and the other parts stay, and the rule repeats over both pairs until it adds nothing. The week less its served days is then a sum over at least two days, one of them at or above the floor, which no reader can split; a week with no sub-floor day keeps every day. A tool-day or `live` read's `steps` or `of` is the day's steps over the served tools only, so a tool served at the floor reads against the served tools' day and not the whole day's. `asOf.pool`, `asOf.day`, and `weeksSinceLast` come from the served cells alone, so a sub-floor cell's size moves none of them, while the first sub-floor part of a family withholds one more part, which a reader sees. The (name, `platform`, `shell`) cells keep the rule of `ENVIRONMENT_CELLS` (every part served or the total is not) and are also dropped when their (motif, grain, day, exposure) matches a withheld bucket cell. Flag and pull cells overlap their program cells, so they are neither parts nor triggers of the shape/name rule. The local read has no floor and sums every cell it holds.

The pool serves all nine order 1 families, `recovery` included. `fit`'s call-shape method stays out, because no cell is keyed on a tool's input key names, though a skeleton now carries them as `keys` (below); `recovery` serves only the edge a skeleton can carry (below), not the signature record, because a skeleton has no error row, `sigHash`, or `outcome`.

The (name, `platform`, `shell`) cell is its own cell, `env:<platform>:<shell>`, a week cell that names no version and no model, so a bundle for any harness version holds it (a session of a harness that records no version has none to key on). It counts the same calls as the version cells, so a total beside only some of its parts would show the rest by subtraction. The pool therefore serves it for a motif, week, and exposure only when the total clears the floor of its class and no cell of that motif, week, and exposure, in any bucket or environment, is under the floor of its own class (the `fit` family's floor, less the clear gap for a `clear` cell); one sub-floor part withholds the total (`stored.ts`, `environmentOf`). A total of a clear name is served at the clear floor, so a long-tail version, model, or shell beside it that is under 5 still withholds it, and a clear part under the clear floor does the same. **Known limit of that rule:** a motif with a long tail of versions, models, or shells has a sub-floor part in any week one of them is under the floor, so on a live pool this read is likely to serve rarely (no real pool exists to measure it), and one new version's first account withholds every motif it calls that week. Sending less is the side the rule is on; a later decision about this cell should weigh how often it serves.

**A harness with no version on record.** Cursor, Gemini, Grok Build, and Pi keep no harness version in their local files, and a VS Code Copilot Chat session keeps one only when a request's serialized Copilot Chat `agent` (`extensionId` `GitHub.copilot-chat`, not a third-party participant) carries `extensionVersion` (`sessions-store.md`, each source's section; the VS Code reader is fixture-derived, never run live), so a session with none fills `<harness>/unknown/<model>` cells (`harnessBucket(null)` is `unknown`). A numbered request never reaches them. The route therefore takes the word `unknown` as the version (`/bundle/cursor/unknown/<vocabVersion>`, `oars pool fetch --harness cursor --harness-version unknown`): `bucketPrefix` is `cursor/unknown/`, the same derivation, the same public floor (`PUBLIC_FLOOR`), the same withholding rules, and the same environment cells as any bundle, and the payload's `harnessVersion` is `unknown`, which `verifyBundle` checks like a number. It serves nothing a numbered bundle would not: a request for a harness that does record a version finds no cell of its own under `unknown` (only sessions that recorded none land there). `served-families.test.ts` pins the families of that bundle. **Known limit (t849's, unchanged):** the fallback does not widen a cell. A harness whose few accounts split across models fills each `unknown/<model>` cell separately, so the fallback serves less than the number of its accounts suggests, and the version-free total beside it is withheld by the same rule as above.

`served-families.test.ts` pins the limit at the wire: a skeleton whose tool carries `sigHash` or `outcome`, or that carries error rows, keeps that field in the extensions bag and nowhere a read can reach, and a five-account bundle holds a tool-day read and a recovery read but no call-shape read; the recovery family is withheld at four accounts and served at five.

**What a call touched, in shape and not in value (t870).** A tool carries `keys` (its input key names, sorted), `keysDropped` (a `count` bucket of the names not sent), `targetClass`, and `argClass`; each is optional and absent on a call captured before them. The rule and its limit:

- *Key names only, never a value.* A tool with a pinned input list (`TOOL_INPUT_KEYS` in `public-vocabulary.ts`: the built-in tools of Claude Code) sends the names on its list and counts the rest in `keysDropped`; any other tool sends a name only when it passes the client's one gate (local redaction, the exclusion terms, the name shape, `NAME_MAX`), and counts the rest. A tool that went as `private` sends no names, since a private tool's keys name private work. The server holds a long-tail name and serves it at threshold (`t881`); a name off a pinned list, or a key that is no name shape, reads as `other` and lands in the extensions bag, not a 422. The limit: a public tool with no pinned list (every harness but Claude Code's built-ins, and every MCP tool) takes the gate path, so a name the gate passes goes to the server as it is.
- *`targetClass`* is derived at capture from the target's base and the path's suffix (`source`, `test`, `config`, `doc`, `lockfile`, `generated`, `data`, `none`, `other`; the order a path is asked is `call-shape.ts`, pinned in `call-shape.test.ts`). A call with no path target is `none`. The path and its base name never leave the extractor. The class reads the key the target is hashed on (relative to the repository, or to the cwd), so the folders above a repository never decide it. The limit: a path outside both keeps its absolute key and its leading folders are read, a directory (a search's `path`, or the root as `.`) is `other`, a file the table does not know is `other`, and the order is intended: the folder names the role before the extension does, so `src/doc/render.ts` reads `doc` (a `doc`, `docs`, or `documentation` folder), and a `.json` file outside a test, generated, or doc folder reads `config`, so `data/rows.json` is not `data`.
- *`argClass`* is derived at capture from the call's input: the sorted set of `path`, `url`, `pattern`, `command`, `number`, `flag`, `text`, and `none` its arguments hold. A key name classes a string (`file_path` is a path, `pattern` a pattern), a number or a boolean classes itself, and any other value is text. The value never leaves the extractor. The limit: a string under a key the table does not know is `text`, even when it is a path.

`pool-wire-keys.test.ts` plants a value in every argument of a captured call and searches the whole batch for it. Nothing of the planted text is on the wire; the key names and the two classes are.

### The set of four (`oars sessions books`)

`oars sessions books` ends with four lines read from the last bundle `oars pool fetch` kept (checked again against the pinned key; with none, it prints `no pool bundle yet`). The bundle carries the same numbers as `books`: totals only, no list that names a value under the floor. Each states its floor (the public floor, `PUBLIC_FLOOR`, 5 by default), the bundle format, the vocabulary version, and the as-of day of the served cells.

- **Served cells** counts week cells at or above the floor that the bundle serves, with a count by week and by constructor tuple (harness, version bucket, and model, which the frame bucket encodes). Environment and version-free cells count in the total and by week and name no tuple, so a version-free cell's calls are not counted a second time beside the versioned cell. **Below floor** is one number: every other week cell the pool holds for the bundle, the sub-floor ones and the served ones that complementary withholding drops, so the served count never overstates what a reader can see. Environment cells enter the served count when served, and the backlog only when withheld, since a sub-floor environment cell is not read. The backlog is per bundle (one harness version), not the whole pool.
- **Panel** counts accounts with a counting deposit in the last 28 days, once each. An account's `source` (migration 0012, default `user`) marks an input that is not a depositor; an operator-fleet or seed account is set to another value and is not counted. It names no account and is not held to the floor. The count is taken on the first fetch of a UTC day and kept in one row, so a fetch reads one row whatever the ledger holds and a deposit after that read counts from the next day; `panelDay` says which day. The bundle's ETag follows the stored cells, so a 304 keeps the panel of the bundle already held.
- **Demand** (accounts that fetched a comparison read, then follow-on reads) and the **goal metric** (read yield, cost per served cell, yield per served cell) have no source yet: no comparison read, follow-on read, or yield exists. Each prints `no source yet` with its reason and is `null` in `--json`, never 0. A later brief fills each place (`DEMAND_SOURCE` and `GOAL_SOURCE` in `packages/pool/src/books.ts`).

Inputs are not stock: a seed or fleet account adds nothing to the panel, and the numbers are counts of cells and accounts, never of rows deposited. `booksTotals` in `packages/cli/src/sessions/pool-books.ts` returns the totals as flat numbers (null for a field with no source) for the health batch to read.

## Clusters

A cell's held count is its number of verified-distinct clusters of accounts, not its number of accounts, so one person with many pseudonymous sign-ins cannot clear `PUBLIC_FLOOR` alone. It is a weighting, never a cap: no account, deposit, or cell is refused, dropped, or hidden by it. Only the count a floor compares changes, and every served read states that count in its `clusters` field (an integer, rounded down). Account ids and signal values never appear on a read.

Two accounts holding a cell join one cluster when any of these holds, and a cluster is the transitive closure (A joins B and B joins C: one cluster):

| Signal | Rule | What the pool keeps |
|---|---|---|
| Machine | They deposited from the same machine id. | Nothing yet. The wire carries no per-machine id, so this signal is absent and joins no one; `repoKey` is machine-salted, so accounts that share repo keys (next row) are the nearest the pool can see. |
| Repo keys | Each account's set holds at least 3 repo keys and the sets' Jaccard overlap is 0.8 or more. | Each account's distinct `repoKey` values from its deposits (`account_repo_keys`). |
| Age and cadence | They were created within the same 24 hours, and each has deposited on at least 3 distinct days (`CADENCE_MIN_DAYS`; fewer is a team installing together, not a sybil cluster), and their deposits fall in the same hour (UTC) on at least 90 percent of the days either deposited. | Creation: GitHub's `created_at`, read from the profile call the sign-in already makes, else the pool's first sight of the account (Google gives none). Cadence: the UTC day and hour the pool received each deposit (`deposit_hours`), on the pool's own clock. |

Only an account that has stood is a holder here: its `access` is `standing`, or its first counting batch is 90 days old (`STANDING_AFTER_DAYS`, "Access" under the pool's rules). A cell none of whose holders has stood is written 0. The standing of an account is read at each recount, so it counts from the first recount after the day it stands, which a deposit of its own makes within a day for an account that deposits nightly.

A cluster counts 1, or 0.5 when every account in it was under 30 days old at its first deposit to the cell (an account whose age is not known is not young). The weighted sum is rounded down. The thresholds (`YOUNG_DAYS`, `YOUNG_WEIGHT`, `CLUSTER_WINDOW_MS`, `REPO_KEYS_MIN`, `REPO_KEYS_JACCARD`, `CADENCE_SHARE`, `CADENCE_MIN_DAYS`) are constants in `packages/pool/src/clusters.ts`, not deploy settings. The count is written to a cell's and a stratum's `clusters` column after each deposit lands, from the committed records, so the SQL that compares the column to a floor and the bundle's own decision (`clustersOf` in `floors.ts`) read one number. A deposit recounts every cell and stratum its account holds, not only the batch's, since the repo keys and hours it adds belong to the account. The recount reads what is committed and then writes, so two deposits at once can leave a count that misses the later one until the next deposit that touches that key.

## Wire field register

One row per field a format 3 batch carries (section 17 of the direction conclusion, rules 2 to 4): no row, no field. `consumer` is the read family that reads the field today, or the future read that is stated for it. The class is the field's projection class at format 3: `clear` (a closed or public list, or a hash the client made that the pool uses only as an opaque key), `thresholded` (held always, served once a public floor of clusters report the same value; `PUBLIC_FLOOR`, 5 by default, see "Serve floors" below), `hashed at ingest` (the pool hashes the value on arrival under `INGEST_HASH_KEY`, a Worker secret), or `raw tier` (stored, never served); no skeleton field is `raw tier`. A field marked `no` is a constant of the client build.

`Bytes` is measured, not estimated: the canonical bytes of one invented session (`REGISTER_FIXTURE` in `packages/cli/src/sessions/pool-fixture.ts`: one transcript with its frames, one prompt, one call, four steps, one delta), summed over every place the field occurs. A real session holds more steps, so read the column as the shape of the cost, not its size. `pool-wire-register.test.ts` parses this table and fails on a field the client emits with no row, a row for a field it does not emit, and a bytes figure that no longer matches the fixture.

An unknown field name a client sends lands in the `extensions` bag of the deposit, not in a row. The bag is ledger class, kept and never served, joined to no read, and left out of every bundle (`wire-contract.test.ts`). A field, a literal, or a value over 8 KiB (`MAX_EXTENSION_BYTES`, as JSON) gets a 422 `too large` at its path, whatever its kind; a newer client's larger structure belongs in a new format version, not an extension.

### Serve floors

Two settings sit beside the field register. They are not fields: no batch carries them, the client does not send them and applies neither, and the pool states them back in every bundle. Both are Worker bindings read on each request (`packages/pool/src/floors.ts`), with the defaults set as plain variables in `wrangler.jsonc`; an unset binding is the default, and so is a value that is not a whole number of at least 1 (a fraction, a negative, `0`, hex, or text), with one line in the Worker's log, so a bad binding can never serve below the floor. A floor is a deploy: no client release, no redeposit, no re-derive by hand.

## The raw tier

A locally redacted raw transcript can be sent to the pool, stored, and not served. It is the one place the pool holds content, so the rules are narrow.

**What it takes.** An account that is signed in, has accepted the covenant in force, and has given **raw consent**, which is its own answer, apart from the covenant (the client asks it separately; nothing in the covenant records it). Every request states, as headers, the redaction version the transcript went through (`oars-redaction-version`) and the capture version (`oars-capture-version`), each 1 to 64 letters, digits, dots, dashes, or underscores, and the first request of an account also states `oars-raw-consent: granted`. The pool records the first `granted` (`accounts.raw_consent`) and a later request need not repeat it; a request that states anything else is refused even when consent is held. The covenant check is the deposit's: with `COVENANT_VERSION` unset every raw route is 403 `deposits_closed`.

**What it refuses**, each by name: before any byte is read, 401 `unauthorized`; 403 `deposits_closed`; 403 `covenant_not_accepted`; 422 `redaction_required` (no redaction version, or one that is not a version); 422 `capture_required`; 403 `raw_consent_required`; 503 `not_configured` when the `RAW` bucket is unbound; and once the part is read, 413 `too_large` for a part over 1 MB (unread when it declares its length) and 422 `empty_part`. A completion is also refused 422 `hash_mismatch` when the parts do not hash to the SHA-256 in the path (see The upload).

**The upload.** A transcript goes in parts of at most 1 MB, the cap a deposit has, keyed by its SHA-256 (64 lowercase hex):

- `PUT /v1/raw/:sha256/parts/:n` stores part `n` (1 to 999,999) under `staging/` in R2. A part sent again replaces itself, so a client retries a lost answer freely. An account holds at most 1000 staged part objects at once (`MAX_STAGED_RAW_PARTS`, one R2 list page): a part that would add one past that gets 429 `staging_full`, and a part that replaces a staged one always passes. The list is read again after the put: a part that finds the page full then, because others arrived with it, deletes its own object and gets the same 429. For an object that already stands it writes nothing and answers 200 `{ok, stored}`, after reading the part (under local workerd on Windows, an answer over an unread body resets the connection).
- `POST /v1/raw/:sha256/complete` takes `{parts, bytes}`, joins parts 1 to `parts` into one object `raw/<account>/<sha256>`, checks that they hold exactly `bytes` and hash to `:sha256`, and writes the ledger row. 409 `part_missing` names the first part that never arrived; 422 `bytes_mismatch` names the count it found; 422 `hash_mismatch` (field `sha256`) means the parts hash to something else; each leaves no object and no row, and the parts stay for the client to send the rest and complete again. A completion sent again answers 200 `{ok, stored}`.

R2 will not complete a multipart upload from parts under 5 MiB (the last excepted) and wants the others equal, so a 1 MB request cannot be an R2 part. The pool stages each request as its own object, then assembles through an R2 multipart upload, cutting the stream into equal 5 MiB parts; memory holds one 5 MiB buffer and one staged part. The staged parts are deleted once the row is written; parts numbered past the `parts` a completion names are not, and are left to the lifecycle rule. A transcript that is never completed leaves its staged parts behind: the deploy steps give the bucket a lifecycle rule that expires `staging/` after 7 days.

**The effective ceiling.** There is no cap on a transcript, but one `complete` does all its work in one Worker request: one R2 `get` per staged part (1 MB each), one `uploadPart` per 5 MiB, the multipart create and complete, and one batched delete (R2 takes at most 1,000 keys in one). The Worker's per-request subrequest limit (1,000 on the paid plan) and CPU time (the hash and the copy) therefore set a practical maximum, roughly several hundred MB by subrequest count, and CPU may bite sooner. Neither is measured against production R2; Miniflare enforces neither. The deploy steps say to verify it before the raw tier opens.

**A ledger row, never the bytes.** D1 holds one `raw_objects` row per object: account, SHA-256, bytes, capture version, redaction version, and the time. The bytes are only in R2. The row is ledger class: migration `0011_raw_tier.sql` gives it the never-delete trigger of `deposits` and `contributors`, and `ledger.test.ts` guards it. `raw.test.ts` dumps every D1 table after an upload and fails if the transcript is in any of them.

**It serves nothing in v1.** No route returns a raw byte, a hash, or a count of what an account holds, and the answers to the two uploads carry `ok`, `stored`, or `part` and nothing else. No bundle, read, or `derive` touches the bucket or the table. `raw-serves-nothing.test.ts` fails if any file but `raw.ts` names the binding or the table, if `raw.ts` lists or heads the bucket or builds a response of its own, and if any other method or path under `/v1/raw` answers anything but 404. The raw tier is not licensed or published either: serving it would need a new decision and a change to that test.

**No limit on contribution.** There is no per-account cap on raw objects or bytes, and `MAX_DEPOSITS_PER_ACCOUNT` and `MAX_DEPOSIT_BYTES_PER_ACCOUNT` do not apply to it (`raw.test.ts` sets both to 1 and uploads three transcripts). Storage figures belong to telemetry.

**What the pool cannot check.** It cannot verify redaction: it takes the client's word, in the redaction version it records, that the transcript was redacted and its hosts masked before it was sent, and it runs no scanner over the bytes. It does check the hash: `complete` runs SHA-256 over the staged parts as it assembles them and refuses 422 `hash_mismatch` unless the digest is the one in the path, so the ledger's hash is the object's own. Redaction, host masking, and the raw consent prompt are the client's (t884).

## Telemetry storage

`POST /v1/telemetry` keeps every accepted batch twice, for two jobs.

**The record is R2.** One object per batch at `telemetry/<YYYY-MM-DD>/<uuid>.json`, the day the batch arrived (UTC). No lifecycle rule sets an expiry, matching the raw tier, because Cloudflare's limits page gives Analytics Engine three months of retention and the record must outlast that. The object is `{received, account?, batch}`: `received` is the arrival time, `account` is the pseudonym of the credential the request carried (absent when it carried none, or one the pool does not know), and `batch` is the request body exactly as it came, so an event type or field this server has never seen is kept. No address, user agent, or other header is read, so none is kept. The route does not join a batch to a deposit, and a batch reaches no bundle.

**The index is Analytics Engine.** Each event becomes one data point, written after the object is kept. A failed write costs the index and never the object (the answer says `indexed: false`). The layout is fixed, because a read names columns by position:

| Column | Holds |
|--------|-------|
| `index1` | the install id (also the sampling key) |
| `blob1` | event `type` |
| `blob2` | `cli`, the oars version |
| `blob3` | `os` |
| `blob4` | the command path, space-joined (`data.path`) |
| `blob5` | `data.errorClass` |
| `blob6` | the account pseudonym, or empty |
| `blob7` | the flag names, comma-joined (`data.flags`) |
| `double1` | `v`, the schema version |
| `double2` | the event time, epoch milliseconds (0 when unreadable) |
| `double3` | `data.durationMs` |
| `double4` | `data.exitCode` |

A field an event does not carry is an empty blob or 0, so a read of `command` events filters on `blob1`. A blob is cut at 128 characters in the index; the record keeps the full text. Only strings and numbers of the known fields are indexed, so an event type this server has never seen reaches the index as its envelope.

## Telemetry rollup

The operator's read lists anomalies over the 30 day window only and counts installs with `COUNT(DISTINCT install)` queries; it never loads the whole table, and finds the first fleet read by reading the rollup from its oldest day a month at a time, stopping at the month that served a cell. A day counts as served when any cell is served in the widest window (30 days), since a 7 day cell implies a 30 day one: five installs reporting a week apart serve a cell on the day the fifth reports. The fleet read and the operator's read come from `telemetry_install_days` (migration 0011), one row per install, account, and day: the day's batch and event counts and its cells (a latency histogram, or hits and observations for a rate). A nightly cron (`17 3 * * *` in `wrangler.jsonc`) runs `rollupRecent`, which rolls up yesterday and then the day before, since a batch whose first answer was lost arrives a day late. A day is rolled up by its R2 prefix (the day the batch arrived), by deleting its rows and writing them in one transaction, so a second run changes nothing. An event counts once per install however many batches carried it (the CLI's delivery is at least once, so a resent batch repeats its events; two events with the same time and data from one install are one).

**Why R2 and not Analytics Engine.** A Worker has a binding to write Analytics Engine and none to read it, so reading it means the SQL API with an account token held as a secret and a second network hop. R2 is already bound, is the record, and outlives Analytics Engine's three months. The index stays what it was, for ad hoc queries outside the Worker.

**Bounds.** One run reads at most 800 batches in all, shared by the two days it rolls (a Worker invocation allows about a thousand subrequests, and each batch read is one). Yesterday is read first, since no earlier run has counted it; the day before gets what is left, and when that cannot read it whole it keeps the rows an earlier night wrote. Batches past the cap go uncounted until a Queue exists: a run lists the same keys in the same order, so the next run reads the same first ones again, and `Rolled.truncated` says the day was cut. A row keeps at most 64 cells, so a crafted batch cannot grow a row. The rollup reads only the telemetry record and writes only its own table: no file of it names a deposit or a contributor (a test pins that), and `ledger.test.ts` allows no other scheduled job. A hook cell's group value is `<harness>/<version>`: the harness from the closed list, else `other`, and `unrecorded` when the fire has none (a nightly run, or a fire from before the field); the version is as written, `other` when not version-shaped, or `unrecorded` when the fire saw none (for example `codex/unrecorded`). A command or store cell's is the oars version as written, or `other` when it is not a version-shaped word. Listing a day's keys is one subrequest per page of 1000, on top of the 800 reads.

## Known gaps

**Bundles read at different times or versions.** Withholding is decided within one bundle, from the cells it holds. Two bundles of one harness version fetched at different times can still be set against each other: a deposit between them can change which day is the smallest served, so the first withholds one day and the second another, and a reader who holds both has each day's number and the week's. Another version's bundle can still serve an environment cell this bundle dropped, so bundles of different versions can also undo withholding by subtraction.

A live read's baseline is not traceable through lineage: the floor counts only the sliced day's cells, so the read cites those and states `value.baseline` from cells it does not cite (cells at the floor, like every other number a bundle serves).

`POST /v1/login/start` and `POST /v1/login/poll` are unauthenticated and, in the Worker, unlimited: each start spends one call to the provider's device-code route and each poll one to its token route (and, on approval, its profile route) from the Worker's address, so the rate-limit rule in deploy step 6 is what bounds them and the pool must not be deployed without that rule.

`POST /v1/telemetry` is unauthenticated and, in the Worker, unlimited, and each request writes one R2 object of up to 1 MiB that never expires: the same rate-limit rule in deploy step 6 is what bounds it, so the pool must not be deployed without that rule.

## Where D1's own limits bind

With no cap on contributing, the only ceilings left are D1's. Cloudflare's page (`developers.cloudflare.com/d1/platform/limits`) could not be reached when this was written, so the figures below are from memory and **unverified**: a database holds 10 GB on the paid plan (500 MB on the free plan), and a row (a string, a BLOB, or the table row) holds 2,000,000 bytes.

- **A row.** The 1,800,000<!-- figure:join-limit -->-byte join limit above is that row limit less the room for the row's small columns. By the fixture's numbers (about 278<!-- figure:per-call~1 --> bytes of skeleton for each tool call: a 5,000<!-- figure:big-calls -->-call session is 1,391,361<!-- figure:big --> canonical bytes, `parts.test.ts`) a session of about 6,500<!-- figure:row-calls~500 --> tool calls is the largest one row holds. A longer session is refused with 413 until its skeleton is stored across rows or in R2.
- **A database.** The ledger holds about 1,900<!-- figure:sample~100 --> bytes for a one-prompt, two-step session (`ingest.test.ts` pins the fixture at 1,938<!-- figure:sample -->) and about 278<!-- figure:per-call~1 --> bytes for each tool call beyond it, so 10 GB holds roughly 5.2 million<!-- figure:sample-sessions~100000 --> minimal sessions, or about 100,000 sessions of 100 KB. The `cells` and `strata` rows add to this and are shared across accounts. These are the numbers that make a migration off a single D1 database the trigger to plan for, at around half of the database (about 5 GB), well before the write fails.
