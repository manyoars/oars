# The `oars sessions` store (version 15)

`oars sessions` keeps a local, deterministic memory of the operator's own Claude Code sessions: no model call, no network, and no session data
uploaded. `gold arms` is the one exception: it sends redacted text through your own Claude subscription. Telemetry (`docs/telemetry.md`) is separate: it records one event per command (its path, flag names, duration, exit code, and error class) and one per hook fire, recall, deposit, and fetch (counts and closed words only), each with a random install id, the oars version, the OS, and the time in its own folder, and sends those events to the Many Oars pool, or the pool server in `OARS_POOL_URL`. This page is the store's format. The types are in `packages/cli/src/sessions/schema.ts`; the commands are in the CLI README.

## Layout

Under `<config>/oars/sessions/` (`%APPDATA%` on Windows, `$XDG_CONFIG_HOME` or `~/.config` elsewhere):

| Path | What it holds |
|------|---------------|
| `observations.jsonl` | The log of captured records, appended to and compacted (below). A changed transcript is deposited again under a higher `rev`; readers keep only the highest `rev` of each session. |
| `derived.json` | The derived records, rewritten from the log alone at the end of every deposit. |
| `hook-index.json` | The recurring error signatures per project and overall, read by the hooks. |
| `skeletons/<session>.json` | One per transcript: ids, timestamps, tool linkage, token counts, a SHA-256 for every content field, and a Merkle root over the raw lines. Hashes only, never content. `verify` checks these. |
| `state.json` | Per file: size, mtime, the `rev`, capture version (`v`), `sid`, and the `--redact-domain` set, so an unchanged file is skipped. |
| `salt` | This machine's salt, which file targets are hashed with. Local-only (class `L`), never shared. Its `sid` (the first 8 hex characters of its SHA-256) is stamped on every capture record. |
| `pending/<hash>.<uuid>.json` | One file per deferral of a session a Stop hook could not deposit because another deposit held the store lock: `{"transcript": "<path>"}`, class A, no prompt text. The next deposit takes it and removes the file. See "A Stop deposit the lock refused". |
| `schedule.json` | `{"schedule":"off"}`, written by `oars sessions hook install --schedule off` so a later plain install leaves the Windows nightly task off; removed by `--schedule nightly`. Holds no session data. Safe to delete (the next plain install on Windows registers the task again). |
| `pipeline-runs.jsonl` | The step log: one row per run of a pipeline step (deposit, derive, index, verify, recall, read), appended when the step ends. See "The step log". |
| `cells.jsonl`, `motifs.jsonl` | Counts per motif, frame bucket, and day, and the motifs they name. Computed from the log, rewritten by `oars sessions read` and by every whole-store deposit (the nightly one and a manual one), and safe to delete. A pull reads them, and writes them only on a store with no stored pool. See "Motifs, cells, and reads". |
| `recalls.jsonl` | One row per recall, pull or push, shown or held, hit or miss. Append-only, written when the recall happens. `sid`, `at`, and `query.text` are class A; the rest is class P. See "Recalls". |
| `consequences.jsonl` | What each recall led to, by recall ID. Computed from `recalls.jsonl` and the log, rewritten by `oars sessions read` and by every whole-store deposit, and safe to delete. A pull neither reads nor writes it, except on a store with no stored pool. |
| `reads/<pool>.jsonl` | One pool version's reads, written once and never rewritten, so a read cited by its ID stays what it was. |
| `pool-outbox/<hash of server>/v<vocab>-<fields and format>/<key>.<sha256>.jsonl`, `pool-outbox/<hash of server>/shown.log`, `pool-outbox/<hash of server>/deltas-sent.log` | Batches `oars pool deposit` built, one per session, as canonical JSON: sorted keys, no optional whitespace, UTF-8, and named for the SHA-256 of exactly those bytes. `shown.log` records which hashes `oars pool outbox` printed, and when. `deltas-sent.log` is the once-only mark of the local deltas a batch carried, one 16-hex hash a line (the account, the entry without its `change`, and the index of its after window on a fixed grid from the epoch), appended only after the batch that carries the delta is written. `deltas-sent.log` is class A and never leaves the machine. A batch is sent only if its hash is in `shown.log` and the file still hashes to its name. A folder from another vocabulary version, field list, or skeleton format is stale: it is never printed or sent, `pool deposit` removes it, and `oars sessions verify` reports the count (`staleBatches`). Class `L`: nothing here leaves the machine until a send, which `oars pool deposit --send` makes after the covenant is accepted (telemetry events never come from this folder). See `docs/pool.md`. |
| `raw/<project>/<path>` | oars' own archive of every deposited transcript (below). |
| `commit-survival.jsonl` | What became of each commit older than `SURVIVAL_DAYS`, appended on a change of state. See "Commit survival". |
| `crossings.jsonl` | Written by `oars gate replay` and appended to by the `oars gate hook` as each crossing happens (a `via` field says which): one `run` row, `registry` rows, and one `crossing` row per package, MCP server, or skill pick found in raw transcripts. Closed-vocabulary fields are class P, among them `policy` (`default`, `file`, or `invalid`), `arm` (`shown`, `held`, or `none`), and `lineShown` and `lineHeld` (ids from a closed table, never free text); `session`, `agent`, `toolUseId`, `ts`, `name`, and `version` are class A, and so are a `registry` row's `name`, `latest`, and `created`. See `docs/gate.md`. |
| `gate-registry.jsonl` | The registry answers the gate hook asked for, kept until the end of the next UTC day (a not-found answer is trusted for 10 minutes) so a name asked about is not asked about again at once: one row per answer, with the `name`, `latest`, `created` of what the registry held, and `ts`, the time it was read. Appended by the hook, and by the helper that finishes an ask the hook had to cut. Class A (a name and a version; `ts` is a finer time; `folder` is a truncated SHA-256 of the folder asked in, and a kept answer answers only that folder). Safe to delete; the next crossing asks again. |
| `gate-policy.json` | The gate policy: per class `warn`, `block`, or `off`, a day count, and the holdback share. Written by the operator only; read by the hook and `oars gate policy`. Class A as a file, since it is operator-written; the values it holds are class P (closed vocabulary and two numbers). A missing or invalid file reads as the defaults. See `docs/gate.md`. |
| `gate-ask-<hash>.lock` | An empty file, one per name a helper is asking the registry about, so a second helper does not start for 5 minutes. The hash is truncated and carries no text. Class A, since a guessed name can be tested against it. Safe to delete. |
| `gate-index.txt` | The hook's novelty index: a header, then one line per name, repository, and session ever seen, each a truncated unsalted SHA-256, never the text. Seeded whole by `oars gate replay`, appended by the hook. Class A, because a guessed name can be tested against an unsalted hash. Safe to delete; the next replay rebuilds it, and until then a hook row reads novelty as `not-read` and the hook shows no note (a block still applies). |

## Capture scope: the allowlist

Capture reads every project folder unless the saved list names some, less every `!` (`--deny`) entry. The rule is one filter, `allow.allows(folder)`, applied in
`deposit` (`store.ts`, `depositLocked`) and in the SessionEnd hook (`depositSessionLocked`, which returns `not-allowed` and writes nothing when nothing is pending, and otherwise leaves the filter to `depositSessionInto`, which returns it after the drain; a hook that finds the lock held applies the same filter in `depositSession` before it defers, so an off-allowlist session leaves no pending entry either). A folder off the list (one a `--deny` entry names, or one the list leaves out
once it names folders) is out of scope by design, so a transcript there is never in `state.json`, `raw/`, or any record. That is a
choice the operator makes, not a gap. Three kinds of folder are read by default and left out once the list names folders, unless it names them too:

- **Other projects.** A repository you never allowed.
- **Throwaway working directories.** Scratch and test folders under the temp directory, and probe directories a harness job starts in.
- **Worktree folders of an allowed repository.** Claude Code names a worktree's folder `<repository>--claude-worktrees-<name>`, a new folder per worktree. An entry naming
  only the repository's folder (`~/work/app`, or its slug) matches that one folder and none of its worktrees. Name them with a folder prefix (`~/work/app/`, trailing slash) or a glob (`*-work-app*`), which matches the repository and every folder under it, including worktrees created later. Matching is on the slug, so either form also reads a sibling folder whose slug starts the same way (`~/work/app/` takes `~/work/app-other`, and `*-work-app*` takes `-work-application`); this list is the privacy gate, so name the prefix with that in mind.

A transcript in an allowed folder that is not yet in the store is a different thing: it is a session still running, or one that ended after the last
whole-store run, and the next `deposit` or nightly run takes it. The SessionEnd hook deposits only its own transcript.

The scope is not silent. `oars sessions deposit` prints the number of folders it skipped. `oars sessions verify` lists, from folder listings alone (it
opens no file in those folders, not even a subagent's `.meta.json`), the folders that hold transcripts and are not on the saved allowlist, with the total of their main transcripts: a text line (names capped at ten) and `scope`
(`folders`, `transcripts`, and every name) in the `--json` document. It is scope, not a failure, so it never fails `--strict`, a folder that cannot be listed is named with no count, and a projects root that cannot be listed reports an empty scope, rather than failing `verify`; the text line says "no main transcript" at a count of 0. A folder that holds only subagent transcripts (`<session>/subagents/agent-*.jsonl`, no main transcript) is named too, since a deposit would capture them; the count is of main transcripts, so it can read 0 for such a folder.
`deposit`'s number also counts folders with no transcript, and uses that run's `--allow`, so it can differ from `verify`'s. The scope covers the whole projects root, also under `--session`.
It reads the saved allowlist, where no entry that names a folder means every folder, so after a state loss (`state.json` missing or torn) it names none until a deposit saves a list again; a saved `!` entry (`--deny`) is off the list.
`oars sessions books` prints the same line (it lists folders only, so it adds no read), so a total over the stored sessions does not read as complete.

## The log's growth and compaction

Every append to `observations.jsonl`, from a hook or a deposit, runs under `store.lock`. A changed transcript adds a full new `rev` of that session, and a
`CAPTURE_VERSION` bump re-captures every transcript, so during that deposit the log holds about two copies of the store. The size is not limited by a string: every reader
streams the log line by line, so a log past Node's 536,870,888-character string limit still loads.

At the end of a whole-store deposit, after `state.json` is written and before the derived records are rebuilt, `compactLog` (`store.ts`) drops every line a higher `rev` of its session
replaces, so the log settles back to the size of the live records. A hook deposit never compacts.

- **What stays.** Only a superseded line goes. A line this version cannot read stays, since a later oars may read it, and a kept line is written back byte for byte. What `loadStore` returns does not change.
- **What triggers it.** What the log holds, not what the run captured, so a run that died after its re-capture is compacted by the next deposit, even one with nothing left to capture. A log with nothing superseded is read once and not rewritten.
- **How it stays safe.** The rewrite goes to `observations.jsonl.<pid>.tmp`, is synced, and replaces the log by `rename`, all under the store lock, which its holder keeps refreshed so a long deposit is not judged stale. A crash before the rename leaves the old log whole and a temp file no reader opens, which the next compaction removes.
- **A holder that hangs.** The holder refreshes the lock for at most six times the stale age (`holdMs`, one hour: the stale age is 10 minutes, and a whole-store re-capture is the work that outlasts it). Past that the refresh stops, the lock ages out like a dead holder's, and the next waiter breaks it and writes one line to stderr naming the holder's pid (`oars: broke the store lock held by pid <pid>, not refreshed for over <staleMs> ms`). A hung process cannot keep every later deposit and hook waiting for good; the run that outlives the cap loses its lock, says so on its own stderr (`oars: this run held the store lock past <holdMs> ms and may lose it; rerun it when it ends`), and should be rerun. The lock names its holder with a per-claim token, so a holder whose lock was broken never deletes the next holder's lock when it ends.
- **When it gives up.** Compaction leaves the log as it was and writes one line to stderr, and the next deposit tries again, if the log's size changed during the rewrite (a waiter broke the lock) or if Windows keeps refusing the rename for 30 seconds because a reader holds the log open. A failed compaction does not fail the deposit: the records are safe and an uncompacted log still loads.

## A Stop deposit the lock refused

The Stop hook waits at most 3 seconds for the store lock. When another deposit still holds it, the hook no longer leaves its session to the next whole-store run (register row A55). It records the session in the pending list and exits as it always did: no output, exit 0, and no wait beyond the 3 seconds.

- **The list.** One file per deferral, `pending/<hash of the transcript path>.<uuid>.json`, holding `{"transcript": "<path>"}` and nothing else: no prompt text, tool text, session id, or project name beyond what the path itself holds. It is class A (account store, local, never uploaded). A file per session, not one shared list, because the hook that defers must not take the lock it just failed to take and two hooks may defer at once: each writes a file name no one else uses, and a drain deletes only the file names it read, so a session that defers again while a drain runs leaves its newer file for the next deposit and an append racing a drain is never lost. The drain dedupes by the hash, so a session that deferred twice is one entry. Each file is written under a temp name and renamed, so a drain never reads a torn one. If the file cannot be written, the refusal is what it was before: an `error` row and a hook-call error. The filter reads the saved allowlist, so a folder that a running deposit is adding (the first-ever whole-store deposit, or one with a new `--allow`) is not on it yet: a hook on that folder returns `not-allowed` with an `ok` row and no pending entry, and the next whole-store run reaches the session.
- **The drain.** Any deposit that holds the lock deposits the pending sessions first and then its own: the Stop hook takes at most 5 (`PENDING_HOOK_CAP`). The cap bounds the count, not the time: a hook that gets the lock late can still deposit five transcripts of any size, and the only time limit is the harness's own ceiling on the hook (30 seconds, `install.ts`). A backlog drains over several hooks, and a whole-store deposit takes all of them before its walk. A Stop hook still never compacts. An entry is removed only after `state.json` is written, so a run that dies between taking the lock and finishing leaves it for the next run. A session already current is a no-op; one whose transcript is gone, or whose folder no `--allow` names now, is dropped and counted; one that fails to deposit stays and is counted, and its failures are in its file name (`.f<n>.json`): entries with fewer failures are taken first, so one that always fails cannot fill the hook's cap, and at 5 failures (`PENDING_MAX_FAILURES`) it is removed and counted as `pendingDropped`, since a whole-store walk still reaches any transcript on the allowlist. An entry that cannot be read at all (a folder named `x.json`) stays where it is and is counted as `pendingKept`; it is listed after the readable entries and does not count toward the cap, so it is neither retried first nor able to fill the hook's cap; a pending folder that cannot be listed is skipped with one line on stderr. A whole-store drain adds what it deposits to the run's `sessions`, `lines`, and `observations` and does not count those files as `unchanged`, and removes `pending/*.tmp` older than the stale-lock age (a hook that died before its rename). Housekeeping never fails a deposit: a temp file the sweep cannot remove, or a settled or failing entry's file that cannot be removed or renamed, costs one line on stderr and is left for the next run. The counts are in the deposit row's `in`: `pending` (entries met, including unreadable ones, so it can exceed the cap), `pendingDropped`, and `pendingKept`.
- **How it is counted.** The refused hook logs a `deposit` row with status `deferred` (below), not `error`.

## Memory

`deposit` and `verify` hold the store as records, so their heap grows with the log's rows, and `verify` also with the skeletons (one entry per transcript line). A reader keeps only each session's highest `rev`, read in
two passes over one open file, so the superseded copies a re-capture leaves behind are never in memory, and a compaction between the passes cannot change what the second pass reads; it keeps one copy of the strings every tool row repeats (the session id, the tool name, the key names).
The cost is time: every read parses the log twice, once for each session's highest `rev` and once for the records at it. No run compared the wall time of the two builds, so the added time is not measured. Two capped runs of the new build at 400 sessions (97 MB log for the no-op and `verify`, the 49 MB clean log for the recapture) took 9.9 and 9.4 s for a no-op `deposit`, 23.4 and 25.1 s for a recapture, and 8.0 and 12.0 s for `verify`.
`deposit` checks for newer captures with one pass that keeps a number per session, and `verify` reads each skeleton without its per-line content hashes, which no check reads.

Measured on a synthetic store (`packages/cli/scripts/sessions-heap.mjs`): peak RSS under `--max-old-space-size=4096`, 8 prompts of 14 tool calls per session, five transcript lines per call that make no log row (text, thinking,
and attachments), so the skeletons hold 2.55 bytes per byte of clean log (the operator's store holds at most 2.8: 1.6 GB beyond a 580 MB log). "No-op" is a deposit that skips every file, as the operator's run did (12 captured, 6,757 unchanged);
"recapture" is a deposit that reads every transcript, as after a `CAPTURE_VERSION` bump. The Log column is the log the no-op and `verify` runs start from, with every record's older copy still in it (a re-capture leaves them until the
deposit's compaction): twice the clean log. The recapture run starts from the clean log, 49 MB at 400 sessions and 97 MB at 800.

| Sessions | Log | `deposit` no-op | `deposit` recapture | `verify` |
|---|---|---|---|---|
| 400 | 97 MB | 409 MB | 419 MB | 567 MB |
| 800 | 195 MB | 480 MB | 501 MB | 833 MB |

The same stores before the change: no-op 477 and 678 MB, recapture 451 and 731 MB, `verify` 673 and 1,048 MB. On a settled log (nothing superseded, 49 and 97 MB), the change gains little: no-op 501 against 483 MB (4 percent), `verify`
896 against 828 MB (8 percent) at 800 sessions. Every whole-store deposit ends in a compaction, so a settled log is the usual state `verify` meets right after one; a store between nightly runs holds the superseded revs its hook deposits wrote, and the larger gains above are for a read that meets such a log. What was measured:
two recapture runs per build at 800 sessions, one with superseded records and one on a settled log (`restore` ignores `--superseded` for a recapture, so the second run repeats the first's shape): old 731 and 551 MB, new 501 and 531 MB. The old build's two runs differ by 180 MB, so two runs per build cannot tell the change from noise. Also measured: the smallest `--max-old-space-size` that finished the 400-session store, before and after: no-op 168 and 104 MB,
`verify` 336 and 248 MB; the recapture is 112 MB on the old build (one run) and 104 and 120 MB on the new (two runs), so no gain is shown for it at this bisect step. The full load that a deposit used to make first, to check for newer captures, is gone; the recapture's measured difference is within the noise.

Where the heap is held (heap by phase, 800 sessions, `sessions-heap.mjs phases`): a no-op `deposit` keeps 150 MB after the load its refresh does, and `verify` keeps 294 MB of lean skeletons and then 439 MB with the store loaded. Which
phase sets each command's peak is not established: the sampler is a timer that cannot fire during a synchronous phase (derive, the index, the verify checks), so those phases show their heap at the end, and the recapture is measured as
one run (about 300 MB sampled) rather than as capture, compaction, and refresh. The kept figures are what decide where to cut next: the skeletons are 294 of `verify`'s 439 MB kept, and `sessionsVerify` still holds them all at once.
Interning the repeated strings took the kept load from 82 to 78 MB at 400 sessions (5 percent); it is not the main holder.

Growth: rows, not files or sessions. One row count (about 45,000 tool rows, and the same skeleton lines) at three session counts gave the same peaks within 6 percent (`--calls` sets the calls per session):

| Sessions x calls | `deposit` no-op | `deposit` recapture | `verify` |
|---|---|---|---|
| 200 x 28 | 403 MB | 415 MB | 602 MB |
| 400 x 14 | 414 MB | 420 MB | 569 MB |
| 800 x 7 | 423 MB | 430 MB | 576 MB |

A session is one file here, so files and sessions were not separated from each other, and tool rows and skeleton lines scale together (the generator makes the same number of non-row lines per call), so those two were not separated either.
From the two sizes above, `verify` grows about 5.5 MB of RSS per MB of clean log from a base of about 300 MB, and `deposit` about 1.5 MB. The smallest heap that finishes (`minheap --sizes 400,800`, new build, clean log 49 and 97 MB):
no-op 104 and 216 MB, recapture 120 and 208 MB, `verify` 248 and 480 MB, which is 4.8 MB of heap per MB of clean log for `verify` (2.3 for a no-op, 1.8 for a recapture), nearly proportional.

**The ratios, old build to old build.** The operator's run before this change, against its 580 MB post-compaction log: `deposit` 6,962 MB, 12.0 times, from a log that still held the stopped runs' copies, so its true ratio to the log it started from is lower; `verify` 6,144 MB, 10.6 times, on a compacted log. The same builds on the synthetic store at 800 sessions (97 MB clean): `verify` 896 MB on a settled log, 9.2 times; `deposit`
678 MB on the superseded log, 7.0 times (501 MB, 5.2 times, settled). The new build: `verify` 828 MB settled, 8.5 times (833 MB, 8.6 times, superseded), `deposit` 480 MB, 4.9 times (483 MB, 5.0 times, settled). The ratio is not scale-free
(a fixed base of about 300 MB sits under it), so `verify`'s two are compared at one log size, 580 MB: the synthetic old build grows 6.1 MB per clean-log MB ((896 - 300) / 97), which is 6.7 times at 580 MB, against the real 10.6, a
factor of about 1.6 and a gap of about 3.9 times. The skeleton share (2.8 bytes per log byte on the real store against 2.55 here, 1.1 times) lifts 6.7 to about 7.3 times: it closes at most 0.6 of that 3.9. No holder sized here
closes `verify`'s gap, and none closes `deposit`'s (7.0 against at most 12.0). The rest is unlocated; a read-only look at the real store's `reads/`, `cells`, and `motifs` sizes, and at `verify`'s counts, is the way to find it.

**The limit.** The new build is not measured on the operator's store, so the answer is by command:

- `deposit`: unmeasured. The synthetic store extrapolates to about 1.3 GB of heap for a no-op and 1.1 GB for a recapture at a 580 MB clean log, but `deposit` is the command whose real ratio the synthetic store does not reach, so that is
  a floor, not a forecast.
- `verify`: unmeasured on that store. The synthetic least heap, 4.8 MB per clean-log MB, extrapolates to about 2.8 GB at 580 MB (the 800-session run's 480 MB over 97 MB, 4.95, gives 2.9). Scaled by the real store's heavier ratio, old build to old build at 580 MB (10.6
  against 6.7, a factor of about 1.6), it is about 4.5 GB. So the least heap is about 2.8 to 4.5 GB, and the upper end is over node's default heap (about 4 GB on a 64-bit machine): the default may not hold. It agrees with a measured run: `verify` at 2,945 MB RSS under a 2.8 GB heap cap on a smaller store
  of the older build: RSS runs above the heap (this store's `verify`: 567 MB of RSS against a 248 MB least heap at 400 sessions) and V8 fills the cap it is given, so that figure bounds the need and does not measure it.

Until a run on the real store measures them, set the heap for both: a store that outgrows it sets its own, as the 580 MB log did: a deposit of that log needed `NODE_OPTIONS=--max-old-space-size=10240`, and the same works for `verify`.
`just sessions-heap` checks that both commands finish a generated store under a fixed small heap, and fails unless a recapture reports every session captured and a no-op reports none.

## Two versions

- `CAPTURE_VERSION` (`cv` on every captured record) names the captured field list. Bump it when the captured field list changes or a
  stored value of an existing captured record or skeleton changes: a bump re-reads every transcript. The skeleton is written at capture and
  carries `CAPTURE_VERSION` in its `v`.
- `EXTRACTOR_VERSION` (`v` on every derived record) names the derivation rules (error normalization, prompt classes, tool-name sequences,
  recovery episodes, prompt outcome signals). A bump re-derives from the log; no raw transcript is read. Version 11 (pool vocabulary spec Section 2) changes no stored value: it moves raw
  `agentType`, `keys`, and `frameId` with the joined `frame` from class P to class A, so they stay in the account store and only their projections (`projectAgentType`, `projectKeys`) may pool; the joined frame pools only as its separate cells (the projection functions ship in this release; the deposit skeleton does not call them yet and keeps sending the joined `frame` until a later release). A store written at 10 re-derives
  on its next deposit with every captured record as it was. What the projection takes from the shell form is computed from the store and never written: `program`,
  `subcommand`, and `flags` come from the record's `steps`, and from its `segments` for a program the curated list does not name. A step's own names are limited to the
  curated lists, since capture narrowed them to those: a program only the snapshot lists, such as `ffmpeg -i in out`, keeps its program, first or later and behind any wrapper,
  `timeout`, or block keyword, but loses `-i` stored, because a segment holds no flag; a program no list names goes on the wire as its basename after redaction, and `private` only when the redactor, an exclusion term, or the name shape rejects it. A record captured before CAPTURE 9 has no
  steps, so its flags are lost and it projects the program and subcommand alone from the A copy of `target` (a `target` cut at 30 characters or masked by redaction projects `program: private`).
  No staged pooled file or outbox exists for the migration to delete.

Version 4 (CAPTURE 4) adds `sid`, `repo`, `fileHashes`, `env`, `promptFingerprint`, `targetBase`, the repository-root path base, and a
1,000-character cap on an error line, and a cap of 100 on `files` and `fileHashes` per session (p99 was 61, max 209, on the 8,253-session
copy store); `recall --path` sees the first 100 sorted paths of a session. Version 5 (CAPTURE 5) changes no field name: it changes the
stored `models` value of an existing skeleton to carry the cost-state keys (see the cost-state paragraph below), so a version-4 store is
behind and its next deposit captures every transcript again. Version 6 (CAPTURE 6) adds `segments`, `pulls`, and `commits` to the tool
record (see "What a shell call captures"), and a version-5 store's next deposit captures every transcript again. Version 8 (CAPTURE 8 and EXTRACTOR 8) changes no
field name either: it changes what `tool`, `error-line`, and the session's `tools`, `bashCmds`, `tldrs`, and `confidences` hold. The harness writes
`api-request-blob` lines, copies of the request body with no `cwd`, `uuid`, or `timestamp`; capture read their blocks as conversation and wrote every call
a second time with status `none` (99.8% of the 55,801 `tool_use` blocks on those lines repeat a real call). It no longer reads them, and a call a
resumed transcript replays under the same tool-use id is written once. The skeleton still lists every line, so the counts and the root bind. A reader
folds an older store the same way (`fold.ts`): one `tool` record per session and tool-use id, the first, with the first status found and, when the first has no `ts`, the
`target`, `targetBase`, `ts`, and `harnessVersion` of the first copy that has one; the kept records are numbered from zero and each `error-line`'s `after`
moves to match, so `next` and `editFollowed` read the same calls as a current capture; and the session's `tools` and `bashCmds` are less the dropped calls. A call with no result is still a record, status `none`. Version 9 (CAPTURE 9)
adds `frame` and `frameId` to the session and prompt records and `steps` to the tool record (see "Frames and steps"), and moves `tool`, `tools`, and a shell-form

## Captured records

Every record carries `kind`, `cv`, `sid`, `session`, and `rev` (a version-3 record reads with `sid` null). Text is redacted (secrets by
pattern and entropy, emails, and the domains named with `--redact-domain`) before it is cut or written. Each field has one class
(the umbrella repository's D1 spec, Section 1.1). The store uploads nothing (telemetry, `docs/telemetry.md`, has its own folder and carries nothing from the store), so a class says what a field may hold, not where it goes:

- `L` the most sensitive: raw transcripts, the unhashed paths, the project folder slug, the salt, `state.json`.
- `A` redacted text (cut to its limit), join ids, and every salted hash.
- `P` the least sensitive: names, versions, counts, durations, status, key names, and day-resolution dates. It holds no free text, URL, path, path hash, session id, or branch.

**Usage totals say what they cover.** A session's and a prompt's `usage` is a sum over the responses that reported usage, and `usageObserved` lists the categories (`input`, `cacheWrite`, `cacheRead`, `output`, `thinking`) at least one of them reported, while `usageResponses` counts those responses (compare it with `assistantTurns` or `turns`). A category not listed was never recorded by the source: its number in `usage` is a placeholder zero, not a measurement, and the skeleton and the pool wire send it as null. A Cursor bubble with a zero token count, a VS Code Copilot request with no `modelTotals` or a zero `inputTokens`, a `modelTotals` entry that names no `cachedTokens` or `outputTokens`, and any line without a `usage` object therefore leave their category unobserved; a `cachedTokens` or `outputTokens` of 0 that a `modelTotals` entry carried is a value and stays observed, since a request with no cache hit really cost nothing there. A record captured before version 20 has neither field and reads as fully observed.

**Local totals read the same labels.** Every local reader that sums or averages usage skips a category the source never recorded, never counting its placeholder zero. A `books` column sums only the prompts that recorded the category and prints `n/a` (`null` in `--json`) when none did; a partial column is named under the table (`<key> cache read: 2 of 3 prompts recorded`), and `--json` carries the counts as `usageRecorded`. `measure`'s cache-write mean is over the sessions that recorded cache writes, prints `n/a` when none did and `-` for an empty window, and says `(n of m)` when it covers only some (`cacheWriteSessions` in `--json`). A derived cell's `tokens` adds only the categories each prompt recorded and only the prompts that recorded input; it is `null` when no session did, and `tokenSessions` says how many of its `sessions` it covers. The self-baseline's cache-read share needs `input` and `cacheRead`, and its output per turn needs `output`, so a prompt that did not record them adds no count to that dimension. The same cell derivation serves the pool server's cells, so a served `tokens` sum holds only what was observed; the served column is a running sum, so a cell no batch session recorded adds 0 to it and carries no coverage count.

Of the class A fields above, two have a form that leaves on a pooled skeleton: `repo` leaves only as the frame's `repoKey` (the same salted hash, 16 hex characters, never the identity), and `tsFirst` and a prompt's `ts` leave only as the UTC `hour` (0 to 23) beside the frame's `day`. The fields themselves stay local.

A `P` date is at day resolution only: the finer timestamps above are all class `A`. `sw` (the per-field local-only switch for text
fields) applies to `urls`, `searches`, `branches`, `tldrs`, `confidences`, `head`, `line`, `sig`, `example`, and `mcp-calls.jsonl` `query`.

`env` (class P) is `{ harness, oars, node, os }`: the last harness version the transcript names, the oars package that captured it, the
Node.js version, and `process.platform`. A library version is recorded only when a transcript states it, and none is read today.
`promptFingerprint` is the hash of the `prompt_snapshot` attachment (version 3's `contextFingerprint` also mixed in the `environment`
snapshot, whose platform and shell now belong to `env`).

### What opens a prompt

A prompt is a main-line, non-meta user line with text and no tool result, read by `promptOpening` in `extract.ts`. `opened` says how it opened, and is closed so it can never name a command:

| The line | Prompt | `opened` | `head` |
|----------|--------|----------|--------|
| The operator's text, a leading `<` included | yes | `typed` | the line |
| A `command-name` or `command-message` wrapper, when a model's turn comes next and the text also holds the closing tag; an unclosed one reads as `typed` | yes | `command` | the command and its arguments with the wrapper tags removed, redacted and cut like any prompt |
| The same wrapper with no model's turn next (`/clear`, a local command with output, a synthetic line alone) | no | | |
| A line the harness injected: `local-command-caveat`, `local-command-stdout`, `local-command-stderr`, `system-reminder`, `task-notification`, `teammate-message`, `scheduled-task`, `bash-input`, `bash-stdout`, `bash-stderr`, when the text also holds the closing tag; an unclosed one reads as `typed` | no | | |

A slash command and a skill write the same wrapper, so one value covers both; a skill's body is a meta line and stays out of `head`. The wrong-way risk is known: a tag the harness adds later reads as `typed` until it joins this list, and its row shows it in `head`. The interrupt marker reads as `typed`. A line that opens no prompt belongs to the prompt before it, or to none at the start of a session. Every harness but Claude Code keeps the old rule, no leading `<`, for now.

### What a shell call captures

`target` stays what it was: the first line's program and subcommand, the retry identity. Three optional fields read the whole command, on every
line and at every shell separator, after heredoc and here-string bodies are dropped and the command is redacted. A shell's own argument
(`bash -c "..."`) is read too. No registry is asked and nothing runs, so each field is what the command and its result say.

| Field | On | Holds | What it does not say |
|-------|----|-------|---------------------|
| `segments` | every shell call | One `{ run, read }` per command, the last 50. `run` is the program's basename and its plain words, at most 12, each cut to 30 characters: no flag, path, variable, or quoted text. A program whose basename holds whitespace stores `<literal>` in its place. `read` is whether the call's status reports that command: false when a pipe follows it, when a later `;`, `&`, newline, or `\|\|` overrides it, when it sits in a group a pipe follows, or when it runs in the background. | An unquoted word is kept, so `echo hello there` is kept as written, redacted. |
| `pulls` | a call that names one | `{ ecosystem, name, version }` with ecosystem `npm` (npm, pnpm, yarn, bun, `npx`, `bunx`, `dlx`), `pypi` (pip, `python -m pip`, uv, `uvx`, pipx), `cargo`, `go`, `gem`, `brew`, `skill` (`npx skills add`), `plugin` (`claude plugin install`, `codex plugin add`), or `mcp` (the full server name from `mcp__<server>__`, on every MCP call). `version` is as stated, or null. A scoped name stays whole. A lockfile install, a local path, and a variable name nothing. | A name is not a verified package, a run of `npx` may hit a local bin, and a failed install still names its pull. A command behind `xargs` or in a script is not read. |
| `commits` | a clean shell call that ran `git commit` | One entry per commit, in order: the sha, or null. The sha comes from the `[branch sha]` line, or from a `git rev-parse HEAD` or one-commit `git log` that is the call's final command, joined by `&&` or `\|` in the same repository with nothing between that moves `HEAD`. A count stands without a sha, and a `-q` commit with no such read-back has none. A dry run or help call is no commit, and neither is one refused with `nothing to commit`, `fatal:`, or `error:`. | A commit behind `;` whose hook failed with other text still counts, since the call came back clean. A failed call records no commit even when its own result proves one: `git commit -m x && git push` with a rejected push holds a `[branch sha]` line, yet `commits` undercounts it and the `redo` window stays open. |

### Frames and steps

CAPTURE 9 gives every call a shared coordinate, so calls compare across harnesses, models, versions, and dates. Nothing here is asked of a
network or a model: a value outside a closed list reads `<literal>` or is dropped. `frame` and `frameId` are class A (EXTRACTOR 11): one hash over harness, version, model, effort, day, platform, shell, and stack is an identifier that links rows, so only the frame's separate fields are to pool, each as a cell under its own rule (the projection functions ship now; the deposit skeleton keeps the joined frame until a later release). The lists live in one file,
`src/sessions/public-vocabulary.ts`, and default to `<literal>` when unsure.

A `frame` sits on each prompt, and on the session for the calls before the first prompt: `{ harness, harnessVersion, model, effort, day, platform,
shell, stack }`. `day` is the UTC date. `stack` is a language mix, framework names, and a repository size bucket, each from a closed
list. `frameId`, beside it on the record, is a 16-hex hash of the frame, and a step names it. `shell` and `stack` are read across the whole
transcript, so they belong to the file at this `rev`: capturing a transcript that has grown can change them, and with them the `frameId` of its
earlier prompts.

`steps` sits on the tool record, one per call, or one per command of a shell call, the last 50 as with `segments` (`&&`, `||`, `;`, pipes, and
subshells, with quoted separators left alone, tied by `seg`). It is nested so `n`, the count bindings, and the Merkle checks do not move.

| Field | Holds |
|-------|-------|
| `n`, `seg` | The call's position in the transcript, and the step's position in the call. |
| `action` | One of the closed list in `src/sessions/actions.ts`, from one table per adapter. An unmapped name is `other`. |
| `native` | The harness's name for the tool when its table lists the name, or when every name it holds is public, else `<literal>`. |
| `identity` | By action: shell `{ program, sub, flags, pulls? }` (flag names, never their values, so `-c1-200` reads `-c` and `head -20` reads `-N`; a pull is `{ registry, name, version }`), MCP `{ server, tool }` (a server name is a label the user picks, so `tool` is `<literal>` unless the allowlist lists that tool under that server, and on a harness whose spelling cannot say where the server name ends, as Cursor's `mcp_<server>_<tool>`), skill `{ skill }`, web `{ host }`, else null. Any value outside the allowlist is `<literal>`. |
| `status` | The call's status where it reports this segment; `none` where it does not, such as a segment a pipe hides. A failed call of several commands (`a && b`) leaves each read segment `none`: the result carries one exit and does not say which command failed, so the failure stays on the call (its `status`, and the `after-error` edge into the next call), and a later clean run of a segment gets no `retried` edge from it. A call of one read command keeps the call's status. |
| `cost` | `{ tokens, durationMs }` on the first segment; later segments hold nulls. `tokens` are the response's output tokens shared evenly among its calls. `allocated: true` marks a figure that was divided among two or more calls; it is absent where the response made one call, so the figure is that call's own. The wire carries it as a step's `allocated`. |
| `parent` | On a subagent's step, the `n` of the call that spawned it, in the transcript its session record names as `spawnedIn` (the main session, or a sibling subagent, since a subagent can spawn another); null when that call is not known. |
| `edges` | The edges arriving at this step, `{ kind, n, seg }` naming the source: `next` (order within a prompt's line of work), `spawned`, `retried` (same native name and same redacted command or target, after that one failed), and `after-error`. `spawned` needs the subagent's `.meta.json`; `raw/` does not hold that file, so a re-capture takes `spawnedBy` from the log, and a subagent first seen in `raw/` has no such edge. On the wire (`docs/pool.md`, "Edges and the spawn link") an edge is `{ kind, target }`, the target a step position in the transcript instead of `{ n, seg }`, and a transcript names its spawner by position (`spawnedIn`); a skeleton-derived store reads them back into this form. |
| `frameId` | The frame of the call's prompt. Class A, like the frame it hashes. On the wire a step names its frame by position instead (`frame`, an index into the transcript's `frames`): the prompt's frame with the call's own `model` and `harnessVersion` (`docs/pool.md`, "Step attribution"). |
| `skill` (on a tool record, not an `identity`) | The skill whose run the call's line sits in (`attributionSkill` on the line). The harness marks no end to a run: the run ends at the first line that no longer names the skill, so a call after it carries none. Class A. A step takes its call's `skill` on the wire: the name after redaction, or `private` when it counts as redacted. Limit: a skill the harness does not name on the line shows nothing, and a nested skill shows only the outer name the line carries. |
| `model` (on a tool record) | The model the call's own line names (`requestedModel`, else the message's model), so a step is attributed to the model that made it and not to its prompt's majority. Class P. Absent when the line names none and on a record captured before it; a step then takes its prompt's model. A name only, never a version of the model. |

### Errors, packages, and stack strata

Version 14 stores what the pool's fit, adoption, and live families need, as values that a projection can reduce to a list member, `other`, or `private`: `projectLanguageShare` and `projectRepoFiles` return null for a value outside their list, and `explore` is a count that the wire half buckets. Nothing here is sent anywhere by capture. Every source below is the transcript, except `repoFiles`, which keeps its existing source: the repository's git index header (`repoFilesFromIndex`), read once on a transcript's first capture and carried by `repoSize` after.

| Field | On | Holds | Class and projection |
|-------|----|-------|----------------------|

### Prompt outcome signals

Each derived `prompt` record (`EXTRACTOR_VERSION` 6) carries four deterministic signals, kept separate: no composite, no score (a fifth, `intervention`, is described after the table). A version-2
line, read as written, has none of them. They read the main line only, with a resumed session's repeated calls dropped; a subagent
transcript's calls are not read.

| Field | Values | Rule | What it does not say |
|-------|--------|------|---------------------|
| `verify` | `passed`, `failed`, `masked`, `none`, `na`, or absent | The last build, test, type-check, or lint runner in `segments` after the prompt's last edit (`isRunner` in `derive.ts`), less a backgrounded call, whose result says only that it started. `passed` and `failed`: the call's status reports that runner. `masked`: a pipe or a later command hides its exit, so the exit is unknown. `none`: no runner ran, or its call has no result. `na`: the prompt edited nothing. Absent: the walk reached a shell call captured before `segments`, which could have been a runner. A failed edit is not an edit. | `passed` means a clean exit, not that the suite covers the change. `failed` includes a call that was rejected or denied and never ran, and a chained command after the runner failing: `npm test && git push`. The runner list is a rule over program names, so a repository's own script name is not seen. `run` holds no flags, so a bare `tsc` reads as a runner even when the call was `tsc --version`. A call that passes `run_in_background` as false is dropped too: capture keeps the key, not its value. |
| `stopped` | `interrupt`, `rejected`, null | `rejected`: a main-line error line starts `The user doesn't want to proceed with this tool use` or `The user doesn't want to take this action`. `interrupt`: the next prompt record starts `[Request interrupted by user`. A rejection wins, since the harness writes the marker right after it. | A classifier or hook denial is not a stop: it is policy, and the model carries on. |
| `commits` | a count | The entries in the prompt's captured `commits`. A record captured before CAPTURE 6 counts a clean call whose `target` is `git commit`. | That older count is a floor: `target` holds only the first line's first program and subcommand. A commit made by a script or an alias is not seen. |
| `redo` | true, false | A later prompt in the session edits a path hash this prompt edited, within `REDO_WINDOW` (3) prompts, with no commit that `commits` can see between them. | A commit a script made does not end the window, and a planned second edit of one file reads the same as rework. |

The interrupt marker is a user line, so capture keeps it as a prompt record of its own, with no tools. It counts toward `REDO_WINDOW`'s
distance and in a share of prompts; its own `stopped` is null and its `verify` is `na`.

### Prompt intervention

A fifth signal, `intervention` (`EXTRACTOR_VERSION` 13; `user-stop` joined the list at `EXTRACTOR_VERSION` 14), says whether a human stepped in after the prompt's work and how. It is one member of a closed list, computed on the machine from the records
the other four signals read, so a transcript re-derives to the same value. It is a record of what the next human prompt did, **not a grade**: `none` does not say the work was good, and a bucket
other than `none` does not say it was bad. Prompt text never reaches the wire; the local rule below reads a prompt's `head` (the first 300 characters, redacted) for one case, and only the bucket leaves.

"The next prompt" is the next prompt record of the same transcript, `Q`, for a prompt `P`. A prompt derived before `EXTRACTOR_VERSION` 13 has no `intervention`; a wire batch carries the field only
for a prompt that holds it, so **absent means not computed** and `unknown` means computed and not sayable.

| Value | Rule (first match, in this order) | Limit |
|-------|-----------------------------------|-------|
| `unknown` | `P` is the interrupt marker's own record, or `P` has no `Q` (the last prompt of its transcript). | The last prompt of every transcript reads `unknown`, so a transcript never reads fully known, and that holds for a last prompt that has `stopped` set (a rejection in the final prompt reads `unknown`, not `user-stop`). `unknown` is not a failure of the work. |
| `user-stop` | `P` has `stopped` set: `rejected` (a main-line error line starts `The user doesn't want to proceed with this tool use` or `The user doesn't want to take this action`) or `interrupt` (`Q` is the interrupt marker, a prompt record that starts `[Request interrupted by user`). It is read from the same records as `stopped` and nothing else, so the two never disagree. | A stop is the human halting the agent mid-turn; it says nothing about why or whether the work was good. It wins over `revert`, `redo`, and `after-error`: a rejected call is settled as an error, so without this row every rejection would read `after-error`. A harness reads a stop only as far as its adapter writes the rejection text or the interrupt marker (see "`user-stop` by harness" below); a harness that records neither reads as it did before. The rule does not see a decline whose text is not the two sentences above (Codex's `exec command rejected by user` and Gemini's `[Operation Cancelled] ...` are classed `user-rejected` in the error code, not `stopped`), so those prompts read as their other rules say. |
| `revert` | `P` made an edit that did not fail (status `ok`, or `none` when no result was recorded), and either (a) `Q` has a clean (`ok`) shell call that undoes work in git: a segment that reads `git revert <commit>` (a bare `git revert` is `--abort`, `--continue`, or `--quit`, which undo no work, and reads `none`), `git restore`, `git checkout .`, or a bare `git checkout` whose step holds none of the flags `<literal>` (a `-`, or any flag off the public list), `-b`, `-B`, `--orphan`, and `--detach` (what `git checkout -- <path>` and `git checkout -f` leave, since a segment drops flags and paths), or a step that reads `git reset` with the `--hard` flag; or (b) `Q`'s `head` begins with `revert`, `undo`, `roll back`, or `rollback` (case-insensitive, after an optional `please`). | A git undo `Q` ran for other work (a branch cleanup) reads the same, and an undo the person does by hand outside the harness is not seen. Rule (b) reads English only. `git stash`, `git clean`, `git reset` without `--hard`, a checkout of a branch or a revision that is a plain word (the segment keeps its name, so `git checkout main` and `git checkout abc1234 -- <path>` are not seen), a `Write` of the old text, and an undo in a prompt later than `Q` are not read. `git restore --staged` reads as an undo, since a segment drops the flag. **A checkout that switches branches reads as an undo when its target is a word the segment drops**: the segment drops a word that holds `/` or `\`, or is quoted, and leaves no flag, so `git checkout feature/x`, `git checkout origin/main`, and `git checkout "main"` leave the same bare `git checkout` as `git checkout -- <path>`. `git checkout -b feature/x` and `git checkout -` read `none`, since the step keeps their flag. **A checkout with a flag off the public list, such as `--theirs` or `--patch`, also reads `none`** (the step turns an unlisted flag into `<literal>`, so `git checkout --theirs -- src/a.ts` is not seen as an undo, while `-p` is); a plain switch to `feature/x` leaves no flag, the stored records cannot tell it from a path restore, and a narrower rule would lose the path restore (`intervention.test.ts` pins both). |
| `redo` | `Q` makes an edit that did not fail (status `ok`, or `none` when no result was recorded) to a path hash `P` also edited that way, with no commit that `commits` can see between the two edits. This is the `redo` signal above narrowed to the very next prompt, so it is a reply to the work and not a later task. | A planned second edit of one file reads the same as rework, and a commit a script made does not end the window. The edit is matched by path hash, so a rename is not seen. |
| `after-error` | The last main-line call of `P` failed (`status` `error`). | The next prompt need not be about the failure: it may open an unrelated task. A prompt whose last call failed and whose agent then answered in words reads the same as one left broken. |
| `unknown` (second case) | Nothing above matched, and `Q` made a shell call captured before `segments` (CAPTURE 6): it could have been a git undo. | An older capture leaves the value `unknown` until the transcript is captured again. |
| `none` | Everything else: `Q` exists and none of the above matched. | `none` is silence in the records, not approval. A person who fixed the work in their editor, or who steered with a prompt that edits another file, reads `none`. |

The precedence is `unknown` (first case), `user-stop`, `revert`, `redo`, `after-error`, `unknown` (second case), `none`: a positive record stands even where a later record is unreadable. A prompt with both a stop and an error reads `user-stop`. The rule reads
the normalized records every harness writes (`Bash`, `PowerShell`, `Edit`, `Write`, `MultiEdit`, the call's `status`, its `target` hash, and its `segments`), so a harness supports a bucket as far as its
adapter fills those records. Commit survival stays in "Commit survival" and no bucket here reads it.

**Harness support.** `intervention-harness.test.ts` writes the same six scenarios (a next prompt that touches other work, a last call that failed, a repeated edit, a git undo, a request to undo, and a
single prompt) in each harness's own form and runs it through the adapter. Claude Code, Cursor, Codex, Copilot CLI, VS Code Copilot Chat, Gemini CLI, and Grok Build all read every bucket but `user-stop` (see "`user-stop` by harness" below), with
one exception that the test pins: **Codex's `revert` by a git command is not seen when the command is the `bash -lc <command>` form its CLI sends**, because the adapter joins the argv with spaces
and the shell reader then takes `bash -lc git` as the command, so the segment is `git` and not `git revert`. A Codex session reads `none` there; its `revert` by a request in the next prompt, and
by an unwrapped argv, is read. No harness is guessed at: a bucket that needs a record the adapter does not fill reads `none` or `unknown` by the table above.

**`user-stop` by harness.** `intervention-stop.test.ts` writes a rejected call and an interrupted turn in each harness's own form, with and without an earlier failed call in the prompt. A harness reads a stop only as far as its adapter fills `stopped`'s two records:

| Harness | Rejected call | Interrupted turn | Why |
|---------|---------------|------------------|-----|
| Claude Code | `user-stop` | `user-stop` | Writes the rejection sentence and the `[Request interrupted by user` user line. |
| Cursor | `user-stop` | `none` | `userDecision` `rejected` becomes the rejection sentence. An aborted terminal call has no outcome and no marker. |
| VS Code Copilot Chat | `user-stop` | `none` | A `Denied` or user-sourced `Skipped` confirmation becomes the rejection sentence. It reads no interrupt. |
| Codex | `after-error` | `none` | A declined call is `exec command rejected by user` (or `patch rejected by user`), classed `user-rejected` but not the sentence `stopped` reads. A `turn_aborted` with reason `interrupted` is counted as a trust event and writes no marker prompt. |
| Gemini CLI | `after-error` | `none` | A cancelled call is `[Operation Cancelled] ...`, not the sentence; the interrupted-reply placeholder is dropped. |
| Copilot CLI | `none` | `none` | `session.error` and `abort` are not read. |
| Grok Build | `none` | `none` | No event names a stop. |

A harness that cannot show a stop reads its prompts as the table above says, as before `user-stop` existed. **The limit:** `user-stop` is only as wide as `stopped`. Widening it to Codex's and Gemini's declines (a rule over the `user-rejected` error code) would move `stopped`, which the books and the gold arms read, and is a separate change.

### Hashing

`target` is a 16-hex SHA-256 of `<salt>\n<path>` (a newline between the two) for a call with a `file_path`, `notebook_path`, or `path`
input; the program and subcommand (`git push`, `npm run`) for a shell call, after any leading `cd <dir> &&` hop, environment assignment,
or `sudo`; else null.
The path is taken **relative to the repository root** of the line's `cwd` (the nearest ancestor holding `.git`; a linked worktree
under `<root>/.claude/worktrees/<name>/` resolves to `<root>` and its segment is dropped), so one file hashes alike from every
subdirectory and worktree. `targetBase` is `repo` then. A path no repository holds keeps the version-3 base: relative to the `cwd`
when it lies under it, else as written, and `targetBase` is `cwd`. `repo` on the session is the salted hash of the repository's identity:
the normalized `origin` remote URL read from the repository's `config` (scheme, credentials, a trailing `.git` and slash stripped, host
lower-cased; a linked worktree's `.git` file is followed to the common `config`), so two clones share it; with no `config` or no `origin`
it is the lower-cased absolute root path of the first `cwd` a repository holds. It is salted; `fileHashes` is the salted hash of each file
path a tool touched, sorted.

On a pooled skeleton the session's `repo` is the frame's `repoKey` (`docs/pool.md`, "Repo key, coverage bands, and hour"): the same salted hash, so a read that groups by repo works on pooled data from one store. A skeleton-derived store sets `repo` to it rather than `null`. The salt is this store's own (`localSalt`, below), not yet the account's (`accountSalt`, the open M4 seam), so the key joins one operator's harnesses on one repository on one machine, not a second machine and not two accounts; a salt rotation or a new machine starts new keys. No cell key reads it.

The **salt** is this machine's, created on first use (`localSalt` in `store.ts`). The one seam for the account's salt is
`SessionsRuntime.accountSalt`: a provider returning `{ salt, sid }`. When it returns another `sid`, each file recorded under the old one is
captured again from the harness or `raw/` at the next deposit, and nothing else changes. How a second machine adopts the account's salt is
an open question (M4); until it is settled two machines of one account hash the same file differently, and `sid` makes that visible
(`verify` reports a store holding more than one).

`verify` also checks the version-4 fields: no version-3 or later session is `cv-behind` (one whose transcript is gone from the harness and
`raw/`, or, for a Cursor session, whose composer is gone from Cursor, is counted `cv-frozen` instead and never fails `--strict`, since it
cannot be captured again), one `sid` across the store, every `fileHash` is a path target of a tool call, and `targetBase` is set on a path
target and on nothing else.

`verify` also reports every session on its own (`--json`: `sessionResults`, each session's ten rows with a status of `pass`, `fail`, or `not run`), audits each session against its raw file (`audit`, layer 4 at T0: the raw-file match, the Merkle root recomputed over the first `leaves` lines, and the count bindings), and scores each session against the operator's own other weeks (`selfBaseline`, layer 2: `not run` below 1,000 tool calls in the week or 4 baseline weeks); `root mismatch` and `counts do not bind` fail `--strict`.

### Commit survival

`oars sessions deposit` and the nightly run, never a hook, read the repository of each allowlisted folder and append one line per changed
sha to `commit-survival.jsonl`: `{ sha, state, day }`, with `sha` as captured (class A), `state` (class P), and a day-resolution `day`
(class P). Only a call in a main transcript whose `ts` is more than `SURVIVAL_DAYS` (7) old counts, so a sha `commits` could not read and a
subagent's commit are not observed. `git commit -q` prints no `[branch sha]` line, so a quiet commit's sha is read only when a read-back is
the call's final command; a store that commits quietly observes few of its commits. The latest line of a sha wins. It is a separate file, so
what `verify` checks is untouched.

| `state` | Rule | What it does not say |
|---------|------|---------------------|
| `reverted` | A commit on the default branch says `This reverts commit <full sha>`, and that revert was not itself reverted. Checked first. | A hand-written or partial undo, and a revert that names a squash's sha rather than this one, are not seen. A revert of a merge marks the merge commit only, so the commits it brought in still read `survived`. |
| `survived` | An ancestor of the default branch. | The lines may since have been rewritten by ordinary later work. |
| `unreachable` | The repository holds the commit, but the default branch does not reach it. | Not a failure: a squash merge, a rebase on landing, and an open branch all read this way. |
| `unknown` | The repository is absent or shallow, it has no default branch this code can name, git failed, or it does not hold the sha. | A session that committed in another repository reads this way, since only its own project's repository is read. |

The repository is the first `cwd` in the session's transcript whose slug is the allowlisted project, then its root (`makeRepoRoot`). A later
`cd` is never followed, and a folder outside this run's allowlist is never read. Git is read-only and asks no network, so the default
branch (`origin/HEAD`, else `origin/main`, `origin/master`, `main`, `master`) is as of the last fetch. A failed read never fails the deposit,
and an `unknown` never replaces a known state, so a passing failure does not undo an observation.

### `books --by package`

`oars sessions books --by package` prints the counts a package field report is built from, from the local store only (it reads the store and the transcripts, writes nothing, and sends nothing). It counts tool calls that pulled a package (installed or ran it by name) on the public list: the pinned registry snapshots plus the curated list, for the ecosystems the snapshots cover. Per package, in name order and with no rank, share, or comparison:

- calls, failed calls (`status` `error`), main sessions (a subagent's call counts toward its main session), and the first and last UTC day a counted call ran;
- per harness and model, calls and failed calls. The model is the call's own, else its prompt's, else `no model`; a model outside the pinned model list reads `another model`;
- failed calls by `errorCode` class, for calls captured at version 14 or later (a failed call at such a version with no class reads `no class recorded`).

A failed call captured before version 14 has no class to count. It is reported as `not measured` and never as a zero or as a class, so a store captured before version 14 shows `not measured`, not an empty list. Names off the public list are never printed: one line gives how many names and calls they hold.

The A38 exclusion applies on every run: the same scan `oars sessions exclusions` runs (a missing or empty term file excludes everything). A transcript is dropped when it or its main session is excluded, so a subagent goes with its parent, and the output states how many transcripts and calls were removed. `--since <days>` narrows by call time; `--repo` is refused. `--json` carries the same data (`rows`, `notPublic`, `excluded`).

### What `books` adds

`oars sessions books --by class|model|harness|pull` adds these columns, in text and `--json`. `--json` also carries `scope`, the same folders-not-read list `verify --json` carries. It covers the whole projects root, also under `--repo`. The signals stay separate, and the text ends
with a line saying they are associations in one operator's logs, not measured lift.

| Column | `--json` | Count, of what |
|--------|----------|----------------|
| `passed` | `verifyPassed` | `verify` passed, of prompts that edited and whose `verify` is readable (not `na`, not `masked`, not absent; `none` counts, since no runner read as passing) |
| `stop` | `stopped` | A stop, of prompts carrying `stopped` |
| `redo` | `redone` | A redo, of prompts carrying `redo` |
| `commits` | `commits` | The prompts' `commits`, with or without a sha |
| `settled` | `settled` | Distinct shas whose state is `survived`, `reverted`, or `unreachable` |
| `survived` | `survived` | `survived`, of `settled` |

Below `BOOKS_MIN_PROMPTS` (30) in its denominator a share prints as `too few`, and `--json` gives its `share` as null beside its `count` and
`of`. A settled commit counts toward that minimum the way a prompt does. `--by pull` has one row per `ecosystem:name` from the calls' `pulls`, a
prompt counts once in each row it pulled, so the rows overlap, and a prompt that pulled nothing is in none. Every column reads the main line
only: subagent work is left out.

## Setup, funnel, and trust shape

harness would have shown the event). Counts, names, and sizes only: no instruction text, hook command or output, or tool description is kept. Nothing here is bucketed or

| `trust.interrupts` | the operator cut a turn short; the marker a rejection is followed by is not a second one | recorded | recorded: `turn_aborted` with reason `interrupted` | absent | absent | absent |
| `trust.rejections` | the operator declined a tool call (`The user doesn't want to ...`) | recorded | absent | absent | absent | absent |
| `trust.denials` | policy refused a call (permission rules, the classifier, or a hook); not the operator | recorded (the first line of a failed result) | absent | absent | absent | absent |
| `trust.trustEvent` | each stop as `{event, tool, prompt}`; `tool` is null when none was in flight | recorded | interrupts only | absent | absent | absent |
| `trust.unattendedRun` | minutes (rounded to two decimals) from each human turn to the agent's last line before the next human turn; one per human turn that has a usable time | recorded; a turn the harness injects (a task notification, a scheduled task) is not a human turn; a `!` shell command and a prompt that is only an image are; a local command nobody answered and a line the harness wrote (a meta line, a synthetic reply) neither open nor extend a run; a rejection ends the run at the agent's last line before it | recorded | absent | recorded (a prompt marked as an autopilot continuation or an injected skill or agent prompt is not read, so it is not a human turn) | recorded; a turn marked `hostTurn` (a slash command) or `hideFromScrollback` (a task, subagent, workflow, notification, or goal check the harness started) is not a human turn, and a `!` shell command and a prompt that is only an image are |

A subagent transcript has no `unattendedRun`: its run is its parent's. `unattendedRun` ends at the agent's last line, so a reply the next morning is not an overnight
run. A wait on a permission prompt the operator approved counts toward the run: this reader sees no approval time, only the result's. A rejection ends the run at the agent's last line before it, and the agent's work after a rejection is not counted until the next human turn. The last turn of a file runs to the file's last line. A resume's replayed human line is one turn, and a line of a sidechain is not read. A compaction summary is the agent working, not a human turn. Tool names are stored as `tools` stores them (`storedToolName`: an MCP name's server part redacted).

## Motifs, cells, and reads

Derivation over the capture records, computed locally under `EXTRACTOR_VERSION` (9 adds them). The capture records stay the primary record: cells and reads can be dropped and computed again, and no rollup replaces what they came from.

- A **motif** is a window of one to four steps within one line of work, hashed with no salt and no frame, so one shape joins across accounts and frames. `shape` hashes actions only and `named` hashes actions and public identities. A `class` motif holds no steps and names a prompt class, which is how cost per class comes from cells. A one-step window is there because fit, adoption, and live count one action, and a prompt of one call has no longer window.
- A **cell** is order 0: `{motifId, frameBucket, grain, day, sessions, clusters, ok, failed, tokens, durationMs, exposed}`. A frame bucket is harness, harness version by tens of patch, and model, with no effort (pool spec rule 3: `effort` appears in one cell only, the pair of an effort level and the bucket of the thinking tokens it spent, which joins no other axis). A (name, `platform`, `shell`) cell is the exception: its frame bucket is `env:<platform>:<shell>`, with no harness, version, or model, and the shared `deriveCells` writes it to a local `cells.jsonl` as the pool does. `grain` is `week` or `day` (rule 6): every cell is keyed on the Monday of its UTC week in `day`, except a `live` cell, a one-step shape motif with a known day, which is also kept at its UTC day; a read of days (`live`, the tool-day read, the day move, call shape) answers from day cells alone and a read of weeks from week cells alone; recovery takes the failed call from a day cell and the step after it from a week cell, since a window of two or more steps has no day cell. Versions are bucketed because most prompts run a version not yet seen, so an exact version goes stale in days. `exposed` is true when the counts sit, wholly or in part, inside a shown recall's consequence window, and it is part of the cell's key, so a motif's exposed and unexposed counts stay apart. A recall's answer from a stored read over a week cell dates its evidence by the week: `firstDay` is the week's Monday, the earliest day the evidence can hold (it may not have touched that day), and `lastDay` is the week's Sunday or the newest day of the pool the read was made from, whichever is earlier, so a recall made inside the week never holds evidence dated after itself.
- A **read** is any derived value citing its inputs: `{readId, family, method, methodVersion, inputs, order, slice, value, n, clusters, interval, asOf, basis}`. `readId` is the hash of the rest, `order` is 1 + the highest order among `inputs` with a cell at 0, a read that cites nothing is refused, and `asOf.pool` pins the pool, whose version hashes the extractor version, each family's method version, every cell, and the error rows recovery reads, so new data or a new rule gives a new read even when the value comes out the same.

The families at order 1, in the order they are listed. None adjusts for its confounders, so a row is a count and not a finding.

| Family | Slice | Value | Not removed |
|--------|-------|-------|-------------|
| `recovery` | signature hash, failed action; in a pool bundle, (failed action, `errorCode`, next action) | sessions, errors, days, what followed | `editFollowed` is not success; refusals and hook denials are local policy. The bundle's edge reads as what others did next, never as a fix |
| `fit` | motif, frame bucket | failure rate | a failure is not a misfit; prompt class; effort, which is no longer sliced |
| `cost` | prompt class, model, ISO week | tokens and seconds per prompt, error share | class drift, subagent work, task size; a prompt with no wall time adds no seconds but still counts, so seconds per prompt understates |
| `change` | motif, harness, version bucket | share and failure rate in that bucket; a move between buckets is order 2 | effort, rule commits, class drift, date |
| `live` | motif, day | share of the day beside its share of the seven days before | the day's mix; no multiple-test control, so it flags nothing |
| `adoption` | motif | share of all steps, first and last week, weeks seen, weeks since last | the operator's own rules |
| `method` | shape of two or more steps, model | share among windows of its length | task assignment by tier, effort; no outcome label |
| `next-step` | prefix of one to three actions | counts of the next action | no outcome label, so the most common step is not the right one |
| `tool-day` | motif, day | failure rate, and share of the day's steps | the day's mix of work, effort, rule commits |

A read's slice and value hold closed vocabulary and numbers only: never a path, a prompt, or an error's text. A signature appears as its hash, computed the same way on any account. `clusters` is 1 on every row of one operator's store, and `oars sessions read` applies no floor at order 1, because every cell is the operator's own.

### Reads over reads

A read above order 1 takes its inputs from the orders below and its interval from theirs: a difference takes each side from the inputs that could push it there (MOVER), so a skewed rate stays skewed. A read with an input under 30 trials does not exist, and `n` and `clusters` state its weakest input. A share rests on its day's or bucket's steps and a failure rate on the tool's calls, so a tool that falls away keeps its share move: zero of a day's steps is a measurement. Inputs count a step as independent and steps cluster in sessions, so these intervals run narrow.

| Family | Order | Slice | Value | Not removed |
|--------|-------|-------|-------|-------------|
| `version-boundary` | 2 | motif, harness, two neighboring version buckets, metric | before, after, and the move in share or failure rate | date, effort, rule commits, class drift |
| `substitution` | 2 | rising tool, falling tool, the boundary | each share move, and the falling tool's move among the steps that are not the rising tool's | date, class drift, rule commits |
| `interaction` | 2 | motif, frame, two tiers | each tier's failure rate, and the gap beyond how those tiers differ on every other tool, kept only when that beyond points the same way as the gap (a tool that resists a tier's main effect is not one that fails more on it) | task assignment by tier, prompt class; effort, which is no longer sliced |
| `day-move` | 2 | motif, metric, two adjacent days | before, after, and the move; a share move exists for a tool on either day, a failure move only for one with 30 calls on both | not screened, so a row is an input and not a finding |
| `lead-lag` | 3 | lead, lag, level | slope, its check, and the score | see below |

The first three state only moves past a screen, each with `tested`, the comparisons it was screened among. A move also has to reach 0.01 to be stated, so a read of nothing means nothing moved that far among the comparisons above the floor.

`lead-lag` asks whether a tool's failure rate moving comes before its share moving. It is labeled `experimental` in every output, its heading and its value both, and no agent path serves it. It is fit on the earlier 70 percent of days and scored on the rest, with a pair dated by the day its outcome is known and at least 30 pairs on each side. `check` is `passed` only if the slope's interval excludes zero, it beats predicting no move on the later days (`skill` above 0), and its sign agrees with the later days better than chance (the agreement's Wilson low above 0.5). A pair shares no day: a failure move ending on one day is paired with the share move starting on the next, because a burst of failing calls lifts that day's failure rate and share at once and would otherwise read as a lead. It runs on days because each model has one version here with no release date, and two version boundaries are too few to cut in time. Not removed: shares sum to one, a change of habit moves many tools at once, and every row states `clusters: 1`.

`oars sessions read` also states what the store cannot read, which tells a question it cannot ask from one that found nothing: a model version boundary (a cell holds no version of a model), a harness boundary with one version bucket or none above the floor, an interaction with one tier, and lead-lag with too few pairs. Each pool's reads file is pinned to `METHODS` as well as the extractor, so a family added later is not hidden by a file written before it. A pull is the exception: it takes the newest reads file whatever its `METHODS` or extractor, so after an upgrade `--family <new>` is a recorded miss until the next whole-store deposit, and on a machine with no schedule until a manual one. Transfer (how far an answer carries) is not read yet: it needs recalls held back from an arm.

## Recalls

A recall is one event in the asker's graph, and a pull and a push are the same object in `recalls.jsonl`. A pull always answers. A push fires at the pre-tool hook and takes its `arm` from a hash of the session, the prefix, and the pool version against a 10 percent holdback: a `held` row stores what it would have shown and injects nothing. Answers render from structured fields only, so no authored text reaches an agent. A miss is kept when somebody asked; a push with no read keeps no row. A pull answers from the newest stored pool and derives nothing; only a store with no stored pool derives one, once. The holdback, like the push it holds back, starts only after a rerun of `oars sessions hook install` (which adds the `PreToolUse` entry) and a deposit that writes `fit` into the index: an index written before has none, and the pre-tool hook then pushes nothing.

A pull names one form (`error` or `path`, `pattern`, `entity`, `family`, or `text`); naming two is refused. A class or a number of days (`--class`, `--since`; `class`, `sinceDays` over MCP) narrows only the `error` or `path` form and the `recovery` and `fit` families. Asked of any other form or family, whose counts cover all time or come from stored reads, a pull is refused with a usage error (`-32602` over MCP) and nothing is recorded, because answering would state counts the slice did not narrow. A `sinceDays` that is not a positive integer, or a `class` that is not a string, is refused the same way and not dropped.

The consequence is computed at derive and never captured, so `recalls.jsonl` stays append-only. Its window opens on the first main-line call stamped after the recall, because the call a push fired on was already decided, and it ends at the prompt's end or after 20 calls. `motifs` (shape level), `followed`, `cost`, and `outcome` are held apart, with no composite. `cost.tokens` is null when no call in the window measured any, as in a capture older than step costs. A held recall gets a consequence too, because it is the baseline. Only a shown recall enters the graph: it adds a `recall.push` or `recall.pull` step and marks its window's cells `exposed` (a shown miss adds the step, and only the motifs holding that step are exposed). Weak spots: a hook inside a subagent reports the parent's session, so its push is placed on the parent's line by time; an MCP pull has no session, so no consequence is read for it.

`oars sessions recall --counts [--day <yyyy-mm-dd>]` prints counts per mode, arm, and answer, and how many held windows share a call with a shown one: the arm is drawn per session and shape, so such a window is a contaminated baseline, stated rather than dropped. `oars sessions lineage <recallId or readId>` walks back through the evidence, one line per hop with its frame range and day. It refuses evidence newer than the recall citing it, and a visited set keeps the walk acyclic. A recall's fit and recovery evidence cites the stored read of its pool, so the walk reaches cells; an entity usage count has no stored read and keeps a hash, so that walk ends at the evidence the recall holds; a read kept from an older pool can cite a cell since rewritten, shown as `missing`.

## The step log

`pipeline-runs.jsonl` is the pipeline's own books of work (runtime-commons pipeline spec, Sections 3.1 and 4): a store-level file beside
`hook-calls.jsonl` (that file counts hook behavior, this one counts pipeline work), append-only, one JSON line per run of a step,
written when the step ends. It carries no `cv` of its own, so it needs no capture bump. It is local: no session command uploads it, and telemetry does not carry it.

| Key | Class | Meaning |
|-----|-------|---------|
| `at` | A (P at UTC day) | When the step ended (ISO time). |
| `run` | A | A local run id; the `deposit`, `derive`, and `index` rows of one nightly or manual run share it. |
| `trigger` | P | `stop` (the SessionEnd hook, argument `stop`; never `session-end`), `nightly` (the scheduled task), `manual` (the verbs), `session-start` and `post-tool` (the lookup hooks). `weekly` is named by A21 and not built; `sync`, `cron`, `release`, `run-end`, and `run-start` are hosted: all are in the schema only. |
| `step` | P | `deposit`, `derive`, `index`, `verify`, or `recall`; the nightly and manual runs log a `derive` row and then an `index` row (the hook index write). `label` is in the schema but nothing local runs it yet. |
| `status` | P | `ok`, `error`, `skipped` (an earlier step of the run failed), or `deferred` (a Stop `deposit` that found the store locked and went to the pending list; its `error` holds the refusal's line). A `deferred` row is not a failed run: it is not in `failed runs`, it never makes a key `stuck`, and it is not in a step's mean time. `measure` counts it on its own line, `deposit@<ev> deferred (store locked)`, and `--json` carries it as `deferred` on the step. An oars from before this status skips such a row as a line it does not know. |
| `ms` | P | Wall time of the step; a `deposit` row excludes the derive and index passes it ends with, which have their own rows. |
| `in`, `out` | P | Counts by kind. `deposit`: `in` is `transcript` (the count asked for) and, when the deposit took sessions from the pending list, `pending`, `pendingDropped`, and `pendingKept`, `out` is `session`, `subagent`, `user-prompt`, `tool`, and `error-line`. `derive`: `in` is `session`, `subagent`, `user-prompt`, and `tool`; `out` is `signature` and `summary`. `index`: `in` is `session`, `subagent`, and `error`; `out` is `signature` and `project`. `verify`: `in` is `session` and `subagent`; `out` is `checked`, `passed`, `cvBehind`, `cvFrozen`, `stuck`, and `merkle` (the sessions whose Merkle root mismatches or whose counts do not bind). `recall`: `in` is `query`; `out` is `matches`. |
| `cv`, `ev` | P | The capture and extractor versions the step ran at. `lv` (the labeler) appears on `label` rows only. |
| `key` | A | A 16-hex hash, so a repeat is visible, built from the step's inputs and never from the state it leaves, so a failed row and the ok row of the same work carry one key. `deposit`: `cv`, `ev`, the trigger, the allow entries (the SessionEnd hook: that one transcript's path), and the redact domains (the SessionEnd hook reads none, so its key has none); this replaces the spec's file, size, and mtime with the inputs the run was asked for, which are known before the work. A failed step logs `error`, and the run's later steps are logged `skipped`; the next trigger retries the same key. A failed
deposit leaves `state.json` as it was; a derive that fails after its deposit wrote the records logs `deposit` `ok`, `derive`
`error`, and `index` `skipped`; an index write that fails logs `deposit` and `derive` `ok`, then `index` `error` (the records
and `state.json` stand; the next deposit rebuilds the derived files and the index). A key that fails on three runs in a row
is `stuck`, counted per step and trigger: an `ok` run of the same step and trigger ends its open streaks, and an `ok` run on
the same key under another trigger ends that key's streak too, so a nightly deposit that fails every night is stuck although
the `stop` deposits between nights succeed. A usage error (`deposit` with nothing to read) is no failed run and leaves no
row. `verify` counts a stuck key (a `verify` streak is not listed: a verify that got here succeeded), prints `FAIL  <step> is
stuck: key <key> failed <runs> runs in a row: <error>`, fails `--strict` with it, and writes the count in its own row. The
stuck check is store-wide; `--session` narrows the invariants and the key only. A row that cannot be appended never changes
the step's outcome: the step's value or its own error reaches the caller. A lookup hook logs an `ok` `recall` row only when
it read the index and searched it; a missing, torn, or unreadable index counts as no index and logs no row, and an `error`
row means the search itself failed. An MCP recall is counted in `mcp-calls.jsonl`, not here. `recall --context` is the manual
recall verb and logs a `manual` row keyed by the cwd and harness. A state.json that cannot be read fails the step like any
other failure: its row is still written, with the line masked by no domains.

`oars sessions measure` prints the counters of spec 3.2 that this log can answer, under the G1 signals, over the whole log (`--last`, `--since`, and `--repo` filter the G1 table only; the step counters are all-time and not repository-scoped): runs of each step (ok, error,
skipped) and mean ms, per step and `ev`; capture records deposited by kind; records derived by type (the newest derive); what the index holds (the newest index); invariants passed of checked and
`cv-behind` sessions and sessions failing the raw audit (the newest verify); recall queries and matches; failed runs by step and `ev`; and the stuck steps. `--json`
carries the same numbers under `steps`. A malformed or torn line is skipped when the log is read.

## Subagent transcripts

`<project>/<session>/subagents/agent-*.jsonl` and `.../subagents/workflows/wf_*/agent-*.jsonl` are deposited as
`<parent>~agent-<id>` and `<parent>~wf_<id>~agent-<id>`, with the parent session id and the subagent type from the sibling
`.meta.json`. They are kept apart from the sessions, so per-session denominators (`measure`, G1) still count main sessions;
`books --by class` adds their tokens to the spawning prompt's class as the `delegated` column. Their errors are derived into the
same `error` records as a main session's, under the parent's `session`, with the agent's transcript in `agent` (class A, a join id) and the
spawning prompt's `prompt` and `cls`: signatures, `measure`, and recall include them, and each signature counts the parent once.

## The raw archive

Each deposit (the `deposit` command and the Stop hook's) hard-links every transcript it reads into `raw/<project>/<path>`, so
the raw outlives the harness's own cleanup (`cleanupPeriodDays`) at no extra disk while both names exist. Across volumes, or on a
file system without hard links, it copies instead. A rerun leaves a present link alone and replaces a stale copy. The archive is
local only and is never read by `derive`.

## The exclusion list

One rule decides which sessions may enter the pool (A38): a session is excluded if any line of its main or subagent
transcript holds a listed term, scanned locally before anything is deposited. A session with no main transcript to scan
is excluded, and so is every session when the term file is missing, empty, or undecodable (a NUL or U+FFFD in the file).
A link is followed at every level: the projects root, the store folder, `raw/`, a project folder, a session folder,
`subagents`, an entry under `subagents`, a main transcript, and the store log. A link that leads nowhere or to the wrong
kind of entry (a file where a folder belongs, a folder where a transcript belongs, a file under `subagents` not named
`.jsonl`) is never clean: the session is excluded as unreadable, or, when the link is a root, the store log, or a
project folder, the command stops and writes no list. The same holds for a plain file (no link) where a folder belongs,
or a folder or other non-file entry where a transcript belongs (the main, or a name ending in `.jsonl` under
`subagents`). A link back into a folder already walked reads unreadable too, because following it would loop. Any other
main transcript or `subagents` folder that cannot be read leaves its session excluded as unreadable too; a project
folder that cannot be listed stops the command and writes no list (it names the folder by ordinal only, except for a
root or a linked project folder, whose message names no folder). The scan reads both the harness's `projects/` folder
and `raw/`, because either can be the only copy left.

The term list is a local file, one term per line, matched without regard to case, never in this repository. The
`OARS_EXCLUSION_TERMS` environment variable names it; the default is `session-commons/exclusion-terms.txt` beside the claude
`projects/` folder. `oars sessions exclusions [--out <file>]` writes the excluded sessions (project and session id, one JSON
object per line) to `session-commons/exclusion-list.jsonl` by default and prints counts only: sessions, excluded by reason,
and the files and sessions that held a term, by main or subagent and by source. The list is written readable by its owner only, since a
folder name can carry a term. It covers the harness's folders, `raw/`, and the sessions the store logged, so a logged session whose raw is gone
everywhere is listed as no raw; a directory that is not a session (no main transcript, and a name that neither is a session id nor ends in `.jsonl`) is counted apart;
an entry named `<x>.jsonl` that is not a file, or a non-folder named like a session id, is listed as unreadable.
The pool's deposit calls `checkSession` (`packages/cli/src/sessions/exclusion.ts`) first and never builds or sends an excluded session.

## The cost-state check

`verify` checks that the harness's `cost-state` totals equal the recorded usage within their scope: the process that wrote them
(from its `startTime`, so a resumed session's earlier lines are outside them) and the session's subagent transcripts, counted
once per request id. A recorded sum above a total fails. A total above the sum is not a failure; it is printed as observed,
under `harness side calls` only on a usage key that a `modelUsage` model with no assistant line reported a nonzero amount on (001cf645 has a
`claude-haiku` entry and no haiku line), else under `other`. Checks that hold only once a scope is applied are counted under `resume scope` and `subagent
transcripts`, each with one example session.

The skeleton's cost state records, per `modelUsage` model (sorted by name), the usage keys its entry reported a nonzero amount on: `input`,
`cacheWrite`, `cacheRead`, `output`. A side model whose cache keys are absent or zero (the haiku case) therefore explains an excess only on
`input` and `output`, and an excess on `cacheRead` stays `other`. The field changes the stored `models` value of an existing skeleton, so it
bears on `CAPTURE_VERSION`, not `EXTRACTOR_VERSION`: the rule is that a captured field changing bumps `CAPTURE_VERSION`, and derived values
alone bump `EXTRACTOR_VERSION`. It is `CAPTURE_VERSION` 5. `models` was added with no bump because no version-3 store had shipped; a
version-4 store is on operators' machines now, so the next deposit captures every transcript again and writes the keys. The compatibility
reader still fills a skeleton written without them (a bare model name, or no `models`) with no keys, so a transcript that is gone from disk
keeps its excess keys under `other`. Class A, with the rest of the skeleton lines.

## More than one repository in a store

One store can hold several repositories, and neither the G1 reading nor the SessionStart block should move because another one deposits.

- `oars sessions measure --repo <root>` counts only the sessions of the repository `<root>` sits in. It uses the test recall uses: a
  project folder belongs when its slug is the root's slug or extends it, so worktrees (`<root>/.claude/worktrees/<name>`) and
  subfolders count. Without the flag the output is the whole store, as before.
  The MCP recall calls it counts are scoped too: each call now records the folder the server ran in, and `--repo` drops a call whose
  folder is another repository. A call written before that field existed has no folder and counts for every repository.
- `oars sessions books --repo <root>` takes the same flag and the same test: it books only the prompts of that repository's sessions, with
  the subagent tokens they spawned, so `books --by class` stays one repository's number when others deposit.
- SessionStart recall ranks by the latest 300 sessions of the repository, not of the whole store. The index groups project folders
  into repositories by slug: a worktree folds into its repository, and a folder that extends another stored folder joins the shortest.
  Three consequences:
  - Sibling folders whose slugs share a prefix (`app` and `app-two`) share one window.
  - A nested repository (`parent/oars`) ranks by its parent's window while `measure --repo parent/oars` counts only itself, so the
    two readings differ.
  - A stored parent folder is a prefix of its children, so one allow-listed session from the parent (the home folder, or the folder
    holding several checkouts) folds those repositories into one window and the isolation reverts to the whole store. Keep such a
    folder off the allow list.
- An installed hook command starts with `[ -f "<hook-bin>" ] || exit 0;`, so a settings file that outlives its build (a cloud worker, a
  clone with no build) exits 0 and prints nothing instead of failing the session. The command still ends in `hook-bin.js" <event>`,
  which is how uninstall finds it.
- `hook install` at `--scope project` or `--scope file` reads the user file's `cleanupPeriodDays` too. When the target file sets no number, a user
  value at or above the 365 floor means nothing is written. A number the target file sets itself overrides the user's, so the user's value only
  counts when the file sets none. The floor is per target file: a lower number in the file is raised to 365, and the user's value is
  never copied into a project file, which can be committed.

## The Cursor source

`oars sessions deposit` also reads a Cursor store, so a Cursor history and a Claude Code history land in one local store. The records
carry `harness: "cursor"`; a record with no `harness` is Claude Code's (`harnessOf`), so the Cursor source itself needs no capture bump and no Claude Code record changes.

- **Where it is read from.** Cursor's `User` folder: `%APPDATA%\Cursor\User` on Windows, `~/Library/Application Support/Cursor/User` on
  macOS, `$XDG_CONFIG_HOME/Cursor/User` (else `~/.config/Cursor/User`) on Linux. `deposit` finds it on its own and skips it silently when
  it is absent. It opens the two SQLite files read-only through the built-in `node:sqlite` (Node 24 or later, no dependency), loaded only
  when a Cursor store exists.
- **Read by default.** Like any other source, it is read by default; `--allow` narrows and `--deny cursor` keeps it out. The nightly
  schedule reuses the saved list.
- **What maps to what.** One session per composer: `workspaceStorage/<hash>/state.vscdb` (`composer.composerData`) names the composers of a
  workspace, and `workspace.json` names its folder; `globalStorage/state.vscdb` (`cursorDiskKV`) holds the messages (`bubbleId:<composer>:<bubble>`)
  and `composerData:<composer>`. A user bubble is a prompt, an assistant bubble a response; `modelInfo.modelName` is the model; `tokenCount`
  feeds `usage`; `toolFormerData` (name, params, status, error) is a tool call, and its path parameters are the files touched. The workspace
  folder is the cwd: a Git repository takes the same `repo` identity and root base as a Claude Code cwd, any other folder its own class-L path,
  and a composer with no workspace gets none.
- **Same field classes.** The transcript is rebuilt as the lines `captureSession` already reads, so redaction, the 1,000-character `line` cap,
  `fileHashes`, and the per-account `sid` salt are the Claude Code code path, not a copy.
- **Idempotent.** `state.json` keeps one entry per composer (`cursor/<composerId>`) whose cursor is the message count and `lastUpdatedAt`;
  a second deposit adds nothing, and a composer that gained messages is captured again.
- **Absent fields.** The store has no cache read or write tokens, thinking tokens, subagents, hooks, cost-state, git branch, or Cursor
  version, so they take the empty value (0, `[]`, or null; `env.harness` is null).
  The version census of t872 found nothing to read: no field of the composer, its headers, or a bubble carries the Cursor build, so `harnessVersion`
  stays null, the session's cells are `cursor/unknown/<model>`, and a bundle for them is asked for as `unknown` (`pool.md`, "What a bundle serves").
  A bubble's time is its `createdAt`, else
  `timingInfo.clientStartTime` when that is an epoch time at or after the composer's start (a smaller value is a relative clock and is
  ignored); a user bubble with neither takes the next assistant bubble's, and any other takes the previous one's, so wall time per prompt is coarse.
  A shell command Cursor records as `completed` with a nonzero `exitCodeV2` is a failed `Bash` call, and a tool `error` is read from its JSON
  wrapper (the model-visible message, else the client-visible one). Nothing goes to `raw/` (there is no transcript file), and the Stop hook does not read Cursor.
- **Not read.** `aiService.prompts` (only `text` and `commandType`) and `aiService.generations` are not read: they carry no session id and no
  time, so they cannot be joined to a composer. On the 2026-11-02 copy, 183 of 788 distinct prompt texts match no captured prompt; that is a
  stated gap, not a silent one. The `session` record carries `harness: cursor`; the skeleton does not (`Skeleton` has no such field), and
  names its source only through the `cursor-` session prefix.
  A terminal call Cursor ended `..._EXECUTION_ABORTED` has no outcome (`none`, as a cancelled edit), a tool call has no duration (the
  store stamps a result with the call's own time), a composer id that is not `[A-Za-z0-9._-]+` is skipped and counted, and a composer with no
  `createdAt` accepts no relative `clientStartTime`.
- **Reading it back.** `recall` and `measure` read the records as they are. `books --by harness` groups the prompts by harness.

## The Codex source

`oars sessions deposit --allow codex` reads OpenAI Codex CLI rollouts into the same store. The records carry `harness: "codex"`, take the same
field classes, redaction, and 1,000-character `line` cap as every other source (the rollout is rebuilt as the lines `captureSession` reads), and
`recall`, `measure`, `books`, and `verify` read them with no special case. Sources are a table (`sources.ts`): a new harness is one entry plus its reader.

**Written from fixtures, then run live once.** This reader was written from the public Codex source (openai/codex @ ac558e2, Apache-2.0: `codex-rs/history`,
`codex-rs/rollout`, `codex-rs/protocol`) and tested on synthetic fixtures until the live run below. OpenAI's documentation names the location but no format
(https://developers.openai.com/codex/config-advanced, read 2026-11-03: "By default, Codex saves local session transcripts under CODEX_HOME (for example,
`~/.codex/history.jsonl`)"; nothing in it describes the rollout files or promises them), and ccusage's Codex guide says "Codex log support is experimental while
the Codex CLI log format continues to evolve" (https://github.com/ryoppippi/ccusage, `docs/guide/codex/index.md:5` @ b4e6193; MIT, `apps/ccusage/LICENSE`). Where ccusage differs from this reader: it takes a comma-separated `CODEX_HOME` (`rust/adapters/codex/src/paths.rs:236-239`, guide `:26`), reads a bare JSONL folder when neither `sessions/` nor `archived_sessions/` exists (guide `:26`), and skips a `.zst` copy when the plain one exists (`paths.rs:92-93`; this reader decompresses a `.zst`-only rollout and lists a plain and a compressed copy of one id once). No ccusage code was copied. Codex also has command hooks, and their input is the structured alternative: it carries `session_id`, `transcript_path`, `cwd`, and `model`, for a tool call `tool_name`, `tool_input`, an untyped `tool_response`, and `tool_use_id` (`codex-rs/hooks/src/schema.rs:324-343`), for a prompt `UserPromptSubmit.prompt` (`:568-583`), and for a reply `Stop.last_assistant_message` (`:589-601`), with `SessionStart` and `SessionEnd` (`:500-511`, `:516-524`). So a Codex release can change the rollout format; an unreadable rollout is warned about by name and skipped, never fatal. The hand run that settles it: on a machine with a Codex account, run one `codex exec` task that makes one prompt, runs one command that exits nonzero (for example
`ls /nonexistent`), and applies one patch, then `oars sessions deposit --allow codex` and `oars sessions verify --strict`. It is settled only if the
session count is nonzero, there are zero violations, the session has a prompt and usage, and it holds an `error` tool record for that command with a
matching error line. A rollout whose shell outcomes were all lost would still show a session count and zero violations, which is why those are required.

## The Copilot source

`oars sessions deposit --allow copilot` reads GitHub Copilot CLI session logs into the same store. The records carry `harness: "copilot"`, take the same
field classes, redaction, and 1,000-character `line` cap as every other source, and `recall`, `measure`, `books`, and `verify` read them with no special case.
It is one more entry in the source table (`sources.ts`). Only the CLI (the agent in a terminal, which the Copilot SDK also drives) is read; VS Code's Copilot Chat
writes its own chat model under `workspaceStorage/<hash>/chatSessions/` and has its own reader (below).

**Fixture-derived, never run live.** This reader was written from the public Copilot SDK's generated event types (github/copilot-sdk @ d28a136, MIT,
`nodejs/src/generated/session-events.ts`, "AUTO-GENERATED ... from session-events.schema.json") and its `docs/features/session-persistence.md`, and tested only on
synthetic fixtures; no Copilot store has ever been read by it. The CLI itself (github/copilot-cli) is closed source, and no vendor statement promises the on-disk
format: the changelog calls the 0.0.342 move "a new session logging format", and the schema marks both fields the outcome rests on `@experimental`:
`shellExecution` is "Experimental shell completion facts" (session-events.ts:9976-9980) and `fileEdits` begins "Experimental. File mutations..." (:9929-9933). When
`shellExecution` is absent a shell call falls back to `success` (false is an error, else ok) with an unknown exit; when `fileEdits` is absent an edit is still
found by its tool name (`edit`, `str_replace_editor`, `apply_patch`, `write_file`), with the path from its request arguments, and a failed one is still an edit. The SDK has hook input (`docs/hooks/*.md`: tool name, arguments, error string), but it
holds no usage and no transcript path, and it sees only what runs after install, so it is not used. A Copilot release can change the log; an unreadable
session is warned about by name and skipped, never fatal. The one hand run that would settle it: on a machine with a Copilot account, run one `copilot -p "<task>" --allow-all-tools` task (the flag lets a non-interactive run execute the command and the edit) that
makes one prompt, runs one command that exits nonzero (for example `ls /nonexistent`), and edits one file, then `oars sessions deposit --allow copilot` and
`oars sessions verify --strict`. It is settled only if the session count is nonzero, there are zero violations, the session holds an `error` tool record for that
command with a matching error line, and usage is nonzero (it is written at shutdown, and is absent when the process dies without one). To check the resume case, resume that session (`copilot --resume`), send one more prompt, and exit: it is cumulative only if the second `session.shutdown`'s `outputTokens` is at least the first's plus the `outputTokens` of every `assistant.message` after the resume, and the chunk case holds only if a multi-chunk response's summed `outputTokens` does not exceed the shutdown's.

- **Where.** `$COPILOT_HOME`, else `~/.copilot` (`%USERPROFILE%\.copilot` on Windows): `session-state/<sessionId>/events.jsonl`, one JSON event per line:
  `{id, parentId, timestamp, type, data}`. The pre-October-2025
  `history-session-state` folder is not read. A log that rotated (when `COPILOT_SESSION_EVENT_LOG_ROTATION_BYTES` is set) leaves archives `events.N.jsonl` beside the
  live file; they are read oldest N first, then the live file, as one session. The session's cursor is the sum of its files' sizes and the newest modification
  time, so a new archive or a longer live file reads the session again and a second deposit adds nothing. The cwd comes from the oldest file's `session.start`.
  The live head's `session.journal_link {previousFile, sessionId, version}` is ignored. The order comes from N, ascending (no page states how the archives are
  numbered); the reader does not follow each head's `previousFile`. Like Cursor and Codex: read by default; `--allow` narrows and `--deny copilot` keeps it out; the nightly run
  repeats the saved list.
- **Mapping.** `session.start` gives the cwd and `copilotVersion`; `assistant.message.model` the model; `user.message.content` a prompt; `assistant.message` a response.
  A shell call is found by shape, not name (`shellToolInfo` on the start event, or `shellExecution` on the completion, which also marks one the start did not),
  because the schema does not list tool names and the vendor's docs disagree on them; its outcome is the real `shellExecution.exitCode`, which decides whatever
  `success` says, so a call that exited 2 with `success: true` is an error and one that exited 0 with `success: false` is not. The schema's `shell_exit` result
  contents are not read: it says persisted result contents are stripped, and no source shows a persisted line holding them. An edit is found by `fileEdits`
  (which also gives the files touched) or by its tool name. `session.resume` and `session.context_changed` move the cwd and model. A `user.message` whose `source`
  starts `skill-` or `agent-` is the harness writing, not a prompt, and is skipped, as is an autopilot continuation. The error line is the unwrapped message or output, not the wrapper.
- **Absent.** Cost has no equivalent. `assistant.usage` is `ephemeral` and never on disk, so per-response input and cache tokens do not exist: output tokens come
  from each `assistant.message`, and the input, cache, and reasoning totals from `session.shutdown.modelMetrics` land once, on the first line of the model's last response (one model call may be several `assistant.message` chunks sharing a `requestId`/`apiCallId`; they are one
  response). They are read from `agentMetrics.main` when the runtime writes it, because the session-wide `modelMetrics` include subagents, else from `modelMetrics`;
  output the responses did not report is the total less what they did. A rotated head's `checkpoint: true` events replay state the archives already hold, so with an archive present they are dropped, and so is any later line whose event `id` was already read: each event counts once. A lone rotated head (its archives deleted) is read as it is, checkpoint events included, since they are then the only record of the earlier part.
  `inputTokens` already includes the cache reads and writes (github/copilot-sdk @ d28a136 `docs/features/usage-and-billing.md:58`: "`inputTokens` already includes `cacheReadTokens` and
  `cacheWriteTokens`, so do not add them to it. The uncached part of the input is `inputTokens - cacheReadTokens - cacheWriteTokens`", the same at `:679` for `getMetrics`, and
  `docs/features/streaming-events.md:717` makes the shutdown's `modelMetrics` the same `ModelMetric`), so the stored input is that uncached part and the cache fields are kept apart, as capture's are.
  A model's totals are taken from its last `session.shutdown`, replacing earlier ones rather than adding to them. Cited: usage totals "belong to a session ... retains its usage and history for resume"
  and are "running totals for the whole session" (`usage-and-billing.md:36`, `:671`), a "Durable session usage checkpoint for reconstructing aggregate accounting on resume" (`session-events.ts:4450`),
  "Accumulated session usage metrics" (`:4042`), and the shutdown holds that same accounting state (`:3945-3949`). Inferred: no line says outright that a resumed session's `session.shutdown.modelMetrics`
  continues the earlier count, but all of it points to cumulative, so the last shutdown is the right one. The totals go on the first line of the model's last response, and the output beyond what all of that model's responses reported is the residual.
  The main conversation's metrics are `agentMetrics.main.modelMetrics` (the schema: "The main conversation uses the stable key `main`", `:3951`), each model's entry a `ShutdownModelMetric` with `usage` (`:4313-4332`). A chunk's `outputTokens`
  is "completion_tokens" of the API response (`:7985`), which does not say whether chunks of one response split it or repeat it; the reader sums them. An `assistant.message` with empty content and no tool requests is dropped with its `outputTokens`
  (the schema splits chunks one per reasoning boundary), so a session with no shutdown loses that output. The hand run checks two against a live store: that a resumed session's second shutdown continues the first, and chunk output sums against the shutdown total.
  A session that never shut down (a crash) has output tokens only from this reader. Its last `session.usage_checkpoint` may hold `providerModelMetrics` (session-events.ts:4472-4474, "Provider/model accounting snapshot that subsumes preceding usage receipts"), per-model totals that are not read; to look for one, open a crashed session's `events.jsonl`, find its last `session.usage_checkpoint`, and see whether `providerModelMetrics` is there. Subagent events (`agentId`, or the deprecated `parentToolCallId`) are skipped; the parent's `task` call is kept. Torn lines are counted as
  unparseable; a file with no parseable line is unreadable. Idempotent per session (`copilot/<id>` in `state.json`, size and mtime).

## The VS Code Copilot Chat source

`oars sessions deposit --allow vscode-copilot` reads the chat sessions VS Code itself writes into the same store. The records carry `harness: "vscode-copilot"`, take
the same field classes, redaction, and 1,000-character `line` cap as every other source, and `recall`, `measure`, `books`, and `verify` read them with no special
case. It is one more entry in the source table (`sources.ts`), and a different surface from the Copilot CLI above: VS Code serializes its own chat model, not Copilot's event log.

**Fixture-derived, never run live.** This reader was written from the public source of microsoft/vscode @ f92b8f3 (`f92b8f3adcd9bc034e6b9ade05c093dd59b99c5f`, MIT; the Copilot Chat
extension is in-tree at `extensions/copilot/`) and tested only on synthetic fixtures that each cite a line upstream can write; no VS Code store has ever been read by it. No vendor text promises the
format: the log form is behind `chat.useLogSessionStorage` with a "remove after stabilizing" note (`chatSessionStore.ts:739`), and the schema is versioned (`version: 3`,
`chatModel.ts:2593`). An unreadable session is warned about by name and skipped, never fatal. The one hand run that would settle it: on a machine with VS Code Stable and Copilot Chat,
open one chat that runs a terminal command and has one tool call refused (press Skip on the confirmation), copy the `Code` folder under `%APPDATA%` (or the platform's equivalent) to a temp
folder, set `APPDATA` and `HOME` to a temp folder with that copy inside, confirm `oars sessions` points at it, then `oars sessions deposit --allow vscode-copilot` and `oars sessions verify --strict`.
It is settled only if the session count is nonzero, there are zero violations, the command's `Bash` record carries its real exit code, the refused call reads `user-rejected`, and usage is nonzero; also check that the request's `agent.extensionVersion` is present (it fills `harnessVersion`) and whether the request holds `modelTotals` at all (if it does not, `input` 0 is expected and means not known, and the `inputTokens` comparison cannot be made).

- **Where.** The folder that holds one folder per VS Code build: `%APPDATA%` on Windows, `~/Library/Application Support` on macOS, `$XDG_CONFIG_HOME` (else `~/.config`) on Linux; `VSCODE_APPDATA` replaces it.
  The builds read are `Code` (Stable), `Code - Insiders`, and `Code - OSS`; a build with another `nameShort`, a portable install, or `--user-data-dir` is not discovered. Inside a build's `User` folder: `workspaceStorage/<hash>/chatSessions/<id>.json` or `.jsonl`,
  `globalStorage/emptyWindowChatSessions/<id>.json|.jsonl` (a window with no folder, so no working directory), and the older `workspaceStorage/no-workspace/chatSessions`. The `<hash>` leads to a working directory through the sibling `workspace.json`
  (`{folder}` or `{workspace}`, a uri). Like Cursor and Codex: read by default; `--allow` narrows and `--deny vscode-copilot` keeps it out; the nightly run repeats the saved list.
- **Two file forms.** `.json` is one `ISerializableChatData`. `.jsonl` is a mutation log, one entry per line: `{kind:0,v}` the initial value, `{kind:1,k,v}` a set, `{kind:2,k,v,i}` a push, `{kind:3,k}` a delete. VS Code reads the `.jsonl` first and the `.json` only when that is unreadable. With `chat.useLogSessionStorage` off it writes only the `.json` (`chatSessionStore.ts:353,394`), so a log left from an earlier run is the older file: this reader stats both files, reads the newer first (the `.jsonl` on a tie), and takes the cursor from it, so a changed `.json` is re-read.
  A malformed log line is skipped and counted in the deposit line (VS Code throws on one). A session moved between workspaces is copied and the original kept, so the newest copy of an id is read. Idempotent per session (`vscode-copilot/<id>` in `state.json`, the newest file's size and mtime).
- **Mapping.** A request is one prompt (`message.text`, or the string in the old format) and one response. A request flagged `isSystemInitiated` or hidden from the transcript is the harness writing, not the operator: its prompt is not read, its response is.
  `modelId` is the model, kept with its vendor prefix. A `toolInvocationSerialized` part is a tool call; its `toolId` is the bare name (`run_in_terminal`) or the contributed one (`copilot_applyPatch`), and both spellings have an `ACTION_TABLES` row, so a shell call reads as `Bash` and an edit as `Edit` or `Write`.
  A `textEditGroup` after an edit gives the file touched. Tool inputs are not persisted, so only a terminal command (`toolSpecificData.commandLine`) and an edit's file are known. A call with `subAgentInvocationId` is a subagent's own and is not read; the parent's `runSubagent` call is.
  A shell call's outcome is its real exit code (`terminalCommandState.exitCode`), never a status field: with no exit code and no error it is unknown. A failed call's error is the unwrapped message, cut at 1,000 characters after redaction.
  A refusal is `isConfirmed` `{type:5, source:'user'}` (the Skip button, which is a confirmation's decline button), `{type:0, source:'user'}` (an explicit cancel), or the boolean `false` (before VS Code 1.104): all store `user-rejected`.
  `{type:0}` or `{type:5}` with `source` `hook` or `riskAssessment` reads as a permission denial, and a `Denied` with no `source` claims neither actor (`chatService.ts:910`: "absence does not identify an actor"), so it is a plain denial.
  A `{type:5}` with no `source` is the skip after approval and has no outcome. Timestamps are epoch milliseconds; a missing or implausible one is never made up, the time carries forward.
- **Absent.** Cost and working-directory changes have no equivalent: the file holds none, and the editor's version is nowhere in it.
  The `version: 3` above is the chat-session schema's, not the extension's. The Copilot Chat extension's own version is the one version the file
  carries: each request holds the agent VS Code serialized beside it, `agent` (`ISerializableChatRequestData.agent`, `UriDto<IChatAgentData>`,
  `chatModel.ts:2196,2243`, written from the response's agent at `chatModel.ts:3849-3870`), and `IChatAgentData.extensionVersion` (`chatAgents.ts:71`)
  is that version, so `harnessVersion` is the newest request's `agent.extensionVersion` (t872's census), read only when `agent.extensionId.value` is `GitHub.copilot-chat`, compared
  case-insensitively as `ExtensionIdentifier` does: a third-party chat participant (another extension's `@name`) is serialized the same way with its own extension's
  version, which is not Copilot Chat's and is never read. A request whose agent has none, or a session of an older build with no `agent`, leaves it unset. The cells are `vscode-copilot/<extension
  version>/<model>`, or `vscode-copilot/unknown/<model>` for a session that names none, which a bundle asks for as `unknown` (`pool.md`, "What a
  bundle serves").
  `completionTokens` on the request is the whole turn's output; `modelTotals[{model, inputTokens, cachedTokens, outputTokens}]`, also on the request (`chatModel.ts:2086,2093`), is the only per-model figure
  (`chatService.ts:176-188`); neither sits under a `usage` key in the file, and a turn that used several models has them summed on its one assistant line, subagent-model tokens attributed to the request model. `promptTokens` is the last model call alone, so it is not read as consumption.
  **Input 0 means not known.** A normal Copilot Chat session, written by the extension, carries no `modelTotals`: the extension API bridge passes the editor only `promptTokens`, `completionTokens`, `outputBuffer`, `copilotCredits`, and
  `promptTokenDetails` (`extHostChatAgents2.ts:463-468`), and a public code search found `modelTotals` written only by the agent-host adapter (`stateToProgressAdapter.ts:936`). On such a session the reader stores
  `input` 0 with the whole turn's `output`, which means the input is not known, not that none was spent; do not read it as a cheap turn. The hand run checks whether the request holds `modelTotals` at all, and the cache comparison below applies only when it does.
  **Stated limit:** the source does not say whether `inputTokens` includes `cachedTokens`, so `inputTokens` is stored whole and the cache field kept apart. If VS Code's figure includes the cache reads, the cache is counted twice;
  the hand run settles it by comparing one turn's figures with the provider's usage. Not read: `result.errorDetails`, per-call durations, and `globalStorage/transferredChatSessions` (a short-lived hand-off written when a session moves to another workspace, removed once read and expired after five minutes, `chatSessionStore.ts:79,275,316`; the destination workspace then holds its own copy, so reading it would only repeat a session). An MCP call reads as `other`: VS Code's spelling of an MCP tool id is unverified, so no pattern is guessed, and the hand run shows the spelling.
  The session's `workingDirectory` overrides the folder in the transcript only, not in the listing's project slug.

## The Gemini source

`oars sessions deposit --allow gemini` reads Gemini CLI chat files into the same store. The records carry `harness: "gemini"`, take the same field classes,
redaction, and 1,000-character `line` cap as every other source, and `recall`, `measure`, `books`, and `verify` read them with no special case. It is one more
entry in the source table (`sources.ts`); the reader is `gemini.ts`.

**Fixture-derived, never run live.** This reader was written from the open-source Gemini CLI (google-gemini/gemini-cli @ 89e9d25d, Apache-2.0, v0.67.0-nightly.20261020;
nothing was copied) and tested only on synthetic fixtures; no Gemini CLI store has ever been read by it. No vendor statement promises the on-disk format:
`docs/cli/session-management.md:18` names only the folder, and the code itself migrates `.json` to `.jsonl` (`chatRecordingService.ts:732`) and marks `$set.messages`
`@deprecated` (`chatRecordingTypes.ts:151`). Hook input exists (`docs/hooks/reference.md:50-57`: session id, transcript path, cwd, timestamp), but it carries no
per-request input and cache split and sees only what runs after install, so, as for Codex and Copilot, the file is read. The one hand run that would settle it: on
a machine with a Gemini account, run one `gemini -p "<task>"` with tool approval on (`--yolo`) that makes one prompt, runs one command that exits nonzero (for
example `ls /nonexistent`), and edits one file, then `oars sessions deposit --allow gemini` and `oars sessions verify --strict`. It is settled only if the session
count is nonzero, there are zero violations, the session holds an `error` tool record for that command with a matching error line, the edit is a `file.edit` action
with the file, and usage is nonzero with `input_tokens` equal to the model's prompt count less its cached count. Run it with `APPDATA`, `HOME`, and `GEMINI_CLI_HOME` set to a temp folder (on Windows Node reads `USERPROFILE`, not `HOME`, so `GEMINI_CLI_HOME`, which the CLI and this reader both honor, is what keeps the run off the real `.gemini`).

- **Where.** `$GEMINI_CLI_HOME`, else the home, then `.gemini` (`%USERPROFILE%\.gemini` on Windows): `tmp/<slug>/chats/session-<time>-<id8>.jsonl`, one session per file. Under `SANDBOX=sandbox-exec` (macOS Seatbelt) the CLI keeps its runtime state, chats included, in `~/.cache/.gemini` instead (`config/storage.ts:93-102`), the same `tmp/<slug>/chats/` layout beside its own `projects.json`; that folder (the home's `.cache/.gemini`, `$GEMINI_CLI_HOME` honored) is listed with the ordinary one, each session once under its own id.
  A legacy single-object `*.json` is read too, and the newer of a `.json` and `.jsonl` with one file name wins. Other files under one session id are other chats, not twins: an AfterAgent hook's `clearContext` resets the chat and starts a new `.jsonl` under the same id (`core/client.ts:1032,1050`; `services/chatRecordingService.ts:780,811-818`), so the file whose head has the earliest `startTime` keeps the id and each later one is its own session, `<id>-<file name>`, with its own cursor. A subagent's file is
  `chats/<parentSessionId>/<agentId>.jsonl`, deposited as a subagent of `gemini-<parentSessionId>` so session counts stay main sessions; the parent's `invoke_agent` call
  stays. A file at the root of `chats/` whose head says `kind: "subagent"` (written there when no parent is set, `chatRecordingService.ts:787,813-814`) is skipped, as the vendor's own
  listing does (`cli/src/utils/sessionUtils.ts:301`). A file holding a head and the CLI's own context turn (every new chat appends a head, `geminiChat.ts:453`, and the `<session_context>` turn, `geminiChat.ts:453-458`, `environmentContext.ts:69,101-108`, so a launch and quit or a `/clear` leaves them) is no session until
  a prompt is appended; it is not reported as unreadable. Like the other sources: read by default; `--allow` narrows and `--deny gemini` keeps it out; read-only, with its own cursor (`gemini/<id>` in
  `state.json`, size and mtime); the nightly run repeats the saved list. The prompt log `logs.json`, the `checkpoint-*.json` copies, and the opt-in telemetry file are
  not read (a subset, copies, and off by default).
- **Mapping.** The file is the vendor's journal, folded the way its loader does: a message `id` written again replaces the earlier record in its place, and
  `$rewindTo`, `$patch`, and a deprecated `$set.messages` apply, with one difference. A history sync (compression, `core/client.ts:724,1294`, and every masking pass,
  `:734,1321`) re-records the kept turns under fresh ids with no `tokens`, `toolCalls`, or `model` (`core/geminiChat.ts:412-417,456,1386-1395`), then lists every old id in
  `$patch.removeIds` (`services/chatRecordingService.ts:1533-1590`). The vendor's loader drops those ids, because it rebuilds the model's history; this reader keeps the removed
  message, which is the only record of its prompt, usage, calls, and errors, and hides the one copy per removed message that has the same type and the same text and none of those fields. Text is compared as the CLI stores a response (zero-width characters and HTML comments stripped, trimmed; `core/geminiChat.ts:1710-1719`), because the copy holds the raw parts. The
  summary a compression records as a user turn (the text turn directly before a reply the CLI wrote, whatever it opens with: the model reasons in a scratchpad first, `context/chatCompressionService.ts:603`; a summary whose reply is gone is read by its `<state_snapshot>` tag) and the canned reply `Got it. Thanks for the additional context!` after it
  (`context/chatCompressionService.ts:665-673`) are the CLI's, not a prompt or a response. So is every turn of a saved chat loaded with `/resume resume <tag>` or `/chat resume`
  (`cli ui/commands/chatCommand.ts:228`, `slashCommandProcessor.ts:553`): `setHistory` records each turn with no tokens or model (`geminiChat.ts:1386-1395`), and a `gemini` message with text and none of
  tokens, calls, or `model` is the CLI's, since a model's text always carries `model` (`geminiChat.ts:1807-1812`); the user turn directly before such a message is the CLI's too. `$rewindTo` is a rollback, and after a pass upstream can only name a copy (`chatRecordingService.ts:1380,1410`), so the reader maps each hidden copy to its original (through a second pass) and rewinds from the original: the rolled-back prompt and response are gone and earlier turns stay, including the hidden copies of earlier turns (upstream keeps everything before the named copy), so a later pass still hides the copies it re-records. An `updates` entry on a message the same `$patch` removes (a masking pass) does not replace a result the call already holds, since the masked turn drops the `error` key (`context/toolOutputMaskingService.ts:224-231`). A `user` message is a prompt, recorded as `displayContent` (what the operator typed) when present; one
  whose parts are all `functionResponse` is a tool result, and one starting `/`, `?`, `<session_context>`, or `<hook_context>` is not the operator's (the vendor's own resume filter,
  `utils/sessionUtils.ts:97`), judged on the text sent (`content`), as the vendor does (`chatRecordingService.ts:220-227`), so a custom command whose `content` is its expansion and
  whose `displayContent` is `/cmd` is a prompt recorded as `/cmd`; with no `displayContent`, a `<hook_context>` part beside the typed text (a BeforeAgent hook's, `core/client.ts:985-989`) is left out. User turns the CLI injects are not prompts either, judged on `content` by the text their writer fixes: loop recovery `System: Potential loop detected.` (it re-sends the operator's `displayContent` beside it, so the prompt would otherwise read twice; `core/client.ts:1338-1354`), the IDE context (`core/client.ts:503,613`), `Please continue.` as the whole text (`core/client.ts:930`), the `!cmd` turn `I ran the following shell command:` (`cli useExecutionLifecycle.ts:61-66`), the manual plan exit note `User has manually exited Plan Mode. Switching to` (`cli useGeminiStream.ts:2060`), and the directory context `- **Workspace Directories:**` (`core/client.ts:396`), and the auto-nudge `[System: You successfully executed a tool but returned an empty response.` that follows a tool round with an empty reply (`cli useGeminiStream.ts:720,1796-1811`, `core agent/legacy-agent-session.ts:254-258`; recorded as a `user` message, `geminiChat.ts:563`). A steering hint (`User steering update:`, `cli useGeminiStream.ts:2345-2347`) holds the operator's own words and stays a prompt. A `gemini` message is a response, with its `model` and `toolCalls`; `thought` parts are left out. The placeholder `[The previous response was interrupted before it completed.]` that upstream closes a failed stream with (`geminiChat.ts:118,921-934`; recorded as a tokenless `gemini` message, `chatRecordingService.ts:1465-1480`) is not a response: it reads as empty, so a message that holds tokens or calls keeps them as a usage-only line. A call's `args.file_path` gives the files
  touched. Tool names have an `ACTION_TABLES.gemini` row (`run_shell_command`, `replace`, `write_file`, `read_file`, and the rest), so a shell call or an edit never reads as unknown.
- **Outcome.** A failed shell call is read from the real exit code, not `status`: the vendor records `status: "success"` for a nonzero exit and appends an
  `Exit Code: N` line (or `Signal:`) to the output (`tools/shell.ts:963-964`), wrapped in `<untrusted_context>`. The reader unwraps it, so the error line is the command's
  own output and can join a Claude Code signature. Output over the executor's threshold (default 40,000 characters, `config/config.ts:487`) is rewritten to a header line, the first
  20%, a marker, and the last 80% (`utils/fileUtils.ts:828-833`), and a hook-modified call gets a note after the closing tag (`scheduler/tool-executor.ts:131-133`); the trailer
  is in the tail that survives, so the reader takes the text before the last closing tag, drops everything through the first opening tag, and still finds the exit code. When the
  text is cut so the closing tag is gone (the stored result is capped at 64 KB, `utils/constants.ts:18`, and `truncateToolOutput` keeps the head and adds a suffix, `utils/tool-utils.ts:178-205`, so 40,000
  multi-byte characters can exceed it), the exit code is lost with it: that call is left unsettled, `none`, as for a call with no result, not recorded as a success. The same holds for a shell `success` under the `summarizeToolOutput` setting (`packages/cli/src/config/settingsSchema.ts:1090`): upstream stores only the wrapped summary, with no `Output: ` and no exit code (`tools/shell.ts:1175-1187`), whatever the exit was, so a result that opens with none of `Output: `, `Command moved to background`, or the timeout sentence is `none`. A shell call that hit the inactivity timeout is an error too: the tool writes one sentence (`Command was automatically cancelled because it exceeded the timeout...`) and no trailer
  (`tools/shell.ts:929-933`), and the executor still records `success` (`scheduler/tool-executor.ts:144-154`), so that sentence is the error line. A call with `status: "error"` or `"cancelled"`, or a `response.error`, is an error with that message. A call's result is the `functionResponse` whose `id` is the call's; a history
  sync writes the whole user turn, every parallel call's response, as the result of each call in it (`chatRecordingService.ts:1500-1525`), so the first response in the list is not read as the call's.
- **Usage.** Per message only (`tokens{input, output, cached, thoughts, tool, total}`); the vendor's session totals are in memory and never written, so nothing is cumulative across a
  resume and each message is taken as it stands. `tokens.input` is the prompt count and includes the cache (`uiTelemetry.ts:317-320` computes the uncached part as
  `input - cached`), so the stored `input_tokens` is `input - cached` with the cache read kept apart, as capture's fields are disjoint. The vendor counts `thoughts` apart from `output` (candidates; `chatRecordingTypes.ts:21-25`), so `output_tokens` is `output + thoughts` and `thoughts` is also
  `output_tokens_details.thinking_tokens`, which keeps thinking within output as `verify` holds; `tool` (the tool-use prompt) is not mapped. A message with no `tokens` has no usage and is not an error.
- **Absent.** `info`, `warning`, and `error` messages (`chatRecordingTypes.ts:74`) are not read: they are the CLI talking to the operator, not a prompt or a response. Cost has no equivalent.
  The CLI version is not in the record and is left unset (t872's census found no other field of the recorded session that carries it), so the cells
  are `gemini/unknown/<model>` and a bundle for them is asked for as `unknown` (`pool.md`, "What a bundle serves").
  A call's duration is not recorded. `setup`, `funnel`, and `trust` other than `unattendedRun` are absent, as for Copilot (`session-shape.ts`).

**Known gaps.**

- *The working folder.* The cwd is `tmp/<slug>/.project_root`, or for a hash-named folder a path that hashes to its name, recorded as written: the vendor lower-cases it on Windows, so a Windows folder reads lower-case. A directory change
  inside a session is not recorded, and `directories` in the head are `/dir add` workspaces, not the cwd. A project folder from before the slug registry is named for `sha256` of the project root and has no marker (`config/storage.ts:263-265`; the CLI moves it to a slug when it next opens that project, `:307-331`, so one still named by hash is a project not opened since). The hash cannot be turned back into a path; it can only be checked against one. The reader hashes the paths it can reach and takes the one that matches the folder's name: the workspace directories the chat's own `<session_context>` turn lists (`utils/environmentContext.ts`), the roots other folders' markers name, and the keys of `projects.json`. A matching path is the session's cwd. A folder none of them match (a chat whose context turn was removed, and no marker or registry entry for the path) keeps no cwd, and a path from the chat that does not hash to the name is never used. A torn `projects.json` names no path and is not reported, since the registry is only a source of candidates. Case matters: the hash is of the path as the CLI held it, and the registry lower-cases a path on Windows, so on Windows the chat's own list is what matches.
- *A loaded chat's last turn.* When a saved chat loaded with `/resume resume <tag>` ends on a user turn with no reply after it, that turn reads as a typed prompt, since only a reply marks the turn before it as the CLI's.
- *Hook continuations.* An AfterAgent hook's `continueReason` is sent as a user turn together with the operator's `displayContent` (`core/client.ts:1052,1061-1067`), so the turn reads as the operator's prompt again: one extra prompt per continuation. It is left as a known limit because a repeated `/cmd` writes a like shape.
- *Slash-prefixed prompts.* A prompt that starts `/` or `?` is not counted as the operator's, following the vendor's resume filter, so one like `/etc/hosts?` is lost.
- *Prompts that match an injected text.* An operator who types exactly `Please continue.` is dropped, and so is a prompt that opens with one of the injected texts listed under Mapping, since the reader cannot tell the two apart.
- *Experimental context management.* With it on (default off, `packages/cli/src/config/settingsSchema.ts:2461-2466`, `core/client.ts:678-724`) the history provider merges an `<intent_summary>` into the first kept user turn (`context/agentHistoryProvider.ts:316-336,411-412`) and `setHistory` re-records it. This opt-in mode is not modeled, and its summaries read as prompts.
- *The shell.* The CLI runs PowerShell on every Windows machine (`utils/shell-utils.ts:658-697` `getShellConfiguration`: `pwsh.exe` when it is on the path, else `powershell.exe`, and `bash` elsewhere), so a shell call in a session whose context turn says `My operating system is: win32` (or, with no context turn, whose working directory is a drive-letter or UNC path) is stored as `PowerShell`, with the frame's `shell` `powershell`. The chat records no shell name, so a session that ran on Windows with its context turn removed and a cwd that is not written the Windows way still reads as bash. Claude Code's `PowerShell` rows are unchanged.
- *Shell output that ends in `Exit Code: N`.* The exit is read from the trailer lines in the vendor's order (`Exit Code`, `Signal`, `Background PIDs`, `Process Group PGID`), so
  output that itself ends in an `Exit Code: N` line with a real exit of zero reads as a failure.
- *The listing reads each chat file whole.* A head read (the first line) cannot answer what the listing decides: whether the file holds any prompt or response (`$set` records can precede the first message, and a `.json` file is one object with no head line), whether a line is torn (a torn file is named, not dropped as empty), and, for a hash-named folder, the `<session_context>` workspace list. So each listing reads every chat file once, and a capture reads the changed ones again. The cost grows with the size of the Gemini store, not of the change; it is left as a known limit, and a size-and-mtime cache of the listing's answers is the fix if a store is large enough to feel it.
- *Not read, by choice.* The opt-in telemetry outfile (`--telemetry-outfile`) carries per-request events but is off by default, and the chat file already holds the prompts, calls, and per-message usage, so it is left unread. A torn or unknown line is
  counted as unparseable and skipped; a file with no parseable line is unreadable, named, and left at its old cursor.

## The Grok Build source

`oars sessions deposit --allow grok` reads Grok Build (xAI's `grok` CLI) session logs into the same store. The records carry `harness: "grok"`, take the same field
classes, redaction, and 1,000-character `line` cap as every other source, and `recall`, `measure`, `books`, and `verify` read them with no special case. It is one
more entry in the source table (`sources.ts`). The TUI, `grok -p`, and the ACP agent mode share one store, so one reader covers them.

**Fixture-derived, never run live.** This reader was written from the public source of the CLI (github.com/xai-org/grok-build @ 2bdd1d6, Apache-2.0, Rust,
`crates/codegen/`) and the Agent Client Protocol schema it implements (agentclientprotocol/agent-client-protocol @ 0e486bcd, `schema/v1/schema.json`), and tested only
on synthetic fixtures; no Grok Build store has ever been read by it. No vendor statement promises the session-file format: the user guide (`17-sessions.md:278`)
steers readers to `grok usage` ("Use this instead of reading session files"), and the only versioned surfaces are the OTel metrics ("Status: alpha") and the
status-line payload. Hooks exist (`10-hooks.md:274-283`, with `exit_code` on `PostToolUse`), but they carry no usage and no history and see only what runs after
install, so they are not used. A Grok Build release can change the files; an unreadable session is warned about by name and skipped, never fatal. The one hand run that
would settle it: on a machine with `grok` signed in, run one `grok -p "<task>"` that makes one prompt, runs one command that exits nonzero (for example `ls /nonexistent`),
and edits one file, then `oars sessions deposit --allow grok` (note any `_meta["x.ai/tool"]` name that differs from the table) and `oars sessions verify --strict`. It is settled only if the session count is nonzero, there are zero
violations, the session holds an `error` tool record for that command with a matching error line, and usage is nonzero. To check the resume and fork cases, resume
that session (`grok -c`), send one more prompt, and confirm `usage.json` `turns` kept adding; then `/fork` it and confirm the child's `summary.json` has `forked_at` and
that a deposit counts only the child's own prompts.

- **Where.** `$GROK_HOME` if set and non-empty, else `~/.grok` (`%USERPROFILE%\.grok` on Windows) (`xai-dirs/src/lib.rs:51-57`; `17-sessions.md:18`):
  `sessions/<percent-encoded cwd>/<session id>/`. The cwd is `summary.json` `info.cwd` (a long path's folder name is a hash, so the name is not read). Three files are
  read: `updates.jsonl` ("the authoritative conversation log", `17-sessions.md:42`), `summary.json`, and `usage.json` (not in the documented layout, but `grok usage`
  prints it). `events.jsonl` is telemetry with no prompt text or cwd, and `chat_history.jsonl` is the model-facing copy; neither is read. Like Cursor, Codex, and
  Copilot: read by default; `--allow` narrows and `--deny grok` keeps it out; the nightly run repeats the saved list. A deposit only reads.
- **Mapping.** Each `updates.jsonl` line is `{timestamp, method, params: {sessionId, update}}` with an ACP `update`. `user_message_chunk` text is a prompt (a prompt that is only an image is one too: it is written as an image block with no data, so the turn is counted and the next reply is a new response, `turn.rs:960-962`, `storage/mod.rs:416`; chunks
  merge into one prompt until the agent speaks or `_meta.promptIndex` changes, so a prompt cancelled before its first reply and then retried stays two prompts,
  `turn.rs:890-895`, `storage/mod.rs:1009`; a change between marked and unmarked opens a new prompt too, `storage/mod.rs:1038-1039`, since a `!cmd` prompt carries only a model id, `tool_dispatch.rs:185-187`, while two unmarked chunks merge). Three markers say the text is not the
  operator's: `_meta.hostTurn` (a slash command's turn), `_meta.hideFromScrollback` (a turn the harness started: a finished task, subagent, or workflow, a notification
  drain, or a goal summary or nudge, `turn.rs:328`, `:896-901`, `session/mod.rs:242-255`), and `_meta.interjection` (a mid-turn steer whose text is a model-facing frame). The first two
  end the turn too, so the next response is a new one. `hostTurn` also marks an `agent_message_chunk` (a slash command's output, `acp_session.rs:1353-1372`, `slash_exec.rs:64`),
  which is dropped and ends the turn, as upstream's own rebuilders do (`storage/mod.rs:429-432`, `replay.rs:448-452`); other `agent_message_chunk` text is a response; a `tool_call`'s `title` is the tool's name (a backend-hosted search is titled `Web search:` or `X search:` for display, so when `rawInput.backend` is true the name comes from
  `rawInput.variant`: `web_search` or `x_search`, `acp_session_impl/tool_dispatch.rs:94-105`), its arguments are `rawInput`, and its outcome is the
  `tool_call_update` with `completed` or `failed`. A shell call is a `run_terminal_cmd`, `run_terminal_command`, or `bash` call, or any call of `kind` `execute` (the
  user's `!cmd` is one; its `rawInput` is the tagged `Bash` input with the full `command`, `tool_dispatch.rs:223-229`, `:250`). Its outcome is `rawOutput.exit_code`, not the status: the agent path marks a call `failed` only on a timeout or a signal, so exit 2 arrives
  `completed` (`acp_conversion.rs:241-250`); the `!` path marks nonzero `failed`. Any other tool's error text is its `content[]` text, except a failed MCP call, which has none and keeps its text in `rawOutput.output.Error`
  (`acp_conversion.rs:325-338`, `types/output.rs:1148-1158`); a `rawOutput` is otherwise a tagged wrapper and is never the error line. An edit is found by tool name (`search_replace`, `apply_patch`, `edit`, `write`, `hashline_edit`); its files are `file_path` (`filePath` for the opencode `edit`, which is camelCase; the tools'
  input structs: `search_replace/mod.rs:74`, `opencode/edit/mod.rs:64`, `:138`, `:579`, `opencode/write/mod.rs:31`, `grok_build_hashline/edit/types.rs:12`), the `*** Add|Update|Delete File:` headers
  of an `apply_patch` `patch` (`codex/apply_patch/tool.rs:104`, `parser.rs:40-42`), and the `diff` parts of the completion's `content[]`, which hold the absolute path (`acp_conversion.rs:202-204`), so a relative `file_path` is joined to the session's folder before the two are compared and each file is stored once, absolute like Claude Code's; those key names are read from the
  structs, not from a recorded line, so they are inferred. An MCP call arrives two ways, and both are recorded as `mcp__<server>__<tool>` with step `mcp.call`: titled `<server>__<tool>` itself, or through the `use_tool` wrapper (the model reaches MCP tools through `search_tool` and `use_tool`, `17-sessions.md:42`), which is titled `use_tool` (`tool_calls.rs:1487`, `use_tool/mod.rs:15`) and holds the qualified name in `rawInput.tool_name` (`use_tool/input.rs:19-20`, `use_tool/mod.rs:308`) with its arguments in `tool_input`; a `use_tool` call whose name holds no `__` stays `use_tool`. The cwd is `info.cwd`,
  then the `current_dir` of each shell call that named no `workdir` (the opencode `bash` tool's one-shot directory, `opencode/bash/mod.rs:376`, `:454`). The struct's comment calls it "the current working directory after the command completes" (`types/output.rs:397`), but the writer stores the cwd resolved before the command runs (`grok_build/bash/mod.rs:1876`, written at `:2240`, with no later assignment), and each call is a new shell (`grok_build_concise/bash.rs:53-54`), so a `cd` inside a command never shows: the field moves only when the session's own folder moved. `info.cwd` is the latest generation
  (`persistence.rs:1157-1159`), so a session that was moved to another directory carries the new cwd on its earlier lines too, until its first `current_dir`; a `cd` outside a shell call
  is not seen until the next shell call (`summary.json` holds `cwd_generation` and `previous_cwd`, which are not used).
- **Timestamps.** The envelope's `timestamp` is epoch seconds with a serde default of 0. A zero, missing, or earlier time takes the latest time so far, starting from
  `summary.created_at`, so no time goes backward. A session whose lines all lack a time has one time: `created_at`, and when the summary has no `created_at` either, the epoch
  (1970-01-01), which is a known gap (pinned by a test, not repaired).
- **Absent.** There is no cost field in the skeleton (`usage.json` has `costUsdTicks`, 1e10 per USD, which is not read), no reasoning text, no per-call model, and no
  per-response usage: usage is per turn. Each turn's totals land on the last response before its `endedAt`, else the first (turn numbers are not used, since a rewind
  renumbers them), and that turn's `primaryModelId` becomes the response's model; other responses carry `summary.current_model_id`, the model the session ended on. No
  file records the Grok Build version (t872's census, from the fixtures and the cited source), so the skeleton's harness version is empty, the cells
  are `grok/unknown/<model>`, and a bundle for them is asked for as `unknown` (`pool.md`, "What a bundle serves").
  `inputTokens` is the full prompt, cache reads and writes included
  (`xai-grok-sampling-types/src/conversation.rs:771-773`: "`prompt_tokens` is always the FULL prompt size (uncached + cache reads + cache writes)", mapped to `inputTokens` at
  `xai-chat-state/src/usage.rs:53` and `usage_file.rs:80`), so the stored input is `inputTokens - cachedReadTokens - cacheCreationTokens` (never below 0) and the cache fields are kept apart, as capture's are.
- **Totals.** `usage.json` `turns[]` are per-turn deltas and `session` is their sum (`usage_file.rs:230-300`), so every turn is added once; there is no cumulative first
  summary to avoid. A resumed session continues the same file. A fork copies its parent's `usage.json` and `updates.jsonl` (`persistence.rs:2608`, `copy.rs:229`): lines older
  than `summary.forked_at` and turns that ended at or before it are not the fork's own and are skipped.
- **Subagents.** A subagent is a separate session in the same tree with `summary.session_kind` `subagent` or `subagent_fork` (`persistence.rs:3016`); it is not listed, and
  the parent's `task` call is the record. A skill call (`skill`, input `{name}`, `opencode/skill/mod.rs:50`) is recorded as `skill.run` with the skill's name, and a `todowrite` call as `plan.update`; no
  separate log marker for the turns a skill runs was found at the pin (not traced further), so they are read as the session's own. A session with `num_messages` 0 holds nothing and is not listed.
- **Known gaps.** A prompt that holds only a `resource_link` or `resource` block opens no turn, so the next reply can extend the last response. `forked_at` is read as the parent reference, as the user guide describes it (`17-sessions.md:42`: "parent session reference for forked or restored
  sessions"); only forks and subagent forks were traced, so a restore that sets it would read as a fork and lose the lines before it. A mid-turn interjection (`_meta.interjection`) is dropped whole: its text block is the model-facing frame and the operator's typed text is kept apart in `displayText` (`storage/mod.rs:972-973`), which is not read, so a real steer is lost from the prompts. A restore that reads as a fork is the case above. `updates.jsonl` keeps rewind markers and the dead branches they cut (`session/storage/jsonl/copy.rs:227`), and the reader counts a rewound branch's prompts and calls as the session's. A failed `list_dir`, `grep_files`, `get_task_output`, or `kill_task` carries no `content[]` and no text in its `rawOutput` that the reader takes (`acp_conversion.rs:186-197`, `:357-400`, `:478-490`), so its error line is `tool failed`, not text; so does a failed backend-hosted search, whose `rawOutput` is only `{action, id, status}` (`sampling_events.rs:581-582`, `tool_dispatch.rs:117-127`, `:403-412`). A session's tools can be renamed: wire names are client-renameable (`xai-grok-tools/src/tool_taxonomy.rs:145`, session `tool_overrides` at `acp_session.rs:804`) and `title` is the wire name (`tool_calls.rs:1487`), so a renamed shell or edit tool reads as unknown. `_meta["x.ai/tool"]` on the `tool_call` carries the kind (`tool_calls.rs:1478`, `normalization.rs:28-37`, `tool_taxonomy.rs:187-196`) and is not read; when renaming is active by default was not traced. No reader change until a live store shows it. A `cd` inside a command is never seen (the `current_dir` the writer stores is the cwd before the command, `bash/mod.rs:1876`, `:2240`), so a session that changes folder only through `cd` keeps its starting cwd. Torn lines are counted as unparseable; a
  file with no parseable line is unreadable. Idempotent per session (`grok/<id>` in `state.json`, the size and latest mtime of `updates.jsonl` and `usage.json`).

## The outcome gold set

`oars sessions gold sample` writes `outcome-gold-<date>.md` to `<claude config>/session-commons/review/`: about 200 prompts in batches of 50, each with the redacted request, the result (commit message and diff stat where found, the transcript's own edit calls, or the actions of a prompt that edited nothing), and a `Judgment: yes|no` line. The draw is seeded and weighted by the square root of each class and model cell, with at most two prompts a session, so its base rate is the sample's, not the store's. Every session passes the exclusion rule (`checkSession`) first: one that holds a listed term, has no raw to scan, or cannot be read is left out, and a missing or empty term file (`OARS_EXCLUSION_TERMS`) refuses the draw. `--exclude-term` adds terms to the file's, never in place of it. A marker prompt, a `no-tools` prompt (its reply is the closing claim), and a session from any other harness (every `SOURCES` name) are not drawn. The signals go to the `.arms.json` file beside it. `oars sessions gold score <file>` prints, per model and pooled, each signal's AUROC with a DeLong 95% interval and the base rate, from whatever is judged so far. Both are local, and neither is ever committed. A signal is an observation, not a label, and no signal is combined with another.

`gold sample` and `gold arms` number turns by the capture's rule ("What opens a prompt"), so an entry drawn before CAPTURE 10 from a session with a command-opened turn no longer matches its view, and `gold arms` counts it as changed and reads nothing for it.

`oars sessions gold arms <file>` fills the same sidecar and leaves the gold file alone, so judgments carry over. From the transcript it reads the closing reply, the turn's last `Confidence:` line, and the next prompt that is not a marker. Fresh single-turn readers then give three separate answers: `evaluator` reads what the judge reads and says whether the work did what was asked, `claim` reads the closing reply and says whether it claims success, and `later` reads the next prompt and says whether the person accepted the work, or that it cannot tell. Each runs through `claude -p` on your own subscription login, on one named model, with no tools, hooks, settings, or session file. Its fixed wording is hashed into the sidecar, and a rerun refuses a sidecar written under other words. The command checks the login first and refuses an API key or another provider. It saves after each answer and resumes, and it prints only how many prompts each arm covers; `gold score` reads each arm against the judgments. This is the one `sessions` command that calls a model. The text it sends is redacted and has no tools to act on.
