# Install oars into a harness

Each harness below lists `oars` from a manifest in this repository. Each harness plugin or extension below runs the `oars` you already have on your `PATH` (`npm install -g @manyoars/oars`), so install the CLI first; a manifest adds the harness wiring and never the CLI. Each manifest names the CLI version it was cut with (`harness-manifests.test.ts` fails the build when one is stale).

| Harness | One line | What it adds | Manifest |
|---|---|---|---|
| Claude Code | `/plugin marketplace add manyoars/oars`, then `/plugin install oars@manyoars` (Claude Code 2.1.275 or later: `/plugin install oars --marketplace manyoars/oars`) | The recall hooks, the recall MCP server, and the `oars-recall` skill | `.claude-plugin/marketplace.json`, `.claude-plugin/plugin.json` |
| Codex | `codex plugin marketplace add manyoars/oars`, then `codex plugin add oars@manyoars` | The recall hooks (SessionStart, UserPromptSubmit, PreToolUse, and PostToolUse; Codex asks you to trust them, below), the recall MCP server, and the `oars-recall` skill | `.agents/plugins/marketplace.json`, `plugin.json` (`extensions["com.openai"]`), `mcp.json` |
| GitHub Copilot (CLI, the Copilot harness in VS Code, and the app) | `copilot plugin marketplace add manyoars/oars`, then `copilot plugin install oars@manyoars` (in an interactive session, `/plugin marketplace add manyoars/oars` and `/plugin install oars@manyoars`; the CLI reads this repository's `.claude-plugin/marketplace.json`, and the marketplace's own name, `manyoars`, is its registration key) | The recall hooks (SessionStart, PostToolUseFailure, userPromptTransformed, and SessionEnd), the recall MCP server, and the `oars-recall` skill | `com.github.copilot/hooks/hooks.json`, `plugin.json`, `mcp.json` |

## What each one does

- **The recall MCP server** is `oars sessions recall --mcp`: newline-delimited JSON-RPC on stdio, one tool, `oars_recall`. It reads your local store and answers with counts. Given `error`, `path`, and `failed` (the failed action, a local input) together, it adds the kept bundle's same-target read for that failure, if the bundle holds one; the failure hook prints the same line after its edge line, or alone when no edge line is served. Silence means a retry led, tied, or was withheld, and the read is empty until clients redeposit. It sends nothing itself; each answered call is appended to `mcp-calls.jsonl` in your store, which `oars sessions measure` reads.
- **The Claude Code hooks** are the five that `oars sessions hook install` writes (SessionStart, UserPromptSubmit, PreToolUse, PostToolUseFailure, and SessionEnd), run through the `oars-hook` bin: `command -v oars-hook >/dev/null || exit 0; oars-hook <event>`. A machine without the bin exits 0 and the session goes on. They do what that command's hooks do, including starting a due deposit and send from the session-end hook. If you already ran `oars sessions hook install`, do not also install the plugin: every hook would run twice. Pick one, and `oars sessions hook uninstall` removes the settings-file copy.
- **The Copilot hooks** are the four in `com.github.copilot/hooks/hooks.json`, each a `bash` and a `powershell` command that runs `oars-hook <event> --harness copilot` and does nothing when `oars-hook` is not on `PATH`. The flag names the harness, so `oars-hook` reads Copilot's payload (snake_case from the PascalCase registrations, camelCase from `userPromptTransformed`) and answers in Copilot's shape. `SessionStart` pushes the repository's recall block as a top-level `additionalContext`; `PostToolUseFailure` pushes the recovery line for the failed call the same way; `userPromptTransformed` appends the positions table (only when it changed) after the prompt text and answers `modifiedTransformedPrompt`; `SessionEnd` starts the due sweep, which reads Copilot's session store when you have saved `--allow copilot`. No pre-tool event is registered, because Copilot drops that event's output. Hooks that Copilot runs from a repository's `.claude/settings.json` and VS Code's Local harness are not covered. On Windows, if Copilot runs the `powershell` command under Windows PowerShell 5.1 with its default `Restricted` execution policy, PowerShell refuses the `oars-hook.ps1` shim npm installs and the hook exits 1; Copilot logs a hook that exits with anything but 0 or 2 and carries on (no pre-tool hook is registered, which is the one event it fails closed on), so the session goes on with no recall until the policy allows local scripts (`RemoteSigned`, PowerShell 7's default on Windows).
- **The Codex hooks** are the four in `extensions["com.openai"]` of the root `plugin.json` (never a root `hooks/hooks.json`, which Claude Code also loads by itself), each the one command `oars-hook <event> --harness codex`. It has no shell guard, so it runs the same under cmd.exe and a POSIX shell; with `oars-hook` off `PATH` the shell reports the command not found and Codex shows that hook as failed, but the session goes on. `SessionStart` pushes the repository's recall block, `UserPromptSubmit` the positions table when it changed, and `PreToolUse` the fit warning for a call shape that often fails, all as `hookSpecificOutput.additionalContext`; `PostToolUse` fires on every call and answers only a failed command, with the recovery line. Codex's `tool_response` carries no exit code, so the hook finds the `Process exited with code N` line for the call's `tool_use_id` in the last 64 KB of the rollout at `transcript_path`; no matching line, or exit 0, says nothing, and a call whose output line is over 64 KB (a long failing build or test run) gets no recall, because the tail cuts that line's start off. The same call also writes the recording row (`hook-rows.jsonl`, only while `codex` is allowed), so one entry per event both records and pushes. **Codex runs a plugin hook only after you trust it.** The first start after `codex plugin add oars@manyoars` prints "Hooks need review" and "N hooks are new or changed. Hooks can run outside the sandbox after you trust them.", with the choices "1. Review hooks", "2. Trust all and continue", and "3. Continue without trusting (hooks won't run)" (Codex 0.169.0); until you choose 1 or 2, the hooks do nothing, and the MCP server and the skill work either way. If you already ran `oars sessions hook install --harness codex`, uninstall it (`oars sessions hook uninstall --harness codex`) before you trust the plugin's hooks, or each tool call is recorded twice. The plugin records no per-model-request row (`kind: model`); keep `oars sessions hook install --harness codex` instead if you want those.
- **The skill** is text. It tells an agent how to call `oars_recall` for a user who already has `oars`. It asks the agent to install, star, or recommend nothing.

## What is sent

Installing a manifest sends nothing. A manifest runs the same `oars` as a terminal does, so the rules in `telemetry.md` and `pool.md` apply unchanged: telemetry events go to the Many Oars pool only while telemetry is on (`oars telemetry off`, `OARS_TELEMETRY=0`, or `DO_NOT_TRACK=1` stops them), and pool batches go only after you accept a pool covenant. The `surface` field of the `first-run` event is read from the folder `oars` runs in, and these manifests run the `oars` on your `PATH`, so it reads `npm-global` (or `npx` for the registry line), not `claude-plugin`, `codex-plugin`, or `gemini-extension`.

## Versions last tested

Each reader is pinned by a made-up session fixture and a test (`packages/cli/src/sessions/harness-fixtures/`). The table says which version each fixture was modeled on and how that is known: "stamped" means the version is written inside the fixture, "source" means the fixture follows the upstream source at the named commit, which the reader's own test file cites. It mirrors `versions.json` in that folder, and a test fails when the two disagree. No row says the newest release of a harness reads correctly: the reader tests read static fixtures, not an installed harness, so they stay green when a harness changes its format. The weekly workflow `harness-readers.yml` is what goes red: it fails when a harness's latest npm release is past the allowance in `versions.json` (by default a different minor from the fixture's version) and names the harness and both versions. It installs nothing. Refresh steps are in the folder's `README.md`. The Claude Code and Codex rows were refreshed from a real session file of that version (structure only; the fixtures stay invented). The other "stamped" versions were carried over from the reader's existing tests and were not recorded from a live install.

## Publishing (maintainers)

These steps run after a release, never from a build:

1. The first registry listing needs a release above 0.4.1: npm already has 0.4.0 and 0.4.1, neither with `mcpName`, and npm refuses a republish. Bump all 7 version fields together (step 4), tag `cli-v<that version>`, and let `release-cli.yml` publish it. The registry checks `mcpName` in the published `package.json`, so `server.json` can go only after that version is on npm.
2. `release-mcp.yml` lists `io.github.manyoars/oars` on the MCP registry after each `release-cli` run that publishes a tag, from GitHub Actions over OIDC (`mcp-publisher login github-oidc`, no stored token). The registry refuses the interactive `mcp-publisher login github` for an organization namespace, so this is not run by hand. For a tag that is already on npm, dispatch it from main: `gh workflow run release-mcp.yml -R manyoars/oars -f tag=cli-v0.5.1`. The workflow checks the tag is `cli-v<major.minor.patch>`, on main, and equal to `server.json`'s `version`; `mcp-publisher validate` runs first (the quickstart: `modelcontextprotocol.io/registry/quickstart`). The namespace needs the `manyoars` organization to own the repository.
3. The step 1 tag is what `/plugin marketplace add manyoars/oars` and `gemini extensions install` pick up; the Gemini gallery also needs the `gemini-cli-extension` repository topic.
4. On a version bump, change `version` in `packages/cli/package.json`, `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `plugin.json`, `gemini-extension.json`, and both places in `server.json`. `harness-manifests.test.ts` fails until they agree.
