# Changelog

All notable changes to `@manyoars/oars`. Versions follow semver; a release is the tag `cli-v<version>`.

## Unreleased

- The client has one gate and the pool enforces the rest (t881): `pool deposit` sends an MCP server, skill, pull name, program basename, native tool name, and host as they are after redaction, and `private` only for a name the redactor changes, an exclusion term matches, that is not a name, or that is over 128 characters. The pool holds a name off the public lists and serves it only once five accounts report it, hashes a host on arrival under `INGEST_HASH_KEY` (an unset key refuses the deposit), and every signed bundle states its `floor`. A long-tail program goes with no subcommand or flags for now. `outbox` still prints every byte that would leave, hosts included.
- The Codex reader keeps the shell outcomes of Codex 0.166+, which runs commands in a code-mode cell: an `exec` cell settles from its own `Script completed|failed|running with cell ID` header (`failed` carries its `Script error:` text) and a `wait` settles the cell it polled, and each `CommandExecution` item no call owns (`exec-<uuid>`) is its own `Bash` record with its exit code, output, and duration. A live 0.166/0.167 store had read every cell as ok and lost all 77 failing commands.
- The pool no longer limits what an account contributes: `MAX_DEPOSITS_PER_ACCOUNT` and `MAX_DEPOSIT_BYTES_PER_ACCOUNT` default to unlimited and stay only as an operator's brake, and a batch past the 1 MiB request cap is cut into 512 KiB parts (`oars-part`, `oars-batch`) that the server keeps as one deposit, a part sent again changing nothing, staging held to the join cap, and `oars pool outbox` printing every part's request (t880). Sending is still disabled in this release.
- A failed call of several commands (`a && b`) no longer marks each segment `error`: the segments read `none` and the failure stays on the call; a Codex dynamic tool call settles from its `DynamicToolCall` item (a failed one is an error, one with no item is unsettled, not ok); and a step's cost carries `allocated: true`, on the wire too, where its tokens were divided among a response's calls rather than measured. The wire's field list moves to version 4 (the new `allocated` field, with its `--explain` row and register row, so batches built under version 3 are discarded and built again), and the capture version moves to 19 because stored segment and Codex values change, so the next capture re-reads every transcript.
- Telemetry is sent now, only to the pool server in `OARS_POOL_URL` (there is no default server, so with none set nothing leaves the machine) and only while telemetry is on and the notice has been shown. The nightly task sends, and a command sends at most once a day from a detached process that blocks nothing; a hook never sends. Batches hold at most 250 events and go to the new `POST /v1/telemetry` route, and only a 2xx answer clears what was sent, so delivery is at least once. See `docs/telemetry.md`.
- The sender treats a spool line the route would refuse (an object with no `type`, or one that is empty or over 64 characters) as junk and drops it with the first batch the server takes, so one malformed line cannot block every later send. A batch is kept without an account, not refused, when the pool's database fails while it reads the credential.
- The skeleton carries edges and the spawn link (format 3): a step's `edges` are `{ kind, target }` with `kind` one of `next`, `spawned`, `retried`, and `after-error` and `target` the position of the step it names in its transcript (the client decides `retried`, since the pool holds no raw key), and a transcript's `spawnedIn` is the position of the transcript that spawned it, so a subagent two deep rebuilds its tree from the batch. Only Claude Code fills the spawn link; Codex and Gemini send null. The server refuses an out-of-range target and a `next` that crosses a prompt; a kind it does not know reads as `other`. The field-list version is 3. Cells are unchanged. Nothing is sent: the batch only grows by the new fields (the 3,400-step test deposit is 876,815 bytes of skeleton, 17 more for the transcript's null `spawnedIn`).
- The pool wire is skeleton format 3 (format 2 is refused like format 1). A tool carries its `errorCode` (the closed list, or null when none was captured; a value off the list reads as `other` and is kept in the extensions bag), so a user refusal, a policy denial, and a real failure stay distinct, and a failed call carries `recoveryCalls` (`next`, the canonical actions of up to the next five calls in the same prompt, and `editFollowed`; no signature hash or text). The pool counts `live` day cells per (name, model, `errorCode`) and (name, `harnessVersion`, `errorCode`), and `recovery` week cells per (failed action, `errorCode`, next action), and the bundle serves the `recovery` family at the floor, worded as what others did next, never a fix. The 3,400-step test deposit grows to 876,798 bytes of skeleton (876,802 stored) from the null `errorCode` on each call. This replaces the 0.3.0 note that `live` provider errors are not built. The field-list version is 3, and the goldens carry it.
- The field-list version is 2 now that a frame's `reach`, a transcript's `frames`, and a step's `frame` and `skill` are on the wire (t867): the register in `docs/pool.md` has a row for each, the goldens are rebuilt, and an unknown name in a reach is read as `other` and kept as sent in the bag, not refused.
- Every entry of the extensions bag is held to 8 KiB, not only an unknown field: an unknown value, a native or MCP tool name set aside under an `other` harness, and the identity of an unknown action are refused as `too large` at their path. `docs/pool.md` states the refusal and that the account byte budget counts the bag.
- The additive wire holds each field the server does not know to 8 KiB (refused as `too large` at the field's path), counts the extensions bag in the account byte budget, keeps the names of a transcript whose harness reads `other` in the bag, and takes a `<field>Literal` as a literal only beside an `other`. The register's class column is clear, thresholded, hashed at ingest, or raw tier.
- The pool deposit wire is additive (skeleton format 3): a batch carries its format, vocabulary, and field-list versions; a field name the server does not know is kept in a stored extensions bag instead of a 422, and an enumerated value it does not know is read as `other` (the value is kept as sent in the bag, served by nothing). Format 1 and 2 batches are refused by name. The client sends no literal beside `other`. `docs/pool.md` gains a wire field register, with a test that fails on an emitted field with no row.
- The skeleton is format 3: a step names its frame (`frame`, a position in the transcript's new `frames` list, which the server refuses when out of range) and the skill whose run it sits in (`skill`, a list member or `private`), and a frame carries `reach` (the MCP servers, skills, and plugins in reach, and `filled`, which says whether the harness recorded any). A call's model and harness version come from its own line, so a model that changes in the middle of a prompt reaches the steps that ran on it. Cells are unchanged. A tool record gains `model` and `skill`. Format 2 batches are refused; nothing is migrated.
- `oars pool fetch --harness-version unknown` fetches the bundle of a harness that records no version in its local files (Cursor, Gemini, Grok Build, and a VS Code Copilot Chat session whose requests carry no agent version), which were absent from every numbered bundle: their cells are `<harness>/unknown/<model>`, and the pool route `/bundle/<harness>/unknown/<vocabVersion>` serves them under the same account floor and withholding as a numbered bundle. The VS Code Copilot Chat reader now fills the harness version from `requests[].agent.extensionVersion` (the Copilot Chat extension's version, read only from the Copilot Chat agent and not from a third-party participant's, from public source and a synthetic fixture, never from a live store); Cursor, Gemini, and Grok Build expose none, so they stay null.
- Telemetry, on by default, with a notice on the first run that is not a hook (stderr, once) and a one-command off switch. Each CLI command except the bare `oars gate hook` (which skips the full CLI to stay inside its time budget) leaves one event in a local, capped spool under `<config>/oars/telemetry/`: the command path, flag names (never values), duration, exit code, and a closed error class, with a random per-install id, the oars version, the OS, the time, and a schema version. Nothing else is recorded: no session content, prompts, paths, URLs, or arguments. Events are sent only to a pool server you configure; this release only records. `oars telemetry status|on|off|show` manages it, and `OARS_TELEMETRY=0` or `DO_NOT_TRACK=1` turns it off. See `docs/telemetry.md`.
- Telemetry now records every hook fire, the bare `oars gate hook` included (t876): a `hook` event with the hook's name, how long its handler took, `hit`, `miss`, `held`, or `error`, the bytes it printed, and the harness version and model when the hook saw them (a name off the public list is `other`). The bare hook is recorded by its own process after its answer is printed, so its stdout and exit code are those of a run without telemetry. This replaces the earlier note that the bare `oars gate hook` records nothing. See `docs/telemetry.md`.
- Telemetry now records every recall (t876): a `recall` event from `oars sessions recall`, the `oars_recall` MCP tool, and the `pre-tool` push, holding only how it was asked (`pattern`, `entity`, `question`, `text`, or `legacy`), push or pull, the read families it served from a closed list, hit or miss, counts of reads, evidence rows, and tokens, and its arm (`shown` or `held`). It never holds the query text, a name, or the rendered answer.
- Telemetry now records deposit passes, sent batches, and fetches (t876): a `deposit` event (sessions counted, batches built and their bytes, and how many sessions each session gate kept out, as counts with no folder, term, or name; a batch sent records `sent` and its bytes) and a `fetch` event (the harness, an ETag hit, a cap hit, and the reads in the bundle). The `oars pool deposit --json` document is unchanged.
- The first-run telemetry notice, the CLI README, and `docs/telemetry.md` name the hook, recall, deposit, and fetch events, so the notice still lists everything that is recorded (t876).
- A hook that the process deadline ends is still recorded (t876): the `hook` event for that fire says `error` with no bytes, written once before the process exits, so the slowest fires reach the spool.
- Every hook fire records the harness version and model when its transcript states them (t876): the bare `oars gate hook`, `post-tool`, `stop`, and a `pre-tool` miss now read them from the tail of the input's `transcript_path`, the same bounded read a push uses. The path itself is never recorded.
- A fetch the pool refuses, and a bundle that fails verification, now record a `fetch` event too (t876): both reached the pool, so `fetches` counts them, with no `reads`. Exit codes are unchanged.
- A 304 to a `oars pool fetch` that named no kept bundle now records its `fetch` event before it fails, so every fetch that reached the pool counts (t876). A hook that reaches its deadline while the transcript is still being read now keeps its event, recorded without the harness version and model (t876).
- Telemetry reports the health of an install and polices the wire (t877). The nightly run leaves a `store-health` event (sessions, skeletons, raw size, verify results, unparseable counts, the capture and extractor versions the store holds (a store with an older session lists both), the harness and model versions seen with off-list values as `other`, and the pool outbox's size and the last seven days of bytes sent) and a `run-cost` event (parse and total time, peak memory, failed or not); a failure oars did not plan for leaves a `crash` event with its built-in class and a hash of its stack with paths hashed, never its message; and `oars pool deposit` leaves a `wire` event for each harness (each register field's presence and bytes) and `--send` a `wire-send` event with the pool's refusal code. Every event passes the closed schema, `docs/telemetry.md` describes each with an example, and the first-run notice says so.

## 0.3.0

Changes since 0.2.0. Four command groups are new (`keys`, `sessions`, `gate`, `pool`); `login` and `logout` keep their flags.

- The hosted-agent commands of 0.2.0 (`deploy`, `status`, and `templates`) are not in this release; a script that calls one gets the unknown-command exit (2).
- `oars keys create|list|revoke` manages your API keys. `keys create --workload <id>` mints a key limited to one workload (authorities `AGENT_OPERATE` and `AGENT_READ` only), so a scheduled agent can change its own schedule without being able to reach another workload.
- `oars sessions` keeps a local, deterministic memory of your own Claude Code sessions: `deposit`, `recall` (with `--mcp` to serve the same query to a running agent), `lineage`, `read`, `books`, `measure`, `verify`, `exclusions`, and `hook`, plus `gold sample`, `gold arms`, and `gold score`. It makes no model call and no network call, except `gold arms`, which sends redacted text through your own Claude subscription. `deposit --allow` also reads Cursor, Codex, Copilot CLI, Gemini CLI, Grok Build, and VS Code Copilot Chat sessions (Stable, Insiders, and OSS builds), each opt-in by name; the VS Code source is written from VS Code's public source and synthetic fixtures and has never run against a live store, and its sessions carry no per-model input figure, so `input` 0 there means not known.
- Every deposited transcript is also hard-linked (copied across volumes) into `<config>/oars/sessions/raw/`, on by default, so it outlives Claude Code's own cleanup. These are raw transcripts on your machine, and the files themselves are not uploaded.
- `oars sessions hook install` writes four fail-open hooks (`SessionStart`, `PreToolUse`, `PostToolUseFailure`, `SessionEnd`) into a Claude Code settings file; `PreToolUse` has no matcher, so it starts node on every tool call, and for a call shape the store has seen fail it adds counts as context, with 10 percent of those held back (they are recorded and nothing is injected); `hook status` lists them and `hook uninstall` removes only the entries install wrote. Install is idempotent, and raises `cleanupPeriodDays` in that file to at least 365 (uninstall leaves it raised). `--schedule nightly` registers a daily deposit task on Windows. A session-end deposit that finds the store locked records its session in `pending/` in the store and exits; the next deposit of any kind deposits the pending sessions first. The step log shows that as a `deposit` row with status `deferred`, which `measure` prints as `deposit@<ev> deferred (store locked)`.
- What a deposit captures (capture version 17): per session, the setup it ran with (permission mode, plugins, hook count, instruction bytes), the tool funnel (tools offered, loaded, removed), the trust shape (interrupts, rejections, policy denials, minutes the agent ran between human turns), the `errorCode` class of each failed call, the packages an install or runner call resolves and the dependency names a manifest shows, and stack strata (language, repo-file bucket, framework, counted `explore`). A call the user refused is a failed call with `errorCode` `user-rejected` for Claude Code, Cursor, Codex, and Gemini. A Gemini session that ran on Windows stores its shell calls as `PowerShell`, and Gemini sessions under `~/.cache/.gemini` are read. A rotated Copilot log (`events.N.jsonl` beside `events.jsonl`) is read oldest first as one session. The MCP tool name after `mcp__` is redacted wherever it is stored. Recall floors a step's token count to its bucket, so no local cell holds an exact number, and cells are weekly (keyed on the Monday of the UTC week), with day cells for the reads of days. A language share on the wire may name `other`, the name a touched file with an extension off the pinned list gets, so a session that touched a `.md` file is not refused; the frame's `languages` list stays closed to the pinned names. The store is at extractor version 12 (a derived prompt carries its strata), and an older store re-derives from its log with no transcript read. A Copilot session's reasoning tokens are shared over the responses of its model in proportion to their output, no line above its own output, so a healthy session passes the thinking invariant of `oars sessions verify --strict`.
- On a large store (a test store whose log holds superseded records), a deposit that skips unchanged files needs a 104 MB heap and `verify` 248 MB; a store too large for node's default heap still needs `NODE_OPTIONS=--max-old-space-size=<MB>` (`docs/sessions-store.md`). A deposit whose read of its own `store.lock` is refused at the end (an antivirus share violation on Windows) removes the lock instead of leaving it for 10 minutes, a store lock whose holder hangs is refreshed for at most an hour and, once it has aged 10 more minutes, the next deposit breaks it and prints one line naming the holder's pid, and a Codex thread that a crash tore stays readable. A deposit that loses its store lock (held past the hour cap, then broken by a waiter that a second deposit followed) checks that the lock file still carries its own token before it writes `state.json`, replaces the log, or compacts, and stops with `This run lost the store lock to another deposit` (exit 1) when it does not, before any further capture, raw archive, pending, derived, or hook index write. It never overwrites the second deposit's `--allow` and `--redact-domain` entries, so no domain stops being masked.
- `oars sessions verify` audits each session against its raw file (raw-file match, Merkle root, count bindings), reports every session on its own, and scores each against your own other weeks on its harness (`selfBaseline`). `verify` and `books` name the project folders that hold transcripts but are not on the saved allowlist, which are never read (`scope` in `--json`); that list never fails `verify --strict`.
- `oars sessions exclusions` scans your sessions against a local term file (`OARS_EXCLUSION_TERMS`) and writes the excluded ones to a list, printing counts only. `gold sample` refuses a draw with no term file, and `--exclude-term` only adds to that file's terms.
- `oars sessions` ships a pinned public vocabulary (`VOCAB_VERSION` 1, snapshot of 2026-11-04, `packages/cli/vocab/`, about 6 MB raw in the package) and the functions that project the fields a pool would carry; they compute from the store and write nothing to disk. A shell call projects to `program`, `subcommand`, and `flags` from that program's list, so `grep AcmeWidgetMerger` is `grep` alone; a program, package, tool, or skill outside the vocabulary is `private`, `custom`, or only a count. A client more than 30 days past its snapshot builds no pool batch (`vocabulary_expired`).
- `oars gate install` and `oars gate uninstall` wire one fail-open `PreToolUse` hook into Claude Code's user settings (rerunning changes nothing, and `install` sets the file's mode after writing and follows a symlink that points at nothing yet), and `oars gate hook` records each package, MCP server, and skill pick as it happens into `crossings.jsonl`, in under a second. `oars gate replay` finds the same crossings in session logs already on disk, and `oars gate report` counts that one file once per crossing, by who recorded it. Names are read exactly: an `npx <name>` whose folder holds `node_modules/.bin/<name>` is `local-bin-run`, not `fetch-and-run`; a name is not sent to a registry when `HOME`, `sudo`, a sourced file, or a package-manager config setting could change its configuration; a version with a character such as `#`, `&`, `?`, `;`, or `%` counts as `unreadable-name`; and a resumed transcript counts a call once.
- `oars gate hook` adds a note about a name first published within 30 days or not found, with no policy file needed. `gate-policy.json` (in the sessions store, written by you) sets each class (`young-name`, `not-found`) to `warn`, `block`, or `off`, with a day count and a holdback share (default 10 percent, which withholds notes at random and never a block). A note states a registry fact; a block is a labeled deny that exists only for `not-found` (an npm name; a Python name never reads `not-found`) and only when you write `block`. Each row records its `arm`, the `lineShown`, the `lineHeld`, and the `policy` it ran under, and `oars gate policy` prints the policy in force. A registry ask the hook has to cut is finished by a detached helper that fills the cache; a call starts at most three helpers. The hook makes the lock for a helper in the same step that starts it, and takes the lock back before the process can end when the helper cannot start (the start throws, or the child reports an error), so no lock outlives its helper and keeps a name unasked for five minutes. A hook the deadline ends stops its own ask and writes one not-read row, written before the stop so a slow stop (a `taskkill` on Windows) cannot cost it; the deadline writes nothing when the hook's own append has already put the record on disk and then stalled, and another hook's row in the same file never makes it skip its own. One name twice in a call is one note and one counted row, and a block label prints once (the call is still denied). A kept registry answer is read only in the folder that asked. A crossing goes nowhere unless you opt in, and no opt-in exists yet.
- The pool's ledger has no expiry: migration `0009_ledger_no_delete.sql` makes the database abort any `DELETE` of a `deposits` row or a `contributors` record. A counting batch turns an account from `pending` to `standing` after 90 days and stays on the ledger. The pool counts two strata of their own beside the single ones, (language, share) and (repo size, explore bucket), each held to five accounts and served only in the bundle's `strata`; provider errors in `live` are not built yet. The pool's bundle serves tool-day reads from day cells (a tool's failure rate and its share of the day's steps, with the floor counted within its day) and a version-free (name, `platform`, `shell`) fit cell, stored as `env:<platform>:<shell>`, served only when no cell of that motif, week, and exposure is under the floor, so a total beside its parts never shows a sub-floor part by subtraction. Recovery and fit's call-shape method are not served. The bundle's `ETag` hashes the list of served families. A local store holds the `env:<platform>:<shell>` rows in `cells.jsonl` beside its other cells.
- `oars pool` talks to a pool server you name with `--server` or `OARS_POOL_URL` (there is no default server): `oars pool login` runs the provider's device flow (RFC 8628, Google or GitHub) itself and sends the provider's token to the pool once; every request prints (request line, every header, and body) before it is sent, with the device code, the provider's token, and the credential shown only as `<credential: n bytes>`. The client ID and Google's client secret come from `OARS_GITHUB_CLIENT_ID`, `OARS_GOOGLE_CLIENT_ID`, and `OARS_GOOGLE_CLIENT_SECRET`; an unset one stops the command before it sends anything and names the variable.
- `oars pool deposit` writes batches to an outbox and stops: nothing is sent. It sends each stack language with its share bucket (`languageShares`, one of `0`, `under-10`, `10-50`, `over-50`; a share outside the list is dropped and its language still goes) and each prompt's `explore` as a `calls` bucket (the `count` edges, then doubling to over 4,096); the exact count never leaves. `--send <hash>` sends no request: a batch that was shown and is unchanged stops with `sending_disabled` (exit 5), and any other hash stops with its own refusal. It builds one batch per main session, once the session and its subagents have all been quiet for 6 hours, in skeleton format 2: a shell step holds the projected program, subcommand, and flags, usage and step costs are buckets, a name off the public lists goes as `private`, and nothing carries a session id, root path, date, or exact value. Each session passes the folder allowlist and the exclusion check before any projection runs; one that fails either is counted by reason and never built, and a session that later fails a gate has its earlier batch removed. The batch also carries your own before and after windows as `deltas` (a plugin added or removed as `private`, a `permissionMode` or `effort` changed by field name alone, or a public package removed; 7 days each, at least 5 sessions a side, marked once in `deltas-sent.log`). A batch built under an older vocabulary or field list is rebuilt, and the older file removed. `oars pool outbox` prints each batch exactly as it would be sent, then its SHA-256, and records that it was shown; `--explain` adds each field's rule. `--json` carries `batched`, `excluded.folder`, `withdrawn`, and `discarded`.
- `oars pool fetch --harness-version <version>` fetches that version's signed bundle for one harness (`--harness <name>`; with no flag, the harness your local store holds the most sessions of, claude-code when none leads, and it prints which it chose and how to change it; only counts are read, and none leave the machine), verifies it against the key pinned at login, and keeps it per harness (`pool-replica/<server>/<harness>/<version>.json`). It checks the sign-in before it reads the local store, prints every request line and header before sending (credential shown only as `<credential: n bytes>`), keeps the bundle's `ETag` and sends `If-None-Match` so an unchanged bundle is a 304 that keeps the file, and on the weekly cap (429) keeps the bundle, says when to try again, and exits 10 (`CAPPED`). A bundle of another vocabulary version, or made for another harness, is refused even when its signature holds (`bundle_unverified`).
- `oars login` with the built-in issuer not answering discovery (no answer, an error status, or a body that is not discovery JSON) exits 2 with the not-launched message instead of exit 8 or 1; a failure on `--issuer-url` or `OARS_ISSUER_URL` is still reported as that failure, with its own exit code. A request the network refuses (exit 8) now names the server and the network's reason (`Cannot reach the server at https://api.manyoars.com: getaddrinfo ENOTFOUND api.manyoars.com`) in place of `Cannot reach the server: fetch failed`; an `OAUTH_TIMEOUT` does not name the server.

## 0.2.0

- `oars templates` lists the starter templates, and `oars deploy --template <id>` deploys one without an image of your own.
- `oars login` works with no flags once Many Oars has launched: the production issuer is built in, and
  `https://manyoars.com/.well-known/oars.json` (`{"launched": true}`) switches it on. The flag never supplies the URL.
  Before launch, `login` says "Many Oars has not launched yet: pass --issuer-url or set OARS_ISSUER_URL." and exits 2.
  `--issuer-url` and `OARS_ISSUER_URL` still win.
- An exit 6 ends with a "Needs you:" line that names the link for the step only a person can do, such as finishing account setup.
- `deploy` refuses a mix of flags with a message that uses the serial comma; a `--template` the catalog lacks exits 2 and an
  unreachable catalog exits 8, before anything is registered.

## 0.1.0

- First release: `login`, `logout`, `deploy`, and `status`.
